What one request binds, and when each line is written

The logger binds only the hooks the governing rule names, so a skip rule binds nothing. Each bound hook is bracketed by three priorities, the callbacks on a significant event are wrapped, and two transport pairs bind as the rule's log_http and log_queries allow. PHP's shutdown, not WordPress's, closes the record.

hook_starthook_start_priority, default −10000

wrap_callbacks() wraps only priorities strictly between the start and the spacer, so the three never wrap themselves; it skips any callback whose reflection reports a by-reference parameter; each wrapper claims accepted_args = 99 and slices back to the original's count. The spacer absorbs the pointer shift a self-removing filter (es-wp-query) causes, so hook_complete still fires. A rule with trace_hooks puts the calling frame on l.

per ruletwo transport pairs

Outbound HTTP, log_http on by default

http_start on pre_http_request at PHP_INT_MAX, after every short-circuiting filter has voted, and opens NOTHING when $preempt is not false. http_end on http_api_debug at PHP_INT_MIN, so the span covers the request rather than the other listeners there, closing the label it opened.

SQL, log_queries off by default

query_start on the query filter at hook_start_priority, ahead of the chain, so the span covers every rewrite; query_end, the one that sees the rewritten SQL, on log_query_custom_data at PHP_INT_MIN, which fires only under SAVEQUERIES. It drains $wpdb->queries, so Query Monitor would find it empty.

Both spans label l with origin_frame( true ), which climbs past the transport class, up to TRANSPORT_ORIGIN_DEPTH 16 frames, to the code that asked. It climbs whatever trace_callers says: that budget attaches caller to hook entries alone, so l is the one field on a transport span naming who asked.
