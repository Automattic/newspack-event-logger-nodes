A request is filed in the bucket it FINISHED in, and a write into a folded hour goes to the hour key

Two halves of one rule: a stats write must land where a reader will actually read it. The record reaches Flame_Builder_Node at completion, and an hour folds exactly once.

1 · Which bucket: the completion, clamped

bucket = min( now, timestamp + round( duration_ms / 1000 ) )

Filing under timestamp, the START, would put a long request in a bucket that may already have closed. Completion needs no new field, and for an aborted request it is the abort moment, because Request_Builder sets duration_ms = now - start at eviction. That removes the request's own duration from the exposure, which the 600 s assembly window bounds at ten minutes.

Clamped to now: a completed request cannot have finished after it reached us, so a skewed spoke clock or a bogus duration cannot file into a future bucket that readers, walking backwards from now, would never reach.

2 · Which key: url_shard_intent() picks the tier

Transit is the second half. Decision 17's reader skips a folded hour's fine buckets, so a record arriving after its hour folded, written to its fine bucket, would sit where nothing reads it and never merge into the coarse key that replaced it.

3 · When the memo is right

folded_hours is per-process, and one partition has one worker (persist_aggregate_stats(): read-then-write is not atomic), so a respawn is the only way it goes stale; there is no peer to race.

flush() therefore rolls up BEFORE it persists: the roll-up is what probes the coarse tier, so the first flush after a respawn has an accurate memo before a single row is placed.

The trigger is routine, not exotic

wp nodes deactivate complete; wp nodes gc --force; wp nodes activate complete replays the whole retention window, and every replayed record carries its original timestamp. Steady state never sees it: measured on a hub, records reach the builder about 14 s old against a fine tail of 65 to 120 minutes.
