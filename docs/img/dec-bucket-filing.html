A request is filed in the bucket it FINISHED in, and a late record is one more delta at its own t

A stats row must land where a reader will read it. The record reaches Flame_Builder_Node at completion, so its bucket is the completion's, clamped to now; and since every row is a delta a read sums, a record that arrives late needs nothing more than the next settle.

1 · Which bucket: the completion, clamped

bucket = min( now, timestamp + round( duration_ms / 1000 ) )

Filing under timestamp, the START, would change a bucket the dashboards already read as complete. The completion needs no new field, and for a timed-out request it is when live traffic timed it out, because Request_Builder sets duration_ms = due - start at eviction, due the stream boundary its window fell due at. The 1080 s assembly window bounds that at eighteen minutes, and a reprocess files a timed-out request among the stamps it replayed.

Clamped to now: a completed request cannot have finished after it reached us, so a skewed spoke clock or a bogus duration cannot file into a future bucket that readers, walking back from now, never reach.

2 · A late record: one more delta

Every settle appends at each row's own t (decision 36), so a record arriving after its bucket, or its hour, has passed files one more delta row there. A read sums every row it finds, so the late one counts wherever it landed.

The one bound is the lifespan: a row whose t is already past the Ledger's lifespan drops at the Ledger, counted past the lifespan on the stats writes line, because no reader reads that far back.

The trigger is routine, not exotic

A hub sees late records with no replay at all: one flame-builder partition takes every spoke's records, so a spoke feeding a backlog while its peers are caught up files rows in buckets they left minutes ago. Each lands where it happened.
