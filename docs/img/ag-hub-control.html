The hub pushes settings and pulls discovery, one signed command per spoke

hub-control is the substrate's settings-sync topology plus this plugin's three option registrations and its Discovery_Collector, pinned to one partition. Neither fan-out goes through a Tee: a command is signed under its spoke's session key, and re-addressing it after the mint verifies nowhere.

Settings out: an option change becomes a push

1
any request on the hub

An admin edit, an auto-tune decision, a performance set

All three write a WordPress option. Settings_Event_Writer::maybe_emit() watches the newspack_ prefix and returns on any other name.

2
settings.p0

One event per change: the option NAME always

Old and new value excerpts ride only for options on newspack_nodes/settings_audit_values_allowlist. They are audit detail; the sync never reads them.

3
settings:consumer → Settings_Sync, every 300 s too

The value is read at CONSUME time

A burst of writes to one option collapses to one current-value push, and no stale value can race a fresher one. The full registered set is re-pushed on the tick.

ELN's newspack_nodes/settings_sync/value filter substitutes the OWNING config's default for a blank ('') or absent (false) value, substrate keys against the substrate's defaults, and runs the ruleset through Rule_Set::hydrate_array() so pointer rules ship hook-complete.

4
per live spoke, over an operator-wired HTTP_Out

One signed set per registered option per spoke

The registrations: the substrate's num_partitions and each remote_* axis twice (once onto the spoke's own geometry, once to seed its remote_* copy for ITS spokes), addressed to the spoke's settings CI; plus this file's rules, log_memory and flush_every_line, addressed to its performance CI.

5
on the spoke, for ELN's three keys

performance set, a TUNE verb

Writes one of the three SETTINGS_OPTIONS names; anything else comes back as "unknown option". Rule_Set::OPTION_RULES routes to apply_synced() instead, which re-tiers on arrival and holds its own no-op gate.

Discovery in: what each spoke could log

1
Discovery_Collector, every 300 s

fire() walks the live targets

make_node Discovery_Collector discovery-collector 300; a blank token also means 300 s. A target with no established session is skipped after asking the egress for a handshake.

2
per live spoke

One signed discovery.get TM_COMMAND

Addressed at that spoke's discovery CI, FROM this node.

3
on the spoke

discovery get, the CI's only verb

Answers { registered_hooks, custom_events }: Rule_Set::instrumented_union() across every LOG rule, custom-event names filtered out of the hooks so the two catalogs stay disjoint. It reports the ruleset and never writes it.

4
the reply self-routes, TO = FROM

fill() union-merges, one reply at a time

Monotonic, so out-of-order or partial replies converge. Remote strings are sanitized; both catalogs are capped at MAX_EVENTS 10,000.

5
two non-autoloaded options

It stages, it does not instrument

stage_discovered() writes hooks into discovered_hooks and custom events into discovered_events; within one reply, a name reported as a custom event never also stages as a hook. The rules editor's picker reads them, and the editor is the only writer of rules.

Ungated by design, and still authorized

A watched option change always records an event. Without hub-control active and per-spoke HTTP_Out <name> <vault-id> nodes wired from the console, the event is tailed and dropped: on a spoke or a standalone site there is no consumer. Cheaper and harder to misconfigure than a per-listener get_option gate. Who may make the change is a separate question: Auto_Tuner_Node::authorized() and the TUNE capability still stand.

Credentials are the substrate's

The Vault holds each spoke's URL and credentials, sealing the password at rest under a key derived from wp_salt( 'auth' ); this plugin stores none and offers no CRUD surface. On newspack_nodes/vault/changed, Bootstrap::reload_vault_consumers() walks every active topology carrying a Remote_Link or Remote_Source node and asks each partition's lock to RELOAD, over the reload channel rather than the restart one, so a credential change costs no process recycle.
