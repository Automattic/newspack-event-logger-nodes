The open bucket is durable in the offsetlog until it closes, and the carry is capped

A held frame is in no durable log until its bucket closes (decision 10), so the worker's checkpoint carries it. What bounds that carry, which frame goes first when it binds, and what the log says when it fires.

1 · A write lands in memcache and is HELD

Each stats write is mirrored into a per-namespace buffer keyed by its entry key, last state wins. The buffer's residency is one open bucket: flush_stats_mirror() drains every closed bucket at each checkpoint, so its size is the distinct keys that bucket sees, which nothing else bounds.

2 · Every 30 s the checkpoint carries the held frames

save_state() packs them into the Consumer's offsetlog keyframe beside the cursor; restore_state() takes them back. The worker's rehydrate seam consults held frames FIRST, or a mid-bucket eviction makes the read-modify-write restart the bucket from zero. A restored frame carries what is LEFT of the retention window, bounded by its role's TTL (substrate ADR-18): a frame whose CACHE lifetime ran out is still read.

3 · The bucket closes: written once to flame-stats

At the first checkpoint after is_open_bucket() says it closed, the frames go to the partition under the unscoped mirror key and leave the buffer.

The carry is capped at MAX_CHECKPOINT_MIRROR_BYTES, 2,097,152 bytes, and the WIDEST frame is dropped first

Why the widest goes first: narrowest-first keeps the most keys recoverable per byte, and a dropped frame is re-merged from memcache by the next write to its bucket, lost only if the process AND memcache both fail before the bucket closes. Partition_Node DROPS an oversize record outright, and that record is the whole checkpoint, cursor included.
The pack orders by ENTRY COUNT, not encoded bytes, and encodes only what it carries plus the one it stops on: encoding every held frame to sort them would make the budget bound the OUTPUT and never the work, megabytes of throwaway JSON every thirty seconds. A frame is a map of small numeric entries, so count tracks size closely, and the budget is still enforced against real encoded bytes as they accumulate.

What the log carries when it fires

How many frames dropped of how many held, the budget, the bytes it carried, and the WIDEST held frame with its namespace and size: a sharded urls key and an lb_s key are both opaque, and which one fired is the whole question. Sharding keeps the tripwire's other half honest: an unsharded urls blob would exceed the whole budget and always be the widest frame, satisfying "the widest is NOT a per-server leaderboard" permanently. Sixteen smaller frames sort in among the leaderboards, so the fleet-size signal reads true.

What the GET_STATS payload reports

mirror_held_bytes: the exact held total, on a verb an operator asks rather than every checkpoint. Read the trend in BYTES: urls is sharded, so one open URL bucket holds SIXTEEN frames a sixteenth the size, and a frame count steps up with no fault behind it. mirror_held_frames: the WIDEST single namespace's held count, because the backstop is per namespace and a cross-namespace total cannot warn about it: six namespaces holding five thousand each read as thirty thousand with nothing near the bound, while one spilling on every write reads as ten thousand and fifty.

The spill, and the case with no partition

It spills a band rather than one frame: ranking the buffer is a pass over it, and the buffer PINS at the bound under exactly the traffic the bound exists for, so one frame per write puts that pass on every write past it, quadratic in a spray's length. The band is the hysteresis trim_entries() already uses; a rank-ordered structure is NOT the alternative, since a merge changes a key's rank and keeping the buffer ordered pays per write instead. With no partition to spill into, nothing already HELD is discarded: flush_stats_mirror() reads an unresolved name as one that may resolve next checkpoint and keeps the buffer, and the backstop takes the same reading, refusing the ARRIVAL, whose value is still in memcache and whose bucket's next write re-offers it.
