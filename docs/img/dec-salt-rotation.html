The tables flush IS the schema migration, and nothing compensates for skipping it

A durable Table's key carries no salt, so rotating the install salt leaves the stats' SQLite rows alone. Emptying the three stats Tables replaces each partition's files, so a schema change leaves no old-shape row to read.

A salt rotation reaches a volatile key, not a stats row

Before: a volatile Table's key, as the substrate writes it through Cache_Backend::site_key().

The scope is the first 12 hex of md5( DB_NAME : table prefix : salt ). A durable Table skips it, and Stats_Store keeps no salt of its own.

wp nodes memcache flush→Cache_Backend::rotate_salt() stores a new salt

After: the same logical key under a new scope. The old key sits in memcached until its TTL, and nothing will ask for it.

newspack_nodes:{v}:9f8e7d6c5b4a:table:evlog:p0:urlsrv:2026-09-11-14-05

A long-running worker memoizes the scope for its life, so the rotation asks every worker to restart.

SQLite: no salt, so the flush is by name

The stats Tables store {namespace}:{key} as a row of {base}/tables/{table}.p{N}.sqlite, so the rotation leaves the statistics where they are.

kv:key · value · expires

One table a file: the key, the serialized value, and when it expires.

wp nodes tables flush flame-stats:url …→replaces each partition's files

Nothing survives the flush, so no row carries a version component.

Skip the flush

The dashboard reads garbage for one retention window. That is an operator error with a one-command fix, wp nodes tables flush on the three stats Tables, not a case for the runtime to detect.

No second mechanism beside it

No reader or writer carries a shape probe, a version component in a key, or a row-level legacy test. Each would be a second migration mechanism beside this one command, maintained against every future row shape.

One mechanism, two uses

Schema bumps and emergency resets share it: a reset and a migration are the same flush.
