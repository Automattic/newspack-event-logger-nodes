The tables flush IS the schema migration, and nothing compensates for skipping it

No stats key carries a salt, so rotating the install salt leaves the Ledger rows and the url blobs alone. wp nodes tables flush empties them by name, so a schema change leaves no old-shape row to read.

A salt rotation reaches a volatile key, not a stat

Before: a volatile Table's key, as the substrate writes it through Cache_Backend::site_key().

newspack_nodes:{v}:a1b2c3d4e5f6:table:eln-urls-page:…

The scope is the first 12 hex of md5( DB_NAME : table prefix : salt ). A Ledger or a durable Table skips it, and Stats_Store keeps no salt of its own.

wp nodes memcache flush→Cache_Backend::rotate_salt() stores a new salt

After: the same logical key under a new scope. The old key sits in its store until its TTL, and nothing will ask for it.

newspack_nodes:{v}:9f8e7d6c5b4a:table:eln-urls-page:…

A long-running worker memoizes the scope for its life, so the rotation asks every worker to restart.

SQLite: no salt, so the flush is by name

A stats Ledger's rows sit in one file every partition shares, {base}/ledgers/{name}.sqlite, and each URL's blob in one url Table file a partition, {base}/tables/flame-stats:url.p{N}.sqlite.

rows:t · k · x · w · s · c0 …

One table a Ledger file, declared by the topology's make_node line.

wp nodes tables flush stats:… flame-stats:url→drops and redeclares each Ledger's rows in one transaction; replaces each url Table file

The Ledger file is never unlinked, because every partition holds it open. A live worker flushes its own over its command channel.

Skip the flush

A Ledger whose file another declaration made refuses to open, naming the flush. A change to what a key means reads rows of two shapes until the old ones age out: an operator error with a one-command fix, not a case for the runtime to detect.

No second mechanism beside it

No reader or writer carries a shape probe, a version component in a key, or a row-level legacy test. Each would be a second migration mechanism beside this one command, maintained against every future row shape.

One mechanism, two uses

Schema bumps and emergency resets share it: a reset and a migration are the same flush.
