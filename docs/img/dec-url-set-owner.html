Every rate divides by the window

RECENT_BUCKETS × Stats_Store::BUCKET_SECONDS

It drops the bucket still filling, and never divides by the buckets that happened to carry traffic: a URL seen in two of twelve would read six times its rate beside a header that does not.

The totals are exact

MAX_URLS_PER_SHARD folds each shard's tail into a synthetic Other row (Stats_Store::OTHER_KEY) carrying only the fields that ADD, splits included: exact site-wide, and per server for every server MAX_SERVER_VALUES keeps, since its own tail folds into an Other server no real fleet reaches. The row is marked aggregate and un-clickable.

Workers are excluded by default

The row RECORDS worker traffic, never guessing from ?worker_type; include_workers opts IN, and the tail folds into TWO overflow rows (Stats_Store::other_key()). A header summed from rows keeping worker timing reads "Avg Response" as 227 ms of cron against 3 ms of reader traffic on a staging hub.

One scope rule across the surface

A FETCH sends the live selection, so urls, dump_url and ask all ask for what is selected now. A LABEL reads the scope the server echoed back, because it names numbers already on screen. dump_url takes the same server, because the modal opens from a row that filter scoped, and a site-wide average under a scoped count is the same defect one click in.

Where the scope does not reach

dump_url's breakdown_time_series, category_time_series and aggregate_flame are per-URL only: a per-URL-per-server series would be new storage on the axis decision 11 watches. find_recent_requests_for_url() has no server in the request index. Both are harmless while a stored url is absolute, which makes one URL one site.
