A span says how long, never who asked; two knobs answer the second question, at two prices

A /wp-admin/post.php record: the_content fired sixteen times at about 2.4 s each, 93% of a 40.6 s request, and every span said the same thing. Both knobs are per rule and add no new wire field: Log_Manager::message() merges arbitrary keys into the entry, [ 'n', 'k' ] + $data + [ 'ts' ].

trace_hooks: one frame on every firing, into the aggregation label

origin_frame() takes ONE frame, who called the hook, and puts it on the entry's l. Flame_Tree and Flame_Fold aggregate on l, so one node splits into a node per caller, each with MEASURED durations, and no tree code changes.

It must NOT synthesise ancestor nodes: that parent would assert a duration nobody measured, which is decision 12's whole point. Attribution is honest; invented ancestry is not. Gyrobase already uses the idiom for include: /Macros/Global.html.

0.9 µsdebug_backtrace( DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH )
12.7 µswp_debug_backtrace_summary(): walks and formats the whole stack to keep one frame

The depth LIMIT is the lever, not IGNORE_ARGS: args are refcounted, not copied, and cost 0.8 µs even on a multi-megabyte the_content. At 0.9 µs it runs on every firing (2,601 render_block calls = 2.3 ms), so the split is complete rather than cut at a budget.

trace_callers: a deep chain on the first N firings of each hook

caller_of() records wp_debug_backtrace_summary( self::class ), ignoring the instrumentation class so the top frame is the caller, onto the hook's OWN start entry:

the_content hook (start) · m … · caller "rest_preload_api_request, apply_filters('the_content'), …"

The field is caller, not c, which already means COUNT throughout this schema. The window is 20 frames (CALLER_FRAMES), and MAX_DATA_SIZE is the only other bound.

The cap is per HOOK, not per request: firings past the twentieth carry no chain.

The RULE names the count: trace_callers IS the number of deep chains, default 0, and a stored true decodes to Rule::TRACE_CALLERS_DEFAULT (20), because what a diagnostic run wants is not what steady state wants. Sixteen firings fit inside twenty, enough to see a repeat whole; a hot hook stops paying after twenty. The same question asked of render_block on that record would be 2,601 backtraces.

A fixed 20 leaves 21% of a real record's time unattributed, and an 8-frame window stops one frame short of rest_preload_api_request, the frame that explains the whole request.

A field nothing renders is a field that does not exist

So LogEntriesTable renders what the knobs capture: the l origin frame, then caller as "called by …", muted ahead of the entry's value.

Where each knob sits

Both off by default, like log_queries (decision 23) and unlike log_http (decision 21): a backtrace is cheap once and not cheap always. Neither reaches the transport spans: their l climbs past the transport whatever trace_callers says.
