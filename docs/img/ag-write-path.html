Every line of one request lands in one firehose partition

This plugin writes the firehose from inside a WordPress request through Log_Manager alone. Its three gates, the entry it stamps, the envelope it packs and the hash that picks the partition are the whole write path; three sibling logs take jobs.

Log_Manager opens, or stays inert

Constructed on first use, at plugins_loaded 11 or earlier. Three gates, in order:

1enable_logging on
2not root: posix_geteuid() ≠ 0
3the governing rule says log

Which hooks bind is App\Core's later choice and gates nothing: a log rule naming no hooks still writes process (start), request, environment_v3 and resources.

Inert means is_started() false and every message() a no-op for the rest of the request. Started means finish() is handed to PHP's register_shutdown_function(), so the terminal is written even after a fatal.

The entry: three stamped keys, one cap

message( category, data ) stamps n (from 1) and k ahead of the caller's data and ts behind it, redacts an m carrying a ?, then encodes the WHOLE entry and holds that encoding to 3,840 bytes.

nline, from 1

…more data
tsepoch float

Shaded keys are stamped; m, l and the rest (duration_ms, status_code, caller, rule, …) are the caller's. Over the cap the entry goes through fit_data(), which cuts m first and never renames the category.

The envelope, and the partition

The entry rides a 7-field substrate Message: TYPE = TM_STRUCT, KEY = the request id, VALUE = the entry, TIMESTAMP = the clock message() read, which is the entry's ts unless the caller supplied its own, as process (start) and the profiler's plugin spans do.

_firehose:topic, built once per process, hashes the KEY: Partition_Node::hash_to_partition( rid, num_partitions ). Every line of one request lands in one firehose.pN, appended with O_APPEND under PIPE_BUF, so many PHP workers share one file without a lock.

The request id is HTTP_X_A8C_REQUEST_ID, else UNIQUE_ID, each clipped to 64 characters; absent both, generate_request_id() mints up to 32 base-36 characters and publishes them into $_SERVER['UNIQUE_ID'], so a subprocess inherits the identity. It is not one of the entry's fields: readers group a request's lines by the envelope's KEY.

logs/firehose.pN
Log_Manager, per request; a gyrate subprocess's Gyrobase::Log too

Every entry of every logged request, jobs included as k:"job". Under 4 KB a line, lock-free, and the only log a hub pulls from a spoke.

logs/jobfeed.pN
Job_Intake::feed()

Small jobs alone, no lock, PIPE_BUF-bounded. A site tailing this with job-feed reads jobs without reading every request's lines.

logs/jobintake.pN
Job_Intake::queue()

Large jobs, up to 32 MiB, behind the partition's write lock taken by allow_large_writes(). Local only: nothing here reaches a hub.

logs/jobdelay.p0
a future not_before or delay

Parks the job until Job_Delay::sweep() re-writes it through write_job() with a fresh envelope.
