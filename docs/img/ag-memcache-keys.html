Every stats key ends in its bucket, and the URL index is stored at two resolutions

Stats_Store writes through the substrate's Table, which prefixes the install scope; below that, one partition's keyspace is evlog:p{N}, then the namespace, then the scope parts, then the bucket LAST, so every scope is a pure key prefix, one lookup_multi serves it, and retention is the key's own TTL.

<install scope>the substrate's salt lives here; rotating it orphans every key
evlogPREFIX_BASE
p{N}the flame-builder partition
{namespace}one of seventeen
{scope parts}a server's fnv1a32, a shard, a url_hash, a dimension
{bucket}Y-m-d-H-i floored to 5 minutes, or Y-m-d-H for a coarse tier

Lexical order is chronological order, which is what lets expiry compare keys and is_open_bucket() decide from the key alone whether a bucket is still being written. Three namespaces end in something else: url and urlmap key on a hash, urltoken on a server and a token.

What one read of the URL index asks for

The fine tier lives 7,200 s: 13 buckets plus the rest of their hour is just under two hours at the worst minute, and at that width it costs 24 buckets a shard, as many keys as the coarse tier holds at a 24-hour retention and twice what it holds at the default. Performance_CI_Node::load_index_default() folds INDEX_READ_CHUNK 12 buckets at a time and drops each chunk before reading the next.

A URL row is positional: fourteen indexes, named once in ROW_FIELD_NAMES

0count
1timed_count
2sum_ms
3sum_peak_mb
4count_2xx
5count_3xx
6count_4xx
7count_5xx
8min_ms
9max_ms
10max_peak_mb
11last_seen
12worker
13path

Indexes 0 to 7 ADD, in ROW_SUMS order; extremes at 8 and 9 stay the URL's own. Index 13 is the row's one string, its path: no scheme or host for an https URL under the key's own server, the whole URL otherwise, cut to MAX_PATH_BYTES 1,024. The host lives in the key, so a scope is the server's own keys and an unscoped read walks every server urlsrv names. Measured on live rows: 672 bytes named, 398 positional.

Caps fold into a synthetic Other rather than dropping, so a total summed from a capped namespace stays exact. Every value is capped BEFORE it is written to ITEM_BUDGET, 900,000 bytes uncompressed, by an estimate for the configured serializer: fixed bytes a part plus the strings it carries. The one cap that does not fold is a payload bound: sums_to_display() keeps a category's fifty slowest entries by average exclusive time past a hundred.
