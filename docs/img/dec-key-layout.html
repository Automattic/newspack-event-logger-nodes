Every stat lives under one key shape, and the bucket or hour is always the last component

Three SQLite Tables per flame-builder partition hold the stats (decision 34). Because every scope is a key PREFIX, one MGET per Table serves them all through Stats_Store::bucket_get_multi(), and retention is the row's own TTL rather than a hand-rolled cutoff pass.

Three Tables, three TTLs, one window

The window is Config::stats_retention_seconds(): the substrate's min_lifetime (default 43,200) floored at MIN_RETENTION_SECONDS = 3,600. flame-stats:aggregate holds every namespace but two groups for <eln:stats_ttl>, max( 90,000, window ), so every hour key a chart reads is stored; a urltoken member alone states its own lifetime, the window from its last add. flame-stats:url-fine holds a FINE urls, urlsrv, urlrank_s or urlhdr bucket for <eln:stats_url_fine_ttl>, min( window, FINE_TTL_SECONDS = 7,200 ), because the coarse tier answers for everything behind the current hour: 24 buckets a shard. flame-stats:url holds the per-URL blob for <eln:stats_url_ttl>, max( 3,600, window / 24 ).

A slotted chart hour takes no byte cap: SQLite stores a row of any size, and its count caps apply per slot (decision 35). The server ceiling is 128 rather than 20 because 20 binds on a real fleet: it folds every spoke past the twentieth into Other, and a 24-spoke fleet loses four sites from its own picker. Reading the axis as the fleet and leaving it uncapped is wrong: server_name is SERVER_NAME, under Apache's default UseCanonicalName Off the client's Host header, so a catch-all vhost makes it visitor input. Decision 30 owns the reopen condition. A shard is the one component naming no dimension of the data: physical partitioning, because one blob per server per bucket is the pressure every cap here is sized against.
