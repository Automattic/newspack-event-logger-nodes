A spoke writes only job; the hub's rewrite is what makes a job central

Every site runs the same plugin and the same write path. A hub is a site that also activates aggregator and hub-control: substrate Remote_Source nodes pull each spoke's firehose over SSE, and the one application node between them and the hub's Topic flips k:"job" to k:"remote_job", so the same handler name can mean local work on the spoke and central work on the hub.

Spoke 1

firehose.pN written by Log_Manager; job-hub or complete routes its own firehose k:"job" entries and dispatches them against newspack_nodes/job_handlers (job-spoke tails only jobfeed.pN and jobintake.pN). It runs neither aggregator nor the rewrite.

Spoke 2

The same. Its /messages/stream?subscribe=firehose.pN serves the hub's pull from a slot the pull may take past the browser reserve, three per identity.

Spoke N

The same. Credentials for the hub's pull are the spoke's hub user, sealed in the hub's Vault under wp_salt( 'auth' ); TLS posture is vault_verify_ssl / vault_require_ssl.

Hub: aggregator + hub-control active, plus complete for its own traffic

Remote_Source spoke-1

One per spoke AND partition, operator-wired on the console: <vault-id> firehose.p<partition> <offsetlog> <deadletter>. Patrons its own SSE_In + HTTP_Out, resumes from JSON positions, owns reconnect and backoff, and publishes remote:<node>:<partition> status.

Remote_Source spoke-2

set_multi_writer true on every one: it asks the SPOKE's reader to hold a superseded segment for the seal grace, or a straggler's process (complete) is orphaned and the request never finalizes here.

Remote_Source spoke-N

Scope the offsetlog with <topology> so two hubs pulling one spoke partition never share a cursor. Omitting the two directories means no cursor and no quarantine.

remote-job-rewrite

Remote_Job_Rewrite_Node: an array VALUE with k:"job" leaves as k:"remote_job", 7 bytes longer; everything else passes untouched. A graph node, not a filter, so the substrate's sources stay application-agnostic.

firehose:topic

Multi-partition Topic, firehose.p{partition}: KEY-routes by request-id hash onto the hub's own firehose.pN on disk, so each downstream partition sees its own slice, exactly as a local request would.

the hub's own complete workers

Request_Builder assembles spoke requests beside local ones; Flame_Builder's set_is_hub turns on the per-server aggregates; Job_Worker dispatches remote_job against newspack_nodes/remote_job_handlers.

Where a handler registers decides where it runs

filterruns
job_handlers onlylocally on every site, hub included; the hub ignores the aggregated remote_job copy
remote_job_handlers onlyon the hub alone, after aggregation; spokes write the entries and never act on them
bothlocally everywhere AND centrally on the hub, and the two implementations may differ

The kind is read from the ENTRY's k, never the body's, so the rewrite wins over whatever the spoke wrote inside.

Hub-mode is derived, never configured

Config::resolve_eln_token( 'is_hub' ) answers on either of two signals: an active topology NAMED aggregator, or one whose include tree reaches it; or any active graph carrying a Remote_Source node. The stock file ships no such node, so only its name gives it away; a renamed fork gives itself away by its wired reader. Memoized, and re-entrancy-guarded, since a topology naming <eln:is_hub> resolves through here.

No enable_aggregator, no enable_workers: RetiredConfigKeysTest holds both names out. Only firehose entries cross to a hub; jobfeed and jobintake stay on the site that wrote them.
