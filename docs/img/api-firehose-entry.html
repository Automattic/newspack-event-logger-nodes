A firehose line is one TM_STRUCT message, and the entry inside it is held to 3,840 bytes

Log_Manager::message( category, data ) builds the entry, fits its encoding under MAX_DATA_SIZE, and hands it to the firehose Topic keyed by the request id. Linux appends atomically up to 4,096 bytes; the 256 left over cover the key and the JSON framing.

The message: seven slots, four of them filled
[ 0TYPETM_STRUCT (16), 1TIMESTAMPnow, the cached clock, 2FROMempty, 3TOempty, 4IDempty, 5KEYthe request id: one request, one partition, 6VALUEthe entry, below ]

The entry: [ 'n', 'k' ] + $data + [ 'ts' ], in that precedence

nthe line number, stamped by the writer; the builder gap-checks it
kthe category. x (start) opens a span, x (complete) closes it, process (start|complete|aborted) brackets the record. Never renamed.
…the caller's keysm the payload (a string carrying ? is URL-redacted first); l the aggregation label; duration_ms on a close; caller under trace_callers; rule on the start line. A caller's own ts wins over the stamp, which is how the profiler back-dates plugin-load rows.
tsthe same cached clock the TIMESTAMP slot carries
truncatedpresent, and true, only when the ladder ran
encoded entry ≤ 3,840
Fits. The encoding is measured once; nothing is touched.
over the cap
Over. fit_data() sets truncated: true and works on m alone: it is the only value that reaches this size.
m cut to 3,840 · 3,456 · 3,110 · …
A string m is shortened ten percent a step, re-encoding the whole entry each step because JSON escaping expands bytes, until the encoding fits. Every other key survives, l and caller included.
m dropped
No step fits, or m is not a string: m is dropped whole and the rest re-encoded.
n · k · m[:1000]… · ts
The floor, when the other keys alone still exceed the cap: n, k, ts, truncated and, as m, the first 1,000 bytes of the oversized encoding plus a literal .... A reader can still place the line; that m is a legible dump, not decodable JSON.

Why the category is never touched

A " (truncated)" suffix would break Flame_Tree::PATTERN_START and Request_Builder_Node's ' (start)' test: the span would never open and its (complete) would orphan. Nothing is chunked and nothing reaches error_log; the entry says so itself.

Anything that can exceed the cap

goes through \Newspack_Nodes\Job_Intake::queue(), which takes the auto-lock around large writes and accepts up to MAX_JOB_SIZE, 32 MiB. The constant is private, so a producer sizing its own payloads keeps its own copy: Pyrobase's Runtime\Log does.
