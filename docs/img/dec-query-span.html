Query spans are the same pair as decision 20, with a different gate

wpdb brackets a query with the query filter before and, only under SAVEQUERIES, log_query_custom_data after. The span opens ahead of the filter chain and reads the statement at the close, where it is the one the database was asked. Bound only when the rule sets log_queries (default false).

apply_filters( 'query', $sql ) inside wpdb::query()

hook_start_priority · query_startopens sql, label only: the SQL here is what the caller wrote
later prioritiesfilters that rewrite the SQL run INSIDE the span

The same priority the generic hook timer uses (default −10000), so the span covers the filter chain as well as the round trip. A rule marking query significant gets its per-callback timings nested inside sql, and query itself is not bound as an ordinary hook: the SQL span covers it.

every later prioritythe other listeners, outside the span

Then it DRAINS $wpdb->queries. _do_query() gates the close on the constant, so App\Core defines SAVEQUERIES when it is not already. A constant cannot be withdrawn: a long-running worker keeps it for its life, bounded by the drain.

Named for its caller, not its table

l is origin_frame( true ): the first non-machinery frame is the transport, and the walk climbs past every frame of it. A fixed skip cannot: wpdb::get_row() reaches the filter through wpdb::query(), and SHOW FULL COLUMNS arrives four wpdb frames deep, hence TRANSPORT_ORIGIN_DEPTH (16) against ORIGIN_DEPTH (8). The table says SELECT wp_posts ran 156 times, never which code ran it.

Why it cannot be always-on

Anything else reading $wpdb->queries (Query Monitor) finds it empty after the drain.
