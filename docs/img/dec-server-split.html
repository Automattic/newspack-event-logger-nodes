A server scope the key cannot carry rides inside the value, and is applied as a projection

Every other scope is a key prefix (decision 1). The URL index cannot take one: a per-server namespace would apply MAX_URLS_PER_SHARD per key and grow O(servers × that cap) rows per bucket, on the axis decision 11 watches. So each row carries its own per-server split, and a server-scoped read is a projection over the MERGED row.

2 · Merge first, across buckets and partitions

Every merge, reader or writer, runs expand_sole_server() BEFORE summing; sum_fields() skips a non-array, so an unexpanded null would delete that host from the merge.

Because every split field adds, selecting then summing and summing then selecting agree. So the scope need not reach the loader: ONE fold_index_row() merges for the table and the modal alike, and a scoped poll pays no second fan-out.

3 · Project for one server

swap_url_server_sums() replaces the row's eight summed fields with the selected server's and unsets the split: the one place the split's fields become names.

Performance_CI_Node::project_row() finishes it: unsets srv_recent, divides the means once from sum_ms and sum_peak_mb, so nothing un-averages a figure another function divided, and computes the recent-window share, reader geometry the schema has no name for.

min_ms and max_ms are extremes, so a scoped row keeps the URL's own: deliberate, and invisible on a fleet of disjoint sites. A server absent from srv drops the row from the scoped read.

A url_hash's shard is its first hex digit. Each shard keeps its best $offset + $limit rows by the sort key and its best SLOWEST_ROWS by mean (the dark band), then drops the rest before the next shard is read.
dump_url point-reads the one shard url_shard() names (dark cell): a sixteenth of the keys, through the same $read_index seam the table folds, and raw_row() point-reads the same way.

No whole-index memo. The merged index counts the DISTINCT URLs in the window, which nothing bounds. Holding it exhausts a production hub's 512 MB inside the fold itself.

The axis is visitor input

server_name is SERVER_NAME, and under Apache's default UseCanonicalName Off that is the client's Host header, so a domain-mapped multisite or a catch-all vhost has no ceiling. The cap sits far above any fleet in evidence (five times the largest hub, three times the widest per-URL split any test asserts), and the tail FOLDS, so every total stays exact.

Not hub-gated

Unlike the three per-server aggregates beside it, the split is stored everywhere: the filter is offered wherever the server dimension has values, and a scoped read of a row without a split returns nothing, so gating it would empty the URL table on every spoke.
