An auto-tune decision is a message to a hidden sibling, and a rule edit like any other

Flame_Builder_Node judges each completed request against its governing rule's two thresholds, batches the candidates to its five-second flush, and sends them to the owned {name}:auto-tuner node, which mutates ONE rule through Rule_Set. From there the change reaches spokes the way an admin edit does.

Flame_Builder_Node

One per partition, in the flame-builder worker.

Auto_Tuner_Node

Owned, hidden, patron-linked; never built in TSL.

Rule_Set

The durable ruleset, one option plus per-rule hook options.

hub-control

Settings_Sync tailing settings.p0.

1Per completed request, with a non-zero threshold on the rule: a hook firing more than auto_disable_threshold times in ONE request is a disable candidate; a hook whose leaderboard mean ms per call reaches auto_protect_time_threshold, over this partition's requests in the current five-minute bucket since the last flush, is a candidate for significant status. Worker traffic and the callback and plugin views feed neither test.
2Candidates accrue until the 5 s flush. Across the emit batch the builder holds a 5 s evlog:auto_disable_lock taken with Memcached::add(), the one call site on the raw handle, and releases it only while the value it wrote is still there; two partitions flushing at the same instant would otherwise emit overlapping decisions twice. With no shared handle, or no Stats_Store, it fires unlocked.
3One message per list to tune. KEY discriminates which per-rule list; VALUE names the rule and the items.
disable_hookshooks minus the items; significant events preserved
disable_custom_eventscustom_events minus the items; significant events preserved
add_significant_eventssignificant_events ∪ items
VALUE{ rule_id, items }
4authorized(): NEWSPACK_NODES_WORKER_TYPE in $_SERVER (the flame-builder worker) or the TUNE capability (an admin request), manage_options until wp nodes caps install moves it; otherwise nothing is written. The check reads the process and the user, never where the message came from.
5mutate_rule() calls \Newspack_Nodes\Config::invalidate_options_cache() first, so the read starts from a fresh snapshot rather than clobbering a concurrent worker; it reads the rule by id, applies the one apply_* the KEY names, and compares before and after with both hook lists resolved to concrete form (unchanged()), because a pointer-tier rule stores hooks = null. A no-op decision skips the write.
6Rule_Set::save() re-tiers and persists the whole ruleset. The option write records a settings event; where hub-control is active, Settings_Sync pushes the changed option to every spoke, and its 300 s sweep re-pushes every option as a backstop. There is no remote_manager job and no suppress_sync guard.
