# Architecture Decisions

The load-bearing design decisions of the event logger. "Fixing" one usually reintroduces a bug already paid for. Each record states what forced the choice, what it costs, what was weighed against it, and the concrete condition that reopens it. A **Revisit if** is a sufficient tripwire, not the only door: an argument on the merits also reopens a decision.

Numbers are stable. Code comments, docblocks, `AGENTS.md` and `docs/architecture-guide.md` cite a record as "decision N", so supersede a record rather than renumber it. The substrate keeps its own series under the name `ADR-N`, and a "substrate ADR-N" here links to that file.

## Decision 1: Namespaced memcache schema

Memcache is where stats are written and read; the durable mirror of decisions 10 and 11 shadows them only for read-back on a miss. Per-partition prefix `evlog:p{N}:`, which the substrate's `Table` wraps in the salted install scope (`Cache_Backend::site_key()`) rather than carrying the salt inside, the durable mirror's key (decision 10) carries neither, then namespace: `hourly`, `lb`, `lb_h`, `lb_s`, `urls`, `urls_h`, `urlmap`, `urlnames`, `urlnames_h`, `url`, `dim`, `url_dim`, `categories`, `url_cat`. `urls` and `urls_h` are decision 17's two resolutions of one index, and `lb`/`lb_h` are the same two of the leaderboard: the heaviest read the dashboard makes, one category per hook the site fires across 288 buckets and four partitions, folded hourly for exactly the reason decision 17 folds the URL index. The per-SERVER leaderboard keeps the fine path: a shard count is a constant the schema chooses, but the servers present in an hour cannot be enumerated from the keyspace, and `docs/architecture-guide.md`'s Memcache Schema table is the full list with its key shapes. The `urls` index is additionally SHARDED: `urls:{shard}:{bucket}`, sixteen shards by the first hex digit of the url_hash, and again by POPULATION: a `w` prefix on the same token (`urls:w3:…`) carries worker traffic, which the table excludes by default, so an ordinary read never carries rows it discards and a URL a job also visits keeps its reader row. A stored row carries the 12-char hash and no URL string; `urlmap:{hash}` holds `[ path, origin ]` once, re-written only past half its TTL, and readers resolve only the hashes they display. `urlmap` answers about ONE hash; a SEARCH asks about a whole SHARD, and answering that per hash cost 668,918 keys a poll on a production hub, 200-290s and 350-510MB per `urls` request. `urlnames:{shard}:{bucket}` and its `urlnames_h` fold answer it in ~40 keys a shard, on the same geometry and the same `read_plan()` as the rows, and carry PATHS only: the origin is already the `ROW_SRV` split's key and already the `server` dimension the picker is built from, so a third copy would also put the dropdown's question inside the search box. Uncapped, deliberately: every URL must be searchable, and a cap drops exactly the URL somebody is looking for. It is NOT bounded by `MAX_URLS_PER_SHARD`: `cap_url_rows()` runs inside the ROW intent's merge, after the name map is built, so what bounds it in practice is the distinct URLs a shard sees in a bucket, and what bounds it in the end is `url_name_intent()`'s refusal log, which it carries for exactly that reason. That took the widest row from 811 to 699 bytes and the common sole-server row from 290 to 189, which is what pays for `Flame_Builder_Node::MAX_URLS_PER_SHARD` at 2,000: 32,000 distinct URLs a bucket, against a measured client refusal at 5,000 rows a shard. A shard is not a scope, which is what makes it the one component here that names no dimension of the data: it is physical partitioning, and it exists because one blob per bucket is the pressure every cap in this schema is sized against. **All but `url` and `urlmap` are bucketed, and the bucket key is always the LAST component**, so every scope (server, URL, dimension) is a pure key prefix, one `lookup_multi` serves them all through `Stats_Store::lookup_buckets()`, retention is the key's own TTL rather than a hand-rolled cutoff pass, and whether the bucket a key names is still open is decided from the key alone (`Stats_Store::is_open_bucket()`). Those two key on the url_hash instead, and a 12-character hash is not bucket-shaped, so neither ever reads as open. Retention is one TTL per storage ROLE, and there are three. Per-URL flame stats (`url`) get `max(3600, max_lifespan/24)`. A FINE `urls` bucket gets `min(max_lifespan, FINE_TTL_SECONDS)`, two hours: its own read window rather than the whole one, because decision 17's coarse tier answers for everything behind it. At that width the tier costs 24 buckets a shard, the same as the coarse tier's 24 hours. Everything else gets the full `max_lifespan`: a `Stats_Store` constructor property seeded from the substrate's `min_lifetime` key (default 43200) through `Config::stats_retention_seconds()`, which floors it at `Stats_Store::PREFIX_FLOOR` = 3600. `max_lifespan` is not itself a config key on either side. Caps prevent value-explosion against memcache's 1MB limit: `MAX_DIM_VALUES=20`, and the `server` axis takes `MAX_SERVER_VALUES=128` instead (`Stats_Store::dim_cap()`), through the same traffic-ranked `Other` fold. Exempting it on the reading that a cap is a cardinality guard and this axis is the FLEET, one `{c,s,m}` per spoke, so a hundred cost about four kilobytes and there is nothing to guard, is wrong: `server_name` is `$_SERVER['SERVER_NAME']`, which under Apache's default `UseCanonicalName Off` is the CLIENT'S Host header, so a domain-mapped multisite or any catch-all vhost taking Host-header spray makes the axis visitor input with no ceiling. The ceiling is 128 rather than `MAX_DIM_VALUES`' 20 precisely because 20 bound on a real fleet: it dropped every spoke past the twentieth into `Other`, per bucket by request count, which is how a 24-spoke fleet lost four sites from its own picker. So it sits far above any fleet in evidence and the tail FOLDS rather than dropping, keeping every total exact. **Decision 14 owns the reopen condition for this ceiling**: wherever the `server` axis is stored, one tripwire, stated there. `MAX_URL_DIM_VALUES=10`, `MAX_CAT_VALUES=50`. Overflow rolls into a synthetic "Other" bucket; the `total` pseudo-category is preserved before capping. A category entry is POSITIONAL (decision 18) and its `CAT_MS` is stored ROUNDED to `Stats_Store::CAT_MS_DECIMALS` places: `Flame_Builder_Node::fold_categories()` rounds after the cap, because the cap re-sums its tail into `Other` and a sum of rounded doubles is not itself rounded. These are milliseconds a chart draws as seconds-per-second or as a mean, so a microsecond is already past anything rendered, where a full-precision double spends twelve more bytes per entry saying it. **The same fact obliges the WIRE to round again**: `Performance_CI_Node::compact_category_series()` emits a sum across one `Stats_Store` per flame-builder partition, and a stored entry already being rounded is the reason that sum is not. Measured over 5,000 realistic millisecond pairs, 22.1% of two-store sums and 30.0% of four-store sums serialize LONGER than their rounded value, worst case `0.30000000000000004`. `Stats_Store::sum_entry()` is what makes every merge here shape-exact: it rebuilds an entry from its field table and DISCARDS anything outside it, so a pre-deploy `{t,c,n}` met by a positional one is dropped rather than hybridised into a six-key object. A caller wanting a field the table does not name puts it back itself, beside the reason: `add_totals()` replaces its sum onto the bucket it was given so a merged time series keeps the `hour` it is keyed by, and `merge_url_row()` reads its extremes off `$into`.

## Decision 2: Sums, not means

Leaderboard buckets hold raw `count`, `sum_req_time`, `samples`, `sum_time`, `sum_count`, so cross-bucket and cross-partition merges are exact addition and the display layer computes means at read time. Do NOT regress to running-mean storage: it is what produced the EMA-clamp bug this rule exists to keep out.

---

## Decision 3: Fail-soft stats, fail-closed SSE slots

Every `Stats_Store` method returns `null` / `[]` / `false` when memcache is unreachable and never throws, so dashboards show "no data" instead of erroring. The substrate's `SSE_Slot_Pool` fails CLOSED at the caller: memcache down means a new connection gets HTTP 429, preserving the rate-limit invariant. The asymmetry is the decision; the two halves live in two plugins.

---

## Decision 4: Settings fan-out is a node graph; no consumer means a silent no-op

Propagation is the substrate `Settings_Sync_Node` graph in the `hub-control` topology. A change to any `newspack_`-prefixed option records a settings event, which `Settings_Event_Writer` appends to `settings.p0` (only an allowlisted option carries its old and new VALUES), and `Auto_Tuner_Node` mutates the specific rule named in the message (`rule_id`) and persists the whole ruleset via `Rule_Set::save()`: no `remote_manager` job, no `suppress_sync`; each write records a settings event like any admin edit. Nothing fans the change out unless `hub-control` is active and per-spoke `HTTP_Out` nodes are wired; on a spoke or standalone site the event is tailed and dropped. That IS the structural gate. There is no `enable_workers` or `enable_aggregator` key: hub-mode derives from which topologies are active.

---

## Decision 5: Salt-rotation schema migration

Flushing is the substrate's one button, `Cache_Backend::rotate_salt()`, which moves the install scope for every plugin at once; `Stats_Store` keeps no salt of its own. Schema bumps and emergency flushes share the mechanism. The scope is memoized per process, so restart long-running workers for immediate effect. **The rotation IS the migration, and nothing in the code compensates for skipping it.** A schema change orphans the old keys the instant the salt moves, so no reader or writer carries a shape probe, a version component or a row-level legacy test: every one of those is a second migration mechanism beside this one button, and each has to be maintained against every future row shape. Skip the button and the dashboard reads garbage for one retention window; that is an operator error with a one-command fix (`wp nodes memcache flush`), not a case for the runtime to detect. **The durable mirror is the one tier the button does not reach**, by decision 10, so it carries the one version component this decision otherwise rejects: `Stats_Store::MIRROR_KEY_VERSION`, folded into every durable key, bumped when a frame shape changes, and nothing else compensates for skipping that either. *Alternatives rejected:* a schema-version component in the key prefix, a permanent extra component on every key, for the identical orphaning the salt already does; detect-and-purge at boot (memcached cannot enumerate, and a boot pass over the whole keyspace is decision 6's latency cliff). **Revisit when** a deploy can no longer be relied on to rotate, at which point the mechanism to add is one that forces the button, not one that tolerates its absence.

## Decision 6: `get_multi` batching is essential

Reader paths multi-get across all retention buckets per partition in one round-trip; per-key `get` is a latency cliff on dashboards. Implemented in both the real and Fake memcached.

---

## Decision 7: Job_Intake for >4KB payloads, the firehose for ≤4KB

Small runtime jobs ride the firehose with `k:"job"`, and `Job_Router_Node` extracts them. Large jobs go straight to `jobintake` via `\Newspack_Nodes\Job_Intake::queue()`, which takes the per-Partition write lock. The substrate offers two more ingress logs. `jobfeed` is the unlocked PIPE_BUF-bounded path the router also tails, so a spoke's router can tail jobs alone instead of the whole firehose. `jobdelay.p0` holds what is not due yet, and no router tails it: `Job_Delay::sweep()` runs on `newspack_nodes/periodic`, circulating the log and delivering each due entry into the live `jobintake` the router already reads. The wrong path loses jobs: `Log_Manager` trims `m` on any ENTRY over `MAX_DATA_SIZE` (3840B), so the handler never sees a parseable payload.

---

## Decision 8: Hub vs spoke topology

Hub = the `aggregator` (+ `hub-control`) topologies active; there is no `enable_aggregator` toggle. A producer only ever writes `k:"job"`, and every node runs its own `Job_Worker_Node` dispatching those against `newspack_nodes/job_handlers`. The hub additionally runs `aggregator`: per-spoke substrate `Remote_Source_Node`s pull spoke firehoses, and ELN's `Remote_Job_Rewrite_Node`, wired between the sources and the firehose `Topic`, rewrites incoming `k:"job"` to `k:"remote_job"`, which the hub's `Job_Worker_Node` dispatches against `newspack_nodes/remote_job_handlers`. The two filters are independent registrations, so a job type registers under either or both depending on where it should run.

---

## Decision 9: CRC32 + 31-bit-mask partition routing

Inherited from `Partition_Node::hash_to_partition()`. Used by Topic, `Job_Intake`-keyed mode and `Log_Manager`'s URL routing. Same key → same partition across all producers.

## Decision 10: The durable mirror writes a bucket once, when it closes, under a key that carries no install scope

`Stats_Store::entry_key()` is `evlog:m{V}:p{N}:{key}`, never the Table's `Cache_Backend::site_key()` form: the mirror exists to outlive `wp nodes memcache flush`, and a scoped key is orphaned by the very rotation it should survive: an operator flushed, the reader hashed the new scope, and weeks of on-disk history stopped answering. The mirror write, the `stats-index` hash, the rehydrate compare and the held-frame lookup all go through that one function, so they cannot disagree, and `restore_state()` keeps only keys `is_mirror_key()` claims, so a checkpoint carried across the change holds nothing it cannot look up. `V` is `MIRROR_KEY_VERSION`, the mirror's own migration lever (decision 5). `flame-stats` is append-only and last-frame-wins per key, so mirroring the bucket still being accumulated into, once per 30s checkpoint, ten times over a 5-minute bucket, leaves nine dead copies retained for `stats_mirror_lifetime`. Measured before the change: **4,279,767 of 5,531,418 bytes (77.4%)** of a real `flame-stats.p0` were frames a later frame had already superseded. `flush_stats_mirror()` therefore holds a bucket's frames until `Stats_Store::is_open_bucket()` says it closed. *Alternatives rejected:* writing every checkpoint and shortening `stats_mirror_lifetime` instead (loses history rather than duplicates); keying frames by bucket+checkpoint and compacting later (a compactor to own, for the same bytes). **Revisit if** the partition ever stops being last-frame-wins on read.

## Decision 11: The open bucket is durable in the OFFSETLOG until it closes, and the carry is capped

A held frame is in no durable log, so `save_state()` carries the held frames and `restore_state()` takes them back: a self-pruning ring of at most 60 keyframes, where the mirror retains for twice the stats window, so the open window costs bounded disk in the cheap place. Three invariants the code must keep: the worker's `rehydrate` seam consults held frames FIRST, or a mid-bucket eviction makes the read-modify-write restart the bucket from zero; a restored frame carries what is LEFT of the RETENTION window, bounded by its own storage role's TTL, per [substrate ADR-18](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-18-a-table-can-front-a-durable-record-the-walk-that-finds-it-stays-in-the-app): a frame whose CACHE lifetime ran out is still read, so refusing it lost an evicted `urls_h` that the fine buckets on disk could have rebuilt; and the carry is capped at `MAX_CHECKPOINT_MIRROR_BYTES` because the per-server aggregates grow with the spoke count while `Partition_Node` DROPS an oversize record, and that record is the whole checkpoint, cursor included. **Dropping the biggest is the design, not a fault**: narrowest-first keeps the most keys recoverable per byte, and a dropped frame is re-merged from memcache by the next write to its bucket, lost only if the process AND memcache both fail before the bucket closes. The budget is set from the observed held size, ~267KB–348KB per checkpoint on a production hub, against a topics cache peaking under 3.8MB across a day, and clears that peak by ~6x, so the log does NOT fire in routine operation and "it fired at all" is informative. The margin is what buys that: at a budget of 262144 the held totals sit just over the cap, so a multi-spoke hub drops one to thirteen frames on essentially every checkpoint and the tripwire trips permanently, which tells you nothing. The log carries the numbers too: how many frames dropped of how many held, the budget, the bytes it carried, and the WIDEST held frame with its namespace and size: the namespace because a sharded `urls` key and an `lb_s` key are both opaque, and which one fired is the whole question this tripwire asks. **The pack orders by ENTRY COUNT, not by encoded bytes**, and encodes only what it carries plus the one it stops on: encoding every held frame to sort them made `MAX_CHECKPOINT_MIRROR_BYTES` bound the OUTPUT and never the work, which at the held-frame backstop is megabytes of throwaway JSON every thirty seconds. A frame is a map of small numeric entries, so its count tracks its size closely, and the ordering only has to be APPROXIMATE: the budget is enforced against real encoded bytes as they accumulate, so a proxy that mis-orders two frames costs a slightly worse packing and never an oversize record. `mirror_held_bytes` on the GET_STATS payload still reports the exact held total, on a verb an operator asks rather than every checkpoint; `mirror_held_frames` beside it is the WIDEST single namespace's held count, because `MAX_HELD_FRAMES` is per namespace and a cross-namespace total cannot warn about it: six namespaces holding five thousand each read as thirty thousand with nothing near the bound, while one spilling on every write reads as ten thousand and fifty. **Revisit when** the log fires AT ALL, since any drop means the held set has grown past ~6x the size it was measured at, which is the O(servers) signal arriving, or when the WIDEST held frame the log names is NOT a per-server leaderboard, which would mean something other than fleet size is driving it. Read the CHECKPOINT trend in BYTES, off `mirror_held_bytes`: `urls` is sharded, so one open URL bucket holds SIXTEEN frames rather than one, each a sixteenth the size, and a frame count steps up accordingly with no fault behind it. Frames are what the BACKSTOP is against, which is why `mirror_held_frames` answers for one namespace rather than the set. Sharding also repaired the other half of this tripwire: an unsharded `urls` blob carrying a split and a duration reservoir per row was larger than the whole budget, so it was always the widest frame and "the widest frame is NOT a per-server leaderboard" was permanently satisfied. Sixteen smaller frames sort in among the leaderboards and the fleet-size signal reads true again. What bounds the budget from ABOVE is the offsetlog ring, `OFFSETLOG_MAX_SEGMENTS` × the budget of disk, 60 keyframes, ~120MB, plus a write every 30s. That ring caps keyframe COUNT and never bytes, and nothing else bounds it, so raising the budget raises the disk cost in direct proportion and that is the true cost of the number. NOT `Partition_Node::MAX_LARGE_LINE_SIZE`, which is 16× away and does not bind. **The real lever is upstream, and it is a SPILL rather than an eviction**: buffer-time eviction drops a frame from the durable mirror at bucket close, a strictly larger loss than dropping it from a checkpoint, which is why `STATS_MIRROR_TOPN` rank-caps no per-URL namespace (a top-100 there leaves every quieter URL in memcache alone, and a moved cache scope takes its whole history, measured on a production host as 0 of 12 pre-deploy buckets for a URL at 0.00 req/s). `MAX_HELD_FRAMES` bounds each namespace's held set at 10,000 instead, and `spill_over_backstop()` writes the overflow to the partition early rather than dropping it, so the bound costs one redundant record and never a frame. It spills a BAND, a tenth of the bound, rather than one frame: ranking the buffer is a pass over it, and the buffer PINS at the bound under exactly the traffic the bound exists for, so one frame per write puts that pass on every write past it, quadratic in a spray's length inside the worker this bound protects. The band is the hysteresis `trim_entries()` already uses, and a rank-ordered structure is NOT the alternative: a request merging into a key changes its rank, so keeping the buffer ordered pays per write instead. **With no partition to spill into, nothing already HELD is discarded**: `flush_stats_mirror()` reads a name that does not resolve as one that may resolve next checkpoint, and the backstop takes the same reading, refusing the ARRIVAL instead, whose value is still in memcache and whose bucket's next write re-offers it. The per-server aggregates still grow O(servers), so the CHECKPOINT budget still loses to fleet size eventually; bounding that axis remains the structural fix.

## Decision 12: A stat times the request; a flame value is a rendering artifact

Two numbers describe one request and they are not interchangeable. `duration_ms` on the record is what the request took, measured once. A flame node's `value` is a LAYOUT WIDTH: `Flame_Tree::cover_children()`, `Flame_Fold::flatten()` and `Flame_Builder_Node::fill()` all RAISE it so a parent covers its positioned children, because the browser prunes on a single cutoff and takes a whole subtree with anything it drops, and `treemapDice` scales children by `parentWidth / parent.value`. Raising is correct for drawing and wrong for counting. **Every stat therefore reads `$request['duration_ms']`; nothing measured reads a flame `value`**: that covers every namespace of decision 1 plus the per-URL aggregate's `sum_value`. *Measured before the change:* a 356,312ms request reached `avg_ms` as 724,662.87ms, because `fill()` had raised the root to cover a child that ran 355 seconds after the parent's own occurrence. *Alternatives rejected:* not raising at all (deletes exactly the frames a viewer opened the graph to see); computing stats before the raise (the ordering is invisible at the call site, and one reorder reintroduces it). **Revisit if** the browser stops pruning on a single value cutoff: the raise can go then, and the two numbers converge.

## Decision 13: A sequence-break marker is missing detail, not idle time

`entries (lost)` and `entries (aggregated)` stand in for entries `Request_Builder_Node` removed: discarded on overflow, or merged by the fold. It mints them, so it owns the vocabulary as `Request_Builder_Node::SEQUENCE_BREAK_KEYS`; consumers reference that constant rather than keeping their own copy, and the JS holds the only deliberate duplicate because it is a separate deploy unit. **No consumer may reason across a marker.** `Findings::entry_gap()` skips a gap on either side of one, `Reqgrep_Command` breaks its sequence there, and `logEntryUtils` splices the merged spans back at it. Reading the interval as unexplained had one record's `entry_gap` proposing MORE hooks while its `truncation()` proposed fewer, both at once, on the same record. What a consumer MAY read across one is the record's own ending: whether anything closes the outermost pair. That decides FRAMING, which spans were severed and which ran to the end, and leaves the interval exactly as unmeasurable as it was, which is what this decision protects. `logEntryUtils`' `pruneSeveredSpans()` and `Reqgrep_Command::prune_severed_spans()` are the one rule, and the parity test in `logEntryUtils.test.js` pins the vocabulary they share. **The severance frames the record's RESUMED tail, never the folded interior spliced in at the marker**: those rows are what the TREE puts inside the open span, and the fold is what ate its close, so pruning before them made every merged row a sibling of the parent it ran in: a gyrobase subprocess that exited 0 lost its whole 535s interior out to the request's level, while the same shape whose drain survived the fold nested correctly. The prune therefore waits for the first row the record itself resumes with (`fromFold`). **Revisit if** a marker ever carries its own duration, which would make the interval measurable rather than merely missing.

## Decision 14: A server scope the key cannot carry rides inside the value, and is applied as a PROJECTION

Decision 1's shape is that every scope is a key PREFIX: `lb_s` is `lb` with a server component, and one `lookup_multi` serves it. The URL index cannot follow that: a `urls_s` namespace applies the `MAX_URLS_PER_SHARD` cap **per key**, so the index that is mirrored in FULL, `urls`, like everything absent from `STATS_MIRROR_TOPN`, grows O(servers × that cap) rows per bucket, on the same axis decision 11 already names as the one that outgrows any fixed checkpoint budget. So the split rides in the value instead: each row carries `srv`, its summed fields per reporting server, capped at `Stats_Store::MAX_SERVER_VALUES` by the same ranked `Other` fold `dim_cap()` gives the `server` axis everywhere it is stored. Reading the axis as the FLEET is what argues for leaving it uncapped, and it is wrong: `server_name` is `SERVER_NAME`, and under Apache's default `UseCanonicalName Off` that is the client's Host header, so a domain-mapped multisite or any catch-all vhost makes it visitor input with no ceiling. What a cap must not do is bind on a real fleet: a folded server's scoped read matches nothing, and the URL leaves the filtered table AND its totals silently, exactly as the dimension cap dropped it from the picker. So the ceiling sits far above any fleet in evidence (five times the largest hub, three times the widest per-URL split any test asserts) and the tail FOLDS rather than dropping, keeping every total exact. The cap is applied ONCE, after the `MAX_URLS_PER_SHARD` fold, because the fold is what mixes hosts: a stored `url` is absolute, so a real row carries one or two splits while each family's overflow row carries every server its own tail was seen on. Bytes are then bounded on both factors of rows × servers rather than one, with the refused-write log as the backstop, a guard that REPORTS where the cap CORRUPTED: an oversized shard is one loud line and a bucket's rows lost until the next write. **Revisit when** that log fires at a row count well UNDER `MAX_URLS_PER_SHARD`, since a shard over the item limit on few rows is bytes per row, which is rows × servers, and the answer is a byte-derived row cap, not a lower value count, or when a real fleet approaches `MAX_SERVER_VALUES`, which the picker announces by growing an `Other` entry and which means the ceiling, not the mechanism, is what needs raising. Refusal AT the cap is the row count doing its job and says nothing about the fleet, and the namespace cannot be the signal: the log lives in the URL-index write path and can name nothing but a `urls` shard. A split of ONE server that served every request the row counted stores the host name against `null` rather than restating the row (decision 18): `null` is that server's numbers, absence is still "never served here", and every merge on both sides expands through `Stats_Store::expand_sole_server()` first. **Only fields that ADD are split** (`Stats_Store::URL_SRV_SUMS`): `min_ms` and `max_ms` are extremes, so a server-scoped row keeps the URL's own across every server: deliberate, and on a fleet of disjoint sites invisible. Because every split field adds, selecting then summing and summing then selecting agree, so the scope is a projection over the MERGED row (`Performance_CI_Node::project_row`), not a filter before the merge. **There is no whole-index memo, and reintroducing one is the trap:** the merged index is the count of DISTINCT URLs in the retention window, which nothing bounds: the stored buckets cap at `MAX_URLS_PER_SHARD`, their merge does not. So holding it exhausted a production hub's 512MB inside the fold itself, and decision 17 carries the rest of that fatal's history. `url_page()` folds ONE SHARD at a time, keeping only each shard's best `$offset + $limit` by the sort key and its best `SLOWEST_ROWS` by mean; a url_hash's shard is its first hex digit, so shards are disjoint and the union of the per-shard top-N IS the global top-N. Spec: dndocker's `docs/superpowers/specs/2026-08-31-url-index-per-shard-fold.md`. Specs for these plugins live there, never in the plugin repo. Scoping inside the loader instead made the memo a per-scope cache, and a filtered poll, `urls` scoped, `overview` not, paid the whole `lookup_multi`, unserialize and merge twice, against decision 6. That argument is about the SERVER axis and does not reach the SHARD one, which this same decision names as a constant the schema chooses: `url_row_sources()` takes an optional `$shard`, and `dump_url` point-reads the one shard `url_shard()` names for its hash rather than paying the URL TABLE's fan-out to answer about one row: one shard of the sixteen per partition, so a sixteenth of the keys the table reads, and decision 17 carries what that whole-index fan-out costs. `Performance_CI_Node::raw_row()` point-reads unconditionally, through the same `$read_index` seam the table folds: that seam takes the SHARD, so a point read runs under it too, and a test counting index reads measures the narrowing rather than a branch around it. Both readers fold through ONE `fold_index_row()`, because a second copy of the merge is how the table and the modal come to disagree about the same URL. WHICH fields swap is `Stats_Store::swap_url_server_sums()`, beside the table that defines them: those fields are INDEXES, not names (decision 18), and that is also where the split's eight become names, for the one selected server, because no reader displays a split; the means and the recent-window share are the READER's: a mean is a display division per decision 2, and the window is reader geometry the schema has no name for. So `project_row()` finishes what the store starts. Neither half returns a row in one scope on its own, and both are named for what they do rather than for what the caller wants. The row also carries `sum_ms` and `sum_peak_mb` to display, so the projection divides once, in its own scope, and nothing has to un-average a figure another function divided. The split is capped at persist and not in the accumulator, so an open bucket's rows carry one entry per distinct reporting server SEEN IN THAT FLUSH WINDOW on the checkpoint, which decision 11 counts as uncounted `pending`. Spray does not widen that: an absolute `url` puts the sprayed host in the row KEY, so the accumulator answers it with rows, bounded by `URL_ACCUMULATOR_SIZE`, each carrying one server, not with a wide split. Unlike the three per-server AGGREGATES it sits beside, the split is **not** hub-gated: the filter is offered wherever the `server` dimension has values, and a scoped read of a row without a split returns nothing, so gating it would empty the URL table on every spoke rather than save one. *Alternatives rejected:* a `urls_s` namespace (above); resolving the scope from `url_dim` at read time (O(urls) gets per poll). The `urls_s` rejection is NOT an argument against the sharding that shipped, though both add a key component: a shard count is a constant this schema chooses, while a server count is an input this schema does not control, visitor-driven at worst, and the one decision 11 watches. A per-key axis has nowhere to put a fold, so capping it is not even available. Sixteen shards of `MAX_URLS_PER_SHARD` rows is a ceiling; O(servers) × that is not. **Not taken, deliberately:** `url_dim`'s `server` axis looks like a duplicate and is not one in either direction: it is a per-BUCKET time series of `{c,s,m}`, which is what the URL-detail breakdown chart draws, while `srv` is one window-merged scalar carrying eight fields including the status classes. Neither can produce the other. (Both take `MAX_SERVER_VALUES` on the `server` axis; any remaining cap asymmetry between the two namespaces is unobservable: `dump_url` throws `URL not found` for any hash absent from the index, so a URL that never survives `MAX_URLS_PER_SHARD` cannot reach its own `url_dim` rows.) **Revisit if** `urls` ever gains a top-N mirror bound, which would cap a per-server namespace too and make the key-prefix form affordable again; if the row ever carries its split PER BUCKET, which is the one shape that would retire `url_dim`'s server axis; or if one URL is routinely served by more than `MAX_SERVER_VALUES` servers, at which point `cap_bucket` rolls the surplus into a synthetic `Other`, a scoped read of a demoted server matches nothing, and the URL leaves the filtered table AND its totals silently. That is unreachable today and worth knowing why: a stored `url` is ABSOLUTE (`https://host/path`), so a URL hash belongs to one site and carries one or two splits, not a hundred. The same fact is why `find_recent_requests_for_url()` is not scoped: the request index carries no server, and it does not need one.

## Decision 15: The `urls` verb owns every URL-set fact; `overview` owns the site

One verb applies the filters, so one verb answers for what they left: how many URLs, how many requests, the averages, the rate, the slowest ten, and, as its default page, sorted by count DESC, the busiest. The header and the table beneath it therefore cannot disagree, and a filter matching nothing reads as an empty set rather than as zero traffic. `overview` keeps only what the URL index cannot answer: `total_requests` and the two averages come from the global `hourly` namespace, which has no server dimension, and scoping some of a payload and not the rest is how it comes to contradict itself. It does not touch the index at all, which is also what holds a filtered poll to one fan-out. The two totals differ by construction in two ways worth knowing: `hourly` drops worker requests, while the URL index keeps them on their own rows; and `hourly` counts only requests whose duration was measured, so decision 25's evicted and aborted records reach the index and never the site total. The per-shard cap costs the index nothing: `MAX_URLS_PER_SHARD` folds its tail into a synthetic `Other` row (`Stats_Store::OTHER_KEY`) carrying only the fields that ADD, splits included, so a total summed from this index is exact site-wide, and per server for every server `MAX_SERVER_VALUES` keeps: its own tail folds into an `Other` server no real fleet reaches. That row is marked `aggregate` and the table renders it un-clickable: its key is not a url_hash and `dump_url` cannot answer for it. `dump_url` takes the same `server`, because the modal opens from a row that filter scoped and a site-wide average under a scoped count is the same defect one click in. Every rate divides by the WINDOW, `RECENT_BUCKETS` × `Stats_Store::BUCKET_SECONDS`, dropping the bucket still filling, never by the buckets that happened to carry traffic: divide by those and a URL seen in two of twelve reads six times its rate beside a header that does not. The reply echoes the `filters` it applied, and the Ask brief carries them on EVERY surface, so a narrower number never reads as the site's. Two surfaces the scope deliberately does NOT reach, both because the storage cannot answer them: `dump_url`'s `breakdown_time_series`, `category_time_series` and `aggregate_flame` are per-URL only, since a per-URL-per-server series would be new storage on the axis decision 11 watches, and `find_recent_requests_for_url()` has no server in the request index. Both are harmless while a stored `url` is absolute, which makes one URL one site. The table EXCLUDES worker traffic by default, and so the header does. `$count_global` keeps workers out of every site-wide aggregate, because one long-running job would otherwise dominate the averages, while the per-URL row deliberately keeps their timing, so a header summed from the index inherited them: on a staging hub that made "Avg Response" read 227ms of cron against 3ms of reader traffic. The row RECORDS whether its traffic was a worker (never derived from `?worker_type` in the URL text, which is the substring guess that emptied a table once), the `urls` verb's `include_workers` opts IN because its default excludes, the mirror of `errors_only`, which opts in to narrow, and the capped tail folds into TWO overflow rows (`Stats_Store::other_key()`), because one cannot answer a filter about a mixed set. One scope rule across the surface, so it is not re-litigated per widget: a FETCH sends the live selection, so `urls`, `dump_url` and `ask` all ask for what is selected now, while a LABEL reads the scope the server echoed back, because it names numbers already on screen. Mixing them put a brief for one server beside a panel showing another's. **Revisit if** the header ever needs a number the URL index cannot produce (the answer is a new field on the `urls` reply, not a second source read beside it), or if a host is ever reported by two servers, at which point those three charts and that examples list start describing a wider set than the count above them.

## Decision 16: The breakdown panel is always mounted, and says which kind of nothing it has

`BreakdownControls` is the chart and the dropdowns that drive it: one panel, because the Metric and Breakdown values it reads are exactly the ones its own selects set. Both callers mount it unconditionally: those dropdowns are the only way out of a dimension with no rows, a read still in flight or a refused reply, so any gate that can unmount them can trap an operator. The Overview card's gate is what proved it: it once fell back to `overview.aggregate_time_series` when the selected dimension had no values, which drew a flat series legended "Total" under a dropdown reading "User Agent", and the modal's version once gated on `breakdownData` while `useCommandOnce` treats a refusal as an answer, so an error unmounted the only control that could have recovered from it. There is no "None" breakdown, so the totals are never the requested view and the chart holds no undifferentiated source at all. What replaces the gate is `breakdownState( breakdownData )`, one resolver the chart and the panel both read: `pending` when no series is in hand, `empty` when one arrived carrying no values, `series` otherwise. Only `series` draws. The two callers reach `pending` by two different mechanisms, and the wire guarantees neither on its own. The Overview card reads `overview.breakdowns[ dimension ]`, a map the server keys by every dimension it was ASKED for, so an absent KEY is a dropdown switch the reply has not caught up with. The URL modal's `url_breakdown` reply carries one dimension and no key to look it up by, so its `pending` is the explicit `setBreakdownData( null )` the switch runs, and what keeps a stale answer out of it is the ADDRESS: `subjectOf` makes the subject the (URL, dimension) PAIR, so a superseded dimension's reply matches no outstanding ask, fills nothing, and retires nothing. The distinction is the whole point: "No User Agent data" during a fetch is a lie that flickers, and the totals under either is an answer to a question nobody asked. *Alternatives rejected:* a `mountWhen` prop (a gate, passed in, and every value of it can strand the operator); two panel components (one panel, two callers, and the second copy exists to hang one boolean on); emptiness alone as the discriminator (collapses `pending` into `empty`, which is the flicker). **Revisit if** the server ever OMITS a requested dimension that turned out to have no rows, which would make the two states indistinguishable on the wire and move the fix server-side, and watch `CHART_BREAKDOWN_OPTIONS` against `Performance_CI_Node::DIMENSIONS`, two hand-matched lists in two files. `pending` is terminal, so a dimension the server drops hangs the panel rather than degrading it; `overview` therefore REFUSES a dimension it does not know instead of answering about the rest, which turns that drift into a message under the dropdowns.

## Decision 17: The URL index is stored at TWO resolutions, and the coarse one is DERIVED

Decision 1 gives every bucketed namespace one width, `BUCKET_SECONDS`, and the URL index pays for it hardest: sixteen shards x 288 buckets x four partitions is 18,432 keys and 54 MB of unserialize per request, measured on the staging hub. Against that, `Performance_CI_Node::load_index_default()` makes exactly ONE per-bucket distinction in its entire fold, `isset( $recent[ $bucket ] )`, and sums everything else, so the readers ask at two resolutions only: the whole retention window, and the last complete hour (`RECENT_BUCKETS`). Five-minute precision buys the window's recent EDGE and nothing behind it. `NS_URLS_HOUR` (`urls_h:{shard}:{Y-m-d-H}`) holds one hour of merged rows in the same shape a fine bucket holds, and `Stats_Store::read_plan()` splits a window into `{ fine, hours }`: 36 to 46 keys per shard against 288. The row shape is identical ON PURPOSE: ONE `fold_index_row()` reads both tiers, because a second copy of the merge is how the table and the modal come to disagree about one URL, and ONE `Stats_Store::merge_url_row()` writes both, for the same reason on the other side: the copy written second had already silently dropped `srv`, which `sum_entry()` does not fold, and a folded hour with an empty split takes every server-scoped read of that URL with it. **The coarse key is not a scope and does not reopen decision 1**: the bucket stays LAST, one `lookup_multi` serves the tier, and retention is still the key's own TTL. It is a RESOLUTION: a constant this schema chooses, exactly as the shard count is, and not an input it does not control. **`FINE_BUCKETS` is a FLOOR, not a ceiling**: the fine tail runs to the END of the hour it lands in, because an hour read half fine and half coarse is either counted twice or, worse, read at NEITHER resolution, a hole of up to eleven buckets that breathes with the minute hand and silently shrinks every count on the page. **The fold is idempotent because it OVERWRITES from the fine buckets**; adding into an hour would double-count every re-flush, the fine buckets outlive their fold, and a folded hour's buckets are therefore never read again. **An hour with no coarse key has not been folded YET, and only the GRACE hour, the one immediately behind the fine tail, is answered from its fine buckets** (`Stats_Store::unfolded_hour_buckets()`). That is what makes a fresh deploy, and the hour a worker was restarting through, self-healing rather than a hole; it only works because an EMPTY hour is still written, so absence means exactly one thing. Anything further back is the coarse tier's alone: the fine tier answers the last hour and feeds the fold, and reading it for older hours cost one certain miss per shard per chunk per partition, each of which walked an armed mirror's index in full. **All twelve of the grace hour's buckets, whatever their age against `ttl_url_fine()`**: that TTL is the MEMCACHE lifetime, and the reader is not memcache-only, which is the next sentence's whole point. Bounding the fallback by it instead made an evicted hour unrecoverable (v0.88.3). It is also why the coarse tier is **excluded from the mirror** (`STATS_MIRROR_TOPN`): it is derived from `urls`, which is mirrored in full and retained for `<eln:stats_mirror_lifetime>`, twice the stats window, so a fine bucket long expired from memcache is still on disk and the rehydrate seam rebuilds the evicted hour from it. The FOLD cannot do that, because `roll_up_hours()` reads memcache; a READER can, and that asymmetry is what the exclusion rests on. so a durable copy would store the same information twice on the axis decision 11 watches, and an hour frame would be the largest thing in the held set at a checkpoint. (`NS_URL_DUR` once held the raw duration reservoir out of the rows on the same logic in reverse; decision 19 retired it with the percentiles it existed to compute.) **The READ streams: `load_index_default()` folds one `INDEX_READ_CHUNK` of buckets at a time and drops it before reading the next.** `url_row_sources()` issues one `lookup_multi` across all sixteen shards, so asking it for the whole window returned every bucket's rows at once, hundreds of MB at `MAX_URLS_PER_SHARD` per key, resident beside the index being built. That is what exhausted a production hub's 512MB in `empty_index_row()` after v0.71.3 and v0.72.1 had already removed both duplicate COPIES; the copies were real and neither was the volume. Decision 6 is unharmed: the batch is still one round trip for many keys, just bounded to a chunk. The hour tier is chunked the same way, and the "ALL its shards or none" check stays exact because an hour's shards are read together in one chunk. **The fold runs on the writer's flush path, not on `newspack_nodes/periodic`**, and that is the one place this decision touches [substrate ADR-9](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-9-two-tier-safety-net): the cron pass is the documented home for minute-or-slower derived housekeeping, but `persist_aggregate_stats()` rests on one partition having one writer, and a cron process folding p{N}'s keys puts a second one in a keyspace [substrate ADR-6](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-6-crc32--31-bit-mask-partition-routing)'s routing exists to keep single-writer. Idempotence would make that benign; the invariant is worth more than the placement. `ROLLUP_HOURS_PER_FLUSH` bounds a cold start's backfill so it spreads across flushes rather than stalling one, and the skip probe is ONE `lookup_multi` for the whole window: per hour it paid 23 round trips every flush to learn there was nothing to do, which is the latency cliff decision 6 names. The fold stays PER SHARD and is not regroupable by hash: each shard carries its own `Other` overflow row, and a merge keyed on the url_hash would collapse sixteen of them into one. **The fine tier carries its OWN retention**, `FINE_TTL_SECONDS` (two hours), against `min_lifetime` for the coarse tier that outlives it: the read plan asks for `FINE_BUCKETS` plus the rest of their hour, so 264 of every 288 buckets a shard sat in a 512MB cache with no reader. The tier has exactly two consumers, `RECENT_BUCKETS`' last-hour rate and the fold, and two hours covers both: the plan's fine span is just under two at the worst minute, and an hour folds within a re-probe of it closing. At that width it costs 24 buckets a shard against the coarse tier's 24 hours, where four hours bought margin for a fallback that should not have been reading here at all. TTL is still not a fold trigger; the bound is simply sized to outlive every read and every fold that will touch these buckets. *Alternatives rejected:* reading fewer buckets and accepting the gap (decision 15's totals are summed from this index and must stay exact); rolling up on read (every poll pays the fold this exists to stop paying). **Revisit if** a reader ever needs a THIRD resolution, at which point the tier list is a table rather than two constants; if the skip probe stops being answerable in one round trip; or if late data lands in an already-folded hour often enough to matter: an hour is folded at least an hour after it closes, against a `DEFAULT_EVICTION_WINDOW_SEC` of 600, but a worker replaying hours of backlog writes fine buckets nothing will re-fold, and that traffic leaves the readers' view silently.

## Decision 18: A stored value may be POSITIONAL, and then its indexes are named constants

Decision 1 makes every key a schema this plugin owns; nothing said what a VALUE costs. `serialize()` writes every key NAME into every entry, so a named URL row spends `s:11:"timed_count";`, 19 bytes, to say what `i:1;` says in 4, once per row per field, on a read that already fans out to thousands of keys. Measured on live rows through the real pipeline: 672 B/row named against 398 positional, 40.9%, which takes the hub's 36.1 MB across 58,415 rows to roughly 21. The URL index is the only value here dense enough to earn it, the one namespace whose rows are counted in tens of thousands and whose whole window is read per poll, and the schema already knew the shape of the problem: `DIM_SUMS` is `c`/`s`/`m`, the same cost paid down with single-character names long ago and only half paid: a one-character name still costs 6 bytes of JSON where an index costs none. **The indexes are `Stats_Store::ROW_*` and a bare integer literal is forbidden**: the constants buy back the readability the shape spends, and `$row[3]` is unreadable AND silently mis-typeable, which is [substrate ADR-2](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-2-one-message-format-the-7-field-positional-array)'s own consequence in a second place. **The eight fields that ADD come first, in `URL_SRV_SUMS` order**, so ONE map describes the row's summed half and its per-server split alike: decision 14's "that row restricted to one server" becomes structural rather than a naming coincidence, and `cap_servers()` ranking a split by the field NAME `count` after the fields moved to indexes is exactly the defect that ordering removes: `cap_bucket()`'s sort compared nulls, tied every pair, degraded to insertion order, and past `MAX_SERVER_VALUES` folded the BUSIEST hosts into `Other`, the Host-header-spray case decision 14's cap exists for, invisible to a spray test where 300 servers at one request each have no ranking to get wrong. **`ROW_FIELD_NAMES` is the one place an index becomes a name**, in the shape `Message::TYPE_NAMES` sets: one map beside the constants it names, because a private copy is how a reader ends up omitting a field. **`Performance_CI_Node::fold_index_row()` is the one storage/display boundary for the ROW**: everything above it is positional, the display row keeps its names because it crosses the wire as JSON, and a second copy of the translation is how the table and the modal come to disagree about one URL. **The SPLIT is not display data and never crosses**: `swap_url_server_sums()` merges one server's sums into the row and unsets it, `project_row()` unsets `srv_recent`, and every escape from the index goes through that projection, so the split stays positional through the whole fold and is named ONCE per scoped read, for the one selected server, by the only site that NAMES it. `project_row()` and `url_page()`'s `has_split` accumulator read it too, for a count and an emptiness test, and neither wants a name. Naming it at the fold instead cost a third field map, a memoized derivation and a 25-line translation on the hottest read loop in the plugin, to name data nothing displays: measured at 23-37% of the entire fold pass, 34-98ms per `urls` poll. A thing crosses a boundary where it is CONSUMED, not where it is convenient to convert. **A split of ONE server that served every request the row counted is the row restated, and stores the host name against `null`**, 369 B/row to 290 on the hub's own row shape, a further 21.4%, and 56.8% off the 672 measured above, on the field that was over half the whole read: a stored `url` is ABSOLUTE, so on a fleet of disjoint sites every URL has exactly one host and this is the COMMON row, not the rare one. COUNT alone decides it, because every `URL_SRV_SUMS` field is summed into the row and the split from the same increment, so a matching count means the other seven match by construction. The collapse turns ABSENCE into MEANING, and the two states are adjacent with opposite answers: `null` says "this host's numbers ARE the row's", a host MISSING says "never served here" and drops the row from a scoped read. `Stats_Store::collapse_sole_server()` and `expand_sole_server()` are the pair, and **every merge, reader or writer, must expand BEFORE summing**; `merge_url_row()` and `fold_url_rows()` do it for both sides, which is what covers the re-flush, the coarse fold and the overflow tail. `sum_fields()` skips a non-array value, so an unexpanded null is not a zero: it is that host deleted from the merge, a URL vanishing from a filtered table rather than an error. Naming only the READER here is exactly what let three write-side merges ship broken past a green 1,454-test suite. The suite pins the shape in ONE test that reads a shard raw, and translates at the seed and read helpers everywhere else, so a test that merely touches a row never counts indexes. *Deliberately NOT swept in:* the leaderboard's `{time, count, samples}` entry triple (`LB_ENTRY_SUMS`), positional with no constants on both sides of the language boundary: a closed 3-tuple read by two adjacent functions and one React component, where naming it means naming it twice in two deploy units for three fields. *Alternatives rejected:* a value object (it would have to serialize to something, and that something is this array); compressing the whole value (opaque to every diagnostic, for the same bytes at CPU cost); shortening the field NAMES (keeps the cost and loses the readability the constants restore). **The second-namespace condition below is MET, and is answered with a second constant block rather than a per-namespace table.** `CAT_SUMS`, the category series, `Stats_Store::CAT_MS`/`CAT_CALLS`/`CAT_REQUESTS`, is positional for the stats MIRROR rather than for memcache: a frame is JSON, where a three-field named entry is 30 bytes against 15, and the category series is spelled once per five-minute bucket per scope across a window the mirror keeps whole. Every field ADDS, so `CAT_SUMS` is itself the whole index set and the ordering clause is satisfied trivially. **It has no `CAT_FIELD_NAMES`, and that is not an omission**: `compact_category_series()` is the series' one storage/display boundary and emits a POSITIONAL wire row, so no index ever becomes a name, and a name table with no naming site is a second shape waiting to drift. `StatsStoreTest` asserts `array_keys( CAT_SUMS ) === range( 0, 2 )`, the same mechanism the two row tables get. Two positional namespaces is still two blocks of constants and not yet a table; **`DIM_SUMS` (`c`/`s`/`m`) is deliberately left NAMED**, because converting it is what makes three, and three is the per-namespace declaration this clause asks for, a larger decision than the bytes, which are real (`{"c":29,"s":1.0,"m":1.0}` is 24 against 12) and not the point. **Revisit if** a THIRD namespace wants the shape, and `DIM_SUMS` is the one queued, at which point the index table is a per-namespace declaration rather than a block of class constants, or when a NINTH summed field is added, because indexes 0-7 are full and the contiguity that makes "the eight that add come FIRST" true is prose: appending it at 14 works and quietly falsifies the sentence. `StatsStoreTest` asserts both key sets are exactly `range( 0, 13 )` and `range( 0, 7 )`, which is the mechanism that prose does not have.

## Decision 19: The per-URL percentiles are RETIRED, and the duration reservoir with them

A percentile does not merge, so a fold over N buckets cannot produce the window's: `fold_index_row()` took ONE bucket's and the column was labelled as if it covered the whole retention window. Taking the NEWEST bucket rather than an arbitrary one fixed a column showing a value a day old, and decision 17's hourly tier widened the sample behind it; neither made it true. The two honest ends were a mergeable sketch or deletion. **A fixed-bin histogram was costed and rejected on price**: counts ADD, so it would have merged through `sum_entry()` with no new machinery, but run-encoded at 1.5x bins it measured 71-167 B/row for 1-9% accuracy, +33 to +129 B on a row decision 18's two steps had just cut from 672 to 290: up to 44% back onto the row, and more than the whole sole-server collapse, to make a number nobody sorts by more nearly true. So it goes, and takes with it `ROW_P50_MS`/`ROW_P95_MS`/`ROW_P99_MS` (38 B/row), `ROW_DURATIONS`, `apply_percentiles()`, `MAX_DURATIONS_PER_BUCKET` and the whole `NS_URL_DUR` namespace: up to 100 floats per row per bucket off the WRITE path, its own `STATS_MIRROR_TOPN` carve-out, and one `lookup_multi` per shard per hour fold. **`min_ms` and `max_ms` stay and stay EXACT**: they fold from `duration_ms` directly, cost two fields, and are the extremes the reservoir was blurring anyway. What replaces p95 where something was needed: the `urls` verb's slowest-ten ranks by `avg_ms`, `Findings::for_url()` reports `max_ms`, and `Ask_Assembler` carries both, all exact, all already stored. A mean is more volatile than a 100-sample p95 on a low-count URL: one nine-second request outranks four thousand at 800ms. `max_ms` is the steadier ranking if that shows up. **It moves `ROW_SRV` down onto the retired reservoir's index**, and decision 1's move of the URL string out to `urlmap` moved every index past 7 down again: a row written under either older layout reads its split at an index that now holds something else. Decision 5 governs: each release rotates the salt, so no such row is ever met. The OFFSETLOG checkpoint is not salted, so a checkpoint restored across the change still costs one worker's un-flushed per-server delta once, which `restore_state()` already declares acceptable. **It also STRENGTHENS decision 2**: a stored percentile is a derived, non-mergeable statistic computed at write time, the very shape decision 2 forbids, and the same class of defect as the EMA-clamp bug it was written for. After this the row stores only what adds plus four extremes, and `avg_ms` ranking the slowest-ten is a read-time division over merged sums. *Revisit if* a reader ever needs a distribution rather than a mean and an extreme: the histogram design above is the answer and its cost is measured, so the question is only whether the bytes are worth it then.

## Decision 20: A request is filed in the bucket it FINISHED in, and a write into a folded hour goes to the hour key

Two halves of one rule: a stats write must land where a reader will actually read it. The record reaches `Flame_Builder_Node` at completion, so filing it under `timestamp`, the START, put a long request in a bucket that may already have closed. Completion is `timestamp + duration_ms`, needs no new field, and for an aborted request is its abort moment, because `Request_Builder` sets `duration_ms = now - start` at eviction. That removes the request's own duration from the exposure, which the 600s assembly window bounds at ten minutes. **It does not remove transit**, and that is the second half. An hour folds exactly once (`folded_hours`) and decision 17 has the reader skip a folded hour's fine buckets: they outlive the fold, and reading both counts the hour twice. So a record arriving after its hour folded was written to a fine bucket nothing would ever read, and never merged into the coarse key that replaced it. `Flame_Builder_Node::url_shard_intent()` picks the tier: a bucket whose hour this process has folded addresses `Stats_Store::url_hour_parts()` under the hour key rather than `url_shard_parts()` under the bucket, with the same `merge_url_row()` and the same `cap_url_rows()` ceiling: only the key differs. **The trigger is routine, not exotic**: `wp nodes deactivate complete; wp nodes gc --force; wp nodes activate complete` replays the whole retention window, and every replayed record carries its original timestamp. Steady state never sees it: measured on a hub, records reach the builder ~14s old against a fine tail of 65 to 120 minutes. *Alternatives rejected:* dropping the hour from `folded_hours` so the next flush re-folds: fine buckets age out on their own TTL while the hour key lives on, so a re-fold after any of the twelve expired would rebuild the hour SMALLER and destroy counts that are currently right; and having the reader take both tiers, which decision 17 already rejects as double-counting. The completion is **clamped to now**: a completed request cannot have finished after it reached us, and a skewed spoke clock or a bogus duration filing into a future bucket is the same written-then-unreadable failure this decision exists to close. **`folded_hours` is per-process, and one partition has one worker** (`persist_aggregate_stats()` says so: read-then-write is not atomic), so a respawn is the only way the memo goes stale: there is no peer to race. `flush()` therefore rolls up BEFORE it persists: the roll-up is what probes the coarse tier, so the first flush after a respawn has an accurate memo before a single row is placed. **Revisit when** a write needs to reach a bucket older than the coarse tier retains, which this does not answer: the row is capped by the hour's own lifetime either way.

## Decision 21: Outbound HTTP is timed as a span, and a short-circuited request opens nothing

Without these spans a request that spends its time below PHP userland reports as unmeasured, which is the one answer a reader cannot act on. A BDN `wp-admin/post.php` record made the cost concrete: 41.7s wall against 12.2s CPU, with `Image_CDN::filter_the_content @999999` holding 29.4s of self time and no interior, so the 29.5s off-CPU remainder had no name. A hook cannot reach it, since `WP_Http::request()` is not a hook, but WordPress already brackets the call: `pre_http_request` before, `http_api_debug` after. `App\Core` binds that pair for any log rule, so the span costs two registrations per request and two entries per remote call. **The pair is NOT balanced, and that asymmetry is the whole design.** `WP_Http::request()` short-circuits with a bare `return $pre;` and never fires `http_api_debug` (`class-wp-http.php`), so a span opened before the short-circuit would never close and would adopt every row after it: the severed-span damage decision 13 exists to bound. So `http_start` binds at **PHP_INT_MAX**, after every short-circuiting filter has voted, and opens nothing when `$preempt` is not false: a short-circuit is a cache hit with no I/O to time. Every other return path fires the action first, so within one request the pair is exact. `http_end` binds at PHP_INT_MIN so the span covers the request and not the other listeners on that action, and it closes the label it OPENED rather than one re-derived from the URL: a redirect hands the action the FINAL url, and a label that no longer matches leaves the span open. The span is named for its **caller**: `l` is `origin_frame( 0 === $this->trace_callers )`, whose true argument climbs past every frame of the class that applied the filter, `WP_Http` here, at `TRANSPORT_ORIGIN_DEPTH` (16) rather than `ORIGIN_DEPTH` (8), because "which of my code paths makes this call, how many times" is the question a reader has; the redacted URL rides as the entry's value and the status code closes it. A rule already buying that answer as a full backtrace through decision 24's `trace_callers` makes the argument false, so the span takes the cheaper shallow walk and names the transport rather than paying twice. **Naming the HOST instead answers nothing**, because every call so often goes to the same one. **Instrumentation never CONSTRUCTS the logger it reports into**: `Log_Manager::instance()` lazily creates one, so both callbacks ask `has_instance()` first: a binding that outlived its request would otherwise build the logger inside the callback and stamp `process (start)` with that moment instead of the mu-profiler's `request_ts`, which is exactly how it first broke the suite. *Alternatives rejected:* a per-rule opt-in flag (a new `Rule` property, its serialization, its editor control and its migration, to gate two registrations and a per-call cost that is zero on the requests that make no remote calls); timing inside a `significant_events` wrapper on `http_api_debug` (that times the action's LISTENERS, which is not the request). **Revisit when** SQL wants the same treatment, though `$wpdb` offers no completion signal without `SAVEQUERIES`, so it is a different mechanism and not an extension of this one, or if a transport ever fires `http_api_debug` more than once for one request, which would pop a label that is still in flight. **Per-rule** (`log_http`), like decisions 23 and 24: a logged request pays two entries per outbound call whether or not a brief reads them. Absent means ON, so a rule that never names the flag keeps the spans and only an explicit false drops them.

## Decision 22: The fold keeps the CLOSE of any span the kept head left open

The fold keeps a head, a rolling tail of `FOLD_KEEP_TAIL` and an unbounded `keep` bucket, and `is_kept()` argues that sizing the tail around a producer's shutdown sequence is guesswork the producer should settle by marking the line. A span's close is not that guess: the fold just chose the head, so it knows exactly which frames it left open, and there are at most `FOLD_KEEP_HEAD` of them. It is also not detail: a span opened in the head FRAMES every row after it, so losing its `(complete)` costs the record its shape rather than one line. That is what happened on a `community.thecoast.ca` job: the gyrobase subprocess closed after 535.8s of a 536.2s request, and the PHP parent's ten post-subprocess rows (`nuclear_gyrobase`, two `query hook` pairs, `updated_option hook`, memory, resources, terminal) filled the rolling tail and evicted it. The flame still counted the span: `Flame_Fold::close()` is the only path that increments a node's count, and the tree read `gyrobase` count 1, 535829.753ms. But the entry list left it open, and three separate display defects followed from the view reconstructing framing the record no longer stated. `open_in_head()` records the open bases at the fold and `closes_head_span()` routes their completes into `keep`, which the assembly splices between the marker and the tail. **The request's own frame is exempt**, exactly as it is for the display's severed-span prune: `process (complete)` is the terminal and must END the record, and `keep` lands BEFORE the tail. *Alternatives rejected:* having the producer mark the line (`Gyrobase::Log` could set `keep` on its nested `complete('gyrobase', …)`, but that fixes one producer in another repo and leaves every other one to rediscover it); closing the span in the VIEW from the tree's count and value (puts derived data in the entry list, and leans on exactly the reasoning across a marker decision 13 restricts). **Revisit if** a head ever legitimately leaves more frames open than the tail can afford to carry, which would mean `FOLD_KEEP_HEAD` is choosing a head the record cannot frame.

## Decision 23: Query spans are the same pair as decision 21, but PER-RULE

Decision 21 left SQL as its reopen condition and called it a different mechanism; it is the same shape with a different gate. `wpdb` brackets a query with `apply_filters( 'query', … )` before and, only under `SAVEQUERIES`, `log_query_custom_data` after, so `App\Core` binds `query_start` at PHP_INT_MAX (after every filter that rewrites the SQL, so the span names what the database is actually asked) and `query_end` at PHP_INT_MIN. **The asymmetry with HTTP is the gate, and it is measured, not assumed.** HTTP is unconditional for any log rule because a request making no remote calls pays two `add_filter` calls. Queries cost two log entries EACH, and the close does not fire at all without `SAVEQUERIES`, so a rule opts in with `log_queries`, default false. What that constant costs was measured rather than feared: 3,000 queries ran in 1.117s with it and 1.254s without, so the `get_caller()` backtrace is noise against a 0.4ms round trip; what is real is retention, 217 bytes per query held in `$wpdb->queries`, which is the memory pressure that folds these records. `query_end()` therefore DRAINS that array, which is also why this cannot be always-on: anything else reading it (Query Monitor) would find it empty. **The span is named for its CALLER**: `l` is `origin_frame( 0 === $this->trace_callers )`, decision 21's gate, whose true argument takes the first non-machinery frame as the transport and climbs past every frame of it, and the SQL rides the entry whole but for the host's trailing annotation (`without_host_annotation()`), bounded only by `Log_Manager::MAX_DATA_SIZE`. A fixed skip cannot do that job: `wpdb::get_row()` reaches the `query` filter through `wpdb::query()`, and `SHOW FULL COLUMNS` arrives four `wpdb` frames deep, which is why the transport climb runs to `TRANSPORT_ORIGIN_DEPTH` (16) where a hook's own origin needs `ORIGIN_DEPTH` (8). Naming the TABLE instead tells you `SELECT wp_posts` ran 156 times and never which code ran it, and which code ran it is the only version of the question worth asking. A constant cannot be withdrawn, so a long-running worker keeps `SAVEQUERIES` for its life, bounded by the drain, and stated where it is defined. *Alternatives rejected:* the `query` filter alone, closing each span at the NEXT query (charges every query with the PHP that ran after it); `$wpdb->num_queries` deltas on existing spans (free and always-on-safe, but counts are not spans, and the flame is what is being asked for); a `db.php` drop-in (accurate and SAVEQUERIES-free, but the host already ships one). **Revisit if** a reader needs the full callstack `log_query_custom_data` hands us rather than the one origin frame.

## Decision 24: A span says how long, never who asked. Two knobs answer the second question, at two prices

Decisions 21 and 23 add spans; this one adds PROVENANCE, because a hook that fires sixteen times reads as sixteen identical mysteries and no amount of timing distinguishes them. A `/wp-admin/post.php` record is the case: `the_content` fired sixteen times at ~2.4s each, 93% of a 40.6s request, and every span said the same thing. What was missing was the caller. **`trace_hooks` is the cheap one and does the real work**: `origin_frame()` takes ONE frame, who called the hook, and puts it on the entry's `l`, which is the flame's aggregation label, so `Flame_Tree` and `Flame_Fold` split `the_content ×25` into one node per caller with MEASURED durations and no new tree code. That is the same idiom gyrobase already uses for `include: /Macros/Global.html`. It deliberately does NOT call `wp_debug_backtrace_summary()`, which walks and formats the whole stack to produce a string all but one frame of which is discarded: measured at **12.7us against 0.9us** for `debug_backtrace( DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH )`. The LIMIT is the lever, not `IGNORE_ARGS`: args are refcounted, not copied, and cost 0.8us even on a multi-megabyte `the_content`; depth is what costs. At 0.9us it runs on EVERY firing (2,601 `render_block` calls = 2.3ms), which is what makes the split complete rather than truncated at a budget. **What it must NOT do is synthesise ANCESTOR nodes** for the uninstrumented frames: a `wp_trim_excerpt` parent valued at the `the_content` inside it would assert a duration nobody measured, which is decision 12's whole point. Attribution is honest; invented ancestry is not. **`trace_callers` is the expensive one**, default 0: `caller_of()` records `wp_debug_backtrace_summary( self::class )` onto the hook's OWN start entry as `caller`, not `c`, which already means COUNT throughout this schema, ignoring this class so the top frame is the caller and not the instrumentation. **The cap is what makes it affordable and it is per HOOK, not per request**: the RULE names the number: `trace_callers` IS the count of DEEP chains, `true` decoding to `Rule::TRACE_CALLERS_DEFAULT` (20), because what a diagnostic run wants is not what steady state wants. A fixed 20 left 21% of a real record's time unattributed, and `CALLER_FRAMES` at 8 cut its stack one frame short of `rest_preload_api_request`, the frame that explained the whole request; the window is 20 frames and `Log_Manager::MAX_DATA_SIZE` is the only bound. The cap exists at all because the same question asked of `render_block` on that record would be 2,601 backtraces. Sixteen firings fit inside twenty, which is the shape it was sized for: enough to see a repeat whole, few enough that a hot hook stops paying after the first twenty. `Log_Manager::message()` merges arbitrary keys into the entry (`[ 'n', 'k' ] + $data + [ 'ts' ]`), so this needed no new wire field. **A field nothing renders is a field that does not exist**: `LogEntriesTable` reads `entry.m` and nothing else, so a release that shipped the capture without touching it wrote every traced caller and dropped it. Per-rule and off by default, like decision 23 and unlike 21: a backtrace is cheap once and not cheap always. *Alternatives rejected:* capturing unconditionally for bound hooks (a rule naming sixty hooks pays sixty times per request for an answer nobody asked); tracing only firings AFTER the first, on the reading that a repeat is the signal (the first caller is half the answer: which of the sixteen is the odd one out is exactly what you are reading for); a separate `(called by)` entry (a new keyword that `logEntryUtils` and `Reqgrep_Core` would both have to learn, to carry a field the start entry already had room for). **This decision's revisit condition is MET.** It named a THIRD per-rule diagnostic knob as the trigger, on the reading that two booleans is a pair and three is a flags map. `Rule` carries four, `log_queries`, `log_http`, `trace_hooks` and `trace_callers`, and they are still four separate constructor properties.

## Decision 25: A duration nobody measured is not a timing sample

`Flame_Builder_Node::accumulate_all_stats()` runs two independent gates, and conflating them is the classic bug in that class. Decision 15 covers the first, `$count_global`, which keeps worker traffic out of every site-wide aggregate. The second is `$record_timing`, true only when `duration_ms` is positive AND `error_status` is neither `T` nor `A`. Both of those durations measure elapsed time to an interruption rather than what the request cost: `Request_Builder_Node::evict_request()` stamps `T` and `now - start` on a trace the LRU evicted mid-request, and `Log_Manager` stamps `A` when a cooperative stop lands inside `finish()` or when `end_job_context()` is told the job never finished. Summing either skews `sum_ms`, `max_ms`, `min_ms` and every mean drawn from them. A request failing the gate still COUNTS: it increments `ROW_COUNT` and its `count_Nxx` bucket, `ROW_SUM_PEAK_MB`, `ROW_MAX_PEAK_MB`, `ROW_LAST_SEEN` and `ROW_WORKER` on the per-URL row, the `c` of every dimensional slot with `s` left at zero, and `count` on the per-URL flame aggregate. It contributes nothing to `ROW_TIMED_COUNT`, `ROW_SUM_MS`, `ROW_MIN_MS`, `ROW_MAX_MS`, the aggregate's `sum_value` and children merge, the dimensional `s`, or `hourly`'s `count` and `sum_ms`; and `accumulate_profiles()` is skipped whole, so both leaderboards, the three category series and auto-tune never see it. **So `count` and `timed_count` diverge for a reason that has nothing to do with workers**, since the row records worker traffic separately in `ROW_WORKER`, which is why `Performance_CI_Node::mean_ms()` divides `sum_ms` by `timed_count` while `avg_peak_mb` divides by `count`. `hourly` does not keep those two populations apart: its `sum_peak_mb` accumulates from every non-worker request while its `count` takes only the timed ones, so `overview`'s `global_avg_peak_mb` divides across a wider set than its divisor. **Revisit if** an evicted or aborted request ever carries a duration someone measured, which would make it a sample like any other.
