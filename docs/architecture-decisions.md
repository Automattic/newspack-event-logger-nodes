# Architecture Decisions

The load-bearing design decisions of the event logger. "Fixing" one usually reintroduces a bug already paid for. Each record states what forced the choice, what it costs, what was weighed against it, and the concrete condition that reopens it. A **Revisit if** is a sufficient tripwire, not the only door: an argument on the merits also reopens a decision.

Numbers are stable. Code comments, docblocks, [`AGENTS.md`](../AGENTS.md), [`docs/architecture-guide.md`](architecture-guide.md) and the rendered sheets cite a record as "decision N", so no record is ever renumbered: a record a later one replaces keeps its number and its heading, and opens with **Superseded by** that record. The substrate keeps [its own series](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md) under the name `ADR-N`, and a "substrate ADR-N" here links to that file.

## Decision 1: Namespaced memcache schema

The stats are written to and read from three SQLite Tables per flame-builder partition ([decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss)). [`docs/architecture-guide.md`'s Stats Schema table](architecture-guide.md#stats-schema) is the full list with its key shapes.

![The stats key and the twenty namespaces. The key, component by component: the prefix evlog, the flame-builder partition p{N}, the namespace, the time key right after it, the five-minute bucket Y-m-d-H-i or the hour Y-m-d-H, so one flush's keys in a namespace share one prefix, and then zero or more scope components (a dimension, a server key, a shard, a list set or a url_hash). A table lists every namespace with its key after the prefix, its value and its Table's TTL: the five chart series hourly_h, dim_h, categories_h, url_dim_h and url_cat_h, each an hour key holding its twelve five-minute slots, url_dim_h one row a URL-hour holding them for every dimension; url_row_h, one URL's index row a server and hour, each family's row in the slot of its bucket; the leaderboards lb_h and lb_sh, one sum an hour; urls (one server's rows in sixteen shards plus a w-prefixed worker family, positional rows carrying the 12-character hash and the path) and its coarse tier urls_h; the server index urlsrv and urlsrv_h; urlmap; url; the ranked lists urlrank_s and urlrank_sh; the header records urlhdr and urlhdr_h; urltoken, one set of URL hashes per six-hour bucket per server per whole word, urltoken:{bucket}:{server_key}:{word}; and urlbucket, one set of URL hashes per five-minute bucket per server, urlbucket:{bucket}:{server_key}. Three TTLs derive from one window, the substrate's min_lifetime (default 43,200) floored at MIN_RETENTION_SECONDS, 3,600: flame-stats:url-fine keeps a fine urls, urlsrv, urlrank_s or urlhdr bucket min(window, FINE_TTL_SECONDS = 7,200), 24 buckets a shard; flame-stats:url keeps the per-URL blob max(3,600, window / 24); and flame-stats:aggregate keeps everything else max(90,000, window), so every hour a chart reads is stored, except a urltoken member, which lives the window, an hour and a flush from its last add, and a urlbucket member and a urlmap name, which live the Table's TTL, an hour and a flush from their last write. Every value but a slotted chart hour is capped to ITEM_BUDGET, 900,000 bytes, before it is written, and overflow folds into Other: MAX_DIM_VALUES 20 per slot but none on the server axis or the server index, MAX_URL_DIM_VALUES 10, MAX_CAT_VALUES 50 with the total pseudo-category preserved, MAX_LB_CATEGORIES 200, and a URL shard by its estimated bytes.](img/dec-key-layout.png)

Every key starts with the per-partition prefix `evlog:p{N}:`, which the substrate's durable `Table` stores as `{namespace}:{key}`, with no install scope and no salt. The namespace follows: the five chart series `hourly_h`, `dim_h`, `categories_h`, `url_dim_h` and `url_cat_h`; the leaderboards `lb_h` and `lb_sh`; the URL index `urls` and `urls_h`, with its server index `urlsrv` and `urlsrv_h`, its ranked lists `urlrank_s` and `urlrank_sh` and its header records `urlhdr` and `urlhdr_h`; `urlmap`; `url`; `urltoken`; or `urlbucket`. **All but `url` and `urlmap` carry a time key, the five-minute bucket, the hour, or for `urltoken` the six-hour bucket, and it comes IMMEDIATELY after the namespace**, before every scope component (server, shard, URL, dimension, list set) *(Chris, 2026-09-29)*. One rule places it, `Stats_Store::key_at()`, which every `[ parts, bucket ]` read, write and forget goes through: the namespace, the time, then the parts. So everything one flush touches in a namespace shares the prefix `{ns}:{time}` and sits together in the Table's key order, one `MGET` per Table still serves any mix (`Stats_Store::bucket_get_multi()`), and retention is the row's own TTL rather than a hand-rolled cutoff pass. `url` and `urlmap` key on the url_hash instead, which is not time-shaped. `urltoken` takes its six-hour bucket through the same `key_at()`, so a flush's adds share the prefix `urltoken:{bucket}` ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)).

The order is locality, measured. On the eln staging hub's `flame-stats:aggregate.p0` Table, 1,165,386 live keys, one `MGET` of 500 random keys took 46.6 ms at p50 and 54.8 ms at p90, and 500 keys adjacent in key order 5.7 ms and 17.1 ms: eight times faster at the median. With the time last, `url_dim_h:{hash}:{dim}:{hour}` held 1,019,586 of those keys, one per URL, dimension and hour, so a flush's current-hour rows were scattered across the whole B-tree, and the aggregate Table answered at 108 ms a message, 58% of the worker's time. With the time first, a flush's keys in every namespace are one contiguous run of the index. `url_dim_h` also became one row a URL-hour holding every dimension ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)), so a flush writes a URL once an hour where it wrote it once per dimension.

**Migration:** none in code ([decision 5](#decision-5-a-stats-schema-change-is-migrated-by-the-tables-flush-and-by-nothing-in-this-code)). Every time-keyed key moved, so nothing the earlier layout wrote is read again: the charts, the leaderboards, the URL index and its lists start empty after the upgrade and refill from the next flushes, and the old rows age out on their Table's TTL. Until the roll-up has folded each planned hour, which holds no index at the new keys, `waiting_hours()` counts it as owed, so a ranked `urls` page and its header read `provisional` and go uncached. The roll-up writes those hours' indexes empty, `ROLLUP_HOURS_PER_FLUSH` (2) a flush, so on a builder with traffic the window closes within seven flushes at the default 12-hour window and thirteen at the 24-hour read ceiling, each partition on its own: the first flush sets the data clock, and `ceil( hours / 2 )` more fold the rest (`FlameBuilderTest::test_a_fresh_builder_owes_no_hour_after_the_flushes_the_docs_cite`).

*Alternatives rejected:* the time last, which kept one scope's hours together, a locality that serves a chart read of one scope's 25 hours but not the flush, which writes one hour of many scopes on every tick; and a per-namespace choice of where the time goes, which leaves every reader to know each namespace's shape.

Retention is one TTL per Table, declared in [`flame-builder.tsl`](../topologies/flame-builder.tsl) and derived from one window, `Config::stats_retention_seconds()`: the substrate's `min_lifetime` key (default 43200), floored at `Stats_Store::MIN_RETENTION_SECONDS` (3600). `flame-stats:url` holds the per-URL flame stats (`url`) for `<eln:stats_url_ttl>`, `max(3600, window / 24)`. `flame-stats:url-fine` holds the FINE `urls`, `urlsrv`, `urlrank_s` and `urlhdr` buckets for `<eln:stats_url_fine_ttl>`, `min(window, Stats_Store::FINE_TTL_SECONDS)`, two hours: its own read window rather than the whole one, because [decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)'s coarse tier answers for everything behind it, and at that width the tier costs 24 buckets a shard against the 25 hours the coarse tier stores at the default window. `flame-stats:aggregate` holds everything else for `<eln:stats_ttl>`, the window floored at the `Stats_Store::CHART_HOURS` (25) hours a chart reads ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)), except a `urltoken` member, a `urlmap` name and a `urlbucket` member, the three writes stating their own lifetime, each as long as its readers read and one refresh more (`Stats_Store::filing_ttl()`): the window, an hour and a flush for a `urltoken` member, and `<eln:stats_ttl>`, an hour and a flush for a name or a `urlbucket` member ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)). `Stats_Store::table_for()` is the one map from a namespace to its Table.

`urls` and `urls_h` are decision 17's two resolutions of one index. The chart series and the leaderboards take one resolution, the hour key, which every flush writes, the open hour's included: a chart series holds its hour's twelve five-minute slots, and a leaderboard, the heaviest value the dashboard reads and one nothing charts, holds one sum ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)). The `urls` index keys by SERVER, then SHARD, `urls:{bucket}:{server_key}:{shard}` ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item)): sixteen shards by the first hex digit of the url_hash, and again by POPULATION, where a `w` prefix on the shard token (`urls:{bucket}:{server_key}:w3`) carries worker traffic, which the table excludes by default, so an ordinary read never carries rows it discards and a URL a job also visits keeps its reader row. A shard is not a scope, which makes it the one component here that names no dimension of the data: it is physical partitioning, and it exists because one blob per server per bucket is the pressure every cap in this schema is sized against. The servers present are what `urlsrv:{bucket}` lists, because the keyspace cannot list itself. A stored row carries the 12-char hash and its PATH at `ROW_PATH`, never its host, which the key's server implies; `urlmap:{hash}` holds `[ server_name, path ]` once per server a URL is filed under, re-written at most once an hour beside the URL's search words, and readers resolve only the hashes they display.

`urlmap` answers about ONE hash; a SEARCH asks about a whole SHARD, and answering it per hash costs 668,918 keys a poll on a production hub, 200-290s and 350-510MB per `urls` request. The row carries its own path, so the fold a search runs matches the term against the rows it already reads, on the same geometry and the same `read_plan()`, and the token index of [decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index), `urltoken:{bucket}:{server_key}:{word}`, names the candidate hashes and the shards they fall in first. Every URL carries its path for the check: the path rides on every row the index keeps, and a row the byte cap folds into `Other` is one no search can name.

Caps bound every value: a producer caps each value but a slotted chart hour to `Stats_Store::ITEM_BUDGET`, 900,000 bytes, before it writes it ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item)), a slotted hour's count caps apply per slot ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)), and overflow rolls into a synthetic `Other` entry: `MAX_DIM_VALUES` = 20, `MAX_URL_DIM_VALUES` = 10, `MAX_CAT_VALUES` = 50 with the `total` pseudo-category preserved before capping, `MAX_LB_CATEGORIES` = 200 leaderboard categories with a byte estimate beside it, and a URL shard by its estimated bytes. The `server` axis takes no cap, and neither does the URL index's server index: every server is filed under its own name, the URL's host, so the picker never offers an `Other` that scopes nothing. The host is `$_SERVER['SERVER_NAME']`, which under Apache's default `UseCanonicalName Off` is the CLIENT'S Host header, so on a domain-mapped multisite or any catch-all vhost a Host-header spray grows the axis with every name it sends. **[Decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item) owns the reopen condition**, stated there.

A category entry is POSITIONAL ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)) and its `CAT_MS` is stored ROUNDED to `Stats_Store::CAT_MS_DECIMALS` places: `Flame_Builder_Node::fold_categories()` rounds after the cap, because the cap re-sums its tail into `Other` and a sum of rounded doubles is not itself rounded. These are milliseconds a chart draws as seconds-per-second or as a mean, so a microsecond is already past anything rendered, where a full-precision double spends twelve more bytes per entry saying it. **The same fact obliges the WIRE to round again**: `Performance_CI_Node::compact_category_series()` emits a sum across one `Stats_Store` per flame-builder partition, and a stored entry already being rounded is the reason that sum is not. Measured over 5,000 realistic millisecond pairs, 22.1% of two-store sums and 30.0% of four-store sums serialize LONGER than their rounded value, worst case `0.30000000000000004`. `Stats_Store::sum_entry()` is what makes every merge here shape-exact: it rebuilds an entry from its field table and DISCARDS anything outside it, so a named `{t,c,n}` entry met by a positional one is dropped rather than hybridised into a six-key object. A caller wanting a field the table does not name puts it back itself, beside the reason: `add_totals()` replaces its sum onto the bucket it was given so a merged time series keeps the `hour` it is keyed by, and `merge_url_row()` reads its extremes off `$into`.

## Decision 2: Sums, not means

Leaderboard buckets hold raw `count`, `sum_req_time`, `samples`, `sum_time`, `sum_count`, so cross-bucket and cross-partition merges are exact addition and the display layer computes means at read time. A URL's blob follows the same rule: each flame-builder partition writes the share of the URL's traffic it saw, and `Stats_Store::url_stats()` adds every partition's running flame and profile before dividing once, because the first partition's blob alone answered for a quarter of a four-partition URL. Do NOT regress to running-mean storage: it produces the EMA-clamp bug this rule exists to keep out.

## Decision 3: Stats fail soft

Every [`Stats_Store`](../includes/class-stats-store.php) method returns `null` / `[]` / `false` when a Table does not answer and never throws, and a verb whose Table backend cannot open — the mount throws `\Newspack_Nodes\Table_Unavailable` for a missing `pdo_sqlite` or a directory or file SQLite cannot open — logs `performance: stats Tables did not mount` and answers no stats, so a dashboard shows "no data" where a stat should be. Any other mount failure fails the verb loud: a Table two topologies declare differently, or a tables directory the runtime refuses to adopt. The writer fails soft the same way: a flush chunk whose batch read failed, which `bucket_get_multi()` reports through `$failed`, writes nothing and logs once a window, so its deltas are dropped rather than merged onto an empty read and written over the stored buckets. **A writer never writes from a read a Table left unanswered** *(Chris, 2026-09-28)*. A null in a failed batch is a key nobody could see, not an empty one. So a flush files no URL row, index or name for a bucket whose index went unanswered and drops those deltas, as it drops a failed write chunk's, rather than file a server new to a folded hour against no index, which would leave that hour unranked — holding them for the Table instead would grow the accumulator for as long as the outage lasted — and says so once a window; the bucket's other deltas read no index, so they land, or fail on their own chunk's read. A URL whose stored aggregate went unanswered holds no aggregate that request, so the drain cannot write one request's flame and profile over the blob, and the flush tallies it `unread url blobs`. Work with a queue of its own is left owed on it: a fold, a ranking of a bucket or a stale hour, and the roll-up's reading of which hours are folded each skip what they could not read, so no hour is folded serverless, no bucket is ranked empty and stamped, and no stale hour settles short; each asks again at the next flush. A READER fails soft: a dashboard polling through an outage shows partial or no data, and with the header and the page cached `URL_PAGE_REFRESH_S` a short answer heals within a refresh of the Table answering. `provisional` means a page short of what the Tables hold: ranking lag, or a search whose token sets went unanswered, which narrows nothing and so names no row rather than reading the unanswered sets as words no URL carries. `server_index()` memoizes what a Table answered and nothing it did not. The substrate makes the opposite call for the same outage: a stream its slot pool cannot account for is refused ([SSE host budget](https://github.com/Automattic/newspack-nodes/blob/main/docs/sse-host-budget.md)). The asymmetry is the decision. A missing stat costs a blank card; a stream nobody can account for costs a php-fpm child for as long as it stays open.

## Decision 4: Settings fan-out is a node graph; no consumer means a silent no-op

The three settings a hub pushes, the ruleset, `log_memory` and `flush_every_line`, ride the substrate's settings control plane: [`hub-control.tsl`](../topologies/hub-control.tsl) includes `settings-sync` and adds one `add_setting` line per option, and a change to any of them is an option write like every other, which the substrate's [`Settings_Event_Writer`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-settings-event-writer.php) records. So [`Auto_Tuner_Node`](../includes/class-auto-tuner-node.php) mutates the one rule the message names (`rule_id`) and persists the whole ruleset through `Rule_Set::save()`: no `remote_manager` job, no `suppress_sync`, and an auto-tune write reaches the spokes exactly as an admin edit does. Nothing fans a change out unless `hub-control` is active and per-spoke `HTTP_Out` nodes are wired; on a spoke or a standalone site the event is tailed and dropped. That IS the structural gate: there is no `enable_workers` or `enable_aggregator` key, and hub mode derives from which topologies are active.

## Decision 5: A stats schema change is migrated by the tables flush, and by nothing in this code

A stats schema change here is migrated by emptying the three stats Tables, `wp nodes tables flush flame-stats:aggregate flame-stats:url flame-stats:url-fine`, and `Stats_Store` keeps no salt and no migration path of its own. Schema bumps and emergency flushes share that one command. A durable Table's key carries no salt (it stores `{namespace}:{key}`), so the substrate's `wp nodes memcache flush`, over [`Cache_Backend::rotate_salt()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-cache-backend.php), reaches memcached and APCu alone and leaves the SQLite stats rows in place. `wp nodes tables flush` replaces each named partition's SQLite files, at a cost that does not grow with their rows, and a live owner flushes its own partition over its command channel. **The tables flush IS the migration, and nothing in the code compensates for skipping it.** An old-shape row is never read after the flush, so no reader or writer carries a shape probe, a version component or a row-level legacy test: each would be a second migration mechanism beside this one command, maintained against every future row shape. Skip the command and the dashboard reads garbage for one retention window; that is an operator error with a one-command fix, not a case for the runtime to detect.

![The stats schema migration drawn on one key form in two stores. Left, memcached: a Table that is volatile stores Cache_Backend::entry_key(), a key that carries the salted install scope from Cache_Backend::site_key(), so wp nodes memcache flush runs Cache_Backend::rotate_salt(), which stores a new salt, and the old key sits in its store until its TTL with nothing ever asking for it; a long-running worker memoizes the scope, so the rotation asks every worker to restart. Right, SQLite: the stats Tables store the key as {namespace}:{key}, a row of {base}/tables/{table}.p{N}.sqlite with key, value and expires, so the rotation leaves the statistics untouched, and wp nodes tables flush flame-stats:aggregate flame-stats:url flame-stats:url-fine replaces each partition's files, a live owner flushing its own over its command channel. Below: skipping the tables flush reads garbage for one retention window, an operator error with a one-command fix; no reader or writer carries a shape probe, a version component in a key or a row-level legacy test; and schema bumps and emergency flushes share the one command.](img/dec-salt-rotation.png)

*Alternatives rejected:* a schema-version component in the key prefix, a permanent extra component on every key, for the identical orphaning the flush already does; detect-and-purge at boot (memcached cannot enumerate, and a boot pass over the whole keyspace is [decision 6](#decision-6-get_multi-batching-is-essential)'s latency cliff). **Revisit when** a deploy can no longer be relied on to rotate, at which point the mechanism to add is one that forces the button, not one that tolerates its absence.

## Decision 6: `get_multi` batching is essential

Reader paths ask for all retention buckets of a partition in one `MGET` per Table (`Stats_Store::bucket_get_multi()`); a `GET` per key is a latency cliff on dashboards, a message each and, on SQLite, a statement each.

## Decision 7: Job_Intake for >4KB jobs, the firehose for ≤4KB

Small runtime jobs ride the firehose with `k:"job"`, and [`Job_Router_Node`](../includes/class-job-router-node.php) extracts them; [`job-feed.tsl`](../topologies/job-feed.tsl) tails the substrate's `jobfeed` log instead, so a spoke's router reads jobs alone rather than the whole firehose. A job the firehose cannot carry goes straight to `jobintake` through the substrate's [`Job_Intake::queue()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-job-intake.php), the locked path past the PIPE_BUF cap ([substrate ADR-4](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-4-pipe_buf-atomic-writes)). The wrong path loses jobs: `Log_Manager` trims `m` on any ENTRY over `MAX_DATA_SIZE` (3840B), so the handler never sees a parseable payload.

## Decision 8: A spoke's job is re-keyed `remote_job` when the hub pulls it

A spoke writes `k:"job"` like any producer and never learns it has a hub. The hub's [`aggregator`](../topologies/aggregator.tsl) topology pulls each spoke's firehose through a substrate [`Remote_Source_Node`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-remote-source-node.php) ([hub and spoke](https://github.com/Automattic/newspack-nodes/blob/main/docs/hub-and-spoke.md)), and this plugin's [`Remote_Job_Rewrite_Node`](../includes/class-remote-job-rewrite-node.php), wired between the sources and the firehose `Topic`, flips the incoming `k:"job"` to `k:"remote_job"` and leaves every other key alone. That kind is the only thing telling a spoke's work apart from the hub's own: the hub's `Job_Worker_Node` dispatches it against `newspack_nodes/remote_job_handlers` and never against the map its own jobs use. A job type registers under either map or both, depending on where it should run, and the two registrations are independent, so the hub runs a spoke's job because a handler was registered for it there, not because the spoke asked. What makes a site a hub is [decision 4](#decision-4-settings-fan-out-is-a-node-graph-no-consumer-means-a-silent-no-op)'s: the `aggregator` and `hub-control` topologies being active, with no toggle.

## Decision 9: A request's partition is its id, hashed by the substrate

## Decision 12: A stat times the request; a flame value is a rendering artifact

Two numbers describe one request and they are not interchangeable. `duration_ms` on the record is what the request took, measured once. A flame node's `value` is a LAYOUT WIDTH: `Flame_Tree::cover_children()`, `Flame_Fold::flatten()` and `Flame_Builder_Node::fill()` all RAISE it so a parent covers its positioned children, because the browser prunes on a single cutoff and takes a whole subtree with anything it drops, and `treemapDice` scales children by `parentWidth / parent.value`. Raising is correct for drawing and wrong for counting. **Every stat therefore reads `$request['duration_ms']`; nothing measured reads a flame `value`**: that covers every namespace of [decision 1](#decision-1-namespaced-memcache-schema) plus the per-URL aggregate's `sum_value`.

![A real request, the record and the raised root drawn to scale. The record's duration_ms is 356,312 ms, measured once, and every stat reads it. The flame's root value is 724,662.87 ms after Flame_Builder_Node::fill() raised it to cover a child positioned 355 seconds after the parent's own occurrence, marked as a tick at t = 0, because a parent is widened to the end of its farthest child so the child stays inside it when drawn; a stat reading that raised width reports the URL's avg_ms as 724,662.87 ms. Cards name the three places that raise a value, Flame_Tree::cover_children(), Flame_Fold::flatten() and Flame_Builder_Node::fill(), and why raising is right for drawing: the browser prunes on a single cutoff, taking a whole subtree with anything it drops, and treemapDice scales children by parentWidth / parent.value. The rule covers every namespace of decision 1 plus the per-URL aggregate's sum_value.](img/dec-flame-value.png)

The two diverge by more than rounding: read from its raised root, a 356,312ms request reaches `avg_ms` as 724,662.87ms, because `fill()` raises the root to cover a child that ran 355 seconds after the parent's own occurrence. *Alternatives rejected:* not raising at all (deletes exactly the frames a viewer opened the graph to see); computing stats before the raise (the ordering is invisible at the call site, and one reorder reintroduces it). The same holds for `Findings`: every share it reports divides by `duration_ms`, and no finding or brief carries the root's value as a profiled total. **Revisit if** the browser stops pruning on a single value cutoff: the raise can go then, and the two numbers converge.

## Decision 13: A sequence-break marker is missing detail, not idle time

`entries (lost)` and `entries (aggregated)` stand in for entries [`Request_Builder_Node`](../includes/class-request-builder-node.php) removed: discarded on overflow, or merged by the fold. It mints them, so it owns the vocabulary as `Request_Builder_Node::SEQUENCE_BREAK_KEYS`; consumers reference that constant rather than keeping their own copy, and the JS holds the only deliberate duplicate because it is a separate deploy unit. **No consumer may reason across a marker.** `Findings::entry_gap()` skips a gap on either side of one, `Reqgrep_Command` breaks its sequence there, and [`logEntryUtils`](../src/overview/utils/logEntryUtils.js) splices the merged spans back at it. Reading the interval as unexplained makes one record's `entry_gap` propose MORE hooks while its `truncation()` proposes fewer, both at once, on the same record. What a consumer MAY read across one is the record's own ending: whether anything closes the outermost pair. That decides FRAMING, which spans were severed and which ran to the end, and leaves the interval exactly as unmeasurable as it was, which is what this decision protects. `logEntryUtils`' `pruneSeveredSpans()` and `Reqgrep_Command::prune_severed_spans()` are the one rule, and the parity test in `logEntryUtils.test.js` pins the vocabulary they share. **The severance frames the record's RESUMED tail, never the folded interior spliced in at the marker**: those rows are what the TREE puts inside the open span, and the fold is what ate its close, so pruning before them makes every merged row a sibling of the parent it ran in: a gyrobase subprocess that exits 0 loses its whole 535s interior to the request's level, while the same shape whose drain survives the fold nests correctly. The prune therefore waits for the first row the record itself resumes with (`fromFold`). **Revisit if** a marker ever carries its own duration, which would make the interval measurable rather than merely missing.

## Decision 15: The `urls` verb owns every URL-set fact; `overview` owns the site

One verb applies the filters, so one verb answers for what they left, and `overview` keeps only what the URL index cannot answer.

The modal's Errors Only toggle is its own fetch, seeded from the table's echoed `errors_only` when a URL opens and flipped by the operator after, and while it is on the modal shows that exact count and a summary of the errors listed in place of the whole URL's numbers. A `url:` Ask brief follows the modal's list, not the table: picked in the modal it carries the modal's toggle as `errors_only`, and then briefs the exact `errors` and the summary in place of the whole URL's stats. A `bucket` reaches the stats too, because the storage answers it: `dump_url --bucket`'s `stats` are that bucket's slot of the URL's `url_row_h` value, the row the bucketed table showed, and its request list holds the requests finishing inside the bucket, while `breakdown_time_series`, `category_time_series` and `aggregate_flame` stay the whole URL's, and a bucketed list rebuilds no flame, as an `errors_only` one does not, since a flame folded from it would describe the list rather than the URL. The first two are harmless while a stored `url` is absolute, which makes one URL one site. **Revisit if** the header ever needs a number the URL index cannot produce (the answer is a new field on the `urls` reply, not a second source read beside it), or if a host is ever reported by two servers, at which point `dump_url`'s three series and `find_recent_requests_for_url()`'s examples start describing a wider set than the count above them.

[`BreakdownControls`](../src/overview/components/BreakdownControls.js) is the chart and the Metric and Breakdown dropdowns that drive it, plus a Server select when the caller passes `serverOptions` (the Overview card does): one panel, because the Metric and Breakdown values the chart reads are exactly the ones its own selects set. ## Decision 17: The URL index is stored at TWO resolutions, and the coarse one is DERIVED

The readers ask at two resolutions only, so the URL index is stored at two: a fine five-minute tier for the current hour, and an hourly tier the writer folds out of it for every hour before.

![One shard's read plan across a 24-hour window: Stats_Store::read_plan() splits it into the current hour's five-minute buckets, up to twelve ending now, and 23 coarse keys, urls_h:{Y-m-d-H}:{server_key}:{shard}, one per server per closed hour. An hour with no coarse key is short until the roll-up folds it, and an empty hour is still written, so absence means one thing; no reader reads a closed hour's buckets. The plan reads 24 to 35 keys per shard against 288; read at full resolution, 16 shards by 288 buckets by 4 partitions is 18,432 keys and 54 MB of unserialize per request on the staging hub. [Decision 1](#decision-1-namespaced-memcache-schema) gives every bucketed namespace one width, `BUCKET_SECONDS`, and the URL index pays for it hardest: read at that width, sixteen shards × 288 buckets × four partitions is 18,432 keys and 54 MB of unserialize per request, measured on the staging hub. Against that, [`Performance_CI_Node::load_index_default()`](../includes/app/class-performance-ci-node.php) makes exactly ONE per-bucket distinction in its entire fold, `isset( $recent[ $bucket ] )`, and sums everything else, so the readers ask at two resolutions only: the whole retention window, and the recent rate (`recent_keys()`). Five-minute precision buys the current hour, which no hour key covers yet, and nothing behind it. `NS_URLS_HOUR` (`urls_h:{Y-m-d-H}:{server_key}:{shard}`) holds one server's hour of merged rows in the same shape a fine bucket holds, and `urlsrv_h` lists the servers it holds them for, each beside every shard of both families, because the fold writes them all, and `Stats_Store::read_plan()` splits a window into `{ fine, hours }`: 24 to 35 keys per shard against 288 on a day's window. The row shape is identical ON PURPOSE: ONE `fold_index_row()` reads both tiers, because a second copy of the merge is how the table and the modal come to disagree about one URL, and ONE `Stats_Store::merge_url_row()` writes both, because a second writer is how the two tiers come to disagree about one URL's row. **The coarse key is not a scope and does not reopen decision 1**: the hour sits where every time key does, right after the namespace, one `MGET` serves the tier, and retention is still the key's own TTL. It is a RESOLUTION, a constant this schema chooses exactly as the shard count is, and not an input it does not control.

**The fine tier is the current hour, whole**: the plan splits on the clock hour, because an hour read half fine and half coarse is either counted twice or, worse, read at NEITHER resolution, a hole that breathes with the minute hand and silently shrinks every count on the page. **The fold is idempotent because it OVERWRITES from the fine buckets**; adding into an hour would double-count every re-flush, and the fine buckets outlive their fold. No reader reads a closed hour's buckets; a re-fold does, which is what makes a missing hour key recoverable. **An hour with no coarse key is short, never answered from its buckets** *(Chris, 2026-09-28)*: the builder folds an hour once its data clock has left it, and until it has, a reply is short there rather than paying for a fallback that read twelve buckets a shard per chunk per partition. A fold short of an older hour's key is a short answer, cached like any other ([decision 3](#decision-3-stats-fail-soft)); in the current hour's first bucket a header, a ranked page or a fold short of the hour just closed, whose fold the writer may still owe, is lag, `provisional` and never cached. An EMPTY hour is still written, so absence means exactly one thing: the fold has not reached the hour, which is how `roll_up_hours()` reads it. The fold alone writes the coarse tier, and nothing evicts it before its TTL, because the Tables are durable ([decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss)).

**The READ streams: `load_index_default()` folds one `INDEX_READ_CHUNK` (12) of buckets at a time and drops it before reading the next.** `url_row_sources()` issues one `MGET` across every shard each server's index entry names, so asking it for the whole window returns every bucket's rows at once, hundreds of MB at up to `ITEM_BUDGET` per key, resident beside the index being built. That volume, not any duplicate copy of it, is what exhausts a production hub's 512MB in `empty_index_row()`. [Decision 6](#decision-6-get_multi-batching-is-essential) is unharmed: the batch is still one round trip for many keys, bounded to a chunk. The hour tier is chunked the same way, and the walk is per SHARD: `walk_shard_tiers()` reads the plan's hours for the one shard it was handed, takes every hour the coarse tier answered for from that tier, and reads the current hour's buckets and no others.

**There is no whole-index memo, and reintroducing one is the trap.** The merged index is the count of DISTINCT URLs in the retention window, which nothing bounds: each stored value is capped and their merge is not, and holding it exhausts a production hub's 512MB inside the fold itself. `url_page()` folds ONE SHARD at a time, keeping only each shard's best `$offset + $limit` rows by the sort key and its best `SLOWEST_ROWS` (10) by mean; a url_hash's shard is its first hex digit, so shards are disjoint and the union of the per-shard top-N IS the global top-N. `dump_url` point-reads the one shard `url_shard()` names for its hash, in the one server `urlmap` locates, through the same `$load_index` seam the table folds; the seam takes the shard and the server, so a test counting index reads measures the narrowing rather than a branch around it.

**The fold runs on the writer's flush path, not on `newspack_nodes/periodic`**, and that is the one place this decision touches [substrate ADR-9](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-9-two-tier-safety-net): the cron pass is the documented home for minute-or-slower derived housekeeping, but `persist_aggregate_stats()` rests on one partition having one writer, and a cron process folding p{N}'s keys puts a second one in a keyspace [substrate ADR-6](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-6-crc32--31-bit-mask-partition-routing)'s routing exists to keep single-writer. Idempotence would make that benign; the invariant is worth more than the placement. `ROLLUP_HOURS_PER_FLUSH` (2) bounds a cold start's backfill so it spreads across flushes rather than stalling one, and the roll-up's check, `Stats_Store::url_hours_derived()`, is TWO batched reads for the whole window, the hours' server indexes and then the DONE marker of every server they name, where checking per hour pays 23 round trips every flush to learn there is nothing to do: decision 6's latency cliff. It reads no row, because a marker stands for every shard of its server's hour: a fold writes it only once every write of the fold landed, and the stale ranking only after reading every shard the index names, folding the hour again where one is missing. The fold stays PER SHARD and is not regroupable by hash: each shard carries its own `Other` overflow row, and a merge keyed on the url_hash would collapse sixteen of them into one.

**The fold waits for the data clock, not the wall** *(Chris, 2026-09-29)*. An hour folds once the builder's data clock has left it: `$data_clock`, the newest bucket a flush that drained records wrote. `Flame_Builder_Node::foldable()` hands `roll_up_hours()` the plan hours before the clock's hour, and the roll-up folds only those; it still reads every hour it has not memoized, so a respawn adopts its predecessor's folds before it writes. Folding on the wall clock sends a replay down the late-write path: every replayed hour is already closed, so it folds at the replay's first flush, and every later write into it reads and rewrites its `urls_h` shards and forgets its markers, re-ranking the hour's lists for each server and the site at every flush; a staging re-process spent 14.2 s of 15.8 s in `flame-stats:aggregate` that way. Replaying one hour of 40 URLs over fourteen flushes, its hour-tier writes fall from 168 `urls_h` and 348 `urlrank_sh` to 32 and 29: one fold and one ranking. **The margin is the end of the hour**, and the clock that decides is the one EARLIER flushes left, because the roll-up runs before this flush's rows land: an hour folds on the flush after the first write past it, holding every record filed before that. A further bucket of margin would hide every just-closed hour from the dashboard for five minutes each hour, because the reader switches on the wall hour, and would buy nothing the late-write path does not already get right. **A builder that has drained nothing for `Flame_Builder_Node::IDLE_AFTER_SEC`, a minute, is idle, and its clock is the wall**, so a quiet builder still folds the hours that pass, and one quiet from an hour's close folds it inside the next hour's first bucket, the lag `lagging()` forgives; a replay drains at every flush and every checkpoint, and its slowest measured flush, 15.8 s, fits three times over. An empty `pending` alone is no sign of idleness: every checkpoint's `save_state()` drains it, and a crawl after a crash checkpoints every record, so a tick between two crawled records would otherwise fold the replay's hours. **The clock rides the checkpoint.** `save_state()` carries `data_clock` and `data_clock_hour_since` beside the crumb ([decision 31](#decision-31-a-snapshot-nodes-replay-is-idempotent-by-the-last-folded-crumb)). Both describe data the checkpoint already drained, so a successor restoring them folds nothing early, and a replay recycling its worker every 595 s keeps the fine deadline its first worker started. A process with no carry starts with `worked_at` at its construction and the clock empty, so it folds nothing until its first flush writes. **An hour read holding no index is not read again** until this process folds it (`$absent_hours`): one partition has one writer, so nothing else gives it one. **An hour the clock has stood in for `Stats_Store::fine_ttl()` less a bucket folds regardless**: its first buckets were written when the clock entered it, and a replay filing an hour slower than the fine lifetime would otherwise fold it after they expired, short and silent. Every record after that takes the late-write path, which loses nothing. *What it costs:* the reader keeps the wall clock's plan and reads a closed hour from its key alone, so a replayed hour appears on the dashboard only once it folds. Until then it holds no index, or its servers no DONE marker, and the header and the ranked page read it as provisional-empty ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)): it adds nothing, the reply says `provisional`, and no poll takes the whole-index fold for it. In real time the fold lands one flush after the next hour's first record, where a wall-clock fold lands at the first flush after the close, or `Flame_Builder_Node::IDLE_AFTER_SEC` after a quiet builder's last drain, both inside the next hour's first bucket. **The data clock is only as honest as the stamps it files.** A request the request builder times out is measured to the STREAM boundary its window fell due at (decision 19), so a reprocess files it in its own stream; measured to the wall, one stalled request of a staging reprocess timed out twenty hours long, filed in the wall's bucket, and carried the data clock past every replayed hour, which then folded at its first flush and re-ranked about fifteen times while its rows streamed in, 49.5 s of one worker's 595. The flame builder's own reads split the same way: what a record is filed under, what its per-URL tree and categories age by, and what folds are the stream's, while the read plan's window, the ranking cadence, every TTL and idleness stay on the wall; `Flame_Builder_Node`'s class docblock tabulates each read. The saving covers a builder that files the replayed hours itself: an hour already holding its keys is memoized folded, and a write into it takes the late-write path, as `wp nodes ingest` of past data into a live builder does, whose clock stands at the present.

**The fine tier carries its OWN retention**, `FINE_TTL_SECONDS` (7,200, two hours), against the aggregate Table's `<eln:stats_ttl>` for the coarse tier that outlives it: the read plan asks for the current hour's buckets alone, so at a day's TTL 276 of every 288 buckets a shard would sit in the Table with no reader. The tier has exactly two consumers, the reader's current hour and the fold, and two hours covers both: the current hour, and the hour just closed, which folds once the data clock leaves it and takes late writes for a while after. A replay can hold an hour open longer than that, so an hour the clock has stood in for all but a bucket of the fine lifetime folds regardless. At that width the tier costs 24 buckets a shard against the 25 hours the coarse tier stores at the default window, and a wider bound buys margin for no read the plan makes. TTL is still not a fold trigger; the bound is sized to outlive every read and every fold that will touch these buckets.

**Two more derived tiers ride the ranking** *(Chris, 2026-09-28)*. `urlhdr` and `urlhdr_h` hold each key's header record ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)), derived from the `urls` rows exactly as the lists are and written beside them. A record's key carries `Stats_Store::HDR_SHAPE`, derived from `HDR_VERSION`, the version of the positional layout, and `Url_Sketch::PRECISION`, so a record in an older layout reads as missing, never misread; the flush that migrates the change ([decision 5](#decision-5-a-stats-schema-change-is-migrated-by-the-tables-flush-and-by-nothing-in-this-code)) empties the index with it.

**The chart series are not this decision's.** Each is one key an hour holding the hour's twelve five-minute slots, written at every flush and never folded ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)), so nothing here reads, folds or repairs a chart key, and `url_hours_derived()` asks after the server index and its shards alone.

**The URL index's window starts on the hour** *(Chris, 2026-09-29)*. `Stats_Store::read_plan()` reads the current clock hour so far in its buckets and the WHOLE hours before it, dropping the oldest hour the window holds only part of: at 11:07 a twelve-hour window reads hour 00 whole and none of hour 23. Every URL-set total, rate and ranked page therefore sums whole hour keys exactly, where rounding outward read hour 23's whole key for the 50 minutes of it the window held. `Stats_Store::window_start()` is the start of that oldest whole hour, so the request scans bound themselves by the same window. The charts and the site totals keep a window of their own, the 288 five-minute slots ending at the current bucket ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)).

*Alternatives rejected:* reading fewer buckets and accepting the gap ([decision 15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site)'s totals are summed from this index and must stay exact); rolling up on read (every poll pays the fold this exists to stop paying). **Revisit if** a reader ever needs a THIRD resolution, at which point the tier list is a table rather than two constants; if the roll-up's check stops being answerable in two round trips; or if late data lands in an already-folded hour often enough to matter: an hour folds once the data clock leaves it, so a request still in flight across the boundary, up to the request builder's eviction window, can land there, and so can a spoke's backlog on a hub, and [decision 19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in-and-a-write-into-a-folded-hour-reaches-its-fine-bucket-and-the-hour-key) sends each such write to its fine bucket and the hour key, one extra read and write per key.

## Decision 18: A stored value may be POSITIONAL, and then its indexes are named constants

[Decision 1](#decision-1-namespaced-memcache-schema) makes every key a schema this plugin owns; this decision says what a VALUE costs. `serialize()` writes every key NAME into every entry, so a named URL row spends `s:11:"timed_count";`, 19 bytes, to say what `i:1;` says in 4, once per row per field, on a read that already fans out to thousands of keys. Measured on live rows through the real pipeline, a row is 672 bytes named against 398 positional, 40.9% less, which takes the hub's 36.1 MB across 58,415 rows to roughly 21. Three values here are dense enough to earn the shape. The URL index earns it on its read: the one namespace whose rows are counted in tens of thousands and whose whole window is read per poll. The category and dimensional series earn it on their count, spelled once per five-minute slot per scope across the chart's 288; the last paragraph holds both.

![One URL row as fifteen positional slots, each named by a Stats_Store::ROW_ constant: indexes 0 to 8 are the nine fields that add (COUNT, TIMED_COUNT, SUM_MS, SUM_PEAK_MB, the four status-class counts and ERRORS), which is ROW_SUMS, the one map that describes the row's summed half; 9 to 13 are the extremes, a timestamp and a flag (MIN_MS, MAX_MS, MAX_PEAK_MB, LAST_SEEN, WORKER); and 14 is PATH, the row's one string, cut to MAX_PATH_BYTES. Tiles give the measurements: 672 bytes a row named against 398 positional on live rows, 40.9 percent, taking the hub's 36.1 MB across 58,415 rows to about 21; MAX_PATH_BYTES 1,024, the longest path a row keeps; and 44.1% off JSON-encoded category and dimension entries across 66,966 of them, CAT_SUMS and DIM_SUMS positional too. Cards: ROW_FIELD_NAMES is the one place an index becomes a name, one map beside its constants because a private copy is how a reader ends up omitting a field; fold_index_row() is the one storage and display boundary for the row, and neither CAT_SUMS nor DIM_SUMS has a name table, because each stays positional at the wire; the path is display, not identity, so row_path() drops the host the key's server implies, a merge keeps whichever side's path is non-empty, and an overflow row's is empty.](img/dec-positional-row.png)

A one-character field name is the same cost half paid: it still spends 6 bytes of JSON where an index spends none, which is why `DIM_SUMS` is positional rather than merely short. **The indexes are `Stats_Store::ROW_*` constants, and a bare integer literal is forbidden**: the constants buy back the readability the shape spends, and `$row[3]` is unreadable AND silently mis-typeable, which is [substrate ADR-2](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-2-one-message-format-the-7-field-positional-array)'s own consequence in a second place. **The nine fields that ADD come first, in `ROW_SUMS` order**, so ONE map describes the row's summed half, and `merge_url_row()` and `fold_url_rows()` sum through it without naming a field, as `Performance_CI_Node::add_row_sums()` does on the display side. The ninth, `ROW_ERRORS`, went in at index 8 and moved every field behind it one along: a positional row carries no version, so that move is migrated by [decision 5](#decision-5-a-stats-schema-change-is-migrated-by-the-tables-flush-and-by-nothing-in-this-code)'s tables flush, and the header record's `HDR_SHAPE` moved to `v5` with it.

**`ROW_FIELD_NAMES` is the one place an index becomes a name**, in the shape `Message::TYPE_NAMES` sets: one map beside the constants it names, because a private copy is how a reader ends up omitting a field. **`Performance_CI_Node::fold_index_row()` is the one storage/display boundary for the ROW**: everything above it is positional, the display row keeps its names because it crosses the wire as JSON, and a second copy of the translation is how the table and the modal come to disagree about one URL. **`ROW_PATH`, the row's one string, crosses as `url`**: `fold_index_row()` puts the path on the display row, and `resolve_urls()` replaces it with the whole URL `urlmap` joins for the rows a page shows, so a row whose name has expired still shows its path. A thing crosses a boundary where it is CONSUMED, not where it is convenient to convert.

**`ROW_PATH` is last, and capped.** It is `Stats_Store::row_path()`'s: the path and query with no scheme or host when the URL is https under the row's own server, whose name the key implies ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item)), and the whole URL otherwise, so an http row never displays as https; either is cut to `MAX_PATH_BYTES` (1,024) with a trailing `…`. The hash is the row's identity and the path its display, so a query-string flood cannot grow one row past the cap, and the byte cap counts each row's path. A merge keeps whichever side's path is non-empty, and an overflow row's is empty, because one path describes none of the URLs it folds. The suite pins the row shape in ONE test that reads a shard raw, and translates at the seed and read helpers everywhere else, so a test that merely touches a row never counts indexes.

*Deliberately NOT swept in:* the leaderboard's `{time, count, samples}` entry triple (`LB_ENTRY_SUMS`), positional with no constants on both sides of the language boundary: a closed 3-tuple read by two adjacent functions and one React component, where naming it means naming it twice in two deploy units for three fields. *Alternatives rejected:* a value object (it would have to serialize to something, and that something is this array); compressing the whole value (opaque to every diagnostic, for the same bytes at CPU cost); shortening the field NAMES (keeps the cost and loses the readability the constants restore). **The second-namespace condition below is MET, and is answered with a second constant block rather than a per-namespace table.** `CAT_SUMS`, the category series, `Stats_Store::CAT_MS`/`CAT_CALLS`/`CAT_REQUESTS`, is positional for its count: a three-field named entry is 30 bytes of JSON against 15, and the category series is spelled once per five-minute bucket per scope across the whole window. Every field ADDS, so `CAT_SUMS` is itself the whole index set and the ordering clause is satisfied trivially. **It has no `CAT_FIELD_NAMES`, and that is not an omission**: `compact_category_series()` is the series' one storage/display boundary and emits a POSITIONAL wire row, so no index ever becomes a name, and a name table with no naming site is a second shape waiting to drift. `StatsStoreTest` asserts `array_keys( CAT_SUMS ) === range( 0, 2 )`, the same mechanism the two row tables get. **`DIM_SUMS` is the THIRD, and it is a third block of constants, not a per-namespace index table.** A table would buy one declaration site for three index sets and cost a lookup where a constant stands, on `cap_bucket()`'s comparator and on `sum_entry()`'s rebuild, both of which run per entry per bucket per poll; three closed blocks, each named beside the fields it indexes, are not the drift a table exists to prevent. `Stats_Store::DIM_COUNT`, `DIM_SUM_MS`, `DIM_SUM_PEAK_MB` and `DIM_TIMED` take the ROW block's vocabulary exactly, `DIM_TIMED` beside `ROW_TIMED_COUNT`, because they are the same four measurements and two spellings of one measurement read as two measurements: every request counts for volume, and an average divides the timed ones alone ([decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)). Like `CAT_SUMS` it has no field-name table, for the same reason: `compact_dim_series()` emits the entry positional to the WIRE, `[ nameIndex, count, sumMs, sumPeakMb, timed ]`, so no PHP index becomes a name, and the dashboard's one decoder, `decodeNameTable()`, names a wire row's fields through `DIM_FIELDS`. The ordering clause is what makes the cap honest here too — `cap_dim()` ranks by `DIM_COUNT`, and ranked by a field NAME a positional entry does not carry, the sort compares nulls, ties every pair and folds the BUSIEST values into `Other`, which a cap test that only counts survivors cannot see; `FlameBuilderTest` names the busiest and the quietest instead. Nothing migrates a stored entry into this shape: decision 5's flush does. **A rank entry is positional too and does not count toward the clause below.** `Stats_Store::RANK_HASH`, `RANK_ROW` and `RANK_PATH` — the last present on the `url` lists alone, the path on a server's and the whole URL on the site's — are an ENVELOPE around one row, not a sum table: nothing merges two of them field-wise, so there is no `sum_entry()` rebuild to keep contiguous and no `cap_bucket()` comparator to keep honest, and no `range( 0, N )` assertion fits a shape whose last index two lists of fourteen carry. It takes constants for the reason the three above do, and the clause counts the SUM TABLES. **Revisit if** a FOURTH sum table wants the shape — a fourth set of indexes `sum_entry()` rebuilds and `cap_bucket()` ranks through — which is where the table stops being deferrable, or when a TENTH summed field is added to the ROW, because indexes 0-8 are full and the contiguity that makes "the nine that add come FIRST" true is prose: appending it at 15 works and quietly falsifies the sentence. `StatsStoreTest` asserts the four key sets, `ROW_FIELD_NAMES`, `ROW_SUMS`, `CAT_SUMS` and `DIM_SUMS`, are exactly `range( 0, 14 )`, `range( 0, 8 )`, `range( 0, 2 )` and `range( 0, 3 )`, which is the mechanism that prose does not have.

## Decision 19: A request is filed in the bucket it FINISHED in, and a write into a folded hour reaches its fine bucket and the hour key

A stats write must land where a reader will actually read it, which takes two halves: file a request under the bucket it FINISHED in, and send a write into an already-folded hour to the fine bucket the hour key is derived from as well as to that key.

![A request's stats write across a timeline and three steps. The timeline: a request starts in hour H minus 1 and completes in hour H, so min(now, timestamp + round(duration_ms / 1000)) files it in a five-minute bucket of H rather than the bucket it started in; hour H closes, and once its data clock leaves H the builder folds it into urls_h:{H}:{server_key}:{shard} and records H in folded_hours; the record arrives only after that, as a spoke's backlog does. Beneath it, the two writes hour_tier_intents() files for that record: into its fine bucket, urls:{bucket}:{server_key}:{shard}, which decision 17's reader skips and a re-fold reads, kept at the fine TTL like any fold read; and into urls_h:{H}:{server_key}:{shard}, the key the reader takes, missing or not. The steps: first, which bucket, the completion rather than the start, which needs no new field and for a timed-out request is when live traffic timed it out, because Request_Builder sets duration_ms = due - start at eviction, due the stream boundary its window fell due at, so the 1080-second assembly window bounds the exposure at eighteen minutes; the clamp to now keeps a skewed spoke clock or a bogus duration out of a future bucket readers would never reach. Second, which keys: hour_tier_intents() addresses url_shard_parts() under the five-minute bucket while the hour is not in folded_hours, and once it is, that bucket and url_hour_parts() under the hour key, missing or not, with one merge, for the rows and the server index alike; nothing evicts an hour key and a fold writes every shard it keeps, so a key the late write finds missing holds exactly the late rows; a write that lands in the hour key forgets that server's DONE marker so a flush re-ranks the hour, and a server new to the hour takes it off folded_hours so the next roll-up reads it again; the chart series and the leaderboards take no part, because every flush writes their hour key. Third, when the memo is right: folded_hours is per process and one partition has one worker, so only a respawn can stale it, and flush() rolls up before it persists so the first flush after a respawn reads the coarse tier first, and the fold budget stops folds, never that read. Below, the trigger is routine: a hub sees it with no replay, because one flame-builder partition takes every spoke's records and a spoke feeding a backlog lands rows in hours already folded, while a caught-up spoke's records reach the builder about 14 seconds old, and an hour folds on the flush after the first write past it, so a boundary sends into a folded hour only the records that trail the next hour's first by more than a flush.](img/dec-bucket-filing.png)

The record reaches `Flame_Builder_Node` at completion, so filing it under `timestamp`, the START, puts a long request in a bucket that may already have closed. The bucket is therefore `min( now, timestamp + round( duration_ms / 1000 ) )`: the completion needs no new field, and for a timed-out request it is when live traffic timed it out, because `Request_Builder` sets `duration_ms = due - start` at eviction: `due` is the grid boundary the request's window fell due at on `Request_Builder_Node::stream_clock()`, the newest entry stamp it has consumed, or the wall once it has consumed nothing for `Flame_Builder_Node::IDLE_AFTER_SEC`. `LRU_Cache` hands each eviction that boundary, so a stream that falls silent overnight and repays three windows with its next stamp still times each request out at its own third boundary, not six hours long. That removes the request's own duration from the exposure, which the 1080s assembly window, three windows of the same stream clock, bounds at eighteen minutes, and it holds for a reprocess run a day late, whose timed-out requests file among the stamps they were replayed with rather than in the wall's bucket. The completion is **clamped to now**: a completed request cannot have finished after it reached us, and a skewed spoke clock or a bogus duration filing into a future bucket, which readers walking backwards from now never reach, is the same written-then-unreadable failure this decision exists to close.

**Filing by completion does not remove transit**, and that is the second half. `folded_hours` records the hours this process has folded, and [decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)'s reader takes a folded hour's key and never its fine buckets, because they outlive the fold and reading both counts the hour twice. A record arriving after its hour folded therefore has to reach the hour key to be read, and its fine bucket to survive a re-fold. **`Flame_Builder_Node::hour_tier_intents()` files both writes** for a bucket whose hour this process has folded, in the URL index's namespaces — its rows and its server index — with one merge: the fine key under the bucket, and `urls_h` or `urlsrv_h` under the hour, **missing or not**. The Tables evict nothing before their TTL ([decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss)), and a fold writes every shard of every server it keeps, empty or not, so an hour key the late write finds missing is one the fold never wrote, and the late rows are that key's rows. The chart series and the leaderboards take no part: every flush writes their hour key, folded hour or not ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)). A refused write, fine or hour, is logged and nothing more: a refused hour key keeps what it held, and the late rows wait in the fine bucket for any re-fold the hour gets. A chunk whose batch read FAILED is another matter: `bucket_get_multi()` reports it through `$failed` and the chunk writes nothing ([decision 3](#decision-3-stats-fail-soft)). A re-fold is only ever of an hour whose fine tier still names a server: an hour that holds an index and whose buckets name none has outlived them, and `fold_hour_into_store()` writes nothing rather than empty its index, rows and lists. **The fine write goes through the Table at its declared TTL**: the late write keeps its bucket for `<eln:stats_url_fine_ttl>` (two hours) from the write, which bounds what the late writes add to the few seconds of records each hour boundary sends into a folded hour. The fine write forms no ranking group, because its bucket sits behind the fine tail. **A late write re-ranks its hour.** A URL hour-key write that lands forgets its server's DONE marker for the hour, once per hour per server per flush, so the hour turns stale and a flush re-ranks it from its stored rows within the per-flush bound; the debt lives in the store, so a stop loses none of it. The late write into the hour's server index merges like any other (`Stats_Store::merge_index()`): a server the hour already names keeps every shard, and one it did not is named with the shards its late rows fell in, and the flush takes the hour off `folded_hours`, so the next flush's roll-up reads it again. **The trigger is routine, not exotic**: a hub sees late writes with no replay at all, because one flame-builder partition takes every spoke's records, so a spoke feeding a backlog while its peers are caught up lands rows in hours already folded, and every such write has to be right whenever it arrives. A caught-up spoke's records, measured on a hub, reach the builder ~14s old, and an hour folds on the flush after the first write past it ([decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)), so a boundary sends into a folded hour only the records that trail the next hour's first by more than a flush. **`folded_hours` is per-process, and one partition has one worker** (`persist_aggregate_stats()` says so: read-then-write is not atomic), so a respawn is the only way the memo goes stale, and there is no peer to race. `flush()` therefore rolls up BEFORE it persists: the roll-up reads the coarse tier, so the first flush after a respawn has an accurate memo before a single row is placed. The fold budget stops folds and never that read, so every hour it finds folded is memoized in the flush that reads it, however many newer hours still wait for a fold.

*Alternatives rejected:* dropping the hour from `folded_hours` so the next flush re-folds on every late write: a re-fold reads twelve fine buckets for every shard of both families and rewrites the hour's rows, server index and lists, where the merge into the hour key is one read and one write; re-addressing a write to its fine bucket only when the hour key's read misses, which leaves rows merged into a PRESENT shard out of the fine tier, so a re-fold forced by any other missing shard of the hour drops them; having the reader take both tiers, which decision 17 already rejects as double-counting; and capping the late fine write at what is left of its bucket's fine lifetime, which needs a second write path beside the Table, because a Table holds one TTL, to save a footprint the re-fold's own reads spend anyway. **Revisit when** a write needs to reach a bucket older than the coarse tier retains, which this does not answer: the row is capped by the hour's own lifetime either way.

## Decision 20: Outbound HTTP is timed as a span, and a short-circuited request opens nothing

Without these spans a request that spends its time below PHP userland reports as unmeasured, the one answer a reader cannot act on. A BDN `wp-admin/post.php` record shows the cost: 41.7s wall against 12.2s CPU, with `Image_CDN::filter_the_content @999999` holding 29.4s of self time and no interior, so the 29.5s off-CPU remainder has no name. A hook cannot reach it, since `WP_Http::request()` is not a hook, but WordPress brackets the call: `pre_http_request` before, `http_api_debug` after. [`App\Core`](../includes/app/class-core.php) binds that pair for every log rule whose `log_http` is set, so the span costs two registrations per request and two entries per remote call. **The pair is NOT balanced, and that asymmetry is the whole design.**

![The outbound-HTTP span as a priority ladder. Step 1, apply_filters('pre_http_request', false, $args, $url): any filter may answer the request and return it, and http_start sits at PHP_INT_MAX, last to vote, so it opens nothing when $preempt is not false and otherwise pushes the label http and writes http (start). Step 2, the transport runs: the I/O below PHP userland the span exists to name. Step 3, do_action('http_api_debug'): http_end at PHP_INT_MIN hears it first, pops the label it opened rather than re-deriving it from a URL a redirect may have changed, and writes http (complete) with the status code, ahead of the other listeners. Beside it: WP_Http::request() answers a short-circuit with a bare return $pre; and never fires http_api_debug, so a span opened for it would never close and would adopt every row after it, the damage decision 13 bounds; the entry pair one remote call writes, m the redacted URL and l the calling frame; and the caller label, origin_frame(true), climbing past WP_Http at TRANSPORT_ORIGIN_DEPTH 16 rather than ORIGIN_DEPTH 8 whatever trace_callers says, with that budget reaching this span too, keyed on the redacted URL paired with the calling frame, so l names who asked on every call and caller carries the chain on the first few to each endpoint. Footer cards: the BDN wp-admin/post.php record, 41.7 s wall against 12.2 s CPU with 29.4 s of self time in Image_CDN::filter_the_content @999999 and a 29.5 s off-CPU remainder with no name; the cost, two registrations per request and two entries per remote call, under log_http; and every callback asking Log_Manager::started_instance() first so instrumentation never constructs the logger.](img/dec-http-span.png)

`WP_Http::request()` short-circuits with a bare `return $pre;` and never fires `http_api_debug` (`class-wp-http.php`), so a span opened before the short-circuit would never close and would adopt every row after it: the severed-span damage [decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) exists to bound. So `http_start` binds at **PHP_INT_MAX**, after every short-circuiting filter has voted, and opens nothing when `$preempt` is not false: a short-circuit is a cache hit with no I/O to time. A rule marking `http` significant gets that filter's listeners wrapped by `http_wrap`, bound at PHP_INT_MIN ahead of the chain on each call, the shape `hook_start` uses — `http_start` votes last, so from there a listener could only be wrapped for the NEXT call — so a short-circuiting listener's own cost shows where the span would have been. Every other return path fires the action, so within one request the pair is exact. `http_end` binds at PHP_INT_MIN so the span covers the request and not the other listeners on that action, and it closes the label it OPENED rather than one re-derived from the URL: a redirect hands the action the FINAL url, and a label that no longer matches leaves the span open. The span is named for its **caller**: `l` is `origin_frame( true )`, which climbs past every frame of the class that applied the filter, `WP_Http` here, at `TRANSPORT_ORIGIN_DEPTH` (16) rather than `ORIGIN_DEPTH` (8), because "which of my code paths makes this call, how many times" is the question a reader has; the redacted URL rides as the entry's value and the status code closes it. The climb runs whatever [decision 23](#decision-23-a-span-says-how-long-never-who-asked-two-knobs-answer-the-second-question-at-two-prices)'s `trace_callers` says, and taking the shallow walk under it is rejected: that budget reaches this span too, keyed on the redacted URL paired with the calling frame, so `l` names who asked on every call and `caller` carries the chain on the first few to each endpoint; the shallow walk would trade `l` for a microsecond or two. **Naming the HOST instead answers nothing**, because so many calls go to the same one. **Instrumentation never CONSTRUCTS the logger it reports into**: `Log_Manager::instance()` lazily creates a logger, so every callback asks `started_instance()` first, the wrapped listeners included; otherwise a binding that outlived its request would build the logger inside the callback and stamp `process (start)` with that moment instead of the mu-profiler's `request_ts`.

*Alternatives rejected:* a per-rule opt-in flag (a new `Rule` property, its serialization, its editor control and its migration, to gate two registrations and a per-call cost that is zero on the requests that make no remote calls); timing inside a `significant_events` wrapper on `http_api_debug` (that times the action's LISTENERS, which is not the request). **Revisit when** SQL wants the same treatment, though `$wpdb` offers no completion signal without `SAVEQUERIES`, so it is a different mechanism and not an extension of this one, or if a transport ever fires `http_api_debug` more than once for one request, which would pop a label that is still in flight. **Per-rule** (`log_http`), like decisions [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) and 24: a logged request pays two entries per outbound call whether or not a brief reads them. Off unless the rule sets it, as every diagnostic is, a stored rule that predates the flag included.

## Decision 21: The fold keeps the CLOSE of any span the kept head left open

The fold keeps a head of [`FOLD_KEEP_HEAD`](../includes/class-request-builder-node.php) (10) and a tail holding every later row in arrival order, which evicts only unkept rows past `FOLD_KEEP_TAIL` (10). A span opened in the head FRAMES every row after it, so the fold keeps the close of every span that head left open, an `(orphaned)` close included.

![One job record from community.thecoast.ca folded two ways. The gyrobase subprocess opened in the kept head (FOLD_KEEP_HEAD 10) and closed after 535.8 s of a 536.2 s request, and ten PHP rows followed it: nuclear_gyrobase, two query hook pairs, updated_option hook, memory, resources and the terminal. Without the rule, the close is one more row in the rolling tail (FOLD_KEEP_TAIL 10), the ten rows evict it, and the entry list leaves gyrobase open, so the view reconstructs framing the record does not state and three display defects follow, while the flame, counted only by Flame_Fold::close(), still reads gyrobase count 1, 535,829.753 ms. With the rule, the fold marks the frames still open on its own stack after the head, and the close that matches each is marked kept, pinned in the tail where they arrived; at most FOLD_KEEP_HEAD closes are pinned, and process (complete) is exempt because the terminal arrives last. Notes: is_kept() leaves tail sizing to producers marking their lines, but a span's close is not that guess, because the fold chose the head; and losing a head span's close costs the record its shape, not one line.](img/dec-fold-keeps-close.png)

`is_kept()` argues that sizing the tail around a producer's shutdown sequence is guesswork the producer should settle by marking the line. A span's close is not that guess: the fold just chose the head, so it knows exactly which frames it left open, and there are at most `FOLD_KEEP_HEAD` of them. Nor is the close mere detail: losing a head span's `(complete)` costs the record its shape rather than one line. A `community.thecoast.ca` job shows it: the gyrobase subprocess closes after 535.8s of a 536.2s request, and the PHP parent's ten post-subprocess rows (`nuclear_gyrobase`, two `query hook` pairs, `updated_option hook`, memory, resources, terminal) fill the rolling tail and, without this rule, evict the close. The flame still counts the span, because `Flame_Fold::close()` is the only path that increments a node's count and the tree reads `gyrobase` count 1, 535,829.753ms; but the entry list leaves it open, and three separate display defects follow from the view reconstructing framing the record does not state. After the head's last row, `fold_request()` calls `Flame_Fold::mark_open_frames()` on the fold's own span stack, the one every row already feeds and every checkpoint carries, and `Flame_Fold::add()` reports when a `(complete)` matches a marked frame; the builder marks that row kept, so the rolling tail never evicts it and it stays where it arrived. Because the match is the fold's own LIFO match, a span re-opened past the head keeps its own close rather than the inner one's, a name the head opened twice keeps both, and an `(orphaned)` close, which `Log_Manager::complete()` and `Gyrobase::Log::_unwind_to()` write for every frame above the one closing, is kept as that head frame's close. Moving it ahead of the tail would put the rows logged inside its span outside it, which a pyrobase render inside `template_redirect` does on every folded request, since its rows land before the hook closes. **The request's own frame is exempt**, exactly as it is for the display's severed-span prune: `process (complete)` is the terminal, the last row to arrive, so the tail always holds it.

*Alternatives rejected:* having the producer mark the line (`Gyrobase::Log` could set `keep` on its nested `complete('gyrobase', …)`, but that fixes one producer in another repo and leaves every other one to rediscover it); closing the span in the VIEW from the tree's count and value (puts derived data in the entry list, and leans on exactly the reasoning across a marker [decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) restricts). **Revisit if** a head ever legitimately leaves more frames open than the tail can afford to carry, which would mean `FOLD_KEEP_HEAD` is choosing a head the record cannot frame.

## Decision 22: Query spans are the same pair as decision 20, but PER-RULE

[Decision 20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) leaves SQL as its reopen condition and calls it a different mechanism; it is the same shape with a different gate. `wpdb` brackets a query with `apply_filters( 'query', … )` before and, only under `SAVEQUERIES`, `log_query_custom_data` after. [`App\Core`](../includes/app/class-core.php) binds `query_start` on the [`query`](https://developer.wordpress.org/reference/hooks/query/) filter at the configured `hook_start_priority` (a plugin config key, default -10000), the priority the generic hook timer uses, so the span opens ahead of the filter chain and every filter that rewrites the SQL runs inside it. It records the label only, since the SQL at that point is what the caller wrote. `query_end` binds on `log_query_custom_data` at PHP_INT_MIN, pops the label and writes `sql (complete)` with the statement the database was asked: its host annotation stripped by `without_host_annotation()`, its literals replaced with `?` by `without_literals()`, and bounded only by `Log_Manager::MAX_DATA_SIZE`. A rule marking `sql` significant gets the `query` filter's per-callback timings nested inside the span, and with `log_queries` on, `query` itself is not bound as an ordinary hook.

![The query span as a priority ladder. Step 1, apply_filters('query', $sql) inside wpdb::query(): query_start at hook_start_priority (default -10000), the priority the generic hook timer uses, opens the sql span with its label only, since the SQL at that point is what the caller wrote, and every later filter that rewrites the SQL runs inside the span; a rule marking sql significant gets the query filter's per-callback timings nested inside the span, and query itself is not bound as an ordinary hook. Step 2, the database round trip, about 0.4 ms on the measured host. Step 3, log_query_custom_data, which wpdb fires only under SAVEQUERIES: query_end at PHP_INT_MIN pops the label, writes sql (complete) with the statement as rewritten, its host annotation stripped by without_host_annotation() and its literals replaced with ? by without_literals(), bounded only by MAX_DATA_SIZE, and then drains $wpdb->queries; App\Core defines SAVEQUERIES when it is absent, and a long-running worker keeps the constant for its life, bounded by the drain. Beside it: the entries one query writes; the label l, origin_frame(true), climbing past every wpdb frame at TRANSPORT_ORIGIN_DEPTH 16 because SHOW FULL COLUMNS arrives four wpdb frames deep, where naming the table says SELECT wp_posts ran 156 times and never which code ran it; and why it cannot be always-on, since Query Monitor would find $wpdb->queries empty. Tiles: 3,000 queries in 1.117 s with the constant against 1.254 s without, 217 bytes held per query, and two entries per query against HTTP's two per remote call.](img/dec-query-span.png)

**The difference from HTTP is the cost, and it is measured, not assumed.** Both are per-rule opt-ins, but HTTP's price on a request making no remote calls is two `add_filter` calls. Queries cost two log entries EACH, and the close does not fire at all without `SAVEQUERIES`, so `log_queries` is the flag to weigh. What that constant costs was measured rather than feared: 3,000 queries run in 1.117s with it and 1.254s without, so the `get_caller()` backtrace is noise against a 0.4ms round trip, and what is real is retention, 217 bytes per query held in `$wpdb->queries`, the memory pressure that folds these records. `query_end()` therefore DRAINS that array, which is also why this cannot be always-on: anything else reading it (Query Monitor) finds it empty. `App\Core` defines `SAVEQUERIES` when it is absent, and a constant cannot be withdrawn, so a long-running worker keeps it for its life, bounded by the drain. **The span is named for its CALLER**: `l` is `origin_frame( true )`, as in decision 20, which takes the first non-machinery frame as the transport and climbs past every frame of it, whatever `trace_callers` says. A fixed skip cannot do that job: `wpdb::get_row()` reaches the `query` filter through `wpdb::query()`, and `SHOW FULL COLUMNS` arrives four `wpdb` frames deep, which is why the transport climb runs to `TRANSPORT_ORIGIN_DEPTH` (16) where a hook's own origin needs `ORIGIN_DEPTH` (8). Naming the TABLE instead says `SELECT wp_posts` ran 156 times and never which code ran it, and which code ran it is the only version of the question worth asking. *Alternatives rejected:* the `query` filter alone, closing each span at the NEXT query (charges every query with the PHP that ran after it); `$wpdb->num_queries` deltas on existing spans (free and always-on-safe, but counts are not spans, and the flame is what is being asked for); a `db.php` drop-in (accurate and SAVEQUERIES-free, but the host already ships one). **Revisit if** a reader needs the full callstack `log_query_custom_data` hands us rather than the one origin frame.

## Decision 23: A span says how long, never who asked. Two knobs answer the second question, at two prices

Decisions [20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) and [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) add spans; this one adds PROVENANCE, because a hook that fires sixteen times reads as sixteen identical mysteries and no amount of timing distinguishes them. A `/wp-admin/post.php` record is the case: `the_content` fires sixteen times at ~2.4s each, 93% of a 40.6s request, and every span says the same thing. What is missing is the caller.

![Two provenance knobs at two prices, from a /wp-admin/post.php record where the_content fired sixteen times at about 2.4 s each, 93 percent of a 40.6 s request. Left, trace_hooks: origin_frame() takes one frame, who called the hook, and puts it on the entry's l, the flame's aggregation label, so one the_content node splits into a node per caller with measured durations and no tree code changes, and it never synthesizes an ancestor such as wp_trim_excerpt for an uninstrumented frame, which would assert a duration nobody measured; debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH) costs 0.9 microseconds against 12.7 for wp_debug_backtrace_summary(), the depth limit being the lever, so it runs on every firing, 2,601 render_block calls costing 2.3 ms. Right, trace_callers: caller_of() records wp_debug_backtrace_summary(self::class) onto the hook's own start entry as caller, not c, which means count throughout the schema; the rule's number is the count of deep chains, default 0, with a stored true reading as a count of 1, because the pair key makes one chain per caller a chain from every caller, and a strip of one CALLER's firings of one hook shows the first twenty carrying chains at trace_callers = 20 and the rest none, with a tick under the twentieth, the cap being per caller of a hook, not per hook and not per request; the window is CALLER_FRAMES, 20 frames, because a fixed 20 leaves 21 percent of a record unattributed and an 8-frame window stops one frame short of rest_preload_api_request. Footer: a field nothing renders does not exist, so LogEntriesTable renders the caller chain as called by …; both knobs are off by default, like log_queries and unlike log_http; and Log_Manager::message() merges arbitrary keys into the entry, [ 'n', 'k' ] + $data + [ 'ts' ], so neither needs a new wire field.](img/dec-provenance-knobs.png)

**`trace_hooks` is the cheap one and does the real work**: `origin_frame()` takes ONE frame, who called the hook, and puts it on the entry's `l`, which is the flame's aggregation label, so [`Flame_Tree`](../includes/class-flame-tree.php) and [`Flame_Fold`](../includes/class-flame-fold.php) split `the_content ×16` into one node per caller with MEASURED durations and no new tree code. Gyrobase uses the same idiom for `include: /Macros/Global.html`. It deliberately does NOT call `wp_debug_backtrace_summary()`, which walks and formats the whole stack to produce a string all but one frame of which is discarded: measured at **12.7us against 0.9us** for `debug_backtrace( DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH )`. The LIMIT is the lever, not `IGNORE_ARGS`: args are refcounted, not copied, and cost 0.8us even on a multi-megabyte `the_content`; depth is what costs. At 0.9us it runs on EVERY firing (2,601 `render_block` calls cost 2.3ms), which makes the split complete rather than truncated at a budget. **What it must NOT do is synthesise ANCESTOR nodes** for the uninstrumented frames: a `wp_trim_excerpt` parent valued at the `the_content` inside it would assert a duration nobody measured, which is [decision 12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact)'s whole point. Attribution is honest; invented ancestry is not.

**`trace_callers` is the expensive one**, default 0: `caller_of()` records `wp_debug_backtrace_summary( self::class )` onto that span's OWN start entry as `caller`, not `c`, which already means COUNT throughout this schema, ignoring this class so the top frame is the caller and not the instrumentation. **The cap is what makes it affordable, and it is per KEY, not per request** — a hook name, a query's statement shape or an outbound URL, whichever the flame aggregates that span on, PAIRED with `l`, the calling frame that span is already labelled by. A hook fires, a query shape runs and an endpoint is called for the same reason: code asked. Keying the budget per request instead would spend it on the bootstrap and trace none of the 477 taxonomy reads that came later. Keying it on the hook alone has the same failure one level down: `l` is what SPLITS the flame node, so the caller that fires first takes the whole allowance and every other node reads as an unexplained repeat — which is why the number had to be large enough to cover all of them at once. Paired, 1 reaches every caller, and that is the setting to reach for. The RULE names the number: `trace_callers` IS the count of DEEP chains, and a stored `true` is a count of 1, because the pair key makes one chain per caller a chain from every caller. What a diagnostic run wants is not what steady state wants: a fixed 20 leaves 21% of one real record's time unattributed. The window is `CALLER_FRAMES`, 20 frames, because an 8-frame window stops one frame short of `rest_preload_api_request`, the frame that explains that whole request, and `Log_Manager::MAX_DATA_SIZE` is the only other bound — which a query start entry meets differently from a hook's: it carries `l` and `caller` but no `m`, so `fit_data()` has no string to trim and the entry drops straight to the floor, keeping `n`, `k`, `ts` and a 1000-byte excerpt. The span still opens, because `Flame_Tree::PATTERN_START` reads `k`. The cap exists because the same question asked of `render_block` on that record would be 2,601 backtraces. Price the whole of it before raising either number: a traced rule pays roughly 12.7us per chain, times the number of KEYS it meets — hook names plus distinct statement shapes plus distinct URLs, none of which the operator declares — and the pair key multiplies that count by the distinct CALLERS of each, which is exactly why the number comes down as the key narrows: sixty shapes at twenty is about 15ms and five hundred is 127ms, where the same sixty shapes asked from three places each at 1 is about 2ms, and a traced query also pays `without_literals()` twice, once for the budget key at the open and once for the statement `m` at the close. A cap that bound tighter used to stop tracing the shape being hunted, which is why the answer was the per-key budget and a rule the operator turns off again rather than a smaller number; narrowing the key to the pair is what makes a smaller number safe, because 1 now buys one chain from EVERY caller instead of one from the first. The budget resets on every scope change, so a worker draining a hundred jobs traces each one rather than spending the request's allowance on the first. Sixteen firings of one hook are one budget PER CALLER — three callers, three chains at 1 — so there is no named default: `true` reads as 1, and an operator who wants more writes the number. There is nothing for a named default to seed, either: the editor fills its field from the stored value or 0, and `to_array()` writes an int. `Log_Manager::message()` merges arbitrary keys into the entry (`[ 'n', 'k' ] + $data + [ 'ts' ]`), so neither knob needs a new wire field. **A field nothing renders is a field that does not exist**, so `LogEntriesTable` renders `l` and then `caller`, as "called by …", muted ahead of the entry's value. Per-rule and off by default, like decision 22 and unlike 21: a backtrace is cheap once and not cheap always.

*Alternatives rejected:* capturing unconditionally for bound hooks (a rule naming sixty hooks pays sixty times per request for an answer nobody asked); tracing only firings AFTER the first, on the reading that a repeat is the signal (the first caller is half the answer: which of the sixteen is the odd one out is exactly what you are reading for); a separate `(called by)` entry (a new keyword that `logEntryUtils` and `Reqgrep_Core` would both have to learn, to carry a field the start entry already had room for). **This decision's revisit condition is MET.** It named a THIRD per-rule diagnostic knob as the trigger, on the reading that two booleans is a pair and three is a flags map. `Rule` carries five, `log_queries`, `log_http`, `log_plugin_loads`, `trace_hooks` and `trace_callers`, and they are still five separate constructor properties. A flags map would buy one property and cost every reader a lookup and every knob its type — `trace_callers` is an int, not a boolean — so the count alone is not the trigger it was taken for.

## Decision 24: A duration nobody measured is not a timing sample

[`Flame_Builder_Node::accumulate_all_stats()`](../includes/class-flame-builder-node.php) runs two independent gates, `$count_global` ([decision 15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site)) and `$record_timing`, and conflating them is the classic bug in that class. `$count_global` is "not a worker": it keeps worker traffic out of every site-wide aggregate. `$record_timing` is true only when `duration_ms` is positive AND `error_status` is neither `T` nor `A`. Both statuses mark a duration that measures elapsed time to an interruption rather than what the request cost: `Request_Builder_Node::evict_request()` stamps `T` and the stream boundary its window fell due at, less the start, on a trace the LRU evicted mid-request, and `Log_Manager` stamps `A` when a cooperative stop lands inside `finish()` or when `end_job_context()` is told the job never finished. Summing either skews `sum_ms`, `max_ms`, `min_ms` and every mean drawn from them.

![The two gates every completed request passes in accumulate_all_stats(). Gate 1, $count_global, is simply not a worker: it keeps worker traffic out of every site-wide aggregate while the per-URL row keeps worker timing on rows of its own. Gate 2, $record_timing, requires duration_ms above zero and an error_status that is neither T, which Request_Builder_Node::evict_request() stamps with the stream boundary its window fell due at minus start on a trace the LRU evicted, nor A, which Log_Manager stamps when a cooperative stop lands inside finish() or end_job_context() hears the job never finished. A table shows what every request adds and what only a timed request adds: on the per-URL row, ROW_COUNT and its count_Nxx bucket, ROW_SUM_PEAK_MB, ROW_MAX_PEAK_MB, ROW_LAST_SEEN and ROW_WORKER always, and ROW_TIMED_COUNT, ROW_SUM_MS, ROW_MIN_MS and ROW_MAX_MS only when timed; on the per-URL flame aggregate, count always and sum_value with the children merge only when timed; on every dimensional slot, DIM_COUNT and DIM_SUM_PEAK_MB always and DIM_SUM_MS and DIM_TIMED only when timed; in hourly_h, non-worker only, requests and sum_peak_mb from every request and count and sum_ms only when timed; and the profiles, both leaderboards, the three category series and auto-tune, skipped whole. So count and timed_count diverge for a reason that has nothing to do with workers: mean_ms divides sum_ms by timed_count while avg_peak_mb divides by count, and hourly_h and every dimensional row keep both counts, so each average divides the population it summed.](img/dec-timing-gate.png)

A request failing the timing gate still COUNTS: it increments `ROW_COUNT` and its `count_Nxx` bucket, `ROW_ERRORS` when it timed out ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)), `ROW_SUM_PEAK_MB`, `ROW_MAX_PEAK_MB`, `ROW_LAST_SEEN` and `ROW_WORKER` on the per-URL row, the `DIM_COUNT` and `DIM_SUM_PEAK_MB` of every dimensional slot, `hourly_h`'s `requests` and `sum_peak_mb`, and `count` on the per-URL flame aggregate. It contributes nothing to `ROW_TIMED_COUNT`, `ROW_SUM_MS`, `ROW_MIN_MS`, `ROW_MAX_MS`, the aggregate's `sum_value` and children merge, the dimensional `DIM_SUM_MS` and `DIM_TIMED`, or `hourly_h`'s `count` and `sum_ms`; and `accumulate_profiles()` is skipped whole, so both leaderboards, the three category series and auto-tune never see it. **So `count` and `timed_count` diverge for a reason that has nothing to do with workers**, since the row records worker traffic separately in `ROW_WORKER`, which is why `Stats_Store::mean()` divides `sum_ms` by `timed_count` while `avg_peak_mb` divides by `count`. `hourly_h` and every dimensional row keep the two populations apart the same way: `global_avg_ms` and a chart's average duration divide by the timed count (`count`, `DIM_TIMED`), and `global_avg_peak_mb` and the memory metric by every request (`requests`, `DIM_COUNT`). **The mean of nothing is null.** `Stats_Store::mean()` answers null for a zero divisor, so `avg_ms` is null where no timed request reached a URL row, the header totals, `global_avg_ms` or a board, and so is `avg_peak_mb` for a scope with no request at all. A URL row no timed request reached has no extreme either: `Performance_CI_Node::project_row()` answers its `min_ms` and `max_ms` null whenever its `timed_count` is 0, whatever the row stored, and every surface emitting the row carries that null rather than deciding it again. Such a URL ranks last on `avg_ms`, `min_ms` and `max_ms` in both orders (`Stats_Store::TIMED_SORTS`): the writer's lists and the reader's fold both rank through `Stats_Store::rank_order()`, which orders every timed row ahead of every untimed one. Every reader carries the null to its surface and shows it as unmeasured, never as 0, because a 0 reads as fast: a dash in a table or a brief, no bar on the URL table, and a gap in a chart, where a count or a sum of none stays a real 0. **Revisit if** an evicted or aborted request ever carries a duration someone measured, which would make it a sample like any other.

## Decision 25: Read tools and TUNE-scoped write tools share one MCP session, and every tool result is fenced

Every read tool returns recorded site traffic, and a visitor writes part of it. `dump_request` carries the `environment_v3` entry, whose `m` map is the curated `$_SERVER` block: `HTTP_USER_AGENT`, `HTTP_REFERER` and `HTTP_X_FORWARDED_FOR` are the visitor's own prose, capped at 256 bytes and stripped of control characters but otherwise verbatim. Serialized into a tool result with no delimiter, that prose reaches an agent's context indistinguishable from the server's own answer — and the same session may hold `rules_upsert` and `rules_delete`, so the agent it is talking to can edit the logging ruleset. What forced the decision is that pairing: recorded visitor text arriving unmarked beside a write tool.

One marking serves both exits, named once. A value recorded from site traffic leaves inside `<site-data>…</site-data>`, and the reader is told in standing text that whatever sits inside that tag is recorded data and never an instruction. `MCP_Controller::fence()` encodes every reply with `wp_json_encode( $reply, JSON_HEX_TAG | JSON_UNESCAPED_SLASHES )` and wraps the result, so a string reply encodes as a JSON string and the reader needs no second rule for it. `JSON_HEX_TAG` is what makes the fence unbreakable from inside: every `<` and `>` in the payload becomes `\u003C` or `\u003E`, so no visitor string can carry a literal `</site-data>` and close the tag early. The `initialize` reply's `instructions` field carries the standing text alongside the measurement caveat. An `isError` result is left alone, because that text is the site's own message rather than anything a visitor wrote. The browser's own exit, `src/overview/askBrief.js`, applies the same marking to the values a log record wrote — the subject URL and an entry's message — escaping `<` as `\u003C`, the spelling the MCP fence produces, collapsing control characters to one space and capping at 512 characters with a trailing `…`; both prompts it builds carry the same sentence. Rule ids, rule patterns, span names, hashes, rids and numbers stay bare, because the operator or the server wrote those. `Ask_Assembler::entry_shape()` ships the `environment_v3` entry with no body at all: its map is the visitor's headers and the peer, and the brief's `env` field already carries the allowlisted facts, so a second list over the map would only drift from the writer's.

Two alternatives were weighed and rejected. The first was a separate write-only session, so that no session holding a read tool could also edit the ruleset. That does not remove the injection, it only moves it: an agent holding both sessions reads the same recorded data out of one and writes through the other, and the operator now maintains two credentials for a boundary the agent crosses in a single turn. The second was dropping the write tools entirely. That would cost the surface its point — the ruleset is exactly what an agent investigating a slow URL needs to widen — for a defence the fence already provides more cheaply. The scope is subtractive and bounded by the minting user, so a `read` session offers no write tool at all and a `tune` session minted by someone who holds nothing does nothing; the operator chooses `tune` at mint time knowing the agent can then edit the logging ruleset and nothing beyond it, since the vault and the fleet are substrate `manage` and unreachable here. The fence plus the `initialize` instructions are the defence, and the blast radius stays recoverable: the ruleset is re-seeded from the config file and the schema through `Rule_Set::seed_from_config()`.

The cost is real. Every tool result is JSON, so an agent client that parsed a string reply as text has to strip the fence and decode; the hex-escaped angle brackets make a raw result harder for a human to read in a transcript; and the wrapper adds bytes to every reply. The marking is also advisory — it tells a reader what the bytes are, and a model that ignores standing instructions is not stopped by a tag. **Revisit if** MCP gains a transport-level way to label untrusted content, or a write tool appears whose blast radius is not recoverable from the config file, at which point the write half needs its own session after all.

## Decision 26: A merged transport node keeps the statements it ran

The fold replaces a request's entries with one node per path, and the statements go with them. A real `/wp-admin/post.php` record says `sql: WP_Query->get_posts` ran 667 times for 58.3s, and cannot say what any one of them was — the question a repeat that size raises. [Decision 22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) argues the other way in as many words, that naming the TABLE "says `SELECT wp_posts` ran 156 times and never which code ran it, and which code ran it is the only version of the question worth asking." That holds for the SPAN'S NAME, and it still does: `l` is the caller, `Flame_Tree::node_name()` merges on it, and this decision does not touch it. What it revises is the unstated second half — that the statement is therefore worth nothing — which is true only while the entries survive to carry it. In a folded record they do not, and the caller alone cannot separate one query repeated 667 times from thirty different ones.

So a merged node whose span is one of the logger's own round trips — `Flame_Tree::is_transport_span()`, the `sql` and `http` states — carries `shapes`: the distinct statements or URLs it ran, each with a call count and summed milliseconds. **Only those two**, because their message is a bounded identifier by construction: `without_literals()` collapses `IN (?,?,?)` to `IN (?)` and every literal to `?`, and a redacted URL is one line. A hook's message is prose of any size and any cardinality, so it gets no table. **The identifier is the FIRST non-empty `m` of the pair**, because which half carries it is the producer's business and they disagree: `http_start` writes the URL and its complete the status code, `query_end` writes the statement and its start nothing. Reading the close alone builds a table of `200`s — and an `http` complete never stands in for a start a checkpoint lost, for the same reason.

Three bounds, and the third is the one that matters. A shape is cut to `MAX_SHAPE_BYTES` (512), measured against 308,395 real `sql` completes here — mean 146 bytes, median 122, p99 488 — so it truncates 0.6% of statements. A node keeps `MAX_SHAPES` (24) rows, one slot of which is reserved for the `…` bucket everything else folds into; one record in 184 had a node exceed it. A full table EVICTS its cheapest row rather than refusing the newcomer, because the statement worth naming is as likely to arrive twenty-fifth as first and first-seen-wins would bury it on exactly the record this exists for. **And the record itself is bounded, at `MAX_RECORD_SHAPE_BYTES` (32KB of new shapes), because the per-node caps bound a NODE and a record's node count is `O(distinct paths)` by design**: the heaviest real folded record here carries 117 transport nodes against 73KB of record, so per-node caps alone admit megabytes. The POOL sizes that number rather than the record: `Request_Builder_Node` holds 300 requests in flight against an entry budget worth ~18MB, so 32KB apiece keeps the worst case near half of it, and that heaviest record — whose own statements cost 33.7KB — is the one shape that spends its budget and buckets the tail. **The budget charges what the table GREW by**, never what a statement the bucket swallowed would have cost: charging the attempt let one high-cardinality caller spend 65,603 bytes to store 9,206 and strip every other node's table, measured at 7.1×. It charges a ROW's cost too, `SHAPE_ROW_BYTES` beside the key's own length, because a byte budget alone bounds bytes and not rows: at eight-byte shapes, which `without_literals()` readily produces, the rows cost twelve times what the budget thought it had allowed. A spent budget refuses a new row the table has ROOM for, and nothing else: a statement the node already keeps costs no bytes to count, and a full table's eviction trades one row for another and pays only the difference, which it may do while spent so long as the new key is no longer than the one it replaces — refusing every trade would bucket the worst statement on the one record shape that ever spends its budget, and admitting a growing one carried a record to 3.2× the budget, one filled table at a time. A folded envelope is also invisible to `Request_Builder_Node`'s pressure loop, which counts `entries` and skips a folded one, so nothing downstream would catch the growth.

The statement is recorded data, so it leaves through [decision 25](#decision-25-read-tools-and-tune-scoped-write-tools-share-one-mcp-session-and-every-tool-result-is-fenced)'s marking like any other: `askBrief.js` gives it a fenced line of its own rather than a slot in the `numbers:` list, which a reader splits on spaces and a statement carries plenty of.

`shape_ms` is a MEASURED sum, unlike the node's `value`, which [decision 12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact) calls a rendering artifact that every producer raises to cover its children. Nothing raises `shape_ms`, and nothing may: it is the time those statements took. The pair is positional per [decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants), under that decision's `LB_ENTRY_SUMS` exemption — a closed 2-tuple read by `Findings::worst_shape()`, `merge_shapes()` and one React function.

**An unfolded record gets the same table, derived rather than stored.** Its entries survive, so the log table shows every statement — but a brief ships sixty entries, so for any reader but the detail view the finding is the only place the answer can land. `Findings` folds the record's entries transiently through `Flame_Fold` and reads each node's table by its name path, which runs the one set of rules rather than a second, and adds nothing to the stored flame. That fold passes no record budget: the budget exists for a pool of in-flight envelopes, and a fold built, read and dropped holds nothing against it — keeping it would bucket a slow statement that first appears late and name a cheaper one.

*Alternatives rejected:* keeping ONE representative statement, the slowest instance's (costs no table, and answers "was it one query or thirty?" with a guess); a digest at the producer, in `App\Core::query_end` (the producer cannot know the record will fold, and a per-request digest would ride the firehose against `MAX_DATA_SIZE` on every request that never folds); the table on the per-URL aggregate (cardinality across thousands of requests is unbounded, and the aggregate's numbers are per-request means, which a summed pair is not — `merge_flame_children_incremental()` rebuilds each node from four keys, so it cannot leak there by accident). **Revisit if** a THIRD span kind earns a table, which would make "is it transport?" the wrong question and a producer-set marker on the entry the right one — `Log_Manager::message()` already merges arbitrary keys, and `Request_Builder_Node` already allowlists such fields beside `keep`. The sibling producers are the reason it would come up: pyrobase's `customquery_sql` and gyrobase's `query_sql`, `search_query` and `<tag> (sql)` spans all carry an already-shaped statement, and none of them is named `sql`.

## Decision 27: The platform's requests to itself are worker traffic, named by path

The cron loopback, the substrate's own endpoints — `/wp-json/newspack-nodes/v1/{auth,command,health/cache,log/stream,messages/stream,workers/spawn}` — and this plugin's MCP route, `/wp-json/newspack-event-logger-nodes/v1/mcp`, are requests the platform makes to itself, and until 0.101.0 the shipped seed skipped every one, so the logger never logged the logger. A skip loses the record: a `command` poll that took nine seconds, or a spawn that fataled, left nothing to read. So the seed is the `/` log rule alone, and [`Log_Manager::PLATFORM_WORKERS`](../includes/class-log-manager.php) names each of those requests a worker by its path — `cron` for the loopback, `restapi` for the seven REST endpoints — as the `worker_type` entry `log_worker()` writes right after `process (start)`. The seven share one name because the path already names each endpoint and `resolved_request_url()` appends the type as the URL's query, so a name per endpoint only repeated it: `…/workers/spawn?spawn`. The substrate's own processes name themselves through `NEWSPACK_NODES_WORKER_TYPE`, and that wins where it is set; the path answers where it is not, which for the spawn endpoint is always, since the substrate sets the var at REST dispatch, after the request was opened. So the spawn endpoint is the one `restapi` row that is renamed: once the worker `Spawn_Controller` validated holds its lock, the substrate fires `newspack_nodes/worker_identified` (2.71.0), and `Log_Manager::identify_worker()` writes `worker_type` and `worker_partition` again into the open record. `Request_Builder_Node` takes the latest of each, so a spawned worker's record and its in-flight gyroscope row sit on that worker's row, and existing `…/workers/spawn?restapi` rows stop accumulating and age out. A refused spawn, or one that loses the lock race to a live worker, never announces, so it keeps `restapi` and cannot mint a row out of the request's own parameters. A worker's record keeps every entry, sits on the worker shard's URL rows, and stays out of the global sums at [decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)'s `$count_global` gate.

**The REST paths are a copy the substrate does not know it owns.** `HTTP_In_Node`, `SSE_Out_Node`, `Log_Stream_Out_Node`, `Spawn_Controller`, `Auth_Controller` and `Health_Cache_Controller` declare those routes in newspack-nodes, and `MCP_Controller` this plugin's; `PLATFORM_WORKERS` spells them again as literals, root-relative and `wp-json`-prefixed, as the seed's skips did before it. They stay literals because `Spawn_Controller` and `Auth_Controller` name their routes inline, with no constant to read. `LogManagerTest` registers every route the platform serves and compares the set to the literals, so a route the substrate adds, moves or drops fails the suite. What no test reaches is chosen with open eyes: a subdirectory install or a site rewriting its REST base yields a request `platform_worker_type()` does not name, and it lands on the global rows as visitor traffic. That is a misclassification the overview would show, where the skip list's failure was a record that never existed. The map is not derived from `rest_url()` or `site_url()` because the seed never was, and because a copy that nothing checks costs one line per route where a derivation costs a `get_option()` per request.

*Alternatives rejected:* keeping the seed's skips (loses the record, and every stored ruleset already carries whatever skips its operator kept); the substrate stamping its own endpoints (its env var is set at dispatch, after `process (start)`, so the stamp would arrive too late for the entry that names the worker); a `Rule` property marking a rule's matches as worker traffic (a sixth knob, its serialization and its editor control, to say what a few literal paths say). **Revisit when** every substrate controller publishes its route path as a constant or filter this plugin can read, at which point the copy becomes a read, or when a platform request is seen in the overview's global totals, which is the symptom this decision accepts.

## Decision 28: The writer ranks each bucket and indexes each name, and the page reads those rather than the index

Folding the whole URL index answers every question about the URL set, and costs the whole index: sixteen shards across every flame-builder partition's store over the whole read plan, 18,432 keys and 54MB on a hub holding 689,800 distinct URLs in its window, decoded and merged by hash. That fold measures 29 to 38 seconds on such a hub, and the overview polls it once per tab; [decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived) forbids memoizing the merged index because nothing bounds its row count. What the dashboard asks for is a page: the top hundred rows by one sort key, `URLS_PER_PAGE`, or the rows whose name carries a word. So the WRITER answers both questions while it already holds the data, and the reader reads its answers.

`Flame_Builder_Node` writes one ranked list per `Stats_Store::URL_SORTS` key and `URL_ORDERS` direction for every server a bucket's server index names — fourteen a server, empty where the server holds nothing rankable, so a reader tells a server ranked idle from one whose lists are missing — as `urlrank_s` and `urlrank_sh` (schema in [decision 1](#decision-1-namespaced-memcache-schema)'s table). **The site's lists are the writer's too** ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item): a site-wide aggregate is one key, and a site list of `URL_RANK_N` entries is one item): `ranked_writes()` ranks each sort's site list once as it writes the servers', over the union of the rows their lists of that sort hold, which cuts where one list over all their rows would, so a site page reads one list a key a partition. Merged at read time instead, it cost every site poll the merge of every server's lists — 2.6s of CPU for one page on a 9-server, 4-partition staging hub *(Chris, 2026-09-28)*. That merge is exact because URLs are disjoint by server: a URL names its host. A tie breaks by hash, ascending in both directions, in the one `Stats_Store::rank_order()` the writer and the merge both call, because source order is the one tie-break a merge of two servers' lists cannot reproduce. An entry is positional ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)): the hash, the row's thirteen scalars, and on the `url` lists the path. The union of the per-shard top-N is exactly the server's top-N for the bucket, because every URL lives in one shard, so one ranking over the merged shards is enough.

**A bucket is ranked over its whole STORED content, not over the flush.** Each row intent collects what its write produced through the intent's `landed` closure, and `rank_flushed_buckets()` reads back — in ONE multi-get per chunk of buckets — only the shards of either family each bucket's index names for a server that this flush did not land: a shard the index does not name holds nothing to read back. A chunk is at most `WRITE_BATCH_KEYS` over the thirty-two shards (15) (server, bucket) groups, and a bucket is never split across two, so a ranking holds no more rows than a write chunk does. Ranking the flush's own rows instead would rank one worker's slice of five minutes and call it the bucket. The ranking runs per `flush_writes()` chunk rather than after the flush, so a replay spanning the window holds a chunk's buckets rather than the window's. One server's row writes in one bucket, both families, form one ranking GROUP — thirty-two keys — and `flush_writes()` chunks by `WRITE_BATCH_KEYS` without splitting one, and a bucket ranks once every one of its groups has landed, from every shard, rather than off whichever part of it the first chunk carried; a bucket a failed chunk left short ranks after the flush from what the store holds. `Stats_Store::ranked_writes()` is the one entry to ranking and takes every server's rows at once, answering with all their lists, because a caller left to enumerate the servers itself is a caller that can forget one; `write_url_ranks()` chunks those writes the way the flush does.

**A bucket's lists are rewritten at most once a minute.** The page cache holds a ranked page for `Stats_Store::URL_PAGE_REFRESH_S` (60 seconds) and the dashboard polls against that, so ranking every five-second flush spends twelve rankings on one read. The reader's TTL and the writer's cadence are ONE constant, on the store both read, because they are one number. Under traffic a ranked row lags live traffic by up to twice it plus `Flame_Builder_Node::FLUSH_INTERVAL_SEC`, because a ranking waits for the flush it runs in. The header takes the same bound: its window always holds the open bucket, so `url_header()` caches it for `URL_PAGE_REFRESH_S`, and a server filed after the site record's last ranking is short from the header no longer than its rows are from the lists. Only a MISSING record is lag, in the open and just-closed buckets, and a hole older than that *(Chris, 2026-09-28)*. The flame builder flushes from its Router-tick timer whenever it owes work — a record folded since the last flush, a bucket still pending, a stale hour, an hour its data clock has left that it has not rolled up, or auto-tune decisions a lock held back — so on a partition that goes quiet a deferred or closed-bucket ranking still runs at the next tick it comes due, and a stale hour at the next flush with room under its bound. Two constants that happened to be equal would drift the first time either moved, and nothing would fail. A bucket that has CLOSED since it was last ranked is ranked whatever the cadence says, because nothing will come back for it. A bucket the cadence defers drops its collected rows and is remembered as PENDING instead; `rank_owed()` runs at the end of every flush and ranks each one that has come due, in those same chunks, gap-filling every shard of both families that the bucket's index names for each server from the store, which is the whole content it ranks anyway; every due bucket ranks in that flush, and only the batch is bounded. Every ranking ends its owing whether its lists landed or were refused: a bucket is stamped and leaves the pending memo, and an hour leaves the stale set. `rank_due()` tests buckets alone; a stale hour has no cadence and ranks at the next flush with room under its bound. **No list is written that cannot fit one item** ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item)) *(Chris, 2026-09-22)*: a list is top-N bounded BEFORE it is written, so a refused list is a wrong N, a bug the `URL rank write refused` line names, never a size this path copes with. The flush logs a refusal through the rate-limited `print_less_often()`, counts it as attempted and does not retry it; a transient Table failure heals at the ranking the next write into that key brings. The same rule covers the fold, whose refused row, name or list write is logged and not retried by the flush — a worker's first roll-up reads every hour of the plan afresh and folds again one whose server index or row shard is missing, while its fine buckets last — and the token index, whose refused writes are logged and leave their URLs unfiled under those words until the name refresh files them again. The shutdown sweep's flush ranks every bucket still owed whatever its stamp, because the pending memo lives in memory alone and dies with the worker. It ranks no more stale hours than any flush does: every stale hour is one the roll-up found folded with no marker, and the store still holds it that way, so the next worker's roll-up finds it again. The pending memo is what reaches a bucket nothing writes into again — the closed-bucket clause fires on a WRITE, and a bucket whose last writes landed inside the cadence gets none once it closes, so its final rows would otherwise never reach its lists. Both memos are pruned below the oldest bucket of the read plan's fine tail, and a flushed bucket below it is not offered to the ranker at all; `flush()` builds that plan once and hands it to the roll-up and the ranker; the stale set is pruned to the read plan's hours in `roll_up_hours()`, because no reader plans an hour the window has passed. One flush ranks at most `ROLLUP_HOURS_PER_FLUSH` stale hours, the same bound as the folds, since a stale ranking holds an hour's coarse rows as a fold does; a stale hour spends none of the fold budget, because ranking it is not a fold. `set_stats_store()` drops the read plan alone, since the retention window it was built over may have changed, and keeps every other memo: a second `configure_stats` rebuilds the store over the same three Tables, because each `set_*_target` verb refuses any Table but the one the readers mount, so the memos still describe it, and emptying them would lose the rankings the pending memo owes, which live in memory alone. On the HOUR tier each server's DONE marker, `urlrank_sh:{hour}:done:{server_key}`, rides that server's ranking batch whatever its lists answer, and `url_hours_derived()` reads it, naming every server the hour's index names whose marker is missing: it says the ranking ran, and every list that ranking wrote stands beside it until its TTL, because nothing evicts a Table row. One marker stands for every list set of its server, so a late worker write into a folded hour also takes the hour off the reader set's page, which reads it as waiting until the re-rank lands, within the per-flush bound; that is accepted, since a marker per family would double the markers to shorten a gap the next flushes already close. A list the Table refused is a hole `ranked_page()` folds around, and decision 30's bound makes that a bug the `URL rank write refused` line names. `url_rank_window()` answers a site hour only where every server its index names has its list, and `ranked_page()` folds the page otherwise. The marker's value is empty, because its PRESENCE is what it records.

`roll_up_hours()` reads those markers and branches three ways. An hour folded with every server marked is memoized and skipped. An hour folded with any server unmarked — one whose marker was refused, or one a late write landed in — joins the stale hours, and `rank_hours_from_store()` re-ranks every server of it from its STORED coarse rows, never folding it again: its fine buckets may be gone, and a second fold would overwrite the hour with nothing. An hour that is neither is folded and ranked in one pass while the flush's fold budget lasts, and past it waits for the next flush; the roll-up still memoizes every folded hour behind it. A write into a folded hour ([decision 19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in-and-a-write-into-a-folded-hour-reaches-its-fine-bucket-and-the-hour-key)) goes to its fine bucket and into that hour's key, and an hour-key write that lands forgets its server's marker, so the hour turns stale and a flush re-ranks it from the store within the per-flush bound; a refused hour-key write is logged and the key keeps what it held. Same-key intents compose in `add_intent()`, as the flush BUILDS its intents: they are filed by cache key, and each merge receives what the one before it produced, so two fine buckets of one folded hour both reach the hour key rather than the second discarding the first. One key is therefore one intent for the whole flush, which is also why no key can straddle two chunks.

**A list ranks by the BUCKET's own value, and the two averages are means of bucket averages.** `url_rank_value()` ranks `avg_ms` on `sum_ms / timed_count` and `avg_peak_mb` on `sum_peak_mb / count` over that bucket's row, so a page hit rarely but slowly ranks on how slow it is; ranking by the window's totals would hide it behind every busy page *(Chris, 2026-09-22)*. `ranked_page()` then presents the mean of the per-bucket averages the URL ranked with, each at its own tier — a five-minute bucket inside the fine tail, a folded hour behind it — every stored bucket weighing the same, so an hour entry contributes one average covering an hour where a fine entry contributes one per five minutes, and nothing reweights them. That is a different number from the fold's request-weighted mean over the window, so the reply carries `ranked` and the page says so. Every other field folds through `fold_index_row()`, exactly as the fold merges it.

**The reader pages from the lists only when they can answer the whole question.** `ranked_serves()` requires no `search`, no `bucket` and an `offset + limit` inside `URL_RANK_N`; anything else folds. `include_workers` and `errors_only` each read list sets of their own (below). Both tiers are known before the first read, so `ranked_page()` asks each store for every planned hour AND every bucket of the current hour in ONE round trip, and no more. A planned hour that ANY store has FOLDED and holds no list for is a HOLE and takes the whole page back to the fold, which reads the hour's rows, because serving a window an hour short as ranked is worse than folding. **An hour the writer still owes is no hole** *(Chris, 2026-09-29)*: one holding no index, or one a server its index names has no DONE marker for, waits on the builder's data clock ([decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)) or on the re-rank a late write owes. `Stats_Store::url_rank_window()` and `url_headers()` read each such hour's markers in the batch that reads its lists or records, so the markers cost no exchange, name the hour in `$waiting`, and answer nothing for it. The page and the header add nothing for it and say `provisional`, so no cache keeps them. Folding for it would buy nothing, because its rows are not in the coarse tier yet, and the whole-index fold, 26 to 42 seconds of CPU on the staging hub, would run at every poll of a replay. The fold stays for an hour whose markers stand and whose list or record is missing: a refused write the marker's batch landed beside, which nothing but the hour's rows can answer. A window where no hour and no bucket answers any list still folds (`fold: no lists`), and there the fold reads only what stands: no coarse key of an unfolded hour to walk. The hour just closed is the exception while the current hour's first bucket is open: the writer may still owe its fold, so its missing list is lag, skipped and `provisional`, as the header skips a lagging record. **The header is the WRITER's** *(Chris, 2026-09-28)*. On the eln staging hub the first poll after every bucket boundary spent 26 to 42 seconds of CPU folding the whole URL index, 757,445 rows, for the header alone, and a poll arriving during that fold started its own. `ranked_writes()` writes each server's header record beside its fourteen lists and the site's after them: the four sums over every row of its list set the key holds, the overflow rows included, whether one was among them, and a `Url_Sketch` of the rest, a HyperLogLog at precision 14 whose registers merge by per-register max, so the union of any set of records counts a URL once. The sketch is stored as the raw deflate of its 16,384 one-byte registers (`Url_Sketch`), inflated only inside a union or an estimate, so both are exactly what the raw registers gave: deflated at zlib's fastest level, since a record is under 1% of a ranking's bytes: an empty sketch is 89 bytes, one of 50 URLs 276 and a dense one 7,508, and a record over the sketch about 47 bytes more under igbinary, where every record carried 16 KiB raw. `HDR_VERSION` 4 is that layout, so a v3 record reads as missing, and nothing reads it again: the flush of [decision 5](#decision-5-a-stats-schema-change-is-migrated-by-the-tables-flush-and-by-nothing-in-this-code) orphans such a row, as it orphans every row. The sketch reads its register from xxh64 of the url_hash rather than the url_hash itself, because FNV-1a's top bits barely move between URLs that differ in their last characters: read raw, 4,217 sequential post URLs estimate 3,424. `url_header()` sums the records over the read plan, one multi-get per store after the index's, the rate from `recent_keys()`' records and `slowest` from the `avg_ms` lists, each URL weighted by request over the entries it made, and holds the result under the scope, the window bucket, the retention and the store count for `URL_PAGE_REFRESH_S`. A record missing where a key's index names the scope is a HOLE, stricter than `url_rank_window()`, which skips a fine key it holds no list for: a header summed over a window with a key missing understates the traffic and still reads as the site's. The open bucket is the exception: `rank_due()` ranks it at most once a `URL_PAGE_REFRESH_S`, so a server its index names before its first ranking there is lag, skipped as the lists skip it rather than folding every poll of that server for the bucket's life. So is whatever closed last, for the whole of the bucket after it — the bucket before, or in the current hour's first bucket the hour just closed: the writer ranks it at its first flush after the close and folds it once its data clock has left it ([decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)), one flush after the next hour's first record or `Flame_Builder_Node::IDLE_AFTER_SEC` after a quiet builder's last drain, but that flush rides the Router tick unaligned to the boundary and its ranking takes time of its own, so no clock window holds it, and a window wrong by a second is the 26 to 42-second fold again. A header that skipped a lagging record says so with `provisional`, which the dashboard shows beside the totals and the `overview:` brief carries, and is served but never cached, nor is a page carrying it, so the next poll after the ranking lands reads the record. The records' `slowest` never carries the overflow row the fold's may, because no list ranks one. So a hole folds, and the ranking the builder owes its key fills it, which keeps the fold from being routine. The fold remains for a page past the list depth and a hole; a search reads its candidates by key and folds nothing (below).

**A header hole folds the page the poll answers with.** `ranked_page()` asks for the header BEFORE it reads a list, and a hole folds this page — the caller's sort, order, offset and limit — and returns it whole rather than throwing away a `0, 0` fold and then reading the lists as well. So the poll that pays for the walk answers with what it walked, `ranked: false`, and the next poll inside the bucket reads the lists. Both entries are read THROUGH `Table_Node::backed_by()`, the substrate's own read-through, rather than a lookup-build-store wrapper of the reader's; a `provisional` build states `ttl => 0`, which serves it without warming the cache, and so does a fold that may be short of an hour the writer has yet to fold. The page SHAPE rides in the key as an md5 of its field list, because a read-through cannot report a stored value missing a field this reader needs. The reply also carries `as_of`, the page's build time, cached with it, which the dashboard measures each row's `Last seen` age from.

**Four list sets, each a key part** *(Chris, 2026-09-29)*. Every ranking writes its lists and records for each of `Stats_Store::RANK_SETS`: every reader row, under no part of its own; the reader rows that errored, after `e`; every worker row, after `w`; and the worker rows that errored, after `w:e`, each after the time key — `urlrank_s:{bucket}:w:e:{server_key}:{sort}:{order}` and `urlhdr:{bucket}:{HDR_SHAPE}:w:{server_key}`. A set is its key parts, so a further subset is one more part and the reader set's keys carry none. The families come from the shards: `ranked_writes()` takes each server's shard maps and merges each family's apart, so a hash filed in both stays one row in each. A page reads the sets its filters name (`Stats_Store::rank_sets()`) through the same `url_rank_window()` and `url_headers()`, every set in one exchange per store, and merges them by hash, and no hash sits in both families, since every request to a worker's URL is a worker's (decision 27); its header counts each set's overflow row apart, as the fold counts `Other` and `Other:worker`. An `include_workers` page and an `errors_only` page read lists and fold nothing, where each walked the whole index: one `--include_workers` page on the staging hub spent 25.4 s and 190 MB in `url fold` over 800,728 rows, at every minute's poll.

**`errors_only` is the buckets where a URL errored** *(Chris, 2026-09-29)*. A URL's row, the totals and the slowest ten count the traffic of the keys it had a timeout or fatal in — a five-minute bucket inside the current hour, a folded hour behind it — and none of its clean traffic. `Stats_Store::errored_rows()` is the one definition, a key's rows whose `ROW_ERRORS` is positive, overflow rows dropped: the writer ranks those rows as the errored sets, and the fold applies it to each key before it merges, so the two agree by construction. The filter used to test the window's merged row, which no writer can rank, because a key's list cannot know that a URL errs in another key: on eve 427 of the 505 requests of the URLs that errored ran in keys where they did not, so errored lists under that meaning would have missed four fifths of the traffic the fold counted. An errored set ranks `count` by the errors (`Stats_Store::rank_key()`), as the page sorts it, and its header records carry `HDR_ERRORS`, which `totals.errors` sums. **A timeout carries no duration**: its request counts toward `count` and `errors` and never toward `avg_ms`, so a row with no timed request ranks last on the three timed sorts in either order, in every set, as the fold orders it ([decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)). The lists used to leave such a row out, which dropped a timeout-only URL off the errors page's `avg_ms` sort. **A tie breaks by hash in both paths**: `Stats_Store::rank_order()` falls back to the hash, ascending either way, for the writer's lists and the fold alike. **An error is a timeout or a fatal, counted by its own field** *(Chris, 2026-09-30)*. `Flame_Builder_Node::error_counts()` adds one to `ROW_ERRORS` for a record stamped `T` or `F`, whatever status it answered, beside `timing_counts()`, which it never reads: a fatal answers a 500 in a measured duration, so it is timed AND errored, and a timeout is errored and untimed. The field replaced reading an error as a request no status class counted, which missed every fatal, since the 500 files it under `count_5xx`, and counted every CLI worker request, which answers status 0. An abort (`A`) is not an error: it is the logger's own worker stopping mid-request. Nor is a gap (`I`), which is missing detail ([decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time)); `Request_Builder_Node` stamps it over a nominal finish only, so a fatal with a hole in its trace stays `F`. The URL modal's "Errors Only" keeps the same two, on the server: `dump_url --errors_only` walks with `Flame_Builder_Node::error_counts()`.

**Exactness is the same in every set, and it has a direction.** A merge by extreme is exact only in the direction it merges: a URL at the head of the window on `max_ms desc` holds its window maximum in some key and ranks in that key's list behind fewer than N rows, so the union of the per-key lists holds the window's top N. That makes four sorts exact on the sort key and the order: `url asc` and `url desc`, whose key never changes, `max_ms desc` and `last_updated desc`. The other ten may be approximate: `min_ms asc`, because a key's list ranks a URL untimed there at 0, so its timeouts take places that URL's timed minimum elsewhere would not, and a URL listed by its timeouts alone carries no minimum; `min_ms desc`, `max_ms asc` and `last_updated asc`, where a URL whose extreme sits in a key that cut it ranks on a lesser one; `count` (the errors under `errors_only`), which sums the keys a URL made the list in; and `avg_ms` and `avg_peak_mb` both ways, a mean of bucket averages. **The bound is the same on every sort**: a ranked row is the fold's row restricted to the keys where the URL made a list, so its `count` and `max_ms` never exceed the fold's, its `min_ms`, where it has one, never falls below it, and its means lie between the smallest and largest per-key means of that URL. `test_a_page_over_urls_spread_across_cut_lists_is_exact_or_bounded` holds both, on two keys of `URL_RANK_N + 5` rows over URLs spread across both. The pages equal the fold's row for row only where each URL sits in one key whose list holds it, which `test_an_include_workers_ranked_page_is_the_fold_s_page` and `test_an_errors_only_ranked_page_is_the_fold_s_page` hold for all fourteen sorts.

**A search reads a token index, so it names its candidates instead of reading every name.** `urltoken:{bucket}:{server_key}:{word}` is a set KEY on the durable Table's set members (substrate 2.76.0): each member is the hash of one URL of that server whose path carries the word, filed in the six-hour bucket `{bucket}`, valued by the unix second that URL was last named, filed under the server its rows are filed under, its own, under each distinct WORD of its path as `term_tokens()` spells it: the path lowercased and split on every non-alphanumeric run, each run of `TERM_WORD_MIN` (2) characters or more, cut to `TERM_WORD_MAX` (12). A search term's words are looked up the same way. `Flame_Builder_Node::persist_url_tokens()` files the names `persist_url_names()` wrote, one blind `SADD` per `WRITE_BATCH_KEYS` (500) sets: a member needs no read to union with what earlier flushes filed, so nothing is read first and no set is rewritten whole. A URL costs one member row per distinct word, two for `/wombat-7731`. Re-adding a live member in the same bucket replaces its row and creates none. A member lives `filing_ttl()` from its last add, so filing a URL again refreshes it, and a URL no flush names again leaves the set when its member expires, which the Table's purge reclaims. A refused add is logged and tallied `refused urltoken`, and its URLs stay unfiled under that word until the next hour files them again.

**A URL's words are filed at most once an hour per server** *(Chris, 2026-09-29)*: one `SADD` row per word per URL per hour the URL is seen, with its `urlmap` name beside it. The URL's blob in `flame-stats:url`, which the flush reads and writes anyway, carries `filed`: server key => the hour the URL was last filed under that server. `persist_url_names()` skips a pair stamped with the current hour, and `drain_url_stats()` stamps the pairs it filed into the blob it writes, so the rule survives a worker recycle and costs no read and no write of its own. A blob without the stamp, or a URL whose blob the flush does not hold, reads as never filed. The rule was once the builder's in-memory memo, which a recycle every 595 seconds emptied, so every active URL re-added all its words about six times an hour only to refresh their expiry: on the eln staging hub's `flame-stats:aggregate` that was 31 `SADD` calls of 7,150 member rows, 1,879 ms and 44% of the Table's time, and a checkpoint writing 83,869 frames back, 1,686 ms and 39%. **A filing lives as long as the rows it indexes are read, plus one refresh.** A URL's last filing can come up to `Stats_Store::HOUR_SECONDS` + `Flame_Builder_Node::FLUSH_INTERVAL_SEC` before its last row, so a filing that lived only as long as that row is read would retire while the row still is: a URL seen late in its last hour would drop out of search early. `Stats_Store::filing_ttl()` adds that span to a base each call site takes from its readers, so a refresh can never be late for its filing and no window needs refusing. A `urltoken` member serves search, which reads rows over `window_start()`, so it lives the window plus the refresh. A `urlmap` name serves every reader that turns a hash into a URL — the page, `dump_url`, `ask url:` — over rows the aggregate Table keeps for its whole TTL, `Stats_Store::aggregate_ttl()`, the `<eln:stats_ttl>` it declares and never under the 25 hours a chart reads, so it lives that TTL plus the refresh, and a URL seen 13 to 25 hours ago still resolves by name without reading every server's keys. `Config` resolves `<eln:stats_ttl>` through the same `aggregate_ttl()`, so the name cannot drift from its Table. The extra hour costs the read side nothing: `token_buckets()` bounds which buckets are read, a candidate with no row in the window yields no result row, because a search builds rows only from the `url_row_h` values its keys return, and `url_token_sets()` drops every member valued before `window_start()`. Every URL whose rows the window reads was filed inside it, at or after the start of the hour its row falls in, so the drop is exact, and a stale member never counts toward `URL_SEARCH_MAX`. A set the Table answers over-limit still counts every live member, stale ones included, because the limit is the Table's. `FlameBuilderTest::test_a_url_seen_late_in_its_last_filed_hour_stays_findable_until_its_rows_leave_the_window` pins both edges.

**The search index is clustered by time** *(Chris, 2026-09-29)*. `{bucket}` is the six-hour window's start, `Stats_Store::token_bucket()` spelling it as an hour key is spelled, and it follows the namespace as [decision 1](#decision-1-namespaced-memcache-schema)'s time key does, so every add of one flush lands in the current bucket's key range, and the hourly refresh rewrites a URL's row in place for five hours of every six. `TOKEN_BUCKET_SECONDS` argues the width. The cost is at most `ceil( window / 6 h ) + 1` member rows per word per URL, 3 at the 12-hour default, and that many set reads per word per server per search: `Stats_Store::token_buckets()` names every bucket from `window_start()` to now, so a window past a day reads the buckets of the 25 hours a reader reads, not the whole retention. What clustering saves in pages depends on how full the current bucket is, measured on a SQLite `members` table of the Table's own schema holding a 12-hour window of 40,000 URLs, 2,000 of them seen every hour and the rest once. One `SADD` of 256 rows scattered across words dirties 326 pages unbucketed and 336 bucketed: a single add gains nothing. The hourly refresh of all 2,000 active URLs, 8,000 rows in one flush, dirties 3,030 pages unbucketed, 1,877 in the middle of a bucket and 475 in a bucket's first hour. The saving is mostly the rate: about six refreshes an hour of about 3,030 pages each became one of 475 to 1,877.

**A word too common to narrow is one of whose buckets' sets holds more than `URL_SEARCH_MAX` (5,000) members, or whose buckets together do.** `url_token_sets()` asks each bucket's set for `URL_SEARCH_MAX` members, an exact-key seek with a limit; a set holding more answers the Table's over-limit marker and no member, which `Table_Client::members()` reads as `null`, so the reader never holds the members of a word it cannot use. `url_token_sets()` answers `false` for a word any of whose sets is `null`, or whose buckets' union for one server passes `URL_SEARCH_MAX`, so the word narrows nothing, as the saturated sets of the whole-set shape did; otherwise the word's candidates are that union. A term's words are read longest first, `SEARCH_WORDS_READ` (3) to an exchange (`Stats_Store::search_groups()`), because each word read costs up to `URL_SEARCH_MAX` members for every server searched, and a caller's term must not set that multiplier. Three are enough to narrow: the intersection is at most its smallest set, and the walk still holds every candidate to every word of the term. The next three are read only when every word of the last is over the limit in some store, so `blog 2026 category post` narrows on `post` when its three longer words are all too common; a group all over the limit held no member, so reading on keeps the bound. Whether a group narrows is the site's answer, so every store reads the next group together. The saturation sentinel goes with that shape: it existed because a set stored as one value had to be read whole, pruned and rewritten on every flush naming the word, and past the cap a set of five thousand stamps rewritten per flush was the cost to stop paying. Members are added one row at a time and expire one row at a time, so nothing needs stopping; the limit on the read is the only cap, and a common word stops narrowing exactly while it has more than `URL_SEARCH_MAX` live members, and narrows again once enough of them expire. A reader reads one thing off a member's value: whether it was filed before the window.

**An identical write is not a write, in every namespace.** `flush_writes()` compares each composed value with the one it read and drops the write where they are equal, so the key keeps the TTL it had. [Decision 1](#decision-1-namespaced-memcache-schema) makes a key's TTL the retention mechanism, and this is what keeps that honest: a write refreshes a lifetime only where something was ADDED. For a namespace keyed by bucket or hour it never binds — such a key has an intent only when the accumulator holds data for it, and data always adds. The search index is outside it: its members are rows the flush adds blind, not a value `flush_writes()` composes, and a member's lifetime is refreshed exactly when its URL is filed again, at most once an hour. A namespace wanting a touch to mean "still current" has to add something the merge can see.

`search_candidates()` intersects the term's words across every store, smallest set first. Each store answers in one `SMEMBERS` exchange (`Stats_Store::url_token_sets()`): a scoped search reads its one server's sets, and a site search the sets of every server an index across the read plan names, which costs a site search one index read per store before it. It skips any word the store could not answer. A term with no word is REFUSED, and so is one too common to narrow, every word it read over the limit or more candidates than `URL_SEARCH_MAX` across every server. A read left unanswered names no candidate: the page has no rows and reads `provisional`. One unanswerable word among several narrows nothing and costs nothing: the others still name the candidates, and the walk matches the whole term against their paths anyway, so a term carrying one word too common to narrow does not fold the site. WHICH words can be answered is the schema's: `url_token_sets()` returns `false` for one whose set answers more than `URL_SEARCH_MAX` members, or for every word when the read went unanswered, which also sets `provisional`. A word nobody holds is a real answer, an empty set: it reads no row and answers zero totals. A search never sets `estimated`, which belongs to the header records alone.

**Search is the token index, and every candidate is checked** *(Chris, 2026-09-29)*. Nothing stands behind the index *(Chris, 2026-10-04)*: the name scan, the fold that walked every name for a term the index could not answer, is deleted, so a term with no word is refused, saying a search needs a word of `TERM_WORD_MIN` characters or more, and one whose every word is too common is refused as before. Whatever the sets resolve to, every candidate is checked against the whole term by `term_matches()` on the path its own row carries, which the key read returns anyway, so the check reads nothing more and no candidate is cut: the totals and the page count every row that passes. A row whose path was cut at `MAX_PATH_BYTES`, ending `…`, is taken on the index's word for the words it answered, because the cut may hide them; `search_candidates()` reports the words it could not answer, and the cut must keep each of those. That is verification, not a scan of names: a word too common to narrow narrows nothing, yet every URL returned carries it, so `category shoes` with `category` that common returns the URLs whose paths carry both words. No `urls --search` walks names beyond its candidates.

The read that follows reads each candidate's row by key, and matches the term against each candidate row's own path, which the row carries ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)). `term_matches()` matches each word as a whole WORD of the path there, as the index files them; only a term that tokenizes to nothing is a substring match. Two readers share one spelling apiece: `Stats_Store::path_of()` is the one place a reader takes the path out of a URL, and `Stats_Store::token_sets_of()` is the one tokenize-and-group, used by the writer and by the test helper alike.

**A search reads its candidates' rows by key, and never folds** *(Chris, 2026-09-30)*. Mapping candidates to their shards narrowed nothing: a shard is a hash's first hex digit, so a few dozen candidates cover all sixteen, and the walk read and folded every row of each shard over every server and hour before it kept the candidates. On staging `urls --search=performance --include_workers=1` spent 13.6 s in `url fold` to keep 406 rows, and the fold was about 90% of it; `urls --search=v1/` named 3,068 candidates and spent 13.5 s there. So the writer files each URL's row where a URL's key reaches it: `url_row_h:{Y-m-d-H}:{server_key}:{hash}`, one value a URL-hour a server, beside the shard it already writes each flush (`Flame_Builder_Node::url_row_intent()`), holding the path once and, for each family, the row the flush merged into that bucket's shard in the bucket's slot (decision 35's geometry). `search_candidates()` keeps which servers' sets named each hash (`Stats_Store::url_token_sets()`'s `$named_by`), and `candidate_rows()` asks each store in ONE exchange for the value of each (hash, server, hour) whose server index names that server with the hash's shard, over the read plan's hours and the current hour, and folds it through the same `fold_index_row()` in the order the shard walk folds: a folded hour as the sum of its slots, as the hour fold sums its buckets, then the current hour's buckets slot by slot, each only where that bucket's index names the shard, so an unfolded hour is read by neither and `provisional` says so as before. A searched row is therefore the row the table shows, `errors_only` and `include_workers` included, and `load_row()` — `dump_url`, `row()`, `ask url:` — reads the same way, one URL's keys where it read a whole shard per family. The one place it can differ is a row a shard's byte cap folded into `Other`: the shard folds that URL's traffic there, and its `url_row_h` value, capped by count, still holds it. **A term with more candidates than `URL_SEARCH_MAX` across every server is refused** rather than read wider, and so is one whose every word read is over that limit: the refusal names the limit and asks for another word. Past it the key read would cost about a second on eve, 20,000 candidates for `piece`. Nothing stands behind the index: only an unsearched page walks the shards. *What it costs:* one more read-modify-write key per URL-hour per server a flush, beside the `url_dim_h` and `url_cat_h` keys the flush already writes a URL-hour, at most twenty-four rows and a path a value; and a search reads one key per candidate, server and planned hour, where it read every shard.

**A bucket names its URLs through a set of its own** *(Chris, 2026-10-05)*. `urlbucket:{bucket}:{server_key}` is one set per five-minute bucket per server in the aggregate Table, its members the hashes of the URLs that server filed rows for in that bucket, either family. A worker files each URL once per bucket in its life: `Flame_Builder_Node::persist_url_buckets()`, beside the token index, adds the hashes of the flush's buckets, both families, that its memo `$filed_buckets` does not hold, and a set that lands joins the memo, which keeps a bucket while it is at or above the read plan's fine tail, the floor `write_pending()` computes, which turns with the hour, or while a flush still holds it. A refused add never joins it: it is owed in `$owed_buckets`, and every flush adds it again, whatever that flush holds, until it lands, or until its bucket falls below that floor with no flush still holding it and it is dropped. A restarted worker starts with an empty memo, so it files the URLs whose slots an earlier worker wrote before it. **The hour's fold files them again** *(Chris, 2026-10-05)*: `fold_hour_into_store()` already reads every shard its twelve buckets' indexes name, both families, so `refile_buckets()` adds each bucket's hashes, both families and no `Other` row, to that bucket's set of each server, through the same `file_sets()` and its tallies, one `SADD` per `WRITE_BATCH_KEYS` sets, reading nothing more. It runs once a fold, which `$folded_hours` already bounds to once an hour and `ROLLUP_HOURS_PER_FLUSH` hours a flush: a refused add its bucket aged out of the owed list lands there, and a URL already filed is added again, harmlessly, its value and expiry refreshed. A stale hour folded again for a missing shard files again; one ranked from its coarse rows does not, because an hour row names no bucket, and placing each URL would take one `url_row_h` read per URL the hour holds, where the ranking reads at most 32 shards a server. What the fold cannot heal: a URL a shard's byte cap folded into `Other`, which its `url_row_h` slot still holds but no shard row names; a refused add whose shard write was refused too; a refused add a late write made into an hour already folded, once its bucket ages out, since that hour ranks from its coarse rows; and a bucket whose fine shards expired before its hour folded. The adds are blind, through the token index's own `Flame_Builder_Node::file_sets()`, read no row and carry no hook in `flush_writes()`, and a member lives the aggregate Table's TTL and one refresh (`filing_ttl()`), as a `urlmap` name does: at least 26 hours from the bucket's first row, past the 25 hours its rows are stored, so every bucket a reader may ask for can list its URLs. **`--bucket` takes a selection** *(Chris, 2026-10-05)*: a set of bucket keys spelled as comma-separated runs, each `start` or `start..end` over `Y-m-d-H-i` keys, ascending, adjacent buckets merged into one run (`2026-10-05-16-55..2026-10-05-17-10,2026-10-05-18-30`). `Stats_Store::bucket_selection()` parses a spelling to its sorted keys, each once, refusing a piece that is no five-minute key, a run ending before it starts and more than `MAX_READ_BUCKETS` (288) buckets, each refusal naming the piece or the limit; `bucket_spelling()` writes the canonical spelling that `filters.bucket` and both briefs echo. `tests/fixtures/bucket-selection.json` holds this pair and the dashboard's JS pair to one case list. A reply reads through the selection's plan (`plan_for()`): `fine` is its keys newest first, `recent` gives each key 300 seconds, so the rate is the count over 300 × keys, `floor` is the earliest bucket's start, `spans` is the set of the selected buckets' starts its request walk keeps, null exactly for the window's plan, and `bucket` is the canonical spelling the echo, the briefs and a refusal read, `''` for the window's. **A bucket is valid while its rows are stored; every bucket the charts draw is.** `assert_bucket()` checks each key of the selection, accepting one no later than the current bucket and opened inside `Stats_Store::aggregate_ttl()` of the stats window, the lifetime of its `url_row_h` slot, at least 25 hours: so a bucket picked at the chart's 24-hour edge stays valid while the table and the modal poll it. A key off the grid is refused by the parser, and a future or aged-out key with an error naming it. The request walk places a request in a selected bucket by `Flame_Builder_Node::completed_at()`, its start plus its duration rounded to the second, the expression the builder files its stats by, so the list and the slot agree; only the builder clamps that second to the tick the record reached it, which no reader can know. A URL with no slot in any selected bucket answers the zero row, counts 0 and means and `max_ms` null ([decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)), and an empty list, when its stored `urlmap` name, which lives as long as the bucket's rows, names the scoped server or no scope is asked; with no such name, when the window holds a row for it. A hash no stored row or name carries is `URL not found`. `ask` plans the selection only for the `overview:` and `url:` briefs it narrows, which carry its canonical spelling, so every other descriptor ignores it and refuses nothing for it. The page's candidates are the union of its buckets' sets, read one `SMEMBERS` exchange an hour, every selected bucket of that hour in it, newest first, so a store spends one exchange an hour the selection touches, 25 at most under the default retention, however many buckets the selection holds (`Stats_Store::url_bucket_members()`), keeping the hours whose buckets each server's set named each hash in: the scoped server's, or those of every server `indexed_servers()` names, each bucket's own index merged with its hour's (`plan_index()`) — and each partition reads only the hashes its own sets named, because a set names the URLs its partition filed rows for (`bucket_candidates()`). Each candidate's row folds, under each server, the selected slots of the hours whose buckets' sets named it there, read only under those hours, never every hour of the selection, so a bucket whose filing was refused still folds its slot when another bucket of its hour named the URL; the servers fold in the index's order, the order the shard walk folds them in, so the rows read are bounded by the pairs present, one read per hour key however many of its slots the selection holds, summed slot by slot as the window's fold sums them and never as an hour's whole sum, so the row, the totals and `errors_only` are the selection's, and the page is folded, never ranked. Under a selection a search checks the term on every candidate's path, because the token index forgets a URL a window and an hour after its last filing, before its bucket's rows go; it still reads the token index, because only the index vouches for a path cut at `MAX_PATH_BYTES`, and a cut path whose hash the index names passes when what the cut kept carries every word of the term the index could not answer. Where the index cannot answer — a term too common, which is no refusal here, a set left unanswered, or a hash it has forgotten — the path alone decides, and a cut path must carry the term in what the cut kept. A selection whose sets name more than `URL_BUCKET_MAX` (10,000) (hash, server) pairs across every bucket, partition and server, a pair counted once however many of its buckets name it, is REFUSED: the limit caps the whole selection, not each bucket *(Chris, 2026-10-05)*, as a term too common to narrow is in the window, because each pair costs a read by key. The read stops at the first hour taking the pairs past the limit, so a refused selection never reads its older hours' sets, and each hour's sets are asked for the budget left plus the most pairs any one server had named before that exchange: a set repeats only its own server's pairs, so one holding more is past the limit unread, and refuses the page. That bound stays sound with several sets in one exchange, because it counts a set's distinct members against what was held before the exchange. The next store reads only the budget the stores before it left. The bucket limit is twice a search's `URL_SEARCH_MAX` (5,000), so an unscoped bucket page answers on a busier hub, at the cost of a slower read *(Chris, 2026-10-05)*. A set, a token set or a server index read left unanswered answers what it can and reads `provisional`, and a URL's own row read under an unanswered server index, or itself left unanswered, is refused rather than answered as zero or not found.

**A search matches whole words, not prefixes or substrings** *(Chris, 2026-09-29)*. `/wombat-7731` is found by `wombat` and by `7731`; `wom` and `mbat` find nothing, because the index files whole words and the check behind it matches the same words. The search box's placeholder says so. Prefix-as-you-type is what it gives up, for an index under a third the size with half the saturated sets. Measured on the eln staging hub, as memcache sets:

A term whose every word is too common to narrow is refused. **The server scope rides in the KEY for the ranked lists** ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item)), as it does for the rows they rank: a list is `URL_RANK_N` entries per server, and URLs are disjoint by server, so the per-server lists together hold about as many rows as one site list would, not servers times as many. **`URL_RANK_N` is 200 on the fine tier and `URL_RANK_N_HOUR` 500 on the hour tier** *(Chris, 2026-09-22)*, 500 positional rows making a list under 60KB; a page deeper than 200 folds. **And a `count`-ranked page may be approximate** *(Chris, 2026-09-22)*: the union of per-bucket top-Ns is a superset of the window's top-N only in the direction the merge takes: `max_ms desc` and `last_updated desc` (see *Exactness is the same in every set, and it has a direction*), while for a sum a URL just outside every bucket's list can still be top overall and one inside some lists ranks on those buckets alone. An empty list is still written, so a reader tells a set ranked idle from one missing. The only rate a Table guarantees is one 5,000-row batch a minute, keyed rows first and members from what is left. While a batch comes back full, the substrate's catch-up purge spends up to 250 ms a tick (`Table_Node::PURGE_BACKLOG_BUDGET_S`) instead of 50 ms, but the one hub timing, 597 ms for a 5,000-row batch, spends that budget on the first batch, so on the hub the purge runs one batch a minute either way: 5,000 rows against a demand of 4,200 to 5,300. All of it in the worker, none of it in the request. *Alternatives rejected:* window totals maintained incrementally by the writer and EXACT — the window slides a bucket at a time, so the writer must subtract each bucket as it leaves, and an exact distinct count over 690,000 URLs is the merged index again, over the item limit per shard and a fold per flush to rank. The member rows are its row-per-URL half without the prefixes or the scan: each set is read by an exact-key seek, so no read ranges over a prefix. Reopen the deferred design when prefix search is wanted back, its rows are searched without a scan (a prefix scan took 2.3 s at p99, so no design uses one), and a staging measurement, purging only the keys it creates, with one file per partition, shows it fits. ## Decision 29: Every reader dates from the tick, and a reply reads it once

Every stats reader dates from `Core::$now`, never from a wall read of its own. That tick is not still: `Core::right_now()` writes it, so every caller re-pins it, in a worker and in a request alike. Two examples from this plugin, not a list: the firehose logger re-pins it once per line `Log_Manager::message()` writes, and a partition write lock taken inside a flush re-pins it as it is acquired. Loading the substrate's `Core` class pins it first, through `Core::reset()`, so a verb has a tick before it runs. A reader wanting one instant reads it once and passes it down, and a test pins `Core::$now` directly. The flame builder reads it once per flush, in `write_pending()`, the durable half that `flush()` and `save_state()` both run, and hands it to the hour plan, the name memo, the due test, the ranking stamp and the prune floor, with no seam of its own. `shutdown_sweep()` reads none: its flush reads the tick, and the stale hours it ranks after that flush need no instant.

**So a reply reads that clock ONCE, at its entry, and passes it down.** Any `right_now()` caller can advance the tick while a long reply runs, the firehose logger once per line, and a fold over a hub's index runs tens of seconds. Each `Performance_CI_Node` verb reads `self::now()` in its handler and hands the instant to every reader of the window beneath it — `read_window()`, `recent_keys()`, the read plan's floor, the page cache key, the header key, the `$load_index` seam and `as_of` — so one reply is one window: a page keyed under one bucket cannot be built from the next, and two panels of one overview cannot answer for different windows. `read_window()`'s memo stays, keyed on the bucket and the retention, because it saves the `gmdate()` per key; it is not what holds a reply together.

*What it costs:* a `$now` parameter on twenty-eight private `Performance_CI_Node` signatures and on the public `load_index_default()`, plus the `$load_index` seam's signature, which a test replacing the seam must match; a read plan each verb builds from that one read (`plan_for()`), which the URL readers beneath it, `load_row()` among them, take in its place; and an `int $now` on `flush()`'s callees in the flame builder — `drain_url_stats()`, `roll_up_hours()`, `persist_aggregate_stats()`, `persist_url_names()`, `rank_flushed_buckets()`, `rank_owed()`, `rank_buckets()`, `rank_bucket_chunk()` and `rank_due()` — which take the flush's one read.

*Alternatives rejected:* a fresh wall read per reader (`\time()` or `Core::right_now()`), which puts the flame builder's ranking and its prune on either side of a second and lets a reply's panels straddle a bucket — `right_now()` also WRITES the tick, so a reader calling it moves the clock its own reply is dated from; a stamp pinned in `dispatch()` for the readers to consult, because a static stamp is a second clock with a lifetime of its own, which every caller and every test must remember to set, where a parameter makes the instant explicit at each call; and changing `Log_Manager::message()` to stop re-pinning, which leaves request scope with a tick frozen at class load and starves the debounce that reads it. **Revisit if** the substrate's tick ever holds still between drains, with no `right_now()` caller outside the drain in either scope, at which point `Core::$now` is itself one window and the parameter can go; or if a reply ever needs two instants on purpose, which would be a second parameter named for what it measures, never a second read.

## Decision 30: Every memcache value is one server's, carries nothing its key implies, and fits one item

Three rules hold every value `Stats_Store` writes, and each is applied by the value's producer BEFORE it writes, never learned from a refusal.

1. **Per-server data has the server in the KEY.** No value packs several servers' data. A site-wide sum — one number over every server, as `hourly_h`, `lb_h`, `dim_h` and `categories_h` hold — is not per-server data and stays one key. Nor is bookkeeping about the value's own filing, keyed by the server it is filed under, its own host: a URL's `url` blob carries `filed`, the hour it last filed its words (decision 28), so the hourly rule costs no write of its own.
2. **A value carries nothing its key implies.** A URL row filed under its server's key holds its path and not its host.
3. **Every value but a slotted chart hour fits `Stats_Store::ITEM_BUDGET`, uncompressed.** 900,000 bytes. A SQLite Table sets no item limit, so for a stats value the budget bounds what one costs to hold and to read: a worker's memory while its flush merges the value, and the unserialize every reader pays. It sits under memcached's 1,048,576-byte item less a margin for the key and the serializer's framing, because `Rule_Set`'s hook list rides memcached through an `auto` Table and caps to it too. No bound counts on compression, because nothing guarantees production compresses. A slotted chart hour takes no byte cap: its count caps bound each slot ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)).

**The URL index keys by server.** A fine bucket is `urls:{bucket}:{server_key}:{shard}` and an hour `urls_h:{Y-m-d-H}:{server_key}:{shard}`, where `server_key` is `Stats_Store::server_key()`, an FNV hash of the name, so a Host header puts no bytes of its own into a key. Each server's rows compete only with its own for a shard's cap, so a busy spoke cannot fold a quiet spoke's URLs into `Other`. A row's index 13 is `ROW_PATH` ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)), the path with no host when the URL is https under the row's own server, and `get_url_names()` is the one place a reader joins the two back. A row never moves to another server's key, and an http URL keeps its whole URL.

**The keyspace cannot list its servers, so an index does.** `urlsrv:{bucket}` maps each server key holding rows in the bucket, reader or worker, to `[ server_name, shards ]`, positional under `Stats_Store::SRV_NAME` and `SRV_SHARDS` ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)), and `urlsrv_h:{Y-m-d-H}` is its hourly fold. `shards` is an int bitmask of the shards the server wrote in that key: bit `i` is reader shard `dechex(i)`, bit `16 + i` worker shard `w{dechex(i)}`, and `Stats_Store::shard_mask()` and `shards_in()` are the only translations. Every walk reads it first and asks for the shards it names and no other: a page or point read, scoped or not, the hour fold, the roll-up's check and the ranker's gap-fill. A server's five minutes fill a few of its 32 shards, so a reader asking for all of them would read every shard of every key to find the few written. The flush ORs each server's shards into its entry (`Stats_Store::merge_index()`), so an unchanged union reads back identical and is not rewritten; the hour fold names all 32 for every server it keeps, because it writes every shard, empty or not; and `Stats_Store::index_entries()` drops an entry that is not a name beside a mask. Every server is filed under its own name, uncapped, so a bucket holds one server's URL keys for every host its requests named. The hour index is derived, by the fold.

**Every other per-server value follows.** The ranked lists are per server, `urlrank_s:{bucket}:{server_key}:…` and `urlrank_sh:{Y-m-d-H}:{server_key}:…`, each server's hour marked done by `urlrank_sh:{Y-m-d-H}:done:{server_key}`, and the site's, `urlrank_s:{bucket}:{sort}:{order}`, is one key the writer merges from them ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)). The token index is `urltoken:{bucket}:{server_key}:{word}`, one set per six-hour bucket per server per word, so a scoped search reads its own server's sets and a site search every indexed server's. The bucket index is `urlbucket:{bucket}:{server_key}`, one set per five-minute bucket per server, read the same way. A URL's index row is `url_row_h:{Y-m-d-H}:{server_key}:{hash}`, under the server its shard rows are filed under, so the search reads each candidate under the servers whose sets named it. `urlmap:{hash}` holds `[ server_name, path ]`: its key names a hash and no server, so the server belongs in the value, and it is what an unscoped `dump_url` or `ask url:` reads to find the one server whose keys hold the hash. `url_dim` has no `server` axis, because a URL belongs to one server and the axis could only ever hold one value; `dump_url --breakdown` and `url_breakdown` refuse it.

**Every value is capped by an estimate its producer makes before writing.** `Stats_Store::overhead( $part )` is the fixed cost of one stored part — a URL row, a leaderboard category, a category entry, a flame node, a hook name — under the serializer the durable Tables store with, `Durable_Arm::serializer()`: igbinary's where the shared memcached handle is built with it, and PHP's `serialize()`, the larger, otherwise and with no handle. A value's estimate is its parts' overheads plus the `strlen()` of the strings they carry, so no flush serializes a value to measure it.

| Value | Cap |
|---|---|
| `urls`, `urls_h` shard | Estimated bytes alone, busiest rows first; the tail folds into `Other` and `Other:worker` (`cap_url_rows()`) |
| `lb_h`, `lb_sh` | `MAX_LB_CATEGORIES` (200) by `sum_time` AND the byte estimate, in one walk; the tail folds into `Other`, and each category's entries trim at 100 down to 50 |
| `url` | The profiles through the leaderboard cap at half the budget; each of the two flame-tree copies pruned lightest leaf first to a quarter (`Flame_Tree::prune_lightest()`), in the stored copy alone |
| `urlsrv`, `urlsrv_h` | No cap: every server is filed under its own name, each beside its shard mask |
| `url_row_h` | By count: twelve slots a family, two families, and one path of at most `MAX_PATH_BYTES` |
| `eln-rule-hooks` | `Rule_Set::save()` refuses a rule whose hook list's estimate passes the budget, before it writes anything |
| `hourly_h`, `dim_h`, `categories_h`, `url_dim_h`, `url_cat_h` | No byte cap ([decision 35](#decision-35-a-chart-hour-is-one-key-holding-its-twelve-five-minute-slots)): each of the twelve slots is capped by count, `MAX_DIM_VALUES` (the `server` axis uncapped, one value a host), `MAX_URL_DIM_VALUES` or `MAX_CAT_VALUES` |
| Every other value | Bounded by count — `URL_RANK_N` / `URL_RANK_N_HOUR`, `MAX_PATH_BYTES`, `URLS_PAGE_CACHE_MAX_ROWS` — over strings `Log_Manager::MAX_DATA_SIZE` (3,840) already bounds |

`tests/unit/ItemBudgetTest.php` builds the largest value each cap admits and measures it under the serializer the estimate was made for. A hook list is refused rather than trimmed, because a partial list would bind hooks the rule never named.

*What it costs:*

- **Key count.** An unscoped read of one shard reads one key per server whose index entry names that shard, where one shared key served them all; the bytes stay about the same, because URLs are disjoint by server. A server-scoped read reads the index too, one round trip a store, so it asks only for keys that exist. The page cache (60 s) and the per-bucket header cache absorb the poll rate. A site ranked page reads a list per server per key, a site search one index read and one token `SMEMBERS` per store, and the roll-up's check two round trips: each hour's index, then every key it names.
- **Ranking groups.** A group is one (server, bucket) pair, thirty-two shard writes of both families, so `WRITE_BATCH_KEYS` and `chunk_intents()` keep their arithmetic, and one ranking read takes at most `WRITE_BATCH_KEYS` over all thirty-two shards (15) groups.
- **No server cap.** Every server is filed under its own name, so the site merge, the site search and the unscoped `dump_url` locator are exact: URLs are disjoint by server, since a URL names its host. The `server` axis, the server index and the per-server keys grow with every host a request names, and under Apache's default `UseCanonicalName Off` that host is the client's Host header.
- **A key in an earlier shape is never read** ([decision 5](#decision-5-a-stats-schema-change-is-migrated-by-the-tables-flush-and-by-nothing-in-this-code)). The flush that migrates a shape change orphans every old key, so the URL index, its ranked lists and its search index start empty and refill as traffic arrives, and a URL reads as no name until its next flush names it.

*Alternatives rejected:* the per-server split inside the value ([decision 14](#decision-14-a-server-scope-the-key-cannot-carry-rides-inside-the-value-and-is-applied-as-a-projection)), where one shard's rows for every server competed for one row cap, so a busy spoke folded a quiet spoke's URLs into `Other` and the quiet spoke's scoped table came back short, and the name twin beside it carried every server's paths with no cap at all; a bound that relies on compression, which holds only where the cache compresses; a row-count cap alone, which fits typical paths and not long ones; serializing each value to measure it, which puts a `serialize()` of every write on the flush path; trimming an over-budget hook list.

**Revisit if** a Host-header spray grows the server index past `ITEM_BUDGET`; if memcached is configured for a serializer other than PHP or igbinary, which binds `eln-rule-hooks`, the one estimate-capped value memcached still stores, where JSON escaping can spell a string at six times its bytes and the estimate is no longer an upper bound; or if the refused-write log names a stats key, which means an estimate is wrong for that value.

## Decision 31: A snapshot node's replay is idempotent by the last folded crumb

A plain stop leaves the reader's cursor ON the record in flight, and the successor replays it (substrate [ADR-14](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)). Every stop but a bare clean one is plain: one carrying a failure, one combined with a failure, and one no `deferring()` bracket turned clean. The worker's shutdown checkpoint commits that cursor after the snapshot node's `save_state()` has flushed what it folded into the Tables, and what it folded often includes the very record the cursor still points at. A replay must therefore not fold it twice.

`Flame_Builder_Node` keeps `$counted`, the crumb — `Message::ID`, the consumer's `segment:offset:length` — of the last record it folded into its accumulators, and `save_state()` flushes them and carries the crumb as `counted`, beside [decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)'s data clock as `data_clock` and `data_clock_hour_since`, which `restore_state()` reads back. The clock describes data the checkpoint already drained, so restoring it folds nothing early. A carry without the clock keys restores as a process with no clock, which is a fresh process exactly: this is the defined state for a builder that never recorded one, not a migration. `restore_state()` does not refuse such a carry, because the Consumer restores at boot with nothing to catch a throw, and the checkpoint that would clear it is never written, so every builder would crash-loop. `fill()` always stores and forwards the record's flame, then folds the record into the stats only when its crumb is empty or differs from `$counted`, and records the crumb after folding. A replay of the counted record is therefore forwarded again and counted once. An empty crumb matches nothing, so a record the reader stamped no ID on is always counted.

`Request_Builder_Node` needs no crumb: every firehose line carries its request's sequence number `n`, and a line below the request's expected number is dropped as `INFO: duplicate message`, so a replayed line joins nothing twice.

*What it costs:* the crumb and the data clock's key and timestamp in the flame builder's checkpoint, and one comparison per record; a replayed record's flame is written to the flames partition a second time.

*Alternatives rejected:* counting the replay twice, which is what Tachikoma's `Nodes/Consumer.pm` does: its `commit_offset` records the lowest in-flight offset beside a cache that has already folded the messages past it, so a restart replays those and folds them again, and here every stop would inflate the counts, the sums and the leaderboards by the record in flight ([decision 2](#decision-2-sums-not-means)); and staging each record's fold until its `deferring()` bracket closed cleanly, which puts a second accumulator layer and a merge on every record to guard against a stop that lands once per worker life, where one string comparison answers the same question.

**Revisit if** a stop can leave the cursor more than one record behind the fold — a reader that folds a batch before it advances, or a checkpoint that commits a cursor older than the state beside it — since a single crumb then names only the last of several records the successor would count again.

## Decision 32: A builder tells its upkeep on its own worker record, and every narration write is a guarded forward

`Flame_Builder_Node` and `Request_Builder_Node` tell their routine writes and upkeep on the worker's own request record, as `keep`-marked spans and points through the [`Narration`](../includes/trait-narration.php) trait, and never through stderr, which feeds the Error Log. The Error Log therefore hears only faults. Everything a line says rides its `m`, because the stored record keeps an entry's `m` and drops every other producer field. Counters accumulate per name in the node's tally, and writing that name's line resets them.

Each narration line is a write to the firehose Partition, and a Partition write is a point where the worker's cooperative stop can rise. A snapshot node therefore sends every narration line through `guarded()` ([substrate ADR-14](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)), as it sends any downstream forward: inside the `deferring()` bracket of the message or tick in progress, the stop waits for that work to finish and then leaves clean. `spanned()` guards its `(start)` and its `(complete)` apart, through `Log_Manager::timed()`'s `$write`, inside a `deferring()` bracket of its own that is itself one guarded forward, so a stop the start raises still runs the step and closes its span — where a message's or tick's bracket is open it then waits for that work, and where none is, as in the restore `Consumer_Node::init_position()` runs before the first message, it leaves once the span has closed. Unguarded, a `stats rank close` span between two flush chunks stops the flush before it empties its accumulators, and the successor merges chunks already written a second time. An eviction or a fold tells no line of its own, only a count the next `requests writes` rollup carries, because both track visitor traffic; and a `requests checkpoint` is told only when its carry may have moved since the last one told. A request builder's narration, read back off the firehose, is folded but counts as neither a line nor a move: counted, a builder reading its own record, or two reading each other's, would tell for ever. The trait declares `guarded()` abstract, so it composes only with the substrate's `Deferred_Clean_Stop`.

*What it costs:* a closure per narration line, and one per span half, where a record is started; nothing where none is, because with no started logger no line is built.

*Alternatives rejected:* stderr diagnostics, which never stop a worker, since `Event_Framework::stop_check()` does nothing inside a stderr write, but put every routine line in the Error Log beside the faults; and one `guarded()` around a whole `timed()` span, which skips the step itself when its start write raises.

**Revisit if** narration grows past a few hundred lines per worker lifetime, or an operator needs routine lines in the Error Log.

## Decision 34: Stats live in SQLite Tables, and nothing repairs a loss

Memcache evicts, and every mechanism the stats grew since 0.107.0 existed to survive that: the durable mirror of decisions [10](#decision-10-the-durable-mirror-writes-a-bucket-once-when-it-closes-under-a-key-that-carries-no-install-scope) and [11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped), its index format, the sweep of [decision 33](#decision-33-no-dashboard-reads-the-mirror-the-flame-builder-sweeps-it-back-into-memcache), held frames, restore lifetimes, and the probe that re-ranked lists memcache had dropped. Each review of that machinery found holes in the last round's repair. So the stats moved onto a store that loses nothing before its TTL, and the repairs went with the loss *(Chris, 2026-09-29)*.

**One repair stands, scoped to the bucket index** *(Chris, 2026-10-05)*. A `urlbucket` add the Table refused is no row the store lost but a write it turned away, and the flush owes it only while its bucket is young; the fold of its hour files every URL the hour's fine shards name again ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)), reading nothing the fold does not. It repairs nothing else.

**Three Tables per partition, declared in the topology.** [`flame-builder.tsl`](../topologies/flame-builder.tsl) declares `flame-stats:aggregate`, `flame-stats:url` and `flame-stats:url-fine`, each `evlog:p<partition>` on the substrate's `sqlite` backend ([substrate ADR-24](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-24-a-tables-backend-is-chosen-per-table)), at the TTLs `<eln:stats_ttl>`, `<eln:stats_url_ttl>` and `<eln:stats_url_fine_ttl>` ([decision 1](#decision-1-namespaced-memcache-schema)). A Table keeps one file per partition, `{base}/tables/{table}.p{N}.sqlite`, on the one host's local filesystem the substrate already requires. `performance` and `complete` inherit the declarations through their includes, so writer and reader read one declaration, and a topology whose Tables cannot open, `pdo_sqlite` missing among the causes, fails at load, naming the Table.

**The builder writes every flush, and the checkpoint carries the crumb alone.** `Flame_Builder_Node` asks its Tables by message through the substrate's `Table_Client`, one `MGET` and one `MSET` per Table per flush chunk, and every flush writes every pending bucket, the open one included. `save_state()` runs that durable half before the Consumer commits its cursor and returns only [decision 31](#decision-31-a-snapshot-nodes-replay-is-idempotent-by-the-last-folded-crumb)'s crumb, so a replay counts nothing twice and nothing waits in memory for a bucket to close.

**Readers mount for the request.** A `performance` verb mounts the Tables it reads into the request graph through `Bootstrap::mount_table()`, read-only and in-process, and the mount lives for the rest of the request, so a later verb in the same POST reads through it rather than mounting again ([substrate ADR-23](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-23-a-request-carries-no-authority-of-its-own)). That is sound only because every row the three Tables hold is data a READ caller may already read: each is an aggregate of request records and their flames, which `dump_request`, `grep_requests` and the substrate's firehose stream hand a READ caller whole, and each namespace surfaces through a READ verb besides — the `url` blob through `dump_url`; the fine and coarse URL rows, server indexes, rank lists, headers, `urlmap` names and `urltoken` and `urlbucket` sets through `urls`; the chart slots and leaderboards through `overview`, `dump_url` and `url_breakdown`. A mount opens only a file its worker wrote, so a partition whose worker has not flushed yet reads as empty. A Table whose backend cannot open, which the mount raises as `Table_Unavailable`, reads as no stats ([decision 3](#decision-3-stats-fail-soft)); any other mount failure fails the verb, a mount in a process running as root among them.

**The search index is one set per six-hour bucket per server per whole word.** `urltoken:{bucket}:{server_key}:{word}` holds one member per URL of that server whose path carries the word, filed in that bucket, a row of the aggregate Table's set members, and a search reads its term's words longest first, three to one `SMEMBERS` per store over every bucket of the window, the next three only while the last three are all too common, `URL_SEARCH_MAX` members a set, a set holding more answering over-limit, and checks every candidate by `term_matches()` ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)). A word with more than `URL_SEARCH_MAX` live members narrows nothing, and narrows again once enough of them expire. A term with no word, or one too common to narrow, is refused; an unanswered read is no rows and a `provisional` page.

**Deleted with it:** the `flame-stats:partition` mirror, its `stats-index` format and the four `stats_mirror_*` config keys; the sweep; held frames and their checkpoint carry; the probe of lost lists and records; the site-hour refold; the `set_stats_target` and `set_flame_topn` verbs; and `GET_STATS`' `mirror_held_frames` and `mirror_held_bytes`.

**Migration:** none, and no flush. The Tables are new files, so the stats start empty and fill as traffic arrives. Nothing reads the old memcache stats keys, and memcache reclaims them by TTL or eviction; `wp nodes memcache flush` would delete nothing, only rotate the salt, orphaning every memcache key, and restart every worker; it no longer touches the stats at all, and `wp nodes tables flush` is what empties them.

*What it costs:* the `pdo_sqlite` extension on every host running the flame builder; disk under `{base}/tables`, whose expired rows the Router's purge deletes and whose free pages only the `vacuum` verb returns; a stats reader bound to the flame builder's host and filesystem; and a substrate floor at the release that carries the Table arms.

*Alternatives rejected:* memcache with a better repair, each round of which found holes in the last; the substrate's `wpdb` arm, durable and shared across hosts, which puts every flush's batch on the site's database and is sized for low-volume Tables; and a migrator from memcache, which would carry an evictable store's gaps into a durable one.

**Revisit if** a stats reader must run on a host other than the flame builder's, which the `wpdb` arm answers.

## Decision 35: A chart hour is one key holding its twelve five-minute slots

Every chart draws the 288 five-minute slots of the last 24 hours *(Chris, 2026-09-29)*: the Overview's breakdown and category charts, a URL's, and each under a server scope. Reading the current hour's buckets and one summed key for each older hour drew an older hour as one point spread over twelve, and at the default twelve-hour window a chart had 12 to 23 points.

**An hour key holds its twelve slots.** `hourly_h`, `dim_h`, `categories_h`, `url_dim_h` and `url_cat_h` each hold one hour as `SLOTS_PER_HOUR` slots — `url_dim_h` once per dimension, in one row a URL-hour, `url_dim_h:{Y-m-d-H}:{hash}` => `{ dim => slots }`, so a flush writes a URL's dimensions in one write *(Chris, 2026-09-29)* — `60 / BUCKET_MINUTES` = 12, positional and indexed by `Stats_Store::slot_of( $bucket )`, the bucket's minute over `BUCKET_MINUTES`, so a bare index never appears ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)). `Flame_Builder_Node::slot_intent()` folds a bucket's delta into its own slot by the merge and under the count caps a five-minute bucket took, so slot `s` holds exactly what bucket `s` would, and two buckets of one hour, or two dimensions of one URL-hour, compose onto one key through `add_intent()`. A reader names the dimension it draws: `Stats_Store::get_slots( url_dim_parts( $hash ), $hours, $dim )`. Every flush writes the open hour's key. No chart namespace writes a five-minute bucket: nothing evicts an hour key before its TTL ([decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss)), so a fine chart bucket would have no reader.

**The leaderboard stays one sum an hour.** `lb_h` and `lb_sh` are never charted, and they are the heaviest value the dashboard reads, a category per hook, callback and plugin the site fires, 1,198 of them on a production hub; twelve slots of it would be twelve times that for nothing drawn.

**The reader reads 25 hour keys and draws 288 slots.** `Performance_CI_Node::chart_keys()` names the current hour and the 24 before it, `Stats_Store::CHART_HOURS`; `Stats_Store::lookup_slots()` lays each hour out as `{hour}-{MM}` buckets and drops a slot nothing filled; and `merged_across_stores()` keeps exactly the 288 buckets `Stats_Store::chart_buckets()` names, ending at the current one. Twenty-four hours ending mid-hour touch 25 hour keys: at 14:37 the oldest slot drawn is 14:40 yesterday, so the oldest key gives four slots. Each `overview`, `dump_url` and `url_breakdown` reply names its 288 as `slots`, newest first, and the dashboard's axis is exactly those keys, five minutes a slot, so the browser's clock splits nothing. `--bucket` on `urls`, `dump_url` and `ask` takes a selection of up to 288 buckets, each accepted while its rows are stored (`assert_bucket()`, [decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)); every key `Stats_Store::chart_buckets()` names is one, so every slot a chart draws can be selected at once. A selected bucket's numbers are its slot of each hour value, and a selection spanning two hours reads both hour keys and folds the slots it names from each. The site totals, `total_requests`, `global_avg_ms` and `global_avg_peak_mb`, sum those same 288 slots, so they cover what the charts beside them draw. `read_plan()` still governs the URL index alone ([decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)), so at the default window the charts span 24 hours where the URL table spans twelve.

**The leaderboard and its own average share one window.** `build_leaderboard()` sums the 25 `chart_keys()`, up to 25 hours, and `overview` alone attaches `avg_ms`, the timed mean over those same keys, every slot of them: the site's from the `hourly_h` slots the reply already read, and a server's from its row of `dim_h:server`. The Time Breakdown divides the board's categories by that average, so its numerator and denominator cover one window.

**Averages divide what they measured** ([decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)). A dimensional row is five wide on the wire, `[ nameIndex, count, sumMs, sumPeakMb, timed ]`, from the stored `DIM_COUNT`, `DIM_SUM_MS`, `DIM_SUM_PEAK_MB` and `DIM_TIMED`: `count` is every request, for volume, and an average duration divides `sumMs` by `timed`. Peak memory is measured whether or not the duration was, so the memory metric divides `sumPeakMb` by `count`. The `hourly_h` slot carries the same split as named fields: `count` and `sum_ms` are the timed requests', and `requests` and `sum_peak_mb` every request's, so `global_avg_peak_mb` divides by `requests`.

**The wire is a name table.** `breakdowns[ $dim ]` and `breakdown_time_series` go out as `compact_category_series()` already sent categories, `{ names, buckets }`, a name spelled once and each row positional, because 288 slots would spell every value 288 times: a `ua` breakdown is about 1 MB a poll spelled out. `overview` keys `breakdowns` by every dimension asked, an empty one included ([decision 16](#decision-16-the-breakdown-panel-is-always-mounted-and-says-which-kind-of-nothing-it-has)), and an empty series encodes as `{"names":[],"buckets":[]}`. `overview` carries no totals series, because no chart draws one.

**The aggregate Table outlives the charts.** Its TTL, `<eln:stats_ttl>`, is `max( CHART_HOURS × 3600, window )`, 90,000 seconds at least, so every hour key a chart reads is stored whatever `min_lifetime` says. `min_lifetime` also sets the substrate's log retention, so the charts floor the Table rather than raise it. A slotted hour takes no byte cap, since SQLite stores a row of any size, and its count caps apply per slot ([decision 30](#decision-30-every-memcache-value-is-one-servers-carries-nothing-its-key-implies-and-fits-one-item)).

**Migration:** none. The stats Tables start empty ([decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss)), so no stored hour predates the slot layout or the `requests` field. `url_dim_h`'s move to one row a URL-hour came with the time-first layout, and [decision 1](#decision-1-namespaced-memcache-schema)'s Migration line covers both: nothing reads the earlier keys.

*What it costs:* each chart read asks 25 hour keys a scope a store; the bytes grow about twelvefold, an estimated `ua` series from ~106 KB to ~1.3 MB a store; a slotted hour value holds up to twelve buckets' worth; and every chart reply carries its 288 slot keys. A URL-hour row holds all six of a URL's dimensions, so `url_breakdown` and `dump_url --breakdown` read and unserialize six dimensions to draw one: the per-URL chart read pays up to six times the bytes, for one write a URL-hour on the flush in place of six.

*Alternatives rejected:* the summed hour key beside five-minute buckets for the current hour, which drew an older hour as one point; five-minute chart buckets written beside the hour key, which existed to refold an evicted hour and have no reader once nothing evicts; 24 hour keys, which draw 277 to 288 points as the minute moves; raising `min_lifetime` to a day, which lengthens every substrate log's retention too; slotting the leaderboard, twelve times the heaviest value for nothing drawn; one summed average over 288 slots for the Time Breakdown, which divides a 25-hour board by a 24-hour mean; and keeping the dimensional wire keyed by value name, about 1 MB a poll.

**Revisit if** a chart needs a window other than 24 hours, at which point `CHART_HOURS` derives from a setting rather than from `MAX_READ_BUCKETS`; if `BUCKET_MINUTES` stops dividing 60, which breaks `SLOTS_PER_HOUR`; or if anything charts the leaderboard.
