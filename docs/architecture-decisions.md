# Architecture Decisions

The load-bearing design decisions of the event logger. "Fixing" one usually reintroduces a bug already paid for. Each record states what forced the choice, what it costs, what was weighed against it, and the concrete condition that reopens it. A **Revisit if** is a sufficient tripwire, not the only door: an argument on the merits also reopens a decision.

Numbers are stable. Code comments, docblocks, [`AGENTS.md`](../AGENTS.md), [`docs/architecture-guide.md`](architecture-guide.md) and the rendered sheets cite a record as "decision N", so no record is ever renumbered: a record a later one replaces keeps its number and its heading, and opens with **Superseded by** that record. The substrate keeps [its own series](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md) under the name `ADR-N`, and a "substrate ADR-N" here links to that file.

## Decision 1: Namespaced memcache schema

**Superseded by [decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss).** This record laid every stat under `evlog:p{N}:` in one of twenty namespaces of three key-value Tables, the time key right after the namespace, one TTL per Table and a cap on every axis. Decision 34 keeps the stats as the rows of six declared tables in the `flame-facts` Row_Table, each with its own key and window.

---

## Decision 2: Sums, not means

The rows hold raw sums: `timings` and `timings_site` add `ms`, `calls` and `requests` on every upsert, `requests_hourly` adds `count`, `timed`, `sum_ms`, `sum_peak_mb` and `errors` and keeps the greatest `max_ms`, and a `requests` row holds its one request's own duration. Every mean is a division at read time, in [`App\Stats_Query`](../includes/app/class-stats-query.php): a timing's `avg_ms` is `SUM( ms ) / SUM( requests )`, the rollup's `SUM( sum_ms ) / SUM( timed )`. So a merge across buckets, servers and partitions is exact addition, and the leaderboard and a URL's rebuilt flame follow the same rule, dividing once. Do NOT regress to running-mean storage: it produces the EMA-clamp bug this rule exists to keep out.

---

## Decision 3: Stats reads fail soft; a stats write raises

**A reader fails soft.** [`Stats_Query`](../includes/app/class-stats-query.php) reads every partition's file through the substrate's `Row_Table_Node::read()`. It names the schema, never the table: the substrate's `Bootstrap::row_table()` finds the one Row_Table the active topologies declare with `Flame_Facts`. When the files will not open — `pdo_sqlite` missing, a file SQLite cannot attach, or no active topology declaring a `Flame_Facts` Row_Table — the substrate throws `\Newspack_Nodes\Table_Unavailable`, and `Stats_Query` logs `performance: stats rows did not open` once a window and answers no rows with `available` false. An unreadable active topology fails loud instead, because the resolver raises any before it resolves, so a declaration one holds is never silently left out, where a table that will not open fails soft; so do two Row_Tables of the schema, refused naming both. `dump_request` and `search_requests` tell the two apart: an outage answers `no request <rid>: the stats rows did not open`, and only a rid no row names answers `Request not found`. Every `Stats_Query` answer carries `available`, and the `query` verb passes it through. `dump_url` answers zero stats, an empty list and a null flame and profile, and a dashboard draws its "No … data in this window." line where a chart would be. Any other failure, a reader running as root among them, fails the verb loud.

**A writer raises** *(Chris, 2026-10-15)*. A `ROWS` batch the Row_Table refuses or leaves unanswered, or any other failure inside `Flame_Builder_Node::write_rows()`, raises a plain `Worker_Should_Stop` carrying the cause ([substrate ADR-14](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)), and the buffer stays. The Consumer neither dead-letters the record in hand nor commits its cursor past the batch, so the successor replays every record the batch held, and the `requests` row's insert-ignore on `rid` keeps that replay from counting twice ([decision 31](#decision-31-a-snapshot-nodes-replay-counts-each-record-once)). Dropping the batch would lose those requests for good; a reader's outage costs a blank card for as long as it lasts.

The substrate makes the opposite call for another reader: a stream its slot pool cannot account for is refused ([SSE host budget](https://github.com/Automattic/newspack-nodes/blob/main/docs/sse-host-budget.md)). The asymmetry is the decision. A missing stat costs a blank card; a stream nobody can account for costs a php-fpm child for as long as it stays open. **Revisit if** a stats outage must be told from an empty window on screen: `available` carries the difference on the wire, and no widget draws it.

## Decision 4: Settings fan-out is a node graph; no consumer means a silent no-op

The three settings a hub pushes, the ruleset, `log_memory` and `flush_every_line`, ride the substrate's settings control plane: [`hub-control.tsl`](../topologies/hub-control.tsl) includes `settings-sync` and adds one `add_setting` line per option, and a change to any of them is an option write like every other, which the substrate's [`Settings_Event_Writer`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-settings-event-writer.php) records. So [`Auto_Tuner_Node`](../includes/class-auto-tuner-node.php) mutates the one rule the message names (`rule_id`) and persists the whole ruleset through `Rule_Set::save()`: no `remote_manager` job, no `suppress_sync`, and an auto-tune write reaches the spokes exactly as an admin edit does. Nothing fans a change out unless `hub-control` is active and per-spoke `HTTP_Out` nodes are wired; on a spoke or a standalone site the event is tailed and dropped. That IS the structural gate: there is no `enable_workers` or `enable_aggregator` key, and hub mode derives from which topologies are active.

## Decision 5: A stats schema change is a version bump and a rebuild, and nothing in this code migrates

`Flame_Facts_Row_Schema::version()`, 6, versions the shape of the stats rows, and each partition's file carries it as SQLite's `user_version`. A builder opening a file at another version discards it and starts empty, and a reader leaves such a file unattached ([substrate ADR-34](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-34-a-table-may-hold-declared-rows-sqlite-only)), so a row in an older shape is never read. A schema change therefore bumps `version()`, and the rollout rebuilds the rows from what the logs retain:

```bash
wp nodes stop && wp nodes deactivate performance && wp nodes gc --force && wp nodes memcache flush && wp nodes activate performance && wp nodes start
```

That is the sequence for `performance`; on a site running `complete`, or another topology that includes `flame-builder`, name that topology in its place. Deactivating the topology leaves its `requests.p{N}`, `flames.p{N}`, cursors and `flame-facts.p{N}.sqlite` files declared by nothing, and `wp nodes gc --force` deletes them at once. The firehose survives, because this plugin's log producer declares it, so the reactivated request builder, holding no cursor, reads the retained firehose from the start, and the flame builder writes the rows again in the new shape; on `complete` the job router re-reads `jobintake` the same way and runs every retained job younger than the `jobs:sieve` window, 900 seconds, again. `wp nodes memcache flush` rotates the install's cache salt, orphaning the volatile keys this install holds, the hook lists `Rule_Set` keeps among them, and touches no row. Schema bumps and emergency resets share the one sequence.

**The version and the rebuild ARE the migration, and nothing in the code compensates for skipping the rebuild.** Skip it after a bump, and each builder discards its file at its next open, so the dashboards start empty and fill from new traffic while the history the logs hold goes unread. No reader or writer carries a shape probe, a per-row version or a legacy branch: each would be a second migration mechanism beside this one, kept in step with every future shape.

*Alternatives rejected:* a migrator that rewrites old rows (a second write path kept in step with every shape the schema ever had, for rows the logs can rebuild); reshaping a file at open (the same migrator, run on the writer's path). **Revisit when** the logs no longer retain the rows' longest window, seven days, at which point a bump loses history the rebuild cannot recover.

## Decision 6: `get_multi` batching is essential

**Superseded by [decision 36](#decision-36-the-query-vocabulary-is-fixed-no-sql-from-outside-a-picker-chooses-the-rollup).** This record had every reader ask for all of a partition's retention buckets in one `MGET` per Table (`Stats_Store::bucket_get_multi()`), because a `GET` per key was a latency cliff. Under decision 36 a reader asks one SQL statement over every partition's attached file, and fetches no keys.

## Decision 7: Job_Intake for >4KB jobs, the firehose for ≤4KB

Small runtime jobs ride the firehose with `k:"job"`, and [`Job_Router_Node`](../includes/class-job-router-node.php) extracts them; [`job-feed.tsl`](../topologies/job-feed.tsl) tails the substrate's `jobfeed` log instead, so a spoke's router reads jobs alone rather than the whole firehose. A job the firehose cannot carry goes straight to `jobintake` through the substrate's [`Job_Intake::queue()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-job-intake.php), the locked path past the PIPE_BUF cap ([substrate ADR-4](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-4-pipe_buf-atomic-writes)). The wrong path loses jobs: `Log_Manager` trims `m` on any ENTRY over `MAX_DATA_SIZE` (3840B), so the handler never sees a parseable payload.

## Decision 8: A spoke's job is re-keyed `remote_job` when the hub pulls it

A spoke writes `k:"job"` like any producer and never learns it has a hub. The hub's [`aggregator`](../topologies/aggregator.tsl) topology pulls each spoke's firehose through a substrate [`Remote_Source_Node`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-remote-source-node.php) ([hub and spoke](https://github.com/Automattic/newspack-nodes/blob/main/docs/hub-and-spoke.md)), and this plugin's [`Remote_Job_Rewrite_Node`](../includes/class-remote-job-rewrite-node.php), wired between the sources and the firehose `Topic`, flips the incoming `k:"job"` to `k:"remote_job"` and leaves every other key alone. That kind is the only thing telling a spoke's work apart from the hub's own: the hub's `Job_Worker_Node` dispatches it against `newspack_nodes/remote_job_handlers` and never against the map its own jobs use. A job type registers under either map or both, depending on where it should run, and the two registrations are independent, so the hub runs a spoke's job because a handler was registered for it there, not because the spoke asked. What makes a site a hub is [decision 4](#decision-4-settings-fan-out-is-a-node-graph-no-consumer-means-a-silent-no-op)'s: the `aggregator` and `hub-control` topologies being active, with no toggle.

## Decision 9: A request's partition is its id, hashed by the substrate

[`Log_Manager::init_firehose()`](../includes/class-log-manager.php) picks a request's firehose partition with the substrate's [`Partition_Node::hash_to_partition()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-partition-node.php) over the request id ([substrate ADR-6](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-6-crc32--31-bit-mask-partition-routing)), and [`Performance_CI_Node`](../includes/app/class-performance-ci-node.php) finds a request's partition the same way. Neither hashes with a function of its own: the id is every firehose line's Message KEY, so the partition a line lands in and the one a reader looks in are one function of one input.

## Decision 10: The durable mirror writes a bucket once, when it closes, under a key that carries no install scope

**Superseded by [decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss).** This record wrote each bucket's frames to the append-only `flame-stats` partition once, when the bucket closed, under `evlog:p{N}:{key}` with no install scope, so the mirror outlived `wp nodes memcache flush` and kept one frame a bucket rather than ten, one per 30-second checkpoint. Decision 34 keeps the stats in durable Tables, which hold one value per key and need no mirror.

## Decision 11: The open bucket is durable in the OFFSETLOG until it closes, and the carry is capped

**Superseded by [decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss).** This record carried the open bucket's held frames in the offsetlog checkpoint, capped at `MAX_CHECKPOINT_MIRROR_BYTES` (16 MiB) with the widest frame dropped first, because a held frame reached no durable log until its bucket closed. Under decision 34 every flush writes the open bucket to its Table, and the checkpoint carries nothing.

## Decision 12: A stat times the request; a flame value is a rendering artifact

Two numbers describe one request and they are not interchangeable. `duration_ms` on the record is what the request took, measured once. A flame node's `value` is a LAYOUT WIDTH: `Flame_Tree::cover_children()`, `Flame_Fold::flatten()` and `Flame_Builder_Node::fill()` all RAISE it so a parent covers its positioned children, because the browser prunes on a single cutoff and takes a whole subtree with anything it drops, and `treemapDice` scales children by `parentWidth / parent.value`. Raising is correct for drawing and wrong for counting. **Every stat therefore reads `$request['duration_ms']`; nothing measured reads a flame `value`**: that covers every row of [decision 34](#decision-34-stats-live-in-sqlite-tables-and-nothing-repairs-a-loss) and the `sum_value` of a URL's rebuilt flame.

![A real request, the record and the raised root drawn to scale. The record's duration_ms is 356,312 ms, measured once, and every stat reads it. The flame's root value is 724,662.87 ms after Flame_Builder_Node::fill() raised it to cover a child positioned 355 seconds after the parent's own occurrence, marked as a tick at t = 0, because a parent is widened to the end of its farthest child so the child stays inside it when drawn; a stat reading that raised width reports the URL's avg_ms as 724,662.87 ms. Cards name the three places that raise a value, Flame_Tree::cover_children(), Flame_Fold::flatten() and Flame_Builder_Node::fill(), and why raising is right for drawing: the browser prunes on a single cutoff, taking a whole subtree with anything it drops, and treemapDice scales children by parentWidth / parent.value. The rule covers every row of decision 34 and the sum_value of a URL's rebuilt flame.](img/dec-flame-value.png)

The two diverge by more than rounding: read from its raised root, a 356,312ms request reaches `avg_ms` as 724,662.87ms, because `fill()` raises the root to cover a child that ran 355 seconds after the parent's own occurrence. *Alternatives rejected:* not raising at all (deletes exactly the frames a viewer opened the graph to see); computing stats before the raise (the ordering is invisible at the call site, and one reorder reintroduces it). The same holds for `Findings`: every share it reports divides by `duration_ms`, and no finding or brief carries the root's value as a profiled total. **Revisit if** the browser stops pruning on a single value cutoff: the raise can go then, and the two numbers converge.

## Decision 13: A sequence-break marker is missing detail, not idle time

`entries (lost)` and `entries (aggregated)` stand in for entries [`Request_Builder_Node`](../includes/class-request-builder-node.php) removed: discarded on overflow, or merged by the fold. It mints them, so it owns the vocabulary as `Request_Builder_Node::SEQUENCE_BREAK_KEYS`; consumers reference that constant rather than keeping their own copy, and the JS holds the only deliberate duplicate because it is a separate deploy unit. **No consumer may reason across a marker.** `Findings::entry_gap()` skips a gap on either side of one, `Reqgrep_Command` breaks its sequence there, and [`logEntryUtils`](../src/overview/utils/logEntryUtils.js) splices the merged spans back at it. Reading the interval as unexplained makes one record's `entry_gap` propose MORE hooks while its `truncation()` proposes fewer, both at once, on the same record. What a consumer MAY read across one is the record's own ending: whether anything closes the outermost pair. That decides FRAMING, which spans were severed and which ran to the end, and leaves the interval exactly as unmeasurable as it was, which is what this decision protects. `logEntryUtils`' `pruneSeveredSpans()` and `Reqgrep_Command::prune_severed_spans()` are the one rule, and the parity test in `logEntryUtils.test.js` pins the vocabulary they share. **The severance frames the record's RESUMED tail, never the folded interior spliced in at the marker**: those rows are what the TREE puts inside the open span, and the fold is what ate its close, so pruning before them makes every merged row a sibling of the parent it ran in: a gyrobase subprocess that exits 0 loses its whole 535s interior to the request's level, while the same shape whose drain survives the fold nests correctly. The prune therefore waits for the first row the record itself resumes with (`fromFold`). **Revisit if** a marker ever carries its own duration, which would make the interval measurable rather than merely missing.

## Decision 15: The `urls` verb owns every URL-set fact; `overview` owns the site

One verb applies the filters, so one verb answers for what they left. The `urls` verb answers how many URLs, how many requests, the averages, the rate and the slowest ten, and, as its default page sorted by count DESC, the busiest. Its `totals`, its `data` and its `slowest` are three `Stats_Query` statements over one filter and one bucket selection, so the header and the table beneath it cannot disagree about what they describe. Every count is exact, `totals.urls` and `rows` a distinct count of URLs, and every mean is request-weighted: a row's `avg_ms` over its timed requests and its `avg_peak_mb` over every request, never a mean of bucket means. A filter matching nothing reads as an empty set rather than as zero traffic. The reply echoes the `filters` it applied (`server`, `search`, `filter`, `include_workers`, `bucket`), and the Ask brief carries them on every surface, so a narrower number never reads as the site's. `requests_per_second` divides the requests by the seconds the selected buckets have run, the current one only so far, never by the buckets that carried traffic: divide by those, and a URL seen in two buckets of twelve reads six times its rate beside a header that does not. The headline stats read `urls.totals`. `dump_url` takes the same `server`, because the modal opens from a row that filter scoped, and a site-wide average under a scoped count is the same defect one click in.

`overview` answers for the site over the chart's 288 buckets: the non-worker `totals`, the `servers` with any traffic, worker traffic counted so a server serving only cron or job requests can be picked, busiest first, and the 24-hour category `leaderboard`. Its `server` argument scopes the totals and the leaderboard, and never `servers`, the list the picker offers. Chart series are `query` answers ([decision 36](#decision-36-the-query-vocabulary-is-fixed-no-sql-from-outside-a-picker-chooses-the-rollup)), so neither verb carries one.

The table EXCLUDES worker traffic by default, and so do its totals, because one long-running job would otherwise dominate the averages: on a staging hub a header summed with worker timing read 227 ms of cron against 3 ms of reader traffic. The row records whether a worker served the request, as `requests.worker`, never a guess from `?worker_type` in the URL text; `include_workers` opts IN because the default excludes. `dump_url` counts worker requests, so a URL only workers reach answers its own detail while staying out of the site totals. One scope rule holds across the surface, so no widget re-litigates it: a FETCH sends the live selection, so `urls`, `dump_url` and `ask` all ask for what is selected now, while a LABEL reads the scope the server echoed back, because it names numbers already on screen. Mixing the two puts a brief for one server beside a panel showing another's.

One filter list narrows the table, its totals and its slowest ten together. `urls`, `dump_url` and `ask` take `--filter=field=value`, repeatable, bound and refused as `query` binds and refuses it, and a filter on a field, `=` or `!=`, replaces the verb's own scope on it: `worker=1` and `worker!=0` list the workers without `include_workers`. One argument owns each field, and a filter token naming an owned field, `=` or `!=`, is refused, naming its owner, with or without the owner beside it: `server` is `--server`'s, because the dashboard's Server select is the one place a server is chosen; `bucket` is `--bucket`'s, the selection's; and `url` is the hash's where one is named, on `dump_url` and an `ask url:`, so the URL a reply describes is the one the hash names. `urls` keeps `url=`, because nothing else names a URL there, and `worker=` replaces Include Workers, as above. `query` keeps all three, because it owns no field: the select scopes the charts through `server=`, and a chart filters by `url=` and `bucket=`. Every reply's totals carry `errors`, the timeouts and fatals among the requests counted. `status_class=5` keeps the 5xx responses, most fatals among them, and `status_class=Unknown` the requests that answered no status: timeouts, and CLI or cron runs where workers count. `error=T` and `error=F` together keep the timeouts and fatals exactly, as `errors_only` did. On `dump_url` the filter narrows the stats and the list together, so `requests_capped` counts against the narrowed `stats.count`, and a `url:` Ask brief carries the filter and its pointer fetches under it. A `bucket` selection narrows the `urls` rows, totals and rate, and `dump_url`'s stats and list; no flame is rebuilt from a filtered or selected list, since it would describe the list rather than the URL. **Revisit if** the header ever needs a number the `urls` reply cannot produce (the answer is a new field on that reply, not a second source read beside it), or if a host is ever reported by two servers.

## Decision 16: The breakdown panel is always mounted, and says which kind of nothing it has

[`BreakdownControls`](../src/overview/components/BreakdownControls.js) is the chart, the selects that drive it — Metric, Breakdown and Then by, plus a Server select where the caller passes `serverOptions`, as the Overview card does — and the filter chips: one panel, because the values the chart reads are the ones its own selects set. Both callers, the Overview card and the URL modal, mount it unconditionally, and one resolver, [`breakdownState( answer, dims )`](../src/overview/AggregateTimeChart.js), which each caller runs once per answer, tells the panel which kind of nothing it has.

The selects are the only way out of a dimension with no rows, a read still in flight or a refused reply, so any gate that can unmount them can trap an operator: a gate on the reply unmounts, on an error, the only control that can recover from it. There is no "None" breakdown, so the totals are never the requested view. `breakdownState()` returns `{ state, series, groups }`: the state is `pending` when no answer is in hand or its `columns` are not the ones the selected dimensions ask for, which is an answer to a question the selects have since moved past; `empty` when the answer holds no row, `decodeRows()` refuses it, or its stats rows did not open; and `series` otherwise. Beside it, `series` is the decode and `groups` the tuples the answer ranked. Each caller hands the panel that read as `breakdownRead`; the panel reads the state and hands the chart the series, and only `series` draws. The panel checks a refusal first, and `error` prints it under the chart. A read in flight shows a Loading pill and keeps the previous series drawn, and where `groups` exceeds the series drawn a line says how many it draws of how many. "No User Agent data" during a fetch is a lie that flickers, and the totals under either state answer a question nobody asked.

Two things keep a stale answer out of the panel: each chart slice's `Current` gate drops the answer to an ask a newer one superseded, and an answer that passes is matched to the selects by its columns, the bucket, the dimensions and the series measures in order.

*Alternatives rejected:* a `mountWhen` prop (a gate, passed in, and every value of it can strand the operator); two panel components (one panel, two callers, and the second copy exists to hang one boolean on); emptiness alone as the discriminator (collapses `pending` into `empty`, which is the flicker). **Revisit if** the dimensions drift from `Stats_Query::FIELDS`: `REQUEST_FIELDS` in `constants.js` is a hand-matched copy, held to the PHP by a jest test that reads it.

## Decision 19: A request is filed in the bucket it FINISHED in

A stats write must land where a reader will read it, so a request is filed under the five-minute bucket it FINISHED in. The record reaches `Flame_Builder_Node` at completion, and filing it under its START would put a long request in a bucket a reader may already have read. The bucket is therefore `Bucket::id( min( now, Flame_Builder_Node::completed_at( timestamp, duration_ms ) ) )`, `completed_at()` being the start plus the rounded duration: the completion needs no new field, and for a timed-out request it is when live traffic timed it out, because `Request_Builder` sets `duration_ms = due - start` at eviction: `due` is the grid boundary the request's window fell due at on `Request_Builder_Node::stream_clock()`, the newest entry stamp it has consumed, or the wall once it has consumed nothing for `Flame_Builder_Node::IDLE_AFTER_SEC`. `LRU_Cache` hands each eviction that boundary, so a stream that falls silent overnight and repays three windows with its next stamp still times each request out at its own third boundary, not six hours long. That removes the request's own duration from the exposure, which the 1080s assembly window, three windows of the same stream clock, bounds at eighteen minutes, and it holds for a reprocess run a day late, whose timed-out requests file among the stamps they were replayed with rather than in the wall's bucket. The completion is **clamped to now**: a completed request cannot have finished after it reached us, and a skewed spoke clock or a bogus duration filing into a future bucket is a write no reader of the last 288 buckets reaches. The `requests` row also keeps the start, as `started_at`, which the URL modal's request list shows; `finished_at` is the clamped completion.

**Filing by completion does not remove transit**: a request in flight across a bucket boundary, or a spoke's backlog on a hub, reaches the builder after its bucket has closed. Nothing folds a closed bucket, so a late record lands in its bucket's rows like any other, and its hour's `requests_hourly` row takes it the same way; the next read sees it. The only bound is each table's window: a record whose bucket is older than a window is purged on that table's next tick.

*Alternatives rejected:* filing by the start (puts a long request in a bucket the charts already drew); filing by the arrival (moves a spoke's backlog into the buckets it arrived in, which describe the hub's lag rather than the spoke's traffic). **Revisit if** a reader needs a request by when it started, which `started_at` already answers without refiling anything.

## Decision 20: Outbound HTTP is timed as a span, and a short-circuited request opens nothing

Without these spans a request that spends its time below PHP userland reports as unmeasured, the one answer a reader cannot act on. A BDN `wp-admin/post.php` record shows the cost: 41.7s wall against 12.2s CPU, with `Image_CDN::filter_the_content @999999` holding 29.4s of self time and no interior, so the 29.5s off-CPU remainder has no name. A hook cannot reach it, since `WP_Http::request()` is not a hook, but WordPress brackets the call: `pre_http_request` before, `http_api_debug` after. [`App\Core`](../includes/app/class-core.php) binds that pair for every log rule whose `log_http` is set, so the span costs two registrations per request and two entries per remote call. **The pair is NOT balanced, and that asymmetry is the whole design.**

Step 2, the transport runs: the I/O below PHP userland the span exists to name. Step 3, do_action('http_api_debug'): http_end at PHP_INT_MIN hears it first, pops the label it opened rather than re-deriving it from a URL a redirect may have changed, and writes http (complete) with the status code, ahead of the other listeners. `WP_Http::request()` short-circuits with a bare `return $pre;` and never fires `http_api_debug` (`class-wp-http.php`), so a span opened before the short-circuit would never close and would adopt every row after it: the severed-span damage [decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) exists to bound. So `http_start` binds at **PHP_INT_MAX**, after every short-circuiting filter has voted, and opens nothing when `$preempt` is not false: a short-circuit is a cache hit with no I/O to time. A rule marking `http` significant gets that filter's listeners wrapped by `http_wrap`, bound at PHP_INT_MIN ahead of the chain on each call, the shape `hook_start` uses — `http_start` votes last, so from there a listener could only be wrapped for the NEXT call — so a short-circuiting listener's own cost shows where the span would have been. Every other return path fires the action, so within one request the pair is exact. `http_end` binds at PHP_INT_MIN so the span covers the request and not the other listeners on that action, and it closes the label it OPENED rather than one re-derived from the URL: a redirect hands the action the FINAL url, and a label that no longer matches leaves the span open. The span is named for its **caller**: `l` is `origin_frame( true )`, which climbs past every frame of the class that applied the filter, `WP_Http` here, at `TRANSPORT_ORIGIN_DEPTH` (16) rather than `ORIGIN_DEPTH` (8), because "which of my code paths makes this call, how many times" is the question a reader has; the redacted URL rides as the entry's value and the status code closes it. The climb runs whatever [decision 23](#decision-23-a-span-says-how-long-never-who-asked-two-knobs-answer-the-second-question-at-two-prices)'s `trace_callers` says, and taking the shallow walk under it is rejected: that budget reaches this span too, keyed on the redacted URL paired with the calling frame, so `l` names who asked on every call and `caller` carries the chain on the first few to each endpoint; the shallow walk would trade `l` for a microsecond or two. **Naming the HOST instead answers nothing**, because so many calls go to the same one. **Instrumentation never CONSTRUCTS the logger it reports into**: `Log_Manager::instance()` lazily creates a logger, so every callback asks `started_instance()` first, the wrapped listeners included; otherwise a binding that outlived its request would build the logger inside the callback and stamp `process (start)` with that moment instead of the mu-profiler's `request_ts`.

*Alternatives rejected:* a per-rule opt-in flag (a new `Rule` property, its serialization, its editor control and its migration, to gate two registrations and a per-call cost that is zero on the requests that make no remote calls); timing inside a `significant_events` wrapper on `http_api_debug` (that times the action's LISTENERS, which is not the request). **Revisit when** SQL wants the same treatment, though `$wpdb` offers no completion signal without `SAVEQUERIES`, so it is a different mechanism and not an extension of this one, or if a transport ever fires `http_api_debug` more than once for one request, which would pop a label that is still in flight. **Per-rule** (`log_http`), like decisions [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) and 24: a logged request pays two entries per outbound call whether or not a brief reads them. Off unless the rule sets it, as every diagnostic is, a stored rule that predates the flag included.

## Decision 21: The fold keeps the CLOSE of any span the kept head left open

The fold keeps a head of [`FOLD_KEEP_HEAD`](../includes/class-request-builder-node.php) (10) and a tail holding every later row in arrival order, which evicts only unkept rows past `FOLD_KEEP_TAIL` (10). A span opened in the head FRAMES every row after it, so the fold keeps the close of every span that head left open, an `(orphaned)` close included.

![One job record from community.thecoast.ca folded two ways. The gyrobase subprocess opened in the kept head (FOLD_KEEP_HEAD 10) and closed after 535.8 s of a 536.2 s request, and ten PHP rows followed it: nuclear_gyrobase, two query hook pairs, updated_option hook, memory, resources and the terminal. Without the rule, the close is one more row in the rolling tail (FOLD_KEEP_TAIL 10), the ten rows evict it, and the entry list leaves gyrobase open, so the view reconstructs framing the record does not state and three display defects follow, while the flame, counted only by Flame_Fold::close(), still reads gyrobase count 1, 535,829.753 ms. With the rule, the fold marks the frames still open on its own stack after the head, and the close that matches each is marked kept, pinned in the tail where they arrived; at most FOLD_KEEP_HEAD closes are pinned, and process (complete) is exempt because the terminal arrives last. Notes: is_kept() leaves tail sizing to producers marking their lines, but a span's close is not that guess, because the fold chose the head; and losing a head span's close costs the record its shape, not one line.](img/dec-fold-keeps-close.png)

`is_kept()` argues that sizing the tail around a producer's shutdown sequence is guesswork the producer should settle by marking the line. A span's close is not that guess: the fold just chose the head, so it knows exactly which frames it left open, and there are at most `FOLD_KEEP_HEAD` of them. Nor is the close mere detail: losing a head span's `(complete)` costs the record its shape rather than one line. A `community.thecoast.ca` job shows it: the gyrobase subprocess closes after 535.8s of a 536.2s request, and the PHP parent's ten post-subprocess rows (`nuclear_gyrobase`, two `query hook` pairs, `updated_option hook`, memory, resources, terminal) fill the rolling tail and, without this rule, evict the close. The flame still counts the span, because `Flame_Fold::close()` is the only path that increments a node's count and the tree reads `gyrobase` count 1, 535,829.753ms; but the entry list leaves it open, and three separate display defects follow from the view reconstructing framing the record does not state. After the head's last row, `fold_request()` calls `Flame_Fold::mark_open_frames()` on the fold's own span stack, the one every row already feeds and every checkpoint carries, and `Flame_Fold::add()` reports when a `(complete)` matches a marked frame; the builder marks that row kept, so the rolling tail never evicts it and it stays where it arrived. Because the match is the fold's own LIFO match, a span re-opened past the head keeps its own close rather than the inner one's, a name the head opened twice keeps both, and an `(orphaned)` close, which `Log_Manager::complete()` and `Gyrobase::Log::_unwind_to()` write for every frame above the one closing, is kept as that head frame's close. Moving it ahead of the tail would put the rows logged inside its span outside it, which a pyrobase render inside `template_redirect` does on every folded request, since its rows land before the hook closes. **The request's own frame is exempt**, exactly as it is for the display's severed-span prune: `process (complete)` is the terminal, the last row to arrive, so the tail always holds it.

*Alternatives rejected:* having the producer mark the line (`Gyrobase::Log` could set `keep` on its nested `complete('gyrobase', …)`, but that fixes one producer in another repo and leaves every other one to rediscover it); closing the span in the VIEW from the tree's count and value (puts derived data in the entry list, and leans on exactly the reasoning across a marker [decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) restricts). **Revisit if** a head ever legitimately leaves more frames open than the tail can afford to carry, which would mean `FOLD_KEEP_HEAD` is choosing a head the record cannot frame.

## Decision 22: Query spans are the same pair as decision 20, but PER-RULE

[Decision 20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) leaves SQL as its reopen condition and calls it a different mechanism; it is the same shape with a different gate. `wpdb` brackets a query with `apply_filters( 'query', … )` before and, only under `SAVEQUERIES`, `log_query_custom_data` after. [`App\Core`](../includes/app/class-core.php) binds `query_start` on the [`query`](https://developer.wordpress.org/reference/hooks/query/) filter at the configured `hook_start_priority` (a plugin config key, default -10000), the priority the generic hook timer uses, so the span opens ahead of the filter chain and every filter that rewrites the SQL runs inside it. It records the label only, since the SQL at that point is what the caller wrote. `query_end` binds on `log_query_custom_data` at PHP_INT_MIN, pops the label and writes `sql (complete)` with the statement the database was asked: its host annotation stripped by `without_host_annotation()`, its literals replaced with `?` by `without_literals()`, and bounded only by `Log_Manager::MAX_DATA_SIZE`. A rule marking `sql` significant gets the `query` filter's per-callback timings nested inside the span, and with `log_queries` on, `query` itself is not bound as an ordinary hook.

**The difference from HTTP is the cost, and it is measured, not assumed.** Both are per-rule opt-ins, but HTTP's price on a request making no remote calls is two `add_filter` calls. A fixed skip cannot do that job: `wpdb::get_row()` reaches the `query` filter through `wpdb::query()`, and `SHOW FULL COLUMNS` arrives four `wpdb` frames deep, which is why the transport climb runs to `TRANSPORT_ORIGIN_DEPTH` (16) where a hook's own origin needs `ORIGIN_DEPTH` (8). ## Decision 23: A span says how long, never who asked. Two knobs answer the second question, at two prices

Decisions [20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) and [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) add spans; this one adds PROVENANCE, because a hook that fires sixteen times reads as sixteen identical mysteries and no amount of timing distinguishes them. A `/wp-admin/post.php` record is the case: `the_content` fires sixteen times at ~2.4s each, 93% of a 40.6s request, and every span says the same thing. What is missing is the caller.

**`trace_hooks` is the cheap one and does the real work**: `origin_frame()` takes ONE frame, who called the hook, and puts it on the entry's `l`, which is the flame's aggregation label, so [`Flame_Tree`](../includes/class-flame-tree.php) and [`Flame_Fold`](../includes/class-flame-fold.php) split `the_content ×16` into one node per caller with MEASURED durations and no new tree code. Gyrobase uses the same idiom for `include: /Macros/Global.html`. It deliberately does NOT call `wp_debug_backtrace_summary()`, which walks and formats the whole stack to produce a string all but one frame of which is discarded: measured at **12.7us against 0.9us** for `debug_backtrace( DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH )`. The LIMIT is the lever, not `IGNORE_ARGS`: args are refcounted, not copied, and cost 0.8us even on a multi-megabyte `the_content`; depth is what costs. At 0.9us it runs on EVERY firing (2,601 `render_block` calls cost 2.3ms), which makes the split complete rather than truncated at a budget. **What it must NOT do is synthesise ANCESTOR nodes** for the uninstrumented frames: a `wp_trim_excerpt` parent valued at the `the_content` inside it would assert a duration nobody measured, which is [decision 12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact)'s whole point. Attribution is honest; invented ancestry is not.

**`trace_callers` is the expensive one**, default 0: `caller_of()` records `wp_debug_backtrace_summary( self::class )` onto that span's OWN start entry as `caller`, not `c`, which already means COUNT throughout this schema, ignoring this class so the top frame is the caller and not the instrumentation. **The cap is what makes it affordable, and it is per KEY, not per request** — a hook name, a query's statement shape or an outbound URL, whichever the flame aggregates that span on, PAIRED with `l`, the calling frame that span is already labelled by. A hook fires, a query shape runs and an endpoint is called for the same reason: code asked. Keying the budget per request instead would spend it on the bootstrap and trace none of the 477 taxonomy reads that came later. Keying it on the hook alone has the same failure one level down: `l` is what SPLITS the flame node, so the caller that fires first takes the whole allowance and every other node reads as an unexplained repeat — which is why the number had to be large enough to cover all of them at once. Paired, 1 reaches every caller, and that is the setting to reach for. The RULE names the number: `trace_callers` IS the count of DEEP chains, and a stored `true` is a count of 1, because the pair key makes one chain per caller a chain from every caller. What a diagnostic run wants is not what steady state wants: a fixed 20 leaves 21% of one real record's time unattributed. The window is `CALLER_FRAMES`, 20 frames, because an 8-frame window stops one frame short of `rest_preload_api_request`, the frame that explains that whole request, and `Log_Manager::MAX_DATA_SIZE` is the only other bound — which a query start entry meets differently from a hook's: it carries `l` and `caller` but no `m`, so `fit_data()` has no string to trim and the entry drops straight to the floor, keeping `n`, `k`, `ts` and a 1000-byte excerpt. The span still opens, because `Flame_Tree::PATTERN_START` reads `k`. The cap exists because the same question asked of `render_block` on that record would be 2,601 backtraces. Price the whole of it before raising either number: a traced rule pays roughly 12.7us per chain, times the number of KEYS it meets — hook names plus distinct statement shapes plus distinct URLs, none of which the operator declares — and the pair key multiplies that count by the distinct CALLERS of each, which is exactly why the number comes down as the key narrows: sixty shapes at twenty is about 15ms and five hundred is 127ms, where the same sixty shapes asked from three places each at 1 is about 2ms, and a traced query also pays `without_literals()` twice, once for the budget key at the open and once for the statement `m` at the close. A cap that bound tighter used to stop tracing the shape being hunted, which is why the answer was the per-key budget and a rule the operator turns off again rather than a smaller number; narrowing the key to the pair is what makes a smaller number safe, because 1 now buys one chain from EVERY caller instead of one from the first. The budget resets on every scope change, so a worker draining a hundred jobs traces each one rather than spending the request's allowance on the first. Sixteen firings of one hook are one budget PER CALLER — three callers, three chains at 1 — so there is no named default: `true` reads as 1, and an operator who wants more writes the number. There is nothing for a named default to seed, either: the editor fills its field from the stored value or 0, and `to_array()` writes an int. `Log_Manager::message()` merges arbitrary keys into the entry (`[ 'n', 'k' ] + $data + [ 'ts' ]`), so neither knob needs a new wire field. **A field nothing renders is a field that does not exist**, so `LogEntriesTable` renders `l` and then `caller`, as "called by …", muted ahead of the entry's value. Per-rule and off by default, like decision 22 and unlike 21: a backtrace is cheap once and not cheap always.

*Alternatives rejected:* capturing unconditionally for bound hooks (a rule naming sixty hooks pays sixty times per request for an answer nobody asked); tracing only firings AFTER the first, on the reading that a repeat is the signal (the first caller is half the answer: which of the sixteen is the odd one out is exactly what you are reading for); a separate `(called by)` entry (a new keyword that `logEntryUtils` and `Reqgrep_Core` would both have to learn, to carry a field the start entry already had room for). **This decision's revisit condition is MET.** It named a THIRD per-rule diagnostic knob as the trigger, on the reading that two booleans is a pair and three is a flags map. `Rule` carries five, `log_queries`, `log_http`, `log_plugin_loads`, `trace_hooks` and `trace_callers`, and they are still five separate constructor properties. A flags map would buy one property and cost every reader a lookup and every knob its type — `trace_callers` is an int, not a boolean — so the count alone is not the trigger it was taken for.

## Decision 24: A duration nobody measured is not a timing sample

[`Flame_Builder_Node::buffer_request()`](../includes/class-flame-builder-node.php) runs two independent gates, the worker flag and `timing_counts()`, and conflating them is the classic bug in that class. The worker flag, `requests.worker`, is what every site-wide answer filters `worker=0` on, so one long job cannot dominate the site's numbers ([decision 15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site)). `timing_counts()` is true only when `duration_ms` is positive AND `error_status` is neither `T` nor `A`. Both statuses mark a duration that measures elapsed time to an interruption rather than what the request cost: `Request_Builder_Node::evict_request()` stamps `T` and the stream boundary its window fell due at, less the start, on a trace the LRU evicted mid-request, and `Log_Manager` stamps `A` when a cooperative stop lands inside `finish()` or when `end_job_context()` is told the job never finished. Summing either skews `sum_ms`, `max_ms`, `min_ms` and every mean drawn from them.

A request failing the timing gate still COUNTS. Its `requests` row is written with `ms` NULL, so it counts toward `count`, toward `errors` when it timed out, and toward the peak-memory measures, and its `requests_hourly` row adds one to `count` and nothing to `timed` or `sum_ms`. It files no `timings` or `timings_site` row, and its `profiled` is 0, so the leaderboard, the category charts and auto-tune never see it. **So `count` and `timed` diverge for a reason that has nothing to do with workers**, and each mean divides the population it summed: `avg_ms` is `AVG( ms )`, which skips a NULL, or `SUM( sum_ms ) / SUM( timed )` over the rollup, while `avg_peak_mb` divides by every request. **The mean of nothing is null.** An average over no timed row is NULL in SQL, so `avg_ms`, `min_ms` and `max_ms` are null where no timed request reached a URL or a scope, and so is `avg_peak_mb` for a scope with no request at all. A `Stats_Query` sort ranks a null last in either order. Every reader carries the null to its surface and shows it as unmeasured, never as 0, because a 0 reads as fast: a dash in a table or a brief, no bar on the URL table, and a gap in a chart, where a count or a sum of none stays a real 0. **Revisit if** an evicted or aborted request ever carries a duration someone measured, which would make it a sample like any other.

## Decision 25: Read tools and TUNE-scoped write tools share one MCP session, and every tool result is fenced

Every read tool returns recorded site traffic, and a visitor writes part of it. `dump_request` carries the `environment_v3` entry, whose `m` map is the curated `$_SERVER` block: `HTTP_USER_AGENT`, `HTTP_REFERER` and `HTTP_X_FORWARDED_FOR` are the visitor's own prose, capped at 256 bytes and stripped of control characters but otherwise verbatim. Serialized into a tool result with no delimiter, that prose reaches an agent's context indistinguishable from the server's own answer — and the same session may hold `rules_upsert` and `rules_delete`, so the agent it is talking to can edit the logging ruleset. What forced the decision is that pairing: recorded visitor text arriving unmarked beside a write tool.

One marking serves both exits, named once. A value recorded from site traffic leaves inside `<site-data>…</site-data>`, and the reader is told in standing text that whatever sits inside that tag is recorded data and never an instruction. `MCP_Controller::fence()` encodes every reply with `wp_json_encode( $reply, JSON_HEX_TAG | JSON_UNESCAPED_SLASHES )` and wraps the result, so a string reply encodes as a JSON string and the reader needs no second rule for it. `JSON_HEX_TAG` is what makes the fence unbreakable from inside: every `<` and `>` in the payload becomes `\u003C` or `\u003E`, so no visitor string can carry a literal `</site-data>` and close the tag early. The `initialize` reply's `instructions` field carries the standing text alongside the measurement caveat. An `isError` result is left alone, because that text is the site's own message rather than anything a visitor wrote. The browser's own exit, `src/overview/askBrief.js`, applies the same marking to the values a log record wrote — the subject URL and an entry's message — escaping `<` as `\u003C`, the spelling the MCP fence produces, collapsing control characters to one space and capping at 512 characters with a trailing `…`; both prompts it builds carry the same sentence. Rule ids, rule patterns, span names, hashes, rids and numbers stay bare, because the operator or the server wrote those. `Ask_Assembler::entry_shape()` ships the `environment_v3` entry with no body at all: its map is the visitor's headers and the peer, and the brief's `env` field already carries the allowlisted facts, so a second list over the map would only drift from the writer's.

Two alternatives were weighed and rejected. The first was a separate write-only session, so that no session holding a read tool could also edit the ruleset. That does not remove the injection, it only moves it: an agent holding both sessions reads the same recorded data out of one and writes through the other, and the operator now maintains two credentials for a boundary the agent crosses in a single turn. The second was dropping the write tools entirely. That would cost the surface its point — the ruleset is exactly what an agent investigating a slow URL needs to widen — for a defence the fence already provides more cheaply. The scope is subtractive and bounded by the minting user, so a `read` session offers no write tool at all and a `tune` session minted by someone who holds nothing does nothing; the operator chooses `tune` at mint time knowing the agent can then edit the logging ruleset and nothing beyond it, since the vault and the fleet are substrate `manage` and unreachable here. The fence plus the `initialize` instructions are the defence, and the blast radius stays recoverable: the ruleset is re-seeded from the config file and the schema through `Rule_Set::seed_from_config()`.

The cost is real. Every tool result is JSON, so an agent client that parsed a string reply as text has to strip the fence and decode; the hex-escaped angle brackets make a raw result harder for a human to read in a transcript; and the wrapper adds bytes to every reply. The marking is also advisory — it tells a reader what the bytes are, and a model that ignores standing instructions is not stopped by a tag. **Revisit if** MCP gains a transport-level way to label untrusted content, or a write tool appears whose blast radius is not recoverable from the config file, at which point the write half needs its own session after all.

## Decision 26: A merged transport node keeps the statements it ran

The fold replaces a request's entries with one node per path, and the statements go with them. A real `/wp-admin/post.php` record says `sql: WP_Query->get_posts` ran 667 times for 58.3s, and cannot say what any one of them was — the question a repeat that size raises. [Decision 22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) argues the other way in as many words, that naming the TABLE "says `SELECT wp_posts` ran 156 times and never which code ran it, and which code ran it is the only version of the question worth asking." That holds for the SPAN'S NAME, and it still does: `l` is the caller, `Flame_Tree::node_name()` merges on it, and this decision does not touch it. What it revises is the unstated second half — that the statement is therefore worth nothing — which is true only while the entries survive to carry it. In a folded record they do not, and the caller alone cannot separate one query repeated 667 times from thirty different ones.

So a merged node whose span is one of the logger's own round trips — `Flame_Tree::is_transport_span()`, the `sql` and `http` states — carries `shapes`: the distinct statements or URLs it ran, each with a call count and summed milliseconds. **Only those two**, because their message is a bounded identifier by construction: `without_literals()` collapses `IN (?,?,?)` to `IN (?)` and every literal to `?`, and a redacted URL is one line. A hook's message is prose of any size and any cardinality, so it gets no table. **The identifier is the FIRST non-empty `m` of the pair**, because which half carries it is the producer's business and they disagree: `http_start` writes the URL and its complete the status code, `query_end` writes the statement and its start nothing. Reading the close alone builds a table of `200`s — and an `http` complete never stands in for a start a checkpoint lost, for the same reason.

Three bounds, and the third is the one that matters. A shape is cut to `MAX_SHAPE_BYTES` (512), measured against 308,395 real `sql` completes here — mean 146 bytes, median 122, p99 488 — so it truncates 0.6% of statements. A node keeps `MAX_SHAPES` (24) rows, one slot of which is reserved for the `…` bucket everything else folds into; one record in 184 had a node exceed it. A full table EVICTS its cheapest row rather than refusing the newcomer, because the statement worth naming is as likely to arrive twenty-fifth as first and first-seen-wins would bury it on exactly the record this exists for. **And the record itself is bounded, at `MAX_RECORD_SHAPE_BYTES` (32KB of new shapes), because the per-node caps bound a NODE and a record's node count is `O(distinct paths)` by design**: the heaviest real folded record here carries 117 transport nodes against 73KB of record, so per-node caps alone admit megabytes. The POOL sizes that number rather than the record: `Request_Builder_Node` holds 300 requests in flight against an entry budget worth ~18MB, so 32KB apiece keeps the worst case near half of it, and that heaviest record — whose own statements cost 33.7KB — is the one shape that spends its budget and buckets the tail. **The budget charges what the table GREW by**, never what a statement the bucket swallowed would have cost: charging the attempt let one high-cardinality caller spend 65,603 bytes to store 9,206 and strip every other node's table, measured at 7.1×. It charges a ROW's cost too, `SHAPE_ROW_BYTES` beside the key's own length, because a byte budget alone bounds bytes and not rows: at eight-byte shapes, which `without_literals()` readily produces, the rows cost twelve times what the budget thought it had allowed. A spent budget refuses a new row the table has ROOM for, and nothing else: a statement the node already keeps costs no bytes to count, and a full table's eviction trades one row for another and pays only the difference, which it may do while spent so long as the new key is no longer than the one it replaces — refusing every trade would bucket the worst statement on the one record shape that ever spends its budget, and admitting a growing one carried a record to 3.2× the budget, one filled table at a time. A folded envelope is also invisible to `Request_Builder_Node`'s pressure loop, which counts `entries` and skips a folded one, so nothing downstream would catch the growth.

The statement is recorded data, so it leaves through [decision 25](#decision-25-read-tools-and-tune-scoped-write-tools-share-one-mcp-session-and-every-tool-result-is-fenced)'s marking like any other: `askBrief.js` gives it a fenced line of its own rather than a slot in the `numbers:` list, which a reader splits on spaces and a statement carries plenty of.

`shape_ms` is a MEASURED sum, unlike the node's `value`, which [decision 12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact) calls a rendering artifact that every producer raises to cover its children. Nothing raises `shape_ms`, and nothing may: it is the time those statements took. The pair is positional, `[ calls, ms ]`, with no named constants: a closed 2-tuple read by `Findings::worst_shape()`, `merge_shapes()` and one React function, where naming its two fields means naming them twice, in two deploy units.

**An unfolded record gets the same table, derived rather than stored.** Its entries survive, so the log table shows every statement — but a brief ships sixty entries, so for any reader but the detail view the finding is the only place the answer can land. `Findings` folds the record's entries transiently through `Flame_Fold` and reads each node's table by its name path, which runs the one set of rules rather than a second, and adds nothing to the stored flame. That fold passes no record budget: the budget exists for a pool of in-flight envelopes, and a fold built, read and dropped holds nothing against it — keeping it would bucket a slow statement that first appears late and name a cheaper one.

*Alternatives rejected:* keeping ONE representative statement, the slowest instance's (costs no table, and answers "was it one query or thirty?" with a guess); a digest at the producer, in `App\Core::query_end` (the producer cannot know the record will fold, and a per-request digest would ride the firehose against `MAX_DATA_SIZE` on every request that never folds); the table on the per-URL aggregate (cardinality across thousands of requests is unbounded, and the aggregate's numbers are per-request means, which a summed pair is not — `merge_flame_children_incremental()` rebuilds each node from four keys, so it cannot leak there by accident). **Revisit if** a THIRD span kind earns a table, which would make "is it transport?" the wrong question and a producer-set marker on the entry the right one — `Log_Manager::message()` already merges arbitrary keys, and `Request_Builder_Node` already allowlists such fields beside `keep`. The sibling producers are the reason it would come up: pyrobase's `customquery_sql` and gyrobase's `search_query` and `<tag> (sql)` spans all carry an already-shaped statement, and none of them is named `sql`.

## Decision 27: The platform's requests to itself are worker traffic, named by path

The cron loopback, the substrate's own endpoints — `/wp-json/newspack-nodes/v1/{auth,command,health/runtime,messages/stream,workers/spawn}` — and this plugin's MCP route, `/wp-json/newspack-event-logger-nodes/v1/mcp`, are requests the platform makes to itself, and until 0.101.0 the shipped seed skipped every one, so the logger never logged the logger. A skip loses the record: a `command` poll that took nine seconds, or a spawn that fataled, left nothing to read. So the seed is the `/` log rule alone, and [`Log_Manager::PLATFORM_WORKERS`](../includes/class-log-manager.php) names each of those requests a worker by its path — `cron` for the loopback, `restapi` for the six REST endpoints — as the `worker_type` entry `log_worker()` writes right after `process (start)`. The six share one name because the path already names each endpoint and `resolved_request_url()` appends the type as the URL's query, so a name per endpoint only repeated it: `…/workers/spawn?spawn`. The substrate's own processes name themselves through `NEWSPACK_NODES_WORKER_TYPE`, and that wins where it is set; the path answers where it is not, which for the spawn endpoint is always, since the substrate sets the var at REST dispatch, after the request was opened. So the spawn endpoint is the one `restapi` row that is renamed: once the worker `Spawn_Controller` validated holds its lock, the substrate fires `newspack_nodes/worker_identified` (2.71.0), and `Log_Manager::identify_worker()` writes `worker_type` and `worker_partition` again into the open record. `Request_Builder_Node` takes the latest of each, so a spawned worker's record and its in-flight gyroscope row sit on that worker's row, and existing `…/workers/spawn?restapi` rows stop accumulating and age out. A refused spawn, or one that loses the lock race to a live worker, never announces, so it keeps `restapi` and cannot mint a row out of the request's own parameters. A worker's record keeps every entry, and its `requests` row carries `worker` 1, so every site-wide answer filtering `worker=0` leaves it out ([decision 15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site)).

**The REST paths are a copy the substrate does not know it owns.** `HTTP_In_Node`, `SSE_Out_Node`, `Spawn_Controller`, `Auth_Controller` and `Health_Runtime_Controller` declare those routes in newspack-nodes, and `MCP_Controller` this plugin's; `PLATFORM_WORKERS` spells them again as literals, root-relative and `wp-json`-prefixed, as the seed's skips did before it. They stay literals because `Spawn_Controller` and `Auth_Controller` name their routes inline, with no constant to read. `LogManagerTest` registers every route the platform serves and compares the set to the literals, so a route the substrate adds, moves or drops fails the suite. What no test reaches is chosen with open eyes: a subdirectory install or a site rewriting its REST base yields a request `platform_worker_type()` does not name, and it lands on the global rows as visitor traffic. That is a misclassification the overview would show, where the skip list's failure was a record that never existed. The map is not derived from `rest_url()` or `site_url()` because the seed never was, and because a copy that nothing checks costs one line per route where a derivation costs a `get_option()` per request.

*Alternatives rejected:* keeping the seed's skips (loses the record, and every stored ruleset already carries whatever skips its operator kept); the substrate stamping its own endpoints (its env var is set at dispatch, after `process (start)`, so the stamp would arrive too late for the entry that names the worker); a `Rule` property marking a rule's matches as worker traffic (a sixth knob, its serialization and its editor control, to say what a few literal paths say). **Revisit when** every substrate controller publishes its route path as a constant or filter this plugin can read, at which point the copy becomes a read, or when a platform request is seen in the overview's global totals, which is the symptom this decision accepts.

## Decision 29: Every reader dates from the tick, and a reply reads it once

Every stats reader dates from `Core::$now`, never from a wall read of its own. That tick is not still: `Core::right_now()` writes it, so every caller re-pins it, in a worker and in a request alike. Two examples from this plugin, not a list: the firehose logger re-pins it once per line `Log_Manager::message()` writes, and a partition write lock re-pins it as it is acquired. Loading the substrate's `Core` class pins it first, through `Core::reset()`, so a verb has a tick before it runs. A reader wanting one instant reads it once and passes it down, and a test pins `Core::$now` directly. The flame builder reads it once per record, in `buffer_request()`, to clamp the record's completion to the tick that brought it ([decision 19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in)).

**So a reply reads that clock ONCE, at its entry, and passes it down.** Any `right_now()` caller can advance the tick while a reply runs, the firehose logger once per line. Each `Performance_CI_Node` verb reads `self::now()` in its handler and hands the instant to everything beneath it that names a window — `Bucket::last()`, `Bucket::selection()`, the rate's `elapsed_seconds()` and the leaderboard's 24 hours — so one reply is one window: two panels of one overview cannot answer for different buckets, and a rate never divides by a window its rows were not read over. One list is the exception, on purpose: a server-scoped `overview` names the `servers` the overview-prefetch job stored, the picker's list, which no scope changes and which is up to two intervals older than the reply's window ([decision 37](#decision-37-the-overview-reads-a-jobs-snapshot-for-two-intervals)); it arrives as the `servers` parameter, never a second read.

*What it costs:* an `int $now` on each private `Performance_CI_Node` reader that names a window — `answer_overview()`, `url_page()`, `url_detail()`, `answer_query()`, `window()` and the brief assemblers among them.

*Alternatives rejected:* a fresh wall read per reader (`\time()` or `Core::right_now()`), which lets a reply's panels straddle a bucket — `right_now()` also WRITES the tick, so a reader calling it moves the clock its own reply is dated from; a stamp pinned in `dispatch()` for the readers to consult, because a static stamp is a second clock with a lifetime of its own, which every caller and every test must remember to set, where a parameter makes the instant explicit at each call; and changing `Log_Manager::message()` to stop re-pinning, which leaves request scope with a tick frozen at class load and starves the debounce that reads it. **Revisit if** the substrate's tick ever holds still between drains, with no `right_now()` caller outside the drain in either scope, at which point `Core::$now` is itself one window and the parameter can go; or if a reply ever needs two instants on purpose, which would be a second parameter named for what it measures, never a second read.

## Decision 31: A snapshot node's replay counts each record once

A plain stop leaves the reader's cursor ON the record in flight, and the successor replays it ([substrate ADR-14](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)). Every stop but a bare clean one is plain: one carrying a failure, one combined with a failure, and one no `deferring()` bracket turned clean. The worker's shutdown checkpoint commits that cursor after the snapshot node's `save_state()` has written what it buffered, and what it buffered often includes the very record the cursor still points at. A replay must therefore not count it twice.

`Flame_Builder_Node` counts a record once by its rid. `fill()` always stores and forwards the record's flame and buffers its rows; the `requests` row is an insert-ignore on `rid`, and its rollups ride as its `then` ops, applied only when it inserted, so a replay of a record already written adds nothing, however far back the replay reaches. `save_state()` writes the buffer, expires the category window, and carries nothing; a replayed expiry is counted once by its `window_expiry` row, and a successor reads the window's watermark from the file. The replayed record also runs through the successor's auto-tune checks, whose decisions `Auto_Tuner_Node` skips when they leave the rule unchanged.

`Request_Builder_Node` counts a line once by its sequence: every firehose line carries its request's sequence number `n`, and a line below the request's expected number is dropped as `INFO: duplicate message`, so a replayed line joins nothing twice.

*What it costs:* the `requests` table's unique `rid`; a replayed record's flame is written to the flames partition a second time.

*Alternatives rejected:* counting the replay twice, as a reader does that commits the lowest in-flight offset beside a cache that has already folded the messages past it, so a restart replays those and folds them again, which here would inflate the counts, the sums and the leaderboards by the record in flight ([decision 2](#decision-2-sums-not-means)); a crumb of the last record buffered, carried in the checkpoint, which names only the one record under the cursor and so guards a subset of what the insert-ignore guards; and staging each record's rows until its `deferring()` bracket closed cleanly, which puts a second buffer and a merge on every record to guard against a stop that lands once per worker life.

**Revisit if** a row can be counted without a `requests` row to carry the insert-ignore — a rollup written apart from its request.

## Decision 32: A builder tells its upkeep on its own worker record, and every narration write is a guarded forward

`Flame_Builder_Node` and `Request_Builder_Node` tell their routine writes and upkeep on the worker's own request record, as `keep`-marked spans and points through the [`Narration`](../includes/trait-narration.php) trait, and never through stderr, which feeds the Error Log. The Error Log therefore hears only faults. Everything a line says rides its `m`, because the stored record keeps an entry's `m` and drops every other producer field. Counters accumulate per name in the node's tally, and writing that name's line resets them.

Each narration line is a write to the firehose Partition, and a Partition write is a point where the worker's cooperative stop can rise. A snapshot node therefore sends every narration line through `guarded()` ([substrate ADR-14](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)), as it sends any downstream forward: inside the `deferring()` bracket of the message or tick in progress, the stop waits for that work to finish and then leaves clean. `spanned()` guards its `(start)` and its `(complete)` apart, through `Log_Manager::timed()`'s `$write`, inside a `deferring()` bracket of its own that is itself one guarded forward, so a stop the start raises still runs the step and closes its span — where a message's or tick's bracket is open it then waits for that work, and where none is, as in the restore `Consumer_Node::init_position()` runs before the first message, it leaves once the span has closed. Unguarded, the start of the `stats sweep` span around a clean stop's flush stops the worker before the flush writes its batch. An eviction or a fold tells no line of its own, only a count the next `requests writes` rollup carries, because both track visitor traffic; and a `requests checkpoint` is told only when its carry may have moved since the last one told. A request builder's narration, read back off the firehose, is folded but counts as neither a line nor a move: counted, a builder reading its own record, or two reading each other's, would tell for ever. The trait declares `guarded()` abstract, so it composes only with the substrate's `Deferred_Clean_Stop`.

*What it costs:* a closure per narration line, and one per span half, where a record is started; nothing where none is, because with no started logger no line is built.

*Alternatives rejected:* stderr diagnostics, which never stop a worker, since `Event_Framework::stop_check()` does nothing inside a stderr write, but put every routine line in the Error Log beside the faults; and one `guarded()` around a whole `timed()` span, which skips the step itself when its start write raises.

**Revisit if** narration grows past a few hundred lines per worker lifetime, or an operator needs routine lines in the Error Log.

## Decision 34: Stats live in SQLite Tables, and nothing repairs a loss

Memcache evicts, and every mechanism the stats grew to survive that — the durable mirror of decisions [10](#decision-10-the-durable-mirror-writes-a-bucket-once-when-it-closes-under-a-key-that-carries-no-install-scope) and [11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped), the sweep of [decision 33](#decision-33-no-dashboard-reads-the-mirror-the-flame-builder-sweeps-it-back-into-memcache), held frames, the probe of lost lists — repaired a loss. A SQLite file evicts nothing before the window its schema declares, so none of them exists.

**One Row_Table per partition, declared in the topology.** [`flame-builder.tsl`](../topologies/flame-builder.tsl) declares `make_node Row_Table flame-facts Flame_Facts` ([substrate ADR-34](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-34-a-table-may-hold-declared-rows-sqlite-only)), and [`Flame_Facts_Row_Schema`](../includes/class-flame-facts-row-schema.php) declares thirteen tables in `{base}/tables/flame-facts.p{N}.sqlite`:

| Table | One row per | Key | Window |
|---|---|---|---|
| `requests` | completed request: its `rid`, `bucket`, `finished_at`, `started_at`, the log position its record sits at (`partition`, `segment`, `offset`, `length`), `server_id`, `url_id`, `status`, `method`, `country`, `ua_id`, `ja4_id`, `from_id`, `worker`, `profiled`, `error`, `ms` (NULL when untimed) and `peak_mb` | `rid` | 2,016 buckets, seven days |
| `urls` | URL: `id`, `hash`, `server_id`, `path`, with an FTS5 index over `path` | `hash` | while a `requests` or `timings` row names it |
| `servers`, `agents`, `ja4s`, `froms`, `categories`, `entries` | name a row repeats: `id`, `name` | `name` | while a row names it |
| `timings` | bucket, server, URL, category and entry, with `listener` and the summed `ms`, `calls` and `requests` | `bucket`, `server_id`, `url_id`, `category_id`, `entry_id` | 300 buckets, 25 hours |
| `timings_site` | bucket, server, worker, category and entry, with `listener` and the same sums | `bucket`, `server_id`, `worker`, `category_id`, `entry_id` | 300 buckets, 25 hours |
| `requests_hourly` | hour, server, status class, method, worker and country, with the summed `count`, `timed`, `sum_ms`, `sum_peak_mb` and `errors` and the greatest `max_ms` | its six fields | 168 hours, seven days |
| `category_window` | category, entry and worker, with `listener` and the summed `ms`, `calls` and `requests` and the greatest `last_bucket` | `category_id`, `entry_id`, `worker` | 300 buckets, 25 hours |
| `window_expiry` | bucket expired, so a replayed expiry subtracts nothing twice; the newest is the window's watermark | `bucket` | 300 buckets, 25 hours |

A `bucket` is `Bucket::id()` of the five-minute bucket a request finished in ([decision 19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in)) and an `hour` is `Bucket::hour()`. A key column holds no NULL, so `requests_hourly` files an absent status class as 0 and an absent country as `''`, and readers spell both `Unknown`. `urls` and the six name lookups store each repeated string once, the URL, server, agent, JA4, From, category and entry each as `<name>_id`, and the rows naming it carry its id; an id is the partition's own, so a reader joins it inside that partition. `method`, `country` and `error` stay text. A category's own total is its row whose entry is empty. The Table tick purges each table past its window, then each lookup row no table it is `retained_by` still names, and in turn the rows those alone named, and SQLite reuses the freed pages, so a file plateaus at its windows.

**The partition's builder is the file's only writer.** `Flame_Builder_Node` buffers each request's rows and sends the buffer as one `ROWS` batch, one transaction, through the substrate's `Table_Client::write_rows()`: every 5 seconds, at every checkpoint, and as soon as it holds 1,000 requests (`BUFFERED_REQUESTS_LIMIT`) or 20,000 ops (`BUFFERED_OPS_LIMIT`), so a replay commits as often as it buffers. A batch names each URL and each lookup name once. The `requests` row is an insert-ignore on `rid`, and its rollups ride as its `then` ops, applied only when it inserted — `requests_hourly` always, `timings` and `timings_site` when the request was timed and profiled, and `category_window` when its bucket is newer than the window's watermark — so a replay of records already written adds nothing ([decision 31](#decision-31-a-snapshot-nodes-replay-counts-each-record-once)). The checkpoint carries nothing: the builder reads the window's watermark, the newest `window_expiry` bucket, from its own file once, before its first fold. A batch that fails raises ([decision 3](#decision-3-stats-reads-fail-soft-a-stats-write-raises)).

**Readers attach every partition.** `App\Stats_Query` reads through `Row_Table_Node::read()`, which attaches each partition's file read-only into one connection, and answers in one statement over all of them ([decision 36](#decision-36-the-query-vocabulary-is-fixed-no-sql-from-outside-a-picker-chooses-the-rollup)). A partition whose builder never wrote has no file and is not attached, so it holds no rows.

**Migration:** [decision 5](#decision-5-a-stats-schema-change-is-a-version-bump-and-a-rebuild-and-nothing-in-this-code-migrates).

*What it costs:* `pdo_sqlite`, with FTS5, on every host running the flame builder; disk under `{base}/tables`; a stats reader bound to the flame builder's host and filesystem; at most 8 partitions in every fleet, down from 16, because the substrate's `Spawn_Coordinator::MAX_PARTITIONS` clamps every topology to keep a reader's attachments under SQLite's ten, so a site configured for 9 to 16 partitions runs 8 and loses the workers for `p8` and above; and a substrate floor of 2.111.0.

*Alternatives rejected:* three key-value Tables of pre-built key families, which answer only the cross-cuts an accumulation is built for, and measured about 11 GB on a hub taking 2.3 million requests a day; memcache with a better repair, each round of which found holes in the last; the substrate's `wpdb` arm, durable and shared across hosts, which puts every flush on the site's database and is sized for low-volume Tables; and one file shared by every partition, whose writers would contend.

**Revisit if** a stats reader must run on a host other than the flame builder's, or a site needs more than 8 partitions.

**Superseded by [decision 36](#decision-36-the-query-vocabulary-is-fixed-no-sql-from-outside-a-picker-chooses-the-rollup).** This record stored each chart series as one key an hour holding its twelve five-minute slots, so a chart read 25 hour keys to draw 288 slots, with the leaderboard one sum an hour beside them. Under decision 36 a chart is a `query` grouped by `bucket`, its top 20 tuples ranked over the window, and the leaderboard reads the `timings_site` rows.

## Decision 36: The query vocabulary is fixed; no SQL from outside; a picker chooses the rollup

Every performance reader asks the rows one question in one vocabulary, [`App\Stats_Query`](../includes/app/class-stats-query.php): a source, `requests` or `timings`; fields to group and filter by; measures; a bucket selection; a search of URL paths; a sort and an order; a page; or a top-N. The fields and the measures are fixed tables, `Stats_Query::FIELDS` and `MEASURES`, each name mapping to a SQL expression over a table's columns. **No SQL text enters from outside** *(Chris, 2026-10-15)*: a name reaches the statement only through those tables, an unknown source, field, measure, sort or order is refused naming it, and every value binds. The `query` verb and the MCP tool `performance_query` hand a caller the vocabulary; `overview`, `urls` and `dump_url` build their specs from it, and `Stats_Query::newest_requests()`, the URL modal's request list, is the one fixed statement beside it.

**One statement spans every partition.** `run()` builds a `UNION ALL` of one arm per attached partition, each joining its own `urls` and `agents` before the union, because their ids are the partition's own; each partition's arm groups its own rows when every measure composes, and the union merges the partials, so a total and a top-N are exact; a percentile or a distinct count still reads whole rows. An answer without `top` holds at most `MAX_LIMIT` (1,000) rows, and its page starts at most `MAX_OFFSET` (10,000) rows in; a `top` answer holds every time row of its tuples.

**A picker chooses the table** (`Stats_Query::table_for()`). A timings spec reads `timings` when a URL is grouped, filtered or searched; else `category_window` when it spans exactly the window's 288 buckets and names only its `category`, `entry`, `listener` and `worker` fields, and only while every partition's newest `window_expiry` bucket stands one before the range, which `run()` checks and otherwise answers from `timings_site`, the table any other timings spec reads. A requests spec reads `requests_hourly` when every field and measure it names, `top_by` among them, is one the rollup keeps, it names no search, and every bucket range covers whole hours, and `requests` otherwise. The picker chooses a rollup only where it answers exactly, so a rollup changes a question's cost and never its answer. A `query` selection names at most as many buckets as its source keeps, `Stats_Query::retention()`: the 2,016 of a week of `requests` and the 300 of 25 hours of `timings`, each read from the schema's retention, so the week a rollup was built for is one question; the URL table, the charts and `overview` keep the chart's 288 (`Bucket::MAX_SELECTION`). The two rollups exist for the slowest questions the raw rows were timed answering: seven days by day and country, about 5 s over a four-partition hub; and the 25-hour category chart and leaderboard, 2.0 s and 3.9 s over one partition.

**A top-N is exact and keeps no `Other` row.** Under `top`, at most `MAX_TOP` (20), the tuples of the group's non-time fields rank by the sum of `top_by` over their time rows, highest first and ties by their values, and the answer holds every `bucket`, `hour` or `day` row of the top ones, in rank order. One statement groups the union by time and tuple, then ranks the grouped rows through window functions (`SUM() OVER`, `DENSE_RANK()`, `MAX() OVER`). `top_by` must be a measure that adds across buckets, the `ADDITIVE` list: for `requests` `count`, `timed`, `sum_ms`, `sum_peak_mb`, `errors` and `count_2xx` to `count_5xx`, for `timings` `ms`, `calls` and `requests`. A mean or an extreme summed over buckets would rank by a number nobody measured. The tuples outside the top are not folded into an `Other` row: every answer carries `groups`, the tuples the selection holds under `top`, so a chart says it shows the top 20 of 63 instead.

*What it costs:* a question outside the vocabulary needs a field or a measure added in code; a week broken down by a high-cardinality field, `ua` or `ja4`, scans the raw rows, about 5 s on a four-partition hub; and a `top` takes no sort, limit or offset, because its rows come in rank order.

*Alternatives rejected:* SQL text or a clause from the caller (a second language every client couples to, on a READ verb any dashboard session holds); a pre-built breakdown per combination of fields (the twenty key families decision 34 replaced); ranking in PHP across partitions (an exact top-N needs every partition's whole grouping); and an `Other` row for the tail (a sum of tuples nobody can filter to or open).

**Revisit if** a reader needs a field from the other source — timings filtered by a request's status or country — which needs per-request timing rows; or if a question the dashboards send on every refresh misses both rollups and scans raw rows past a second.

## Decision 37: The Overview reads a job's snapshot for two intervals

On eln.newspackstaging.com, after the stats rebuild, every question the Overview polls every 15 s took seconds: 6.0–6.9 s for count and mean by bucket, 8.2–8.3 s for the top 20 buckets by status class, 23.5 s for the URL table's top 200 by count, and 7.8–7.9 s for the 25-hour category chart. Aggregating inside each partition, a covering index and the category window (decision 36) brought every chart under a second on the eln copy, but the live site stayed slower. Under newspack-nodes 2.111.3, which maps each partition file and keeps temporary B-trees in memory, `overview` took 18.6 s live, the URL table's default page 33 s, the request chart 5.8 s by server and 3.6 s by status class, and the category chart 6.2 s, and any other sort, page, server or Include Workers on the URL table ran live at that cost. Atomic's gateway cuts a request at 120 s.

**One job builds the snapshot, once an interval.** [`App\Overview_Prefetch`](../includes/app/class-overview-prefetch.php) is the `eln_overview_prefetch` job handler. It binds each question in [`includes/app/stored-answers.json`](../includes/app/stored-answers.json) — `overview`, the request chart by `server` and by `status_class`, and the category chart, token for token as a default Overview poll sends them, which `usePerformanceGraph.test.js` holds to what the hook puts on the wire — against the verb's declared args and answers it live through `Performance_CI_Node::answer_live()`. The request chart is answered twice because the page's default breakdown, `server`, falls back to `status_class` over one server or under a server filter (`activeChart()`), and the job cannot know which the reader's fleet draws. It then hands those answers to [`App\Url_Snapshot::publish()`](../includes/app/class-url-snapshot.php), which builds one SQLite file:

- **`servers`**, `( id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE )`, each server of the window by an id the file assigns in name order, so ordering by id orders by name.
- **`urls`**, one row per URL over the window's 288 buckets: `Stats_Query`'s `url` group over every partition with `Performance_CI_Node::URL_MEASURES`, so each row carries its hash, its `server_id`, its path, its `worker` flag and every column a `urls` row shows. One statement attaches every partition's file read-only, groups each partition's requests by URL and merges the partials by hash into a scratch table, which the build copies into `urls` in hash order and drops ahead of the indexes, which reuse its pages. A row's rowid therefore ranks as its hash does.
- **Two indexes per sort** the `urls` verb takes: its keys alone, `urls_<sort>`, for the site-wide page, and `server_id` then its keys, `urls_server_<sort>`, for one server's, so every page reads its own rows in order and none sorts. Each key that may be null (`avg_ms`, `min_ms`, `max_ms`) takes a second pair, `urls_<sort>_null` and `urls_server_<sort>_null`, on `k IS NULL, k`. The URL sort's `urls_url_name`, on `server_id, path`, serves both scopes. A page's ORDER BY comes from `Stats_Query::ranking()`, the one rule a live sort follows too: a null last in either order and ties broken in the sort's own direction, spelled ascending as `k IS NULL, k` so the `_null` index serves it. A live page breaks its ties by the hash; the snapshot breaks them by the rowid, which ranks as the hash and which every SQLite index carries, so no index stores the hash and a backward scan serves the other order.
- **`totals`**, one row per view and scope — every server as `server_id` 0, then each — holding the header's count, means and errors and the URL count, which is the pager's `rows`. Each is folded from the URLs' partials by `Stats_Query::fold()`, the definition a live query merges its partitions by, so `avg_ms` is `sum_ms / NULLIF( timed, 0 )` and `avg_peak_mb` `sum_peak_mb / NULLIF( count, 0 )` in one place.
- **`answers`**, the four answers as JSON under `Overview_Prefetch::key()`, the verb and an `md5` of its bound args, and **`meta`**, when the job built the file and when it expires: two intervals on.

The substrate owns the file (its ADR-35): `Row_Table_Node::build( Flame_Facts_Row_Schema::class, 'flame-facts.job', … )` writes a uniquely named build beside `{base}/tables/flame-facts.job.sqlite` with journaling off and the partitions mapped, renames it over the published file when the build answers, and removes the build in a `finally`; `Row_Table_Node::open_snapshot( 'flame-facts.job' )` opens it, and uninstall erases it with `remove_snapshot()`. No reader sees a half-built file, a reader still open on the old one keeps its inode until its request ends, and the file is never in WAL mode, so nothing sits beside it. A build that throws leaves the last publish standing; a fleet with no partition file yet publishes nothing, and a fleet declaring no Flame_Facts table refuses, because `build()` resolves the table before anything else. The substrate's `Log_Cleaner::sweep_tables()` sees the snapshot as an undeclared Table file and keeps it while it is newer than its hour's grace, which each publish's rename renews; `wp nodes gc --force` removes it, and the verbs answer live until the next publish. A job its successor has overtaken, `queued_at` an interval or more behind the clock, runs nothing; an answer the stats could not open for (`available` false) is never stored, so an outage is not served for two intervals; and a job naming no `queued_at`, or an `interval` below one second, fails, so the JobWorker records it.

**Being a worker is a property of the URL.** A URL is a worker or it is not (decision 27 decides it by path), so one row serves both views: the default view keeps the rows whose `worker` is 0, and Include Workers keeps every row.

**One worker runs the job.** [`Overview_Prefetch_Tick_Node`](../includes/class-overview-prefetch-tick-node.php), which `flame-builder.tsl` mounts at 120 seconds, queues the job both ways a small job travels (decision 7): onto `jobfeed.p0` for a spoke's `job-feed`, and as a firehose `job` entry for a hub's `job-router`. A spoke runs it from `jobfeed.p0`. A hub's entry lands on the `firehose.p{N}` its borrowed request id hashes to, and the handler declines on any worker bound to a partition other than 0, so partition 0's JobWorker is the file's one publisher. A hub with several partitions therefore publishes only on the intervals its entry lands on p0, and its verbs answer live once the snapshot has expired. A spoke's firehose copy reaches its hub as a `remote_job` no remote handler claims, and a site with no job topology runs no job, so its verbs answer live.

**The verbs read the snapshot, and answer anything else live.** They name a server by its name and a URL by its hash, as a live page does: a page and the totals map the name to its id through `servers`, a name the file lacks answering no rows and zero totals, and a page answers each URL's hash and server name. `Url_Snapshot::open()` opens the published file read-only and `immutable`: nothing writes a published file, so a reader takes no lock and reads no journal. `urls` with no search, no bucket selection and no filter answers off it for any sort, order, server, Include Workers, `limit` up to `MAX_LIMIT` and `offset` up to `MAX_OFFSET`: its rows off the sort and scope's index, its header and `rows` off `totals`, its slowest ten off the scope's `avg_ms` index, shaped by the same `Performance_CI_Node::url_reply()` as a live page. `overview` and `query` read `answers` by key, and only for a key the job stores, so a chipped or re-dimensioned chart answers live without opening the file; a server-scoped `overview` reads its totals and leaderboard live and its `servers` off the stored overview, because no scope changes that list; a stored answer that will not decode answers live and is said once a window, as a file that opens but will not read is. A snapshot past its expiry, no file, a file that will not open (said once a window, decision 3) or any other question answers live; a search stays live because it is fast already. Every answer carries `as_of`: a served one, when the job built the snapshot.

The job's record carries where its time goes: each answer is a `prefetch answer` span labelled with its question, and the build a `snapshot build` span holding `snapshot group`, `snapshot copy`, one `snapshot index` per index and `snapshot totals`; the architecture guide's table of the job's spans says what each holds. The job runs inside `Event_Framework::uninterruptible()`: each span line is a Partition write, where a worker's cooperative stop could otherwise rise and discard a half-built snapshot, so a stop that falls due waits for the publish and raises at the next pump.

Measured on eln: the snapshot builds in 53.5 s — the group 19.1 s, the servers and the copy into `urls` 4.3 s, the 19 indexes 28.6 s, the totals 1.4 s — into a 462 MB file of 807,314 URLs, 320 MB of it indexes; the four answers take 28.2 s, `overview` 15.9 s of it, so a run comes to 74–92 s, well inside the 240 s a snapshot serves. A page reads in 1.1–1.2 ms and a page at offset 9,900 in 16–17.5 ms, site-wide and for every server alike, the largest's 399,000 URLs included.

*What it costs:* a default Overview is up to two intervals old; the job spends the fleet 74–92 s of SQLite an interval on eln, and a 462 MB file, whether or not anyone is looking; and a question the dashboard's defaults change no longer matches a stored answer until `stored-answers.json` changes with it, which the jest parity test refuses to let drift.

*Alternatives rejected:* storing every shaped page the dashboard can ask, 672 of them across the sorts, orders, first pages, views and servers (Chris chose the indexed table, which answers every page and every offset from one file); a keyed `sqlite` Table one job worker built outside a topology and named into its own graph, which held only the default page and left every other sort, page, server and view live; one row per URL per view, because a URL is a worker or it is not, so the default view is a filter on the one row; a `url_window` rollup, whose merge cost what aggregating the raw rows in each partition costs — 1,013 ms against 1,059 ms for the top 100 by count with the group count, because eln's URLs are 75% unique in a day; ADR-18's `backed_by()` read-through, because a request-graph mount refuses writes, so a read-through cannot warm; and a wpdb Table for the four other answers, durable and shared by every host, which would expire on a clock of its own beside a file expiring on another and write each interval's JSON into the site database. Chris chose to store them as JSON rows in the snapshot's `answers` table, where they live and expire with the file.

**Revisit if** a run outlasts two intervals, so a snapshot expires before the next one publishes, or a server's page reads past a second.
