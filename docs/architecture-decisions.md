# Architecture Decisions

The load-bearing design decisions of the event logger. "Fixing" one usually reintroduces a bug already paid for. Each record states what forced the choice, what it costs, what was weighed against it, and the concrete condition that reopens it. A **Revisit if** is a sufficient tripwire, not the only door: an argument on the merits also reopens a decision.

The numbers run without a gap. Code comments, docblocks, [`AGENTS.md`](../AGENTS.md), [`docs/architecture-guide.md`](architecture-guide.md) and the rendered sheets cite a record as "decision N", so a record that leaves takes every later number down by one, and every citation moves with it. The substrate keeps [its own series](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md) under the name `ADR-N`, and a "substrate ADR-N" here links to that file.

| # | Decision | Summary |
|---|----------|---------|
| [1](#decision-1-namespaced-memcache-schema) | Namespaced memcache schema | Every stat lives under `evlog:p{N}:` in a namespace the schema names, with the bucket key last, one TTL per storage role and a cap on every axis. |
| [2](#decision-2-sums-not-means) | Sums, not means | Buckets store raw sums; means are a read-time division. |
| [3](#decision-3-stats-fail-soft) | Stats fail soft | `Stats_Store` returns empty on a cache failure and never throws. |
| [4](#decision-4-settings-fan-out-is-a-node-graph-no-consumer-means-a-silent-no-op) | Settings fan-out is a node graph; no consumer means a silent no-op | Settings propagate through the `hub-control` node graph, and with no consumer wired the event is dropped. |
| [5](#decision-5-a-memcache-schema-change-is-migrated-by-the-flush-and-by-nothing-in-this-code) | A memcache schema change is migrated by the flush, and by nothing in this code | The substrate's salt rotation is the migration; no reader or writer carries a shape probe or a version component, and the mirror carries none either — an unreadable frame ages out. |
| [6](#decision-6-get_multi-batching-is-essential) | `get_multi` batching is essential | Every reader path multi-gets its buckets in one round trip. |
| [7](#decision-7-job_intake-for-4kb-jobs-the-firehose-for-4kb) | Job_Intake for >4KB jobs, the firehose for ≤4KB | Small jobs ride the firehose; anything over 4KB goes through `Job_Intake`. |
| [8](#decision-8-a-spokes-job-is-re-keyed-remote_job-when-the-hub-pulls-it) | A spoke's job is re-keyed `remote_job` when the hub pulls it | `Remote_Job_Rewrite_Node` flips a pulled `k:"job"` to `k:"remote_job"`, so the hub dispatches it against the map a handler registered for it there. |
| [9](#decision-9-a-requests-partition-is-its-id-hashed-by-the-substrate) | A request's partition is its id, hashed by the substrate | The firehose partition is the substrate's `hash_to_partition()` over the request id, on the write and on every read. |
| [10](#decision-10-the-durable-mirror-writes-a-bucket-once-when-it-closes-under-a-key-that-carries-no-install-scope) | The durable mirror writes a bucket once, when it closes, under a key that carries no install scope | The durable mirror writes a bucket once, at close, under an unscoped key that survives a flush. |
| [11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped) | The open bucket is durable in the OFFSETLOG until it closes, and the carry is capped | Held frames ride the offsetlog checkpoint under a byte budget, and the widest frame is dropped first. |
| [12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact) | A stat times the request; a flame value is a rendering artifact | Stats read `duration_ms`; a flame node's `value` is a layout width and never a measurement. |
| [13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) | A sequence-break marker is missing detail, not idle time | `entries (lost)` and `entries (aggregated)` mark missing detail, and no consumer reasons across one. |
| [14](#decision-14-a-server-scope-the-key-cannot-carry-rides-inside-the-value-and-is-applied-as-a-projection) | A server scope the key cannot carry rides inside the value, and is applied as a PROJECTION | The URL row carries its per-server split inside the value, and a server scope is a projection over the merged row. |
| [15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site) | The `urls` verb owns every URL-set fact; `overview` owns the site | The `urls` verb answers every question about the filtered URL set; `overview` answers for the site. |
| [16](#decision-16-the-breakdown-panel-is-always-mounted-and-says-which-kind-of-nothing-it-has) | The breakdown panel is always mounted, and says which kind of nothing it has | `BreakdownControls` never unmounts, and `breakdownState()` tells `pending` from `empty`. |
| [17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived) | The URL index is stored at TWO resolutions, and the coarse one is DERIVED | The URL index keeps a fine tier and a derived hourly tier, and one `fold_index_row()` reads both. |
| [18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants) | A stored value may be POSITIONAL, and then its indexes are named constants | The URL row and the category entry are positional, indexed by `Stats_Store` constants. |
| [19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in-and-a-write-into-a-folded-hour-reaches-its-fine-bucket-and-the-hour-key) | A request is filed in the bucket it FINISHED in, and a write into a folded hour reaches its fine bucket and the hour key | A request files under the bucket it finished in, and a write into a folded hour goes to its fine bucket and, while that key exists, to the hour key. |
| [20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) | Outbound HTTP is timed as a span, and a short-circuited request opens nothing | `pre_http_request` at `PHP_INT_MAX` opens an outbound-HTTP span; a short-circuit opens nothing. |
| [21](#decision-21-the-fold-keeps-the-close-of-any-span-the-kept-head-left-open) | The fold keeps the CLOSE of any span the kept head left open | The fold keeps the `(complete)` of every span its kept head left open. |
| [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) | Query spans are the same pair as decision 20, but PER-RULE | Query spans use the same pair shape as decision 20, gated per rule by `log_queries`. |
| [23](#decision-23-a-span-says-how-long-never-who-asked-two-knobs-answer-the-second-question-at-two-prices) | A span says how long, never who asked. Two knobs answer the second question, at two prices | `trace_hooks` labels a hook span with its caller for 0.9us; `trace_callers` records a capped number of twenty-frame caller chains per CALLER of each hook, query shape and URL, reset for each job. |
| [24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample) | A duration nobody measured is not a timing sample | An evicted or aborted request counts but never contributes a duration. |
| [25](#decision-25-read-tools-and-tune-scoped-write-tools-share-one-mcp-session-and-every-tool-result-is-fenced) | Read tools and TUNE-scoped write tools share one MCP session, and every tool result is fenced | One session carries both halves; every tool result leaves inside `<site-data>`, and the `initialize` instructions say that whatever sits inside it is data. |
| [26](#decision-26-a-merged-transport-node-keeps-the-statements-it-ran) | A merged transport node keeps the statements it ran | A folded `sql` or `http` node carries a capped table of the statements or URLs it ran, with a count and summed ms each. |
| [27](#decision-27-the-platforms-requests-to-itself-are-worker-traffic-named-by-path) | The platform's requests to itself are worker traffic, named by path | `Log_Manager::PLATFORM_WORKERS` names the cron loopback and the substrate's four endpoints as workers; the paths are a copy, and drift misclassifies rather than refuses. |
| [28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index) | The writer ranks each bucket and indexes each name, and the page reads those rather than the index | The flush ranks every bucket per sort key and direction and files each URL name's token prefixes, so an unfiltered page reads the lists and a search reads the token index. |
| [29](#decision-29-every-reader-dates-from-the-tick-and-a-reply-reads-it-once) | Every reader dates from the tick, and a reply reads it once | Readers date from `Core::$now` rather than a wall read, and a reply reads it at its entry and passes it down, so one reply is one window. |

## Decision 1: Namespaced memcache schema

Memcache is where stats are written and read; the durable mirror of decisions [10](#decision-10-the-durable-mirror-writes-a-bucket-once-when-it-closes-under-a-key-that-carries-no-install-scope) and [11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped) shadows them only for read-back on a miss. [`docs/architecture-guide.md`'s Memcache Schema table](architecture-guide.md#memcache-schema) is the full list with its key shapes.

![The stats key and the nineteen namespaces. The key, component by component: the substrate Table's salted install scope from Cache_Backend::site_key(), the prefix evlog, the flame-builder partition p{N}, the namespace, zero or more scope components that are each a pure prefix (a dimension, a server, a shard or a url_hash), and the five-minute bucket Y-m-d-H-i always last, so is_open_bucket() reads it off the key; the durable mirror files the same key under evlog:p{N}:{key} with no site scope and no version component. A table lists every namespace with its key after the prefix, its value and its TTL role: hourly, lb, lb_h, lb_s, urls (sixteen shards plus a w-prefixed worker family, positional rows carrying the 12-character hash), urls_h, urlnames, urlnames_h, urlmap, url, dim, url_dim, categories, url_cat, the four ranked-list tiers urlrank, urlrank_h, urlrank_s and urlrank_sh, and urltoken; the three coarse tiers lb_h, urls_h and urlnames_h, the four urlrank tiers and urltoken are all derived and none of them is mirrored. Three TTL roles derive from one setting, max_lifespan, seeded from the substrate's min_lifetime (default 43,200) and floored at PREFIX_FLOOR, 3,600: a fine urls, urlnames, urlrank or urlrank_s bucket keeps min(max_lifespan, FINE_TTL_SECONDS = 7,200), 24 buckets a shard like the coarse tier's 24 hours, the per-URL blob max(3,600, max_lifespan / 24), and everything else the whole window. Five caps hold every value under memcache's 1 MB item limit and fold overflow into Other: MAX_DIM_VALUES 20, MAX_SERVER_VALUES 128 for the server axis, MAX_URL_DIM_VALUES 10, MAX_CAT_VALUES 50 with the total pseudo-category preserved, and MAX_URLS_PER_SHARD 2,000, which is 32,000 URLs a bucket against a measured refusal at 5,000 rows a shard.](img/dec-key-layout.png)

Every key starts with the per-partition prefix `evlog:p{N}:`, which the substrate's `Table` wraps in the salted install scope (`Cache_Backend::site_key()`) rather than carrying the salt inside; the durable mirror's key ([decision 10](#decision-10-the-durable-mirror-writes-a-bucket-once-when-it-closes-under-a-key-that-carries-no-install-scope)) carries neither. The namespace follows: `hourly`, `lb`, `lb_h`, `lb_s`, `urls`, `urls_h`, `urlmap`, `urlnames`, `urlnames_h`, `url`, `dim`, `url_dim`, `categories`, `url_cat`, the four ranked-list tiers `urlrank`, `urlrank_h`, `urlrank_s` and `urlrank_sh`, or `urltoken`. **All but `url`, `urlmap` and `urltoken` are bucketed, and the bucket key is always the LAST component**, so every scope (server, URL, dimension) is a pure key prefix, one `lookup_multi` serves them all through `Stats_Store::lookup_buckets()`, retention is the key's own TTL rather than a hand-rolled cutoff pass, and `Stats_Store::is_open_bucket()` decides from the key alone whether the bucket it names is still open. `url` and `urlmap` key on the url_hash instead and `urltoken` on a token, none of which is bucket-shaped, so none of the three ever reads as open.

Retention is one TTL per storage ROLE, and there are three, all derived from `max_lifespan`: a `Stats_Store` constructor property seeded from the substrate's `min_lifetime` key (default 43200) through `Config::stats_retention_seconds()`, which floors it at `Stats_Store::PREFIX_FLOOR` (3600). `max_lifespan` is not itself a config key on either side. Per-URL flame stats (`url`) get `max(3600, max_lifespan / 24)`. A FINE `urls`, `urlnames`, `urlrank` or `urlrank_s` bucket gets `min(max_lifespan, Stats_Store::FINE_TTL_SECONDS)`, two hours: its own read window rather than the whole one, because [decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)'s coarse tier answers for everything behind it, and at that width the tier costs 24 buckets a shard, the same as the coarse tier's 24 hours. Everything else gets the full `max_lifespan`. The three coarse tiers `urls_h`, `urlnames_h` and `lb_h` are derived, as are the four `urlrank` tiers and `urltoken`, so `Stats_Store::is_derived()` names all eight and keeps them out of the durable mirror: a coarse tier and a ranked list are re-derived from the fine buckets on the next flush or the next fold, and a token set is rewritten whenever its URL is next named, which `persist_url_names()` does every half retention window.

`urls` and `urls_h` are decision 17's two resolutions of one index, and `lb` and `lb_h` are the same two of the leaderboard: the heaviest read the dashboard makes, one category per hook the site fires across 288 buckets and four partitions, folded hourly for exactly the reason decision 17 folds the URL index. The per-SERVER leaderboard, `lb_s`, keeps the fine path, because a shard count is a constant the schema chooses while the servers present in an hour cannot be enumerated from the keyspace. The `urls` index is SHARDED, `urls:{shard}:{bucket}`, sixteen shards by the first hex digit of the url_hash, and again by POPULATION: a `w` prefix on the shard token (`urls:w3:…`) carries worker traffic, which the table excludes by default, so an ordinary read never carries rows it discards and a URL a job also visits keeps its reader row. A shard is not a scope, which makes it the one component here that names no dimension of the data: it is physical partitioning, and it exists because one blob per bucket is the pressure every cap in this schema is sized against. A stored row carries the 12-char hash and no URL string; `urlmap:{hash}` holds `[ path, origin ]` once, re-written only past half its TTL, and readers resolve only the hashes they display. Keeping the string out of the row holds the widest row to 699 bytes rather than 811 and the common sole-server row to 189 rather than 290, which is what pays for `Flame_Builder_Node::MAX_URLS_PER_SHARD` at 2,000: 32,000 distinct URLs a bucket, against a measured client refusal at 5,000 rows a shard.

`urlmap` answers about ONE hash; a SEARCH asks about a whole SHARD, and answering it per hash costs 668,918 keys a poll on a production hub, 200-290s and 350-510MB per `urls` request. `urlnames:{shard}:{bucket}` and its `urlnames_h` fold answer it in ~40 keys a shard, on the same geometry and the same `read_plan()` as the rows, and carry PATHS only: the origin is already the `ROW_SRV` split's key and already the `server` dimension the picker is built from, so a third copy would also put the dropdown's question inside the search box. Uncapped, deliberately: every URL must be searchable, and a cap drops exactly the URL somebody is looking for. It is NOT bounded by `MAX_URLS_PER_SHARD`: `cap_url_rows()` runs inside the ROW intent's merge, after the name map is built, so what bounds it in practice is the distinct URLs a shard sees in a bucket, and what bounds it in the end is `url_name_intent()`'s refusal log, which it carries for exactly that reason.

Caps hold every value under memcache's 1MB item limit, and overflow rolls into a synthetic `Other` entry: `MAX_DIM_VALUES` = 20, `MAX_URL_DIM_VALUES` = 10, `MAX_CAT_VALUES` = 50 with the `total` pseudo-category preserved before capping, and `MAX_URLS_PER_SHARD` = 2,000 rows a shard. The `server` axis takes `MAX_SERVER_VALUES` = 128 instead (`Stats_Store::dim_cap()`), through the same traffic-ranked `Other` fold. Exempting it, on the reading that a cap is a cardinality guard and this axis is the FLEET, one `DIM_SUMS` triple per spoke, so a hundred cost about two kilobytes, is wrong: `server_name` is `$_SERVER['SERVER_NAME']`, which under Apache's default `UseCanonicalName Off` is the CLIENT'S Host header, so a domain-mapped multisite or any catch-all vhost taking Host-header spray makes the axis visitor input with no ceiling. The ceiling is 128 rather than `MAX_DIM_VALUES`' 20 because 20 binds on a real fleet: it folds every spoke past the twentieth into `Other`, per bucket by request count, and a 24-spoke fleet loses four sites from its own picker. So it sits far above any fleet in evidence and the tail FOLDS rather than dropping, keeping every total exact. **[Decision 14](#decision-14-a-server-scope-the-key-cannot-carry-rides-inside-the-value-and-is-applied-as-a-projection) owns the reopen condition for this ceiling**: wherever the `server` axis is stored, one tripwire, stated there.

A category entry is POSITIONAL ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)) and its `CAT_MS` is stored ROUNDED to `Stats_Store::CAT_MS_DECIMALS` places: `Flame_Builder_Node::fold_categories()` rounds after the cap, because the cap re-sums its tail into `Other` and a sum of rounded doubles is not itself rounded. These are milliseconds a chart draws as seconds-per-second or as a mean, so a microsecond is already past anything rendered, where a full-precision double spends twelve more bytes per entry saying it. **The same fact obliges the WIRE to round again**: `Performance_CI_Node::compact_category_series()` emits a sum across one `Stats_Store` per flame-builder partition, and a stored entry already being rounded is the reason that sum is not. Measured over 5,000 realistic millisecond pairs, 22.1% of two-store sums and 30.0% of four-store sums serialize LONGER than their rounded value, worst case `0.30000000000000004`. `Stats_Store::sum_entry()` is what makes every merge here shape-exact: it rebuilds an entry from its field table and DISCARDS anything outside it, so a named `{t,c,n}` entry met by a positional one is dropped rather than hybridised into a six-key object. A caller wanting a field the table does not name puts it back itself, beside the reason: `add_totals()` replaces its sum onto the bucket it was given so a merged time series keeps the `hour` it is keyed by, and `merge_url_row()` reads its extremes off `$into`.

## Decision 2: Sums, not means

Leaderboard buckets hold raw `count`, `sum_req_time`, `samples`, `sum_time`, `sum_count`, so cross-bucket and cross-partition merges are exact addition and the display layer computes means at read time. Do NOT regress to running-mean storage: it produces the EMA-clamp bug this rule exists to keep out.

## Decision 3: Stats fail soft

Every [`Stats_Store`](../includes/class-stats-store.php) method returns `null` / `[]` / `false` when memcache is unreachable and never throws, so a dashboard shows "no data" where a stat should be, and a reader past its mirror budget answers from memcache alone. The substrate makes the opposite call for the same outage: a stream its slot pool cannot account for is refused ([SSE host budget](https://github.com/Automattic/newspack-nodes/blob/main/docs/sse-host-budget.md)). The asymmetry is the decision. A missing stat costs a blank card; a stream nobody can account for costs a php-fpm child for as long as it stays open.

## Decision 4: Settings fan-out is a node graph; no consumer means a silent no-op

The three settings a hub pushes, the ruleset, `log_memory` and `flush_every_line`, ride the substrate's settings control plane: [`hub-control.tsl`](../topologies/hub-control.tsl) includes `settings-sync` and adds one `add_setting` line per option, and a change to any of them is an option write like every other, which the substrate's [`Settings_Event_Writer`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-settings-event-writer.php) records. So [`Auto_Tuner_Node`](../includes/class-auto-tuner-node.php) mutates the one rule the message names (`rule_id`) and persists the whole ruleset through `Rule_Set::save()`: no `remote_manager` job, no `suppress_sync`, and an auto-tune write reaches the spokes exactly as an admin edit does. Nothing fans a change out unless `hub-control` is active and per-spoke `HTTP_Out` nodes are wired; on a spoke or a standalone site the event is tailed and dropped. That IS the structural gate: there is no `enable_workers` or `enable_aggregator` key, and hub mode derives from which topologies are active.

## Decision 5: A memcache schema change is migrated by the flush, and by nothing in this code

A memcache schema change here is migrated by the substrate's flush, `wp nodes memcache flush` over [`Cache_Backend::rotate_salt()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-cache-backend.php), and `Stats_Store` keeps no salt and no migration path of its own. Schema bumps and emergency flushes share that one button. **The rotation IS the migration, and nothing in the code compensates for skipping it.** A schema change orphans the old keys the instant the salt moves, so no reader or writer carries a shape probe, a version component or a row-level legacy test: each would be a second migration mechanism beside this one button, maintained against every future row shape. Skip the button and the dashboard reads garbage for one retention window; that is an operator error with a one-command fix, not a case for the runtime to detect.

![The salt rotation drawn on two key forms. Left, memcache: a stats key as the substrate Table writes it through Cache_Backend::site_key(), newspack_nodes:{v}: then a 12-hex scope, the first 12 hex of md5(DB_NAME : table prefix : salt), then :table:evlog:p0:hourly and the bucket. wp nodes memcache flush runs Cache_Backend::rotate_salt(), which stores a new salt, and the same logical key moves under a new scope while the old key sits in memcache until its TTL with nothing ever asking for it; Stats_Store keeps no salt of its own, and a long-running worker memoizes the scope, so workers restart for immediate effect. Right, the durable mirror: evlog:p0:{key} carries no install scope, so the rotation reaches nothing on disk, and the key carries no version component — a frame the merge cannot name sums to a zero count Stats_Store::measured() drops where a sum table names the count, or leaves with its retention window. Below: skipping the flush reads garbage for one retention window, an operator error with a one-command fix; no reader or writer carries a shape probe, a version component in a memcache key or a row-level legacy test; and schema bumps and emergency flushes share the one rotation.](img/dec-salt-rotation.png)

**The durable mirror is the one tier the button does not reach**, by [decision 10](#decision-10-the-durable-mirror-writes-a-bucket-once-when-it-closes-under-a-key-that-carries-no-install-scope), and it takes no version component of its own to compensate. `sum_entry()` rebuilds an entry from its field table, so an entry the flush TOUCHES cannot come out a hybrid of two shapes — it comes out zeros. It is the UNTOUCHED entry that needs answering, because `sum_fields()` starts from the stored bucket and re-derives only the keys the incoming flush names, so a stale one is copied through verbatim. **What removes those is the zero-count filter, and only four namespaces have one**: an entry whose shape the table cannot name reads its count index as absent, so `Stats_Store::measured()` drops it, at the writer's next write to its bucket through `cap_dim()` and `fold_categories()` and at every read through `Performance_CI_Node`'s merges, clearing `dim`, `url_dim`, `categories` and `url_cat`. **The rest are the exposure**, and none of them rebuilds: `add_totals()` replaces its sum onto the stored `hourly` bucket so a field outside `HOURLY_SUMS` rides through, `merge_leaderboard_bucket()` rebuilds only the categories the flush names in `lb` and `lb_s`, the `urls` row and `url` merge by passthrough — `url` only when `set_flame_topn` is non-zero, since 0 mirrors none — and `urlnames` and `urlmap` have no field table at all. A shape change to those is migrated by the flush, by one retention window, and by nothing else: the price of keeping one migration mechanism rather than two, and the reason to weigh a shape change there rather than the reason to build a lever.

*Alternatives rejected:* a schema-version component in the key prefix, a permanent extra component on every key, for the identical orphaning the salt already does; detect-and-purge at boot (memcached cannot enumerate, and a boot pass over the whole keyspace is [decision 6](#decision-6-get_multi-batching-is-essential)'s latency cliff). **Revisit when** a deploy can no longer be relied on to rotate, at which point the mechanism to add is one that forces the button, not one that tolerates its absence.

## Decision 6: `get_multi` batching is essential

Reader paths multi-get across all retention buckets per partition in one round-trip; per-key `get` is a latency cliff on dashboards. Implemented in both the real and Fake memcached.

## Decision 7: Job_Intake for >4KB jobs, the firehose for ≤4KB

Small runtime jobs ride the firehose with `k:"job"`, and [`Job_Router_Node`](../includes/class-job-router-node.php) extracts them; [`job-feed.tsl`](../topologies/job-feed.tsl) tails the substrate's `jobfeed` log instead, so a spoke's router reads jobs alone rather than the whole firehose. A job the firehose cannot carry goes straight to `jobintake` through the substrate's [`Job_Intake::queue()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-job-intake.php), the locked path past the PIPE_BUF cap ([substrate ADR-4](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-4-pipe_buf-atomic-writes)). The wrong path loses jobs: `Log_Manager` trims `m` on any ENTRY over `MAX_DATA_SIZE` (3840B), so the handler never sees a parseable payload.

## Decision 8: A spoke's job is re-keyed `remote_job` when the hub pulls it

A spoke writes `k:"job"` like any producer and never learns it has a hub. The hub's [`aggregator`](../topologies/aggregator.tsl) topology pulls each spoke's firehose through a substrate [`Remote_Source_Node`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-remote-source-node.php) ([hub and spoke](https://github.com/Automattic/newspack-nodes/blob/main/docs/hub-and-spoke.md)), and this plugin's [`Remote_Job_Rewrite_Node`](../includes/class-remote-job-rewrite-node.php), wired between the sources and the firehose `Topic`, flips the incoming `k:"job"` to `k:"remote_job"` and leaves every other key alone. That kind is the only thing telling a spoke's work apart from the hub's own: the hub's `Job_Worker_Node` dispatches it against `newspack_nodes/remote_job_handlers` and never against the map its own jobs use. A job type registers under either map or both, depending on where it should run, and the two registrations are independent, so the hub runs a spoke's job because a handler was registered for it there, not because the spoke asked. What makes a site a hub is [decision 4](#decision-4-settings-fan-out-is-a-node-graph-no-consumer-means-a-silent-no-op)'s: the `aggregator` and `hub-control` topologies being active, with no toggle.

## Decision 9: A request's partition is its id, hashed by the substrate

[`Log_Manager::init_firehose()`](../includes/class-log-manager.php) picks a request's firehose partition with the substrate's [`Partition_Node::hash_to_partition()`](https://github.com/Automattic/newspack-nodes/blob/v2.56.0/includes/class-partition-node.php) over the request id ([substrate ADR-6](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-6-crc32--31-bit-mask-partition-routing)), and [`Performance_CI_Node`](../includes/app/class-performance-ci-node.php) finds a request's partition the same way. Neither hashes with a function of its own: the id is every firehose line's Message KEY, so the partition a line lands in and the one a reader looks in are one function of one input.

## Decision 10: The durable mirror writes a bucket once, when it closes, under a key that carries no install scope

[`Stats_Store::entry_key()`](../includes/class-stats-store.php) is `evlog:p{N}:{key}`, never the Table's `Cache_Backend::site_key()` form, and `flush_stats_mirror()` holds a bucket's frames until `Stats_Store::is_open_bucket()` says it closed.

![One five-minute bucket and the ten 30-second checkpoints inside it. Writing a frame at every checkpoint appends ten frames to the append-only, last-frame-wins flame-stats partition, nine of them dead copies retained for stats_mirror_lifetime; in a real flame-stats.p0 written that way, 4,279,767 of 5,531,418 bytes (77.4%) are superseded frames. Holding the frames in RAM, carried in each checkpoint by decision 11, writes one frame at the first checkpoint after is_open_bucket() says the bucket closed. Below, two keys: the Table's scoped key, newspack_nodes:{v}:{site, salted}:table:evlog:p0:…, is orphaned by the very rotation the mirror should survive, so a flush makes weeks of on-disk history stop answering; the mirror's own key, evlog:p{N}:{key}, is stable across salt rotations and carries no version component, so nothing migrates a frame. One function, entry_key(), keys the mirror write, the stats-index hash, the rehydrate compare and the held-frame lookup, and restore_state() keeps only keys is_mirror_key() claims.](img/dec-mirror-at-close.png)

The mirror exists to outlive `wp nodes memcache flush`, and a scoped key is orphaned by the very rotation it should survive: the reader hashes the new scope, and weeks of on-disk history stop answering. The mirror write, the `stats-index` hash, the rehydrate compare and the held-frame lookup all key through `entry_key()`, so they cannot disagree, and `restore_state()` keeps only keys `is_mirror_key()` claims, so a checkpoint carried across a key change holds nothing it cannot look up. `flame-stats` is append-only and last-frame-wins per key, so mirroring the bucket still being accumulated into, once per 30s checkpoint, writes it ten times over a five-minute bucket and leaves nine dead copies retained for `stats_mirror_lifetime`: in a real `flame-stats.p0` written that way, **4,279,767 of 5,531,418 bytes (77.4%)** are frames a later frame supersedes. Holding the frames until the bucket closes writes each once, and [decision 11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped) carries them meanwhile.

*Alternatives rejected:* writing every checkpoint and shortening `stats_mirror_lifetime` instead (loses history rather than duplicates); keying frames by bucket+checkpoint and compacting later (a compactor to own, for the same bytes). **Revisit if** the partition ever stops being last-frame-wins on read.

## Decision 11: The open bucket is durable in the OFFSETLOG until it closes, and the carry is capped

A held frame is in no durable log, so `save_state()` carries the held frames in the offsetlog checkpoint and `restore_state()` takes them back, under a byte budget that drops the widest frame first. The offsetlog is a self-pruning ring of at most 60 keyframes, where the mirror retains for twice the stats window, so the open window costs bounded disk in the cheap place.

![The held-frame carry in three steps and its bounds. A stats write is mirrored into a per-namespace buffer, last state wins, whose residency is one open bucket; every 30 seconds save_state() packs the held frames into the Consumer's offsetlog keyframe beside the cursor, and the rehydrate seam consults held frames first; at the first checkpoint after the bucket closes, the frames go to flame-stats under the unscoped mirror key. A bar shows the cap, MAX_CHECKPOINT_MIRROR_BYTES of 16,777,216 bytes, half of Partition_Node::MAX_LARGE_LINE_SIZE, against the 2.1 to 3.5 MB a staging hub holds per checkpoint and an outline at 2,097,152 bytes, a budget set from an earlier hub's 267 to 348 KB that the staging hub overran on every checkpoint. Three notes: the widest frame goes first because narrowest-first keeps the most keys recoverable per byte and Partition_Node drops an oversize record, cursor included; the pack orders by entry count, not encoded bytes, and still enforces real bytes. Tiles: MAX_HELD_FRAMES 10,000 per namespace, past which spill_over_backstop() writes a band of a tenth of the bound early; OFFSETLOG_NUM_SEGMENTS 30 keyframes of what is held, about 100 MB of disk for the staging hub; Partition_Node::MAX_LARGE_LINE_SIZE two times away; and 0 of 12 pre-deploy buckets kept by a 0.00 req/s URL under a top-100 rank cap, which leaves every quieter URL in memcache alone, so no per-URL namespace is rank-capped at buffer time. Cards cover what the log carries when it fires; the GET_STATS fields mirror_held_bytes and mirror_held_frames, with six namespaces of five thousand reading as thirty thousand while one spilling on every write reads as ten thousand and fifty; and why the spill is a band, and why, with no partition, flush_stats_mirror() keeps the buffer for the next checkpoint and the backstop refuses the arrival rather than discarding a held frame.](img/dec-held-frames.png)

Three invariants the code must keep. The worker's `rehydrate` seam consults held frames FIRST, or a mid-bucket eviction makes the read-modify-write restart the bucket from zero. A restored frame's lifetime follows [substrate ADR-18](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-18-a-table-can-front-a-durable-record-the-walk-that-finds-it-stays-in-the-app): what is LEFT of the RETENTION window, bounded by its own storage role's TTL, so a frame whose CACHE lifetime ran out is still read, because refusing it loses an evicted `urls_h` that the fine buckets on disk can rebuild. And the carry is capped at `MAX_CHECKPOINT_MIRROR_BYTES` (16,777,216), because the per-server aggregates grow with the spoke count while `Partition_Node` DROPS an oversize record, and that record is the whole checkpoint, cursor included.

**Dropping the biggest is the design, not a fault**: narrowest-first keeps the most keys recoverable per byte, and a dropped frame is re-merged from memcache by the next write to its bucket, lost only if the process AND memcache both fail before the bucket closes. The budget is set from the OUTER limit, half of `Partition_Node::MAX_LARGE_LINE_SIZE` (32MB), which leaves the other half for the cursor, `pending` and the framing the policy cap does not count, so the log does NOT fire in routine operation and "it fired at all" is informative. A budget set from an observed size does not buy that, because the observation is one site: 2,097,152, ~6x the 267KB–348KB a production hub held per checkpoint, dropped 52 to 291 of ~1,400 per-URL frames on EVERY checkpoint of a staging hub holding 2.1–3.5MB, and at 262,144 a multi-spoke hub dropped one to thirteen frames on nearly every one. A tripwire that trips permanently tells you nothing. The log carries the numbers: how many frames dropped of how many held, the budget, the bytes it carried, and the WIDEST held frame with its namespace and size, the namespace because a sharded `urls` key and an `lb_s` key are both opaque, and which one fired is the whole question this tripwire asks.

**The pack orders by ENTRY COUNT, not by encoded bytes**, and encodes only what it carries plus the one it stops on: encoding every held frame to sort them would make the budget bound the OUTPUT and never the work, which at the held-frame backstop is megabytes of throwaway JSON every thirty seconds. A frame is a map of small numeric entries, so its count tracks its size closely, and the ordering only has to be APPROXIMATE: the budget is enforced against real encoded bytes as they accumulate, so a proxy that mis-orders two frames costs a slightly worse packing and never an oversize record. The GET_STATS payload reports two figures, on a verb an operator asks rather than every checkpoint: `mirror_held_bytes`, the exact held total, and `mirror_held_frames`, the WIDEST single namespace's held count, because `MAX_HELD_FRAMES` is per namespace and a cross-namespace total cannot warn about it: six namespaces holding five thousand each read as thirty thousand with nothing near the bound, while one spilling on every write reads as ten thousand and fifty.

What the budget costs is disk, in the offsetlog ring: `OFFSETLOG_NUM_SEGMENTS` (30) keyframes of what is HELD, plus a write every 30s. The hard cap of 60 never binds at that cadence, since it exists for keyframes all younger than the 5-minute hold, of which a 30s cadence makes ten. That ring caps keyframe COUNT and never bytes, and nothing else bounds it, so the budget is the ring's ceiling rather than its size: the staging hub's 3.5MB spends ~100MB, and a hub holding the full budget would spend 480MB. `Partition_Node::MAX_LARGE_LINE_SIZE` is 2× away and does not bind.

**The real lever is upstream, and it is a SPILL rather than an eviction.** Buffer-time eviction drops a frame from the durable mirror at bucket close, a strictly larger loss than dropping it from a checkpoint, which is why no per-URL namespace is rank-capped at buffer time — `set_flame_topn` is the one cap, and it governs `url` alone: a top-100 cap there leaves every quieter URL in memcache alone, and a moved cache scope takes its whole history, measured on a production host as 0 of 12 pre-deploy buckets kept for a URL at 0.00 req/s. `MAX_HELD_FRAMES` bounds each namespace's held set at 10,000 instead, and `spill_over_backstop()` writes the overflow to the partition early rather than dropping it, so the bound costs one redundant record and never a frame. It spills a BAND, a tenth of the bound, rather than one frame: ranking the buffer is a pass over it, and the buffer PINS at the bound under exactly the traffic the bound exists for, so one frame per write would put that pass on every write past it, quadratic in a spray's length inside the worker this bound protects. The band is the hysteresis `trim_entries()` already uses, and a rank-ordered structure is NOT the alternative: a request merging into a key changes its rank, so keeping the buffer ordered pays per write instead. **With no partition to spill into, nothing already HELD is discarded**: `flush_stats_mirror()` reads a partition name that does not resolve as one that may resolve next checkpoint and keeps the buffer, and the backstop takes the same reading, refusing the ARRIVAL instead, whose value is still in memcache and whose bucket's next write re-offers it.

**Revisit when** the log fires AT ALL, since any drop means the held set has grown to half the record cliff, which is the O(servers) signal arriving, or when the WIDEST held frame the log names is NOT a per-server leaderboard, which would mean something other than fleet size is driving it. Read the CHECKPOINT trend in BYTES, off `mirror_held_bytes`: `urls` is sharded, so one open URL bucket holds SIXTEEN frames, each a sixteenth the size, and a frame count steps up with no fault behind it. Frames are what the BACKSTOP is against, which is why `mirror_held_frames` answers for one namespace rather than the set. Sharding is also what keeps the second tripwire honest: an unsharded `urls` blob carrying a split per row would exceed the whole budget and always be the widest frame, satisfying "the widest frame is NOT a per-server leaderboard" permanently, where sixteen smaller frames sort in among the leaderboards. The per-server aggregates still grow O(servers), so the CHECKPOINT budget still loses to fleet size eventually; bounding that axis remains the structural fix.

## Decision 12: A stat times the request; a flame value is a rendering artifact

Two numbers describe one request and they are not interchangeable. `duration_ms` on the record is what the request took, measured once. A flame node's `value` is a LAYOUT WIDTH: `Flame_Tree::cover_children()`, `Flame_Fold::flatten()` and `Flame_Builder_Node::fill()` all RAISE it so a parent covers its positioned children, because the browser prunes on a single cutoff and takes a whole subtree with anything it drops, and `treemapDice` scales children by `parentWidth / parent.value`. Raising is correct for drawing and wrong for counting. **Every stat therefore reads `$request['duration_ms']`; nothing measured reads a flame `value`**: that covers every namespace of [decision 1](#decision-1-namespaced-memcache-schema) plus the per-URL aggregate's `sum_value`.

![A real request, the record and the raised root drawn to scale. The record's duration_ms is 356,312 ms, measured once, and every stat reads it. The flame's root value is 724,662.87 ms after Flame_Builder_Node::fill() raised it to cover a child positioned 355 seconds after the parent's own occurrence, marked as a tick at t = 0, because a parent is widened to the end of its farthest child so the child stays inside it when drawn; a stat reading that raised width reports the URL's avg_ms as 724,662.87 ms. Cards name the three places that raise a value, Flame_Tree::cover_children(), Flame_Fold::flatten() and Flame_Builder_Node::fill(), and why raising is right for drawing: the browser prunes on a single cutoff, taking a whole subtree with anything it drops, and treemapDice scales children by parentWidth / parent.value. The rule covers every namespace of decision 1 plus the per-URL aggregate's sum_value.](img/dec-flame-value.png)

The two diverge by more than rounding: read from its raised root, a 356,312ms request reaches `avg_ms` as 724,662.87ms, because `fill()` raises the root to cover a child that ran 355 seconds after the parent's own occurrence. *Alternatives rejected:* not raising at all (deletes exactly the frames a viewer opened the graph to see); computing stats before the raise (the ordering is invisible at the call site, and one reorder reintroduces it). **Revisit if** the browser stops pruning on a single value cutoff: the raise can go then, and the two numbers converge.

## Decision 13: A sequence-break marker is missing detail, not idle time

`entries (lost)` and `entries (aggregated)` stand in for entries [`Request_Builder_Node`](../includes/class-request-builder-node.php) removed: discarded on overflow, or merged by the fold. It mints them, so it owns the vocabulary as `Request_Builder_Node::SEQUENCE_BREAK_KEYS`; consumers reference that constant rather than keeping their own copy, and the JS holds the only deliberate duplicate because it is a separate deploy unit. **No consumer may reason across a marker.** `Findings::entry_gap()` skips a gap on either side of one, `Reqgrep_Command` breaks its sequence there, and [`logEntryUtils`](../src/overview/utils/logEntryUtils.js) splices the merged spans back at it. Reading the interval as unexplained makes one record's `entry_gap` propose MORE hooks while its `truncation()` proposes fewer, both at once, on the same record. What a consumer MAY read across one is the record's own ending: whether anything closes the outermost pair. That decides FRAMING, which spans were severed and which ran to the end, and leaves the interval exactly as unmeasurable as it was, which is what this decision protects. `logEntryUtils`' `pruneSeveredSpans()` and `Reqgrep_Command::prune_severed_spans()` are the one rule, and the parity test in `logEntryUtils.test.js` pins the vocabulary they share. **The severance frames the record's RESUMED tail, never the folded interior spliced in at the marker**: those rows are what the TREE puts inside the open span, and the fold is what ate its close, so pruning before them makes every merged row a sibling of the parent it ran in: a gyrobase subprocess that exits 0 loses its whole 535s interior to the request's level, while the same shape whose drain survives the fold nests correctly. The prune therefore waits for the first row the record itself resumes with (`fromFold`). **Revisit if** a marker ever carries its own duration, which would make the interval measurable rather than merely missing.

## Decision 14: A server scope the key cannot carry rides inside the value, and is applied as a PROJECTION

[Decision 1](#decision-1-namespaced-memcache-schema)'s shape is that every scope is a key PREFIX: `lb_s` is `lb` with a server component, and one `lookup_multi` serves it. The URL index cannot follow it, so its server split rides in the value and a server scope is a projection over the MERGED row.

![How a server scope reaches the URL index. Step 1: the stored row carries srv at index 13, a map from each reporting server to its eight summed URL_SRV_SUMS fields, where an overflow row carries every server its tail was seen on and a sole server that served every request the row counted stores null, the row restated (decision 18); the split is capped at MAX_SERVER_VALUES (128) once, after the MAX_URLS_PER_SHARD fold, because the fold is what mixes hosts, by the ranked Other fold dim_cap() gives the axis everywhere. Step 2: every merge expands the sole server first, since sum_fields() skips a non-array and an unexpanded null would delete that host; because every split field adds, selecting then summing and summing then selecting agree, so one fold_index_row() merges for table and modal alike. Step 3: swap_url_server_sums() replaces the row's eight summed fields with the selected server's and unsets the split, and Performance_CI_Node::project_row() unsets srv_recent, divides the means once from sum_ms and sum_peak_mb, so nothing un-averages a figure another function divided, and computes the recent-window share; min_ms and max_ms stay the URL's own, deliberately and invisibly on a fleet of disjoint sites, and a server absent from srv drops the row from the scoped read. Below, url_page() folds one of sixteen shards at a time, keeping each shard's best offset plus limit rows and its best SLOWEST_ROWS, so the per-shard top-N is the global top-N, and dump_url point-reads the one shard url_shard() names through the same $load_index seam; there is no whole-index memo, because holding the merged index exhausts a production hub's 512 MB. Cards: the axis is visitor input under UseCanonicalName Off, so the ceiling sits five times above the largest hub and three times above the widest per-URL split any test asserts; and the split is not hub-gated.](img/dec-server-split.png)

A per-server `urls_s` namespace would apply the `MAX_URLS_PER_SHARD` cap **per key**, so the index that is mirrored in FULL, `urls`, like every namespace `Stats_Store::is_derived()` refuses, would grow O(servers × that cap) rows per bucket, on the same axis [decision 11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped) already names as the one that outgrows any fixed checkpoint budget. So each row carries `srv` instead (`Stats_Store::ROW_SRV`): its summed fields per reporting server, capped at `Stats_Store::MAX_SERVER_VALUES` (128) by the same ranked `Other` fold `dim_cap()` gives the `server` axis everywhere it is stored. Reading the axis as the FLEET argues for leaving it uncapped, and that reading is wrong: `server_name` is `SERVER_NAME`, and under Apache's default `UseCanonicalName Off` that is the client's Host header, so a domain-mapped multisite or any catch-all vhost makes it visitor input with no ceiling. What a cap must not do is bind on a real fleet: a folded server's scoped read matches nothing, and the URL leaves the filtered table AND its totals silently, exactly as the dimension cap drops it from the picker. So the ceiling sits far above any fleet in evidence (five times the largest hub, three times the widest per-URL split any test asserts) and the tail FOLDS rather than dropping, keeping every total exact. The cap is applied ONCE, after the `MAX_URLS_PER_SHARD` fold, because the fold is what mixes hosts: a stored `url` is absolute, so a real row carries one or two splits while each family's overflow row carries every server its own tail was seen on. That bounds bytes on both factors of rows × servers rather than one, with the refused-write log as the backstop, a guard that REPORTS where the cap CORRUPTS: an oversized shard is one loud line and a bucket's rows lost until the next write.

A split of ONE server that served every request the row counted stores the host name against `null` rather than restating the row ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)): `null` is that server's numbers, absence is still "never served here", and every merge on both sides expands through `Stats_Store::expand_sole_server()` first. **Only fields that ADD are split** (`Stats_Store::URL_SRV_SUMS`): `min_ms` and `max_ms` are extremes, so a server-scoped row keeps the URL's own across every server, deliberately, and invisibly on a fleet of disjoint sites. Because every split field adds, selecting then summing and summing then selecting agree, so the scope is a projection over the MERGED row, not a filter before the merge, and both readers fold through ONE `fold_index_row()`, because a second copy of the merge is how the table and the modal come to disagree about the same URL. WHICH fields swap is `Stats_Store::swap_url_server_sums()`, beside the table that defines them: those fields are INDEXES, not names (decision 18), and it is also where the split's eight become names, for the one selected server, because no reader displays a split. The means and the recent-window share are the READER's: a mean is a display division per [decision 2](#decision-2-sums-not-means), and the window is reader geometry the schema has no name for. So `Performance_CI_Node::project_row()` finishes what the store starts: it unsets `srv_recent`, computes the recent-window share, and divides the means from `sum_ms` and `sum_peak_mb`, which the row carries so the projection divides once, in its own scope, and nothing has to un-average a figure another function divided. Neither half returns a row in one scope on its own, and both are named for what they do rather than for what the caller wants.

**There is no whole-index memo, and reintroducing one is the trap:** the merged index is the count of DISTINCT URLs in the retention window, which nothing bounds: the stored buckets cap at `MAX_URLS_PER_SHARD`, their merge does not, and holding it exhausts a production hub's 512MB inside the fold itself. [Decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived) carries what the whole-index fan-out costs. `url_page()` folds ONE SHARD at a time, keeping only each shard's best `$offset + $limit` rows by the sort key and its best `SLOWEST_ROWS` (10) by mean; a url_hash's shard is its first hex digit, so shards are disjoint and the union of the per-shard top-N IS the global top-N. Spec: dndocker's `docs/superpowers/specs/2026-08-31-url-index-per-shard-fold.md`; specs for these plugins live there, never in the plugin repo. Scoping inside the loader instead makes every scope its own read of the index, so two readers asking under different scopes pay the whole `lookup_multi`, unserialize and merge twice, against [decision 6](#decision-6-get_multi-batching-is-essential). That argument is about the SERVER axis and does not reach the SHARD one, which this same decision names as a constant the schema chooses: `url_row_sources()` takes an optional `$shard`, and `dump_url` point-reads the one shard `url_shard()` names for its hash, a sixteenth of the keys the table reads, rather than paying the table's fan-out to answer about one row. [`Performance_CI_Node::load_row()`](../includes/app/class-performance-ci-node.php) point-reads unconditionally through the same `$load_index` seam the table folds, and that seam takes the SHARD, so a test counting index reads measures the narrowing rather than a branch around it.

The split is capped at persist and not in the accumulator, so an open bucket's rows carry one entry per distinct reporting server SEEN IN THAT FLUSH WINDOW on the checkpoint, which decision 11 counts as uncounted `pending`. Spray does not widen that: an absolute `url` puts the sprayed host in the row KEY, so the accumulator answers it with rows, bounded by `URL_ACCUMULATOR_SIZE`, each carrying one server, not with a wide split. Unlike the three per-server AGGREGATES it sits beside, the split is **not** hub-gated: the filter is offered wherever the `server` dimension has values, and a scoped read of a row without a split returns nothing, so gating it would empty the URL table on every spoke rather than save one. *Alternatives rejected:* a `urls_s` namespace (above); resolving the scope from `url_dim` at read time (O(urls) gets per poll). The `urls_s` rejection is NOT an argument against sharding, though both add a key component: a shard count is a constant this schema chooses, while a server count is an input this schema does not control, visitor-driven at worst, and the one decision 11 watches. A per-key axis has nowhere to put a fold, so capping it is not even available. Sixteen shards of `MAX_URLS_PER_SHARD` rows is a ceiling; O(servers) × that is not. **Not taken, deliberately:** `url_dim`'s `server` axis looks like a duplicate and is not one in either direction: it is a per-BUCKET `DIM_SUMS` time series, which is what the URL-detail breakdown chart draws, while `srv` is one window-merged scalar carrying eight fields including the status classes. Neither can produce the other. (Both take `MAX_SERVER_VALUES` on the `server` axis; any remaining cap asymmetry between the two namespaces is unobservable: `dump_url` throws `URL not found` for any hash absent from the index, so a URL that never survives `MAX_URLS_PER_SHARD` cannot reach its own `url_dim` rows.)

**Revisit when** the refused-write log fires at a row count well UNDER `MAX_URLS_PER_SHARD`, since a shard over the item limit on few rows is bytes per row, which is rows × servers, and the answer is a byte-derived row cap, not a lower value count; or when a real fleet approaches `MAX_SERVER_VALUES`, which the picker announces by growing an `Other` entry and which means the ceiling, not the mechanism, is what needs raising. Refusal AT the cap is the row count doing its job and says nothing about the fleet, and the namespace is only half a signal: `fold_hour_into_store()` names each refused key through `Stats_Store::key()`, so a coarse row, name or leaderboard refusal is told apart, while the fine-tier intents report a shard and a row count alone. **Revisit if** `urls` ever gains a top-N mirror bound, which would cap a per-server namespace too and make the key-prefix form affordable again; if the row ever carries its split PER BUCKET, which is the one shape that would retire `url_dim`'s server axis; or if one URL is routinely served by more than `MAX_SERVER_VALUES` servers, at which point `cap_bucket` rolls the surplus into a synthetic `Other`, a scoped read of a demoted server matches nothing, and the URL leaves the filtered table AND its totals silently. That is unreachable today, and the reason is worth knowing: a stored `url` is ABSOLUTE (`https://host/path`), so a URL hash belongs to one site and carries one or two splits, not a hundred. The same fact is why `find_recent_requests_for_url()` is not scoped: the request index carries no server, and it does not need one.

**The first of those conditions is UNSPENT, and still guards `urls_s`.** `urls` gained no mirror bound: it is mirrored in FULL, at `MAX_URLS_PER_SHARD` rows a shard, exactly as this decision found it. The ranked lists ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)) do take the key-prefix form, `urlrank_s:{server}:{sort}:{order}:{bucket}`, and what pays for it there is two other facts: a list is `URL_RANK_N` entries whatever the rows behind it, and all four rank tiers answer `Stats_Store::is_derived()`, so the mirror holds none of them. Neither fact reaches the stored rows, which keep the value form, and the rejection above stands.

## Decision 15: The `urls` verb owns every URL-set fact; `overview` owns the site

One verb applies the filters, so one verb answers for what they left, and `overview` keeps only what the URL index cannot answer.

![Two polls side by side. Left, one urls request carries its filters, server, search, errors_only and include_workers, into url_page(), which folds the URL index one shard at a time; the one reply fans into the header totals (URLs, requests, averages, rate), the rows, the slowest ten and the echoed filters, so the header and the table come from the same fold and cannot disagree. Cards give the worker default, where include_workers opts in and a header summed from rows keeping worker timing reads 227 ms of cron against 3 ms of reader traffic on a staging hub; the one scope rule, a fetch sends the live selection while a label reads the scope the server echoed, with dump_url taking the same server because a site-wide average under a scoped count is the same defect one click in; and the surfaces the scope does not reach: dump_url's breakdown_time_series, category_time_series and aggregate_flame, and find_recent_requests_for_url().](img/dec-url-set-owner.png)

The `urls` verb answers how many URLs, how many requests, the averages, the rate and the slowest ten, and, as its default page, sorted by count DESC, the busiest. The header and the table beneath it come from one reply and one scope and cannot disagree about what they describe; they may now differ in AGE by up to `Stats_Store::BUCKET_SECONDS`, the header being a fold cached per bucket and the rows a ranked read cached sixty seconds ([decision 28](#decision-28-the-writer-ranks-each-bucket-and-indexes-each-name-and-the-page-reads-those-rather-than-the-index)). `as_of` names the page, which is the rows' currency. A filter matching nothing reads as an empty set rather than as zero traffic. The reply echoes the `filters` it applied (`server`, `search`, `errors_only`, `include_workers`), and the Ask brief carries them on EVERY surface, so a narrower number never reads as the site's. Every rate divides by the WINDOW, `RECENT_BUCKETS` × `Stats_Store::BUCKET_SECONDS`, dropping the bucket still filling, never by the buckets that happened to carry traffic: divide by those and a URL seen in two of twelve reads six times its rate beside a header that does not. The per-shard cap costs the totals nothing: `MAX_URLS_PER_SHARD` folds its tail into a synthetic `Other` row (`Stats_Store::OTHER_KEY`) carrying only the fields that ADD, splits included, so a total summed from this index is exact site-wide, and per server for every server `MAX_SERVER_VALUES` keeps; its own tail folds into an `Other` server no real fleet reaches. That row is marked `aggregate` and the table renders it un-clickable: its key is not a url_hash and `dump_url` cannot answer for it. `dump_url` takes the same `server`, because the modal opens from a row that filter scoped, and a site-wide average under a scoped count is the same defect one click in.

`overview` reads `total_requests`, `global_avg_ms` and `global_avg_peak_mb` from the global `hourly` namespace, which has no server dimension, so its `server` argument scopes the leaderboard (`build_leaderboard( $server )`), the breakdowns (`merge_dim_across_partitions( $dim, $server )`) and the category series, and never the totals: scoping some of a payload and not the rest is how it comes to contradict itself. `overview` does not touch the URL index at all, which also holds a filtered poll to one fan-out. The two totals differ by construction in two ways worth knowing: `hourly` drops worker requests, while the URL index keeps them on their own rows; and `hourly` counts only requests whose duration was measured, so [decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)'s evicted and aborted records reach the index and never the site total.

The table EXCLUDES worker traffic by default, and so does its header. `$count_global` keeps workers out of every site-wide aggregate, because one long-running job would otherwise dominate the averages, while the per-URL row deliberately keeps their timing, so a header summed from those rows inherits it: on a staging hub such a header reads "Avg Response" as 227ms of cron against 3ms of reader traffic. The row RECORDS whether its traffic was a worker, never derived from `?worker_type` in the URL text, a substring guess that can empty the table; the `urls` verb's `include_workers` opts IN because its default excludes, the mirror of `errors_only`, which opts in to narrow; and the capped tail folds into TWO overflow rows (`Stats_Store::other_key()`), because one cannot answer a filter about a mixed set. One scope rule holds across the surface, so no widget re-litigates it: a FETCH sends the live selection, so `urls`, `dump_url` and `ask` all ask for what is selected now, while a LABEL reads the scope the server echoed back, because it names numbers already on screen. Mixing the two puts a brief for one server beside a panel showing another's.

Two surfaces the scope deliberately does NOT reach, both because the storage cannot answer them: `dump_url`'s `breakdown_time_series`, `category_time_series` and `aggregate_flame` are per-URL only, since a per-URL-per-server series would be new storage on the axis [decision 11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped) watches, and `find_recent_requests_for_url()` has no server in the request index. Both are harmless while a stored `url` is absolute, which makes one URL one site. **Revisit if** the header ever needs a number the URL index cannot produce (the answer is a new field on the `urls` reply, not a second source read beside it), or if a host is ever reported by two servers, at which point `dump_url`'s three series and `find_recent_requests_for_url()`'s examples start describing a wider set than the count above them.

## Decision 16: The breakdown panel is always mounted, and says which kind of nothing it has

[`BreakdownControls`](../src/overview/components/BreakdownControls.js) is the chart and the Metric and Breakdown dropdowns that drive it, plus a Server select when the caller passes `serverOptions` (the Overview card does): one panel, because the Metric and Breakdown values the chart reads are exactly the ones its own selects set. Both callers mount it unconditionally, and one resolver, [`breakdownState( breakdownData )`](../src/overview/AggregateTimeChart.js), tells the chart and the panel which kind of nothing they have.

![The breakdown panel's callers and states. The Overview card reads overview.breakdowns[dimension], a map the server keys by every dimension it was asked for, so an absent key is a dropdown switch the reply has not caught up with; overview refuses a dimension outside DIMENSIONS rather than answering about the rest. The URL modal's url_breakdown reply carries one dimension and no key, so the switch runs setBreakdownData(null), and subjectOf makes the subject the (URL, dimension) pair, so a superseded reply matches no outstanding ask. Both feed breakdownState(), and the panel checks a refusal first: error shows the refusal under the chart and is terminal; pending (null or undefined, no series in hand) shows Loading and draws nothing; empty (a series with no values) shows No User Agent data in this window, naming the dimension; series draws the chart, the only state that does. The dropdowns render in all four, because they are the only way out of a dimension with no rows, a read in flight or a refused reply, and there is no None breakdown to fall back to. A card shows what a gate does: falling back to aggregate_time_series draws a flat Total series under a dropdown reading User Agent, and gating on breakdownData unmounts the only control that can recover from a refusal useCommandOnce treats as an answer.](img/dec-breakdown-state.png)

The dropdowns are the only way out of a dimension with no rows, a read still in flight or a refused reply, so any gate that can unmount them can trap an operator. A gate that falls back to `overview.aggregate_time_series` when the selected dimension has no values draws a flat series legended "Total" under a dropdown reading "User Agent"; a gate on `breakdownData` unmounts, on an error, the only control that can recover from it, because `useCommandOnce` treats a refusal as an answer. There is no "None" breakdown, so the totals are never the requested view and the chart holds no undifferentiated source at all. `breakdownState()` returns `pending` when no series is in hand (`null` or `undefined`), `empty` when one arrived carrying no values, and `series` otherwise; only `series` draws. The panel checks a refusal first: `error` prints the refusal's message under the chart, and a refusal is terminal. The two callers reach `pending` by two different mechanisms, and the wire guarantees neither on its own. The Overview card reads `overview.breakdowns[ dimension ]`, a map the server keys by every dimension it was ASKED for, so an absent KEY is a dropdown switch the reply has not caught up with. The URL modal's `url_breakdown` reply carries one dimension and no key to look it up by, so its `pending` is the explicit `setBreakdownData( null )` the switch runs, and what keeps a stale answer out of it is the ADDRESS: `subjectOf` makes the subject the (URL, dimension) PAIR, so a superseded dimension's reply matches no outstanding ask, fills nothing and retires nothing. "No User Agent data" during a fetch is a lie that flickers, and the totals under either state answer a question nobody asked.

*Alternatives rejected:* a `mountWhen` prop (a gate, passed in, and every value of it can strand the operator); two panel components (one panel, two callers, and the second copy exists to hang one boolean on); emptiness alone as the discriminator (collapses `pending` into `empty`, which is the flicker). **Revisit if** the server ever OMITS a requested dimension that turned out to have no rows, which would make the two states indistinguishable on the wire and move the fix server-side, and watch `CHART_BREAKDOWN_OPTIONS` against `Performance_CI_Node::DIMENSIONS`, two hand-matched lists in two files. `pending` is terminal, so a dimension the server drops hangs the panel rather than degrading it; `overview` therefore REFUSES a dimension it does not know instead of answering about the rest, which turns that drift into a message under the chart.

## Decision 17: The URL index is stored at TWO resolutions, and the coarse one is DERIVED

The readers ask at two resolutions only, so the URL index is stored at two: a fine five-minute tier for the window's recent edge, and an hourly tier the writer folds out of it.

![One shard's read plan across a 24-hour window: Stats_Store::read_plan() splits it into a fine tail of 13 to 24 five-minute buckets ending now, a grace hour behind it, and up to 23 coarse keys, urls_h:{shard}:{Y-m-d-H}, one per closed hour. Anything further back is the coarse tier's alone; an hour with no coarse key has not been folded yet, and an empty hour is still written, so absence means one thing. Only the grace hour is answered from its twelve fine buckets, whatever their age, so a fresh deploy or a restart self-heals. FINE_BUCKETS (13) is a floor: the tail runs to the end of its hour, since an hour read half fine and half coarse is counted twice or read at neither resolution, a hole that silently shrinks every count on the page. The plan reads 36 to 46 keys per shard against 288; read at full resolution, 16 shards by 288 buckets by 4 partitions is 18,432 keys and 54 MB of unserialize per request on the staging hub. Tiles: ROLLUP_HOURS_PER_FLUSH 2; a one-lookup_multi skip probe, where probing per hour pays 23 round trips a flush, decision 6's latency cliff; FINE_TTL_SECONDS 7,200 (24 buckets a shard); INDEX_READ_CHUNK 12, where the walk is per shard and an hour the coarse tier answered for is taken from it, only the leading hour falling back to its twelve fine buckets; and the 512 MB that exhausts in empty_index_row() when the whole window's rows sit resident. Cards: the fold runs on the writer's flush path, not the cron pass, to keep one writer per partition, and is idempotent because it overwrites from the fine buckets, per shard, keeping each shard's Other row; the coarse tier is not mirrored, because urls is mirrored in full and the rehydrate seam rebuilds an evicted hour from disk; and the coarse key is a resolution the schema chooses, not a scope, with decision 6's batching intact.](img/dec-two-resolutions.png)

[Decision 1](#decision-1-namespaced-memcache-schema) gives every bucketed namespace one width, `BUCKET_SECONDS`, and the URL index pays for it hardest: read at that width, sixteen shards × 288 buckets × four partitions is 18,432 keys and 54 MB of unserialize per request, measured on the staging hub. Against that, [`Performance_CI_Node::load_index_default()`](../includes/app/class-performance-ci-node.php) makes exactly ONE per-bucket distinction in its entire fold, `isset( $recent[ $bucket ] )`, and sums everything else, so the readers ask at two resolutions only: the whole retention window, and the last complete hour (`RECENT_BUCKETS`). Five-minute precision buys the window's recent EDGE and nothing behind it. `NS_URLS_HOUR` (`urls_h:{shard}:{Y-m-d-H}`) holds one hour of merged rows in the same shape a fine bucket holds, and `Stats_Store::read_plan()` splits a window into `{ fine, hours }`: 36 to 46 keys per shard against 288. The row shape is identical ON PURPOSE: ONE `fold_index_row()` reads both tiers, because a second copy of the merge is how the table and the modal come to disagree about one URL, and ONE `Stats_Store::merge_url_row()` writes both, because a second writer is how a folded hour drops `srv`, which `sum_entry()` does not fold, and a folded hour with an empty split takes every server-scoped read of that URL with it. **The coarse key is not a scope and does not reopen decision 1**: the bucket stays LAST, one `lookup_multi` serves the tier, and retention is still the key's own TTL. It is a RESOLUTION, a constant this schema chooses exactly as the shard count is, and not an input it does not control.

**`FINE_BUCKETS` (13) is a FLOOR, not a ceiling**: the fine tail runs to the END of the hour it lands in, because an hour read half fine and half coarse is either counted twice or, worse, read at NEITHER resolution, a hole of up to eleven buckets that breathes with the minute hand and silently shrinks every count on the page. **The fold is idempotent because it OVERWRITES from the fine buckets**; adding into an hour would double-count every re-flush, and the fine buckets outlive their fold. No reader reads a folded hour's buckets; a re-fold does, which is what makes a missing hour key recoverable. **An hour with no coarse key has not been folded YET, and only the GRACE hour, the one immediately behind the fine tail, is answered from its fine buckets** (`Stats_Store::unfolded_hour_buckets()`). That makes a fresh deploy, and the hour a worker restarted through, self-healing rather than a hole, and it works only because an EMPTY hour is still written, so absence means exactly one thing. Anything further back is the coarse tier's alone: the fine tier answers the last hour and feeds the fold, and reading it for older hours costs one certain miss per shard per chunk per partition, each of which walks an armed mirror's index in full. The grace hour reads all twelve of its buckets whatever their age against `ttl_url_fine()`, because that TTL is the MEMCACHE lifetime and the reader is not memcache-only: bounding the fallback by it makes an evicted hour unrecoverable. The same asymmetry is why the coarse tier is **excluded from the mirror** (`Stats_Store::is_derived()`): it is derived from `urls`, which is mirrored in full and retained for `<eln:stats_mirror_lifetime>`, twice the stats window, so a fine bucket long expired from memcache is still on disk and the rehydrate seam rebuilds the evicted hour from it. The fold reads through the same seam, which the worker arms unbudgeted, so the re-fold of an evicted hour reads what a reader would. A durable copy would store the same information twice on the axis [decision 11](#decision-11-the-open-bucket-is-durable-in-the-offsetlog-until-it-closes-and-the-carry-is-capped) watches, and an hour frame would be the largest thing in the held set at a checkpoint.

**The READ streams: `load_index_default()` folds one `INDEX_READ_CHUNK` (12) of buckets at a time and drops it before reading the next.** `url_row_sources()` issues one `lookup_multi` across all sixteen shards, so asking it for the whole window returns every bucket's rows at once, hundreds of MB at `MAX_URLS_PER_SHARD` per key, resident beside the index being built. That volume, not any duplicate copy of it, is what exhausts a production hub's 512MB in `empty_index_row()`. [Decision 6](#decision-6-get_multi-batching-is-essential) is unharmed: the batch is still one round trip for many keys, bounded to a chunk. The hour tier is chunked the same way, and the walk is per SHARD: `walk_shard_tiers()` reads the plan's hours for the one shard it was handed, takes every hour the coarse tier answered for from that tier, and falls back to fine buckets only for an hour it did not — the `buckets` half of `Stats_Store::fine_fallback()`, which `unfolded_hour_buckets()` allows for the leading hour alone.

**The fold runs on the writer's flush path, not on `newspack_nodes/periodic`**, and that is the one place this decision touches [substrate ADR-9](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-9-two-tier-safety-net): the cron pass is the documented home for minute-or-slower derived housekeeping, but `persist_aggregate_stats()` rests on one partition having one writer, and a cron process folding p{N}'s keys puts a second one in a keyspace [substrate ADR-6](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-6-crc32--31-bit-mask-partition-routing)'s routing exists to keep single-writer. Idempotence would make that benign; the invariant is worth more than the placement. `ROLLUP_HOURS_PER_FLUSH` (2) bounds a cold start's backfill so it spreads across flushes rather than stalling one, and the skip probe is ONE `lookup_multi` for the whole window, where probing per hour pays 23 round trips every flush to learn there is nothing to do: decision 6's latency cliff. The fold stays PER SHARD and is not regroupable by hash: each shard carries its own `Other` overflow row, and a merge keyed on the url_hash would collapse sixteen of them into one.

**The fine tier carries its OWN retention**, `FINE_TTL_SECONDS` (7,200, two hours), against `min_lifetime` for the coarse tier that outlives it: the read plan asks for `FINE_BUCKETS` plus the rest of their hour, so under the full `min_lifetime` 264 of every 288 buckets a shard would sit in a 512MB cache with no reader. The tier has exactly two consumers, `RECENT_BUCKETS`' last-hour rate and the fold, and two hours covers both: the plan's fine span is just under two at the worst minute, and an hour folds within a re-probe of it closing. At that width the tier costs 24 buckets a shard against the coarse tier's 24 hours, and a wider bound buys margin for no read the plan makes. TTL is still not a fold trigger; the bound is sized to outlive every read and every fold that will touch these buckets.

*Alternatives rejected:* reading fewer buckets and accepting the gap ([decision 15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site)'s totals are summed from this index and must stay exact); rolling up on read (every poll pays the fold this exists to stop paying). **Revisit if** a reader ever needs a THIRD resolution, at which point the tier list is a table rather than two constants; if the skip probe stops being answerable in one round trip; or if late data lands in an already-folded hour often enough to matter: an hour is folded at least an hour after it closes, against a `DEFAULT_EVICTION_WINDOW_SEC` of 1080, so a replay is what lands there, and [decision 19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in-and-a-write-into-a-folded-hour-reaches-its-fine-bucket-and-the-hour-key) sends each such write to its fine bucket and the hour key, one extra read and write per key.

## Decision 18: A stored value may be POSITIONAL, and then its indexes are named constants

[Decision 1](#decision-1-namespaced-memcache-schema) makes every key a schema this plugin owns; this decision says what a VALUE costs. `serialize()` writes every key NAME into every entry, so a named URL row spends `s:11:"timed_count";`, 19 bytes, to say what `i:1;` says in 4, once per row per field, on a read that already fans out to thousands of keys. Measured on live rows through the real pipeline, a row is 672 bytes named against 398 positional, 40.9% less, which takes the hub's 36.1 MB across 58,415 rows to roughly 21. Three values here are dense enough to earn the shape. The URL index earns it on memcache: the one namespace whose rows are counted in tens of thousands and whose whole window is read per poll. The category and dimensional series earn it on the MIRROR, which keeps a whole window of frames; the last paragraph holds both.

![One URL row as fourteen positional slots, each named by a Stats_Store::ROW_ constant: indexes 0 to 7 are the eight fields that add (COUNT, TIMED_COUNT, SUM_MS, SUM_PEAK_MB and the four status-class counts), which is URL_SRV_SUMS, the one map that describes the row and its per-server split alike; 8 to 12 are the extremes, a timestamp and a flag (MIN_MS, MAX_MS, MAX_PEAK_MB, LAST_SEEN, WORKER), never split; and 13 is SRV, the split. Tiles give the measurements: 672 bytes a row named against 398 positional on live rows, 40.9 percent, taking the hub's 36.1 MB across 58,415 rows to about 21; the sole-server collapse from 369 to 290 bytes, a further 21.4 percent and 56.8 percent off the 672; naming the split at the fold costing 23 to 37 percent of the fold pass, 34 to 98 ms a urls poll; and 44.1% off the entries of a JSON mirror frame across 66,966 of them, CAT_SUMS and DIM_SUMS positional too. Cards: ROW_FIELD_NAMES is the one place an index becomes a name, one map beside its constants because a private copy is how a reader ends up omitting a field; fold_index_row() is the one storage and display boundary for the row, the split never crosses it, and neither CAT_SUMS nor DIM_SUMS has a name table, because each stays positional at the wire; a one-server split stores the host against null, which means its numbers are the row's, while an absent host means never served here, so every merge runs expand_sole_server() before summing, and merge_url_row() and fold_url_rows() do it for both sides, which covers the re-flush, the coarse fold and the overflow tail.](img/dec-positional-row.png)

A one-character field name is the same cost half paid: it still spends 6 bytes of JSON where an index spends none, which is why `DIM_SUMS` is positional rather than merely short. **The indexes are `Stats_Store::ROW_*` constants, and a bare integer literal is forbidden**: the constants buy back the readability the shape spends, and `$row[3]` is unreadable AND silently mis-typeable, which is [substrate ADR-2](https://github.com/Automattic/newspack-nodes/blob/main/docs/architecture-decisions.md#adr-2-one-message-format-the-7-field-positional-array)'s own consequence in a second place. **The eight fields that ADD come first, in `URL_SRV_SUMS` order**, so ONE map describes the row's summed half and its per-server split alike, and [decision 14](#decision-14-a-server-scope-the-key-cannot-carry-rides-inside-the-value-and-is-applied-as-a-projection)'s "that row restricted to one server" is structural rather than a naming coincidence. The order also keeps `cap_servers()` honest: ranked by the field NAME `count` on a positional split, `cap_bucket()`'s sort compares nulls, ties every pair, degrades to insertion order, and past `MAX_SERVER_VALUES` folds the BUSIEST hosts into `Other`, the Host-header-spray case decision 14's cap exists for, invisible to a spray test where 300 servers at one request each have no ranking to get wrong.

**`ROW_FIELD_NAMES` is the one place an index becomes a name**, in the shape `Message::TYPE_NAMES` sets: one map beside the constants it names, because a private copy is how a reader ends up omitting a field. **`Performance_CI_Node::fold_index_row()` is the one storage/display boundary for the ROW**: everything above it is positional, the display row keeps its names because it crosses the wire as JSON, and a second copy of the translation is how the table and the modal come to disagree about one URL. **The SPLIT is not display data and never crosses**: `swap_url_server_sums()` merges one server's sums into the row and unsets the split, `project_row()` unsets `srv_recent`, and every escape from the index goes through that projection, so the split stays positional through the whole fold and is named ONCE per scoped read, for the one selected server, by `swap_url_server_sums()`, the only site that NAMES it. Besides it, `project_row()` and `fold_page()`'s split accumulator read the split, for a count and an emptiness test, and neither wants a name. That accumulator never leaves the page either: `fold_page()` answers `totals: null` itself where a scope the rows carry no split for cannot be answered, rather than handing a flag out for each caller to re-derive it from. Naming the split at the fold instead would cost a third field map, a memoized derivation and a 25-line translation on the hottest read loop in the plugin, to name data nothing displays: measured at 23-37% of the entire fold pass, 34-98ms per `urls` poll. A thing crosses a boundary where it is CONSUMED, not where it is convenient to convert.

**A split of ONE server that served every request the row counted is the row restated, and stores the host name against `null`**: 369 bytes a row to 290 on the hub's own row shape, a further 21.4%, and 56.8% off the 672 above, on the field that is over half the whole read. A stored `url` is ABSOLUTE, so on a fleet of disjoint sites every URL has exactly one host and this is the COMMON row, not the rare one. COUNT alone decides it, because every `URL_SRV_SUMS` field is summed into the row and the split from the same increment, so a matching count means the other seven match by construction. The collapse turns ABSENCE into MEANING, and the two states are adjacent with opposite answers: `null` says "this host's numbers ARE the row's", a host MISSING says "never served here" and drops the row from a scoped read. `Stats_Store::collapse_sole_server()` and `expand_sole_server()` are the pair, and **every merge, reader or writer, must expand BEFORE summing**: `merge_url_row()` and `fold_url_rows()` do it for both sides, which covers the re-flush, the coarse fold and the overflow tail. `sum_fields()` skips a non-array value, so an unexpanded null is not a zero: it is that host deleted from the merge, a URL vanishing from a filtered table rather than an error. The rule names writers as well as readers because a write-side merge that skips the expansion breaks no reader's test, and the whole suite stays green. The suite pins the row shape in ONE test that reads a shard raw, and translates at the seed and read helpers everywhere else, so a test that merely touches a row never counts indexes.

*Deliberately NOT swept in:* the leaderboard's `{time, count, samples}` entry triple (`LB_ENTRY_SUMS`), positional with no constants on both sides of the language boundary: a closed 3-tuple read by two adjacent functions and one React component, where naming it means naming it twice in two deploy units for three fields. *Alternatives rejected:* a value object (it would have to serialize to something, and that something is this array); compressing the whole value (opaque to every diagnostic, for the same bytes at CPU cost); shortening the field NAMES (keeps the cost and loses the readability the constants restore). **The second-namespace condition below is MET, and is answered with a second constant block rather than a per-namespace table.** `CAT_SUMS`, the category series, `Stats_Store::CAT_MS`/`CAT_CALLS`/`CAT_REQUESTS`, is positional for the stats MIRROR rather than for memcache: a frame is JSON, where a three-field named entry is 30 bytes against 15, and the category series is spelled once per five-minute bucket per scope across a window the mirror keeps whole. Every field ADDS, so `CAT_SUMS` is itself the whole index set and the ordering clause is satisfied trivially. **It has no `CAT_FIELD_NAMES`, and that is not an omission**: `compact_category_series()` is the series' one storage/display boundary and emits a POSITIONAL wire row, so no index ever becomes a name, and a name table with no naming site is a second shape waiting to drift. `StatsStoreTest` asserts `array_keys( CAT_SUMS ) === range( 0, 2 )`, the same mechanism the two row tables get. **`DIM_SUMS` is the THIRD, and it is a third block of constants, not a per-namespace index table.** A table would buy one declaration site for three index sets and cost a lookup where a constant stands, on `cap_bucket()`'s comparator and on `sum_entry()`'s rebuild, both of which run per entry per bucket per poll; three closed triples, each named beside the fields it indexes, are not the drift a table exists to prevent. `Stats_Store::DIM_COUNT`, `DIM_SUM_MS` and `DIM_SUM_PEAK_MB` take the ROW block's vocabulary exactly, because they are the same three measurements and two spellings of one measurement read as two measurements. Like `CAT_SUMS` it has no field-name table, for the same reason: the entry stays positional to the WIRE, so no index anywhere becomes a name, and the two React sites that read it index it as `LB_ENTRY_SUMS` is indexed. The ordering clause is what makes the cap honest here too — `cap_dim()` ranks by `DIM_COUNT`, and ranked by a field NAME a positional entry does not carry, the sort compares nulls, ties every pair and folds the BUSIEST values into `Other`, which a cap test that only counts survivors cannot see; `FlameBuilderTest` names the busiest and the quietest instead. Nothing migrates a stored entry into this shape: memcache is migrated by decision 5's flush, and a mirror frame the merge cannot name is refused and ages out. **A rank entry is positional too and does not count toward the clause below.** `Stats_Store::RANK_HASH`, `RANK_ROW` and `RANK_PATH` — the last present on the `url` lists alone — are an ENVELOPE around one row, not a sum table: nothing merges two of them field-wise, so there is no `sum_entry()` rebuild to keep contiguous and no `cap_bucket()` comparator to keep honest, and no `range( 0, N )` assertion fits a shape whose last index two lists of fourteen carry. It takes constants for the reason the three above do, and the clause counts the SUM TABLES. **Revisit if** a FOURTH sum table wants the shape — a fourth set of indexes `sum_entry()` rebuilds and `cap_bucket()` ranks through — which is where the table stops being deferrable, or when a NINTH summed field is added to the ROW, because indexes 0-7 are full and the contiguity that makes "the eight that add come FIRST" true is prose: appending it at 14 works and quietly falsifies the sentence. `StatsStoreTest` asserts all three key sets are exactly `range( 0, 13 )`, `range( 0, 7 )` and `range( 0, 2 )`, which is the mechanism that prose does not have.

## Decision 19: A request is filed in the bucket it FINISHED in, and a write into a folded hour reaches its fine bucket and the hour key

A stats write must land where a reader will actually read it, which takes two halves: file a request under the bucket it FINISHED in, and send a write into an already-folded hour to the fine bucket the hour key is derived from as well as to that key.

![A request's stats write across a timeline and three steps. The record reaches `Flame_Builder_Node` at completion, so filing it under `timestamp`, the START, puts a long request in a bucket that may already have closed. The bucket is therefore `min( now, timestamp + round( duration_ms / 1000 ) )`: the completion needs no new field, and for an aborted request it is the abort moment, because `Request_Builder` sets `duration_ms = now - start` at eviction. That removes the request's own duration from the exposure, which the 1080s assembly window bounds at eighteen minutes. The completion is **clamped to now**: a completed request cannot have finished after it reached us, and a skewed spoke clock or a bogus duration filing into a future bucket, which readers walking backwards from now never reach, is the same written-then-unreadable failure this decision exists to close.

**Filing by completion does not remove transit**, and that is the second half. `folded_hours` records the hours this process has folded, and [decision 17](#decision-17-the-url-index-is-stored-at-two-resolutions-and-the-coarse-one-is-derived)'s reader takes a folded hour's key and never its fine buckets, because they outlive the fold and reading both counts the hour twice. A record arriving after its hour folded therefore has to reach the hour key to be read, and its fine bucket to survive a re-fold. **`Flame_Builder_Node::hour_tier_intents()` files both writes** for a bucket whose hour this process has folded, in every hour-derived namespace — URL rows, URL names and the global leaderboard — with one merge: the fine key under the bucket, and `urls_h`, `urlnames_h` or `lb_h` under the hour. A per-server leaderboard has no hour tier and takes its fine write alone. **Only the hour-key write is `present`**: when its read misses, `flush_writes()` writes nothing and forgets the key, because a miss is either a key that is gone or a failed batch read, which `Cache_Backend::read_multi()` reports as all-miss, and a forgotten key is one the reprobe re-folds. `add_intent()` keeps the held intent's `present`: only an hour-tier intent is present, and no fine intent shares its key. The coarse tier is unmirrored and evictable and a fold write can be refused, so an hour this process folded can lack a shard, and a late write merged into the missing key would recreate the shard holding the late rows alone, which `url_hours_derived()` counts as present, so the hour would settle as folded with that shard's original rows lost. With the fine write in place, the reprobe finds the key missing and re-folds every key of the hour from fine buckets that hold the late rows, including the rows merged into keys still present; `url_hours_derived()` counts `lb_h` among an hour's keys, so a missing leaderboard hour is re-folded the same way. **The fine write goes through the Table at the normal fine TTL**, like any fold read that re-warms the bucket: a re-fold reads the same buckets back through the mirror, and `window_remaining()` warms each for up to `ttl_url_fine()`, so the late write adds no footprint the re-fold does not. The fine write forms no ranking group, because its bucket sits behind the fine tail. A URL hour-key write that lands forgets the hour's DONE marker, once per hour per flush, so the probe finds the hour folded and unranked and re-ranks it from its stored rows; the debt lives in the store, so a stop loses none of it. **The trigger is routine, not exotic**: `wp nodes deactivate complete; wp nodes gc --force; wp nodes activate complete` replays the whole retention window, and every replayed record carries its original timestamp. A hub sees it with no replay at all: one flame-builder partition takes every spoke's records, so a spoke feeding a backlog while its peers are caught up lands rows in hours already folded, and every such write has to be right whenever it arrives. A caught-up spoke's records, measured on a hub, reach the builder ~14s old against a fine tail of 65 to 120 minutes. **`folded_hours` is per-process, and one partition has one worker** (`persist_aggregate_stats()` says so: read-then-write is not atomic), so a respawn is the only way the memo goes stale, and there is no peer to race. `flush()` therefore rolls up BEFORE it persists: the roll-up probes the coarse tier, so the first flush after a respawn has an accurate memo before a single row is placed. The fold budget stops folds and never the probe, so every hour the probe finds folded is memoized in the flush that probes it, however many newer hours still wait for a fold.

*Alternatives rejected:* dropping the hour from `folded_hours` so the next flush re-folds on every late write: a re-fold reads twelve fine buckets for every shard of both families and rewrites the hour's rows, names and lists, where the merge into a present hour key is one read and one write; re-addressing a write to its fine bucket only when the hour key's read misses, which leaves rows merged into a PRESENT shard out of the fine tier, so a re-fold forced by any other missing shard of the hour drops them; having the reader take both tiers, which decision 17 already rejects as double-counting; and capping the late fine write at what is left of its bucket's fine lifetime, which needs a second write path beside the Table, because a Table holds one TTL, to save a footprint the re-fold's own reads spend anyway. **Revisit when** a write needs to reach a bucket older than the coarse tier retains, which this does not answer: the row is capped by the hour's own lifetime either way.

## Decision 20: Outbound HTTP is timed as a span, and a short-circuited request opens nothing

Without these spans a request that spends its time below PHP userland reports as unmeasured, the one answer a reader cannot act on. A BDN `wp-admin/post.php` record shows the cost: 41.7s wall against 12.2s CPU, with `Image_CDN::filter_the_content @999999` holding 29.4s of self time and no interior, so the 29.5s off-CPU remainder has no name. A hook cannot reach it, since `WP_Http::request()` is not a hook, but WordPress brackets the call: `pre_http_request` before, `http_api_debug` after. [`App\Core`](../includes/app/class-core.php) binds that pair for every log rule whose `log_http` is set, so the span costs two registrations per request and two entries per remote call. **The pair is NOT balanced, and that asymmetry is the whole design.**

![The outbound-HTTP span as a priority ladder. Step 1, apply_filters('pre_http_request', false, $args, $url): any filter may answer the request and return it, and http_start sits at PHP_INT_MAX, last to vote, so it opens nothing when $preempt is not false and otherwise pushes the label http and writes http (start). Step 2, the transport runs: the I/O below PHP userland the span exists to name. Step 3, do_action('http_api_debug'): http_end at PHP_INT_MIN hears it first, pops the label it opened rather than re-deriving it from a URL a redirect may have changed, and writes http (complete) with the status code, ahead of the other listeners. Beside it: WP_Http::request() answers a short-circuit with a bare return $pre; and never fires http_api_debug, so a span opened for it would never close and would adopt every row after it, the damage decision 13 bounds; the entry pair one remote call writes, m the redacted URL and l the calling frame; and the caller label, origin_frame(true), climbing past WP_Http at TRANSPORT_ORIGIN_DEPTH 16 rather than ORIGIN_DEPTH 8 whatever trace_callers says, with that budget reaching this span too, keyed on the redacted URL paired with the calling frame, so l names who asked on every call and caller carries the chain on the first few to each endpoint. Footer cards: the BDN wp-admin/post.php record, 41.7 s wall against 12.2 s CPU with 29.4 s of self time in Image_CDN::filter_the_content @999999 and a 29.5 s off-CPU remainder with no name; the cost, two registrations per request and two entries per remote call, under log_http; and every callback asking Log_Manager::started_instance() first so instrumentation never constructs the logger.](img/dec-http-span.png)

`WP_Http::request()` short-circuits with a bare `return $pre;` and never fires `http_api_debug` (`class-wp-http.php`), so a span opened before the short-circuit would never close and would adopt every row after it: the severed-span damage [decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) exists to bound. So `http_start` binds at **PHP_INT_MAX**, after every short-circuiting filter has voted, and opens nothing when `$preempt` is not false: a short-circuit is a cache hit with no I/O to time. A rule marking `http` significant gets that filter's listeners wrapped by `http_wrap`, bound at PHP_INT_MIN ahead of the chain on each call, the shape `hook_start` uses — `http_start` votes last, so from there a listener could only be wrapped for the NEXT call — so a short-circuiting listener's own cost shows where the span would have been. Every other return path fires the action, so within one request the pair is exact. `http_end` binds at PHP_INT_MIN so the span covers the request and not the other listeners on that action, and it closes the label it OPENED rather than one re-derived from the URL: a redirect hands the action the FINAL url, and a label that no longer matches leaves the span open. The span is named for its **caller**: `l` is `origin_frame( true )`, which climbs past every frame of the class that applied the filter, `WP_Http` here, at `TRANSPORT_ORIGIN_DEPTH` (16) rather than `ORIGIN_DEPTH` (8), because "which of my code paths makes this call, how many times" is the question a reader has; the redacted URL rides as the entry's value and the status code closes it. The climb runs whatever [decision 23](#decision-23-a-span-says-how-long-never-who-asked-two-knobs-answer-the-second-question-at-two-prices)'s `trace_callers` says, and taking the shallow walk under it is rejected: that budget reaches this span too, keyed on the redacted URL paired with the calling frame, so `l` names who asked on every call and `caller` carries the chain on the first few to each endpoint; the shallow walk would trade `l` for a microsecond or two. **Naming the HOST instead answers nothing**, because so many calls go to the same one. **Instrumentation never CONSTRUCTS the logger it reports into**: `Log_Manager::instance()` lazily creates a logger, so every callback asks `started_instance()` first, the wrapped listeners included; otherwise a binding that outlived its request would build the logger inside the callback and stamp `process (start)` with that moment instead of the mu-profiler's `request_ts`.

*Alternatives rejected:* a per-rule opt-in flag (a new `Rule` property, its serialization, its editor control and its migration, to gate two registrations and a per-call cost that is zero on the requests that make no remote calls); timing inside a `significant_events` wrapper on `http_api_debug` (that times the action's LISTENERS, which is not the request). **Revisit when** SQL wants the same treatment, though `$wpdb` offers no completion signal without `SAVEQUERIES`, so it is a different mechanism and not an extension of this one, or if a transport ever fires `http_api_debug` more than once for one request, which would pop a label that is still in flight. **Per-rule** (`log_http`), like decisions [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) and 24: a logged request pays two entries per outbound call whether or not a brief reads them. Off unless the rule sets it, as every diagnostic is, a stored rule that predates the flag included.

## Decision 21: The fold keeps the CLOSE of any span the kept head left open

The fold keeps a head of [`FOLD_KEEP_HEAD`](../includes/class-request-builder-node.php) (10), a rolling tail of `FOLD_KEEP_TAIL` (10) and an unbounded `keep` bucket, and a span opened in the head FRAMES every row after it, so the fold keeps the close of every span that head left open.

![One job record from community.thecoast.ca folded two ways. The gyrobase subprocess opened in the kept head (FOLD_KEEP_HEAD 10) and closed after 535.8 s of a 536.2 s request, and ten PHP rows followed it: nuclear_gyrobase, two query hook pairs, updated_option hook, memory, resources and the terminal. Without the rule, the close is one more row in the rolling tail (FOLD_KEEP_TAIL 10), the ten rows evict it, and the entry list leaves gyrobase open, so the view reconstructs framing the record does not state and three display defects follow, while the flame, counted only by Flame_Fold::close(), still reads gyrobase count 1, 535,829.753 ms. With the rule, open_in_head() records the open bases at the fold and closes_head_span() routes their completes into keep, spliced between the entries (aggregated) marker and the tail; at most FOLD_KEEP_HEAD closes can land there, and process (complete) is exempt so the terminal still ends the record. Notes: is_kept() leaves tail sizing to producers marking their lines, but a span's close is not that guess, because the fold chose the head; and losing a head span's close costs the record its shape, not one line.](img/dec-fold-keeps-close.png)

`is_kept()` argues that sizing the tail around a producer's shutdown sequence is guesswork the producer should settle by marking the line. A span's close is not that guess: the fold just chose the head, so it knows exactly which frames it left open, and there are at most `FOLD_KEEP_HEAD` of them. Nor is the close mere detail: losing a head span's `(complete)` costs the record its shape rather than one line. A `community.thecoast.ca` job shows it: the gyrobase subprocess closes after 535.8s of a 536.2s request, and the PHP parent's ten post-subprocess rows (`nuclear_gyrobase`, two `query hook` pairs, `updated_option hook`, memory, resources, terminal) fill the rolling tail and, without this rule, evict the close. The flame still counts the span, because `Flame_Fold::close()` is the only path that increments a node's count and the tree reads `gyrobase` count 1, 535,829.753ms; but the entry list leaves it open, and three separate display defects follow from the view reconstructing framing the record does not state. `open_in_head()` records the open bases at the fold and `closes_head_span()` routes their completes into `keep`, which the assembly splices between the `entries (aggregated)` marker and the tail. **The request's own frame is exempt**, exactly as it is for the display's severed-span prune: `process (complete)` is the terminal and must END the record, and `keep` lands BEFORE the tail.

*Alternatives rejected:* having the producer mark the line (`Gyrobase::Log` could set `keep` on its nested `complete('gyrobase', …)`, but that fixes one producer in another repo and leaves every other one to rediscover it); closing the span in the VIEW from the tree's count and value (puts derived data in the entry list, and leans on exactly the reasoning across a marker [decision 13](#decision-13-a-sequence-break-marker-is-missing-detail-not-idle-time) restricts). **Revisit if** a head ever legitimately leaves more frames open than the tail can afford to carry, which would mean `FOLD_KEEP_HEAD` is choosing a head the record cannot frame.

## Decision 22: Query spans are the same pair as decision 20, but PER-RULE

[Decision 20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) leaves SQL as its reopen condition and calls it a different mechanism; it is the same shape with a different gate. `wpdb` brackets a query with `apply_filters( 'query', … )` before and, only under `SAVEQUERIES`, `log_query_custom_data` after. [`App\Core`](../includes/app/class-core.php) binds `query_start` on the [`query`](https://developer.wordpress.org/reference/hooks/query/) filter at the configured `hook_start_priority` (a plugin config key, default -10000), the priority the generic hook timer uses, so the span opens ahead of the filter chain and every filter that rewrites the SQL runs inside it. It records the label only, since the SQL at that point is what the caller wrote. `query_end` binds on `log_query_custom_data` at PHP_INT_MIN, pops the label and writes `sql (complete)` with the statement the database was asked: its host annotation stripped by `without_host_annotation()`, its literals replaced with `?` by `without_literals()`, and bounded only by `Log_Manager::MAX_DATA_SIZE`. A rule marking `sql` significant gets the `query` filter's per-callback timings nested inside the span, and with `log_queries` on, `query` itself is not bound as an ordinary hook.

![The query span as a priority ladder. Step 1, apply_filters('query', $sql) inside wpdb::query(): query_start at hook_start_priority (default -10000), the priority the generic hook timer uses, opens the sql span with its label only, since the SQL at that point is what the caller wrote, and every later filter that rewrites the SQL runs inside the span; a rule marking sql significant gets the query filter's per-callback timings nested inside the span, and query itself is not bound as an ordinary hook. Step 2, the database round trip, about 0.4 ms on the measured host. Step 3, log_query_custom_data, which wpdb fires only under SAVEQUERIES: query_end at PHP_INT_MIN pops the label, writes sql (complete) with the statement as rewritten, its host annotation stripped by without_host_annotation() and its literals replaced with ? by without_literals(), bounded only by MAX_DATA_SIZE, and then drains $wpdb->queries; App\Core defines SAVEQUERIES when it is absent, and a long-running worker keeps the constant for its life, bounded by the drain. Beside it: the entries one query writes; the label l, origin_frame(true), climbing past every wpdb frame at TRANSPORT_ORIGIN_DEPTH 16 because SHOW FULL COLUMNS arrives four wpdb frames deep, where naming the table says SELECT wp_posts ran 156 times and never which code ran it; and why it cannot be always-on, since Query Monitor would find $wpdb->queries empty. Tiles: 3,000 queries in 1.117 s with the constant against 1.254 s without, 217 bytes held per query, and two entries per query against HTTP's two per remote call.](img/dec-query-span.png)

**The difference from HTTP is the cost, and it is measured, not assumed.** Both are per-rule opt-ins, but HTTP's price on a request making no remote calls is two `add_filter` calls. Queries cost two log entries EACH, and the close does not fire at all without `SAVEQUERIES`, so `log_queries` is the flag to weigh. What that constant costs was measured rather than feared: 3,000 queries run in 1.117s with it and 1.254s without, so the `get_caller()` backtrace is noise against a 0.4ms round trip, and what is real is retention, 217 bytes per query held in `$wpdb->queries`, the memory pressure that folds these records. `query_end()` therefore DRAINS that array, which is also why this cannot be always-on: anything else reading it (Query Monitor) finds it empty. `App\Core` defines `SAVEQUERIES` when it is absent, and a constant cannot be withdrawn, so a long-running worker keeps it for its life, bounded by the drain. **The span is named for its CALLER**: `l` is `origin_frame( true )`, as in decision 20, which takes the first non-machinery frame as the transport and climbs past every frame of it, whatever `trace_callers` says. A fixed skip cannot do that job: `wpdb::get_row()` reaches the `query` filter through `wpdb::query()`, and `SHOW FULL COLUMNS` arrives four `wpdb` frames deep, which is why the transport climb runs to `TRANSPORT_ORIGIN_DEPTH` (16) where a hook's own origin needs `ORIGIN_DEPTH` (8). Naming the TABLE instead says `SELECT wp_posts` ran 156 times and never which code ran it, and which code ran it is the only version of the question worth asking. *Alternatives rejected:* the `query` filter alone, closing each span at the NEXT query (charges every query with the PHP that ran after it); `$wpdb->num_queries` deltas on existing spans (free and always-on-safe, but counts are not spans, and the flame is what is being asked for); a `db.php` drop-in (accurate and SAVEQUERIES-free, but the host already ships one). **Revisit if** a reader needs the full callstack `log_query_custom_data` hands us rather than the one origin frame.

## Decision 23: A span says how long, never who asked. Two knobs answer the second question, at two prices

Decisions [20](#decision-20-outbound-http-is-timed-as-a-span-and-a-short-circuited-request-opens-nothing) and [22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) add spans; this one adds PROVENANCE, because a hook that fires sixteen times reads as sixteen identical mysteries and no amount of timing distinguishes them. A `/wp-admin/post.php` record is the case: `the_content` fires sixteen times at ~2.4s each, 93% of a 40.6s request, and every span says the same thing. What is missing is the caller.

![Two provenance knobs at two prices, from a /wp-admin/post.php record where the_content fired sixteen times at about 2.4 s each, 93 percent of a 40.6 s request. Left, trace_hooks: origin_frame() takes one frame, who called the hook, and puts it on the entry's l, the flame's aggregation label, so one the_content node splits into a node per caller with measured durations and no tree code changes, and it never synthesizes an ancestor such as wp_trim_excerpt for an uninstrumented frame, which would assert a duration nobody measured; debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH) costs 0.9 microseconds against 12.7 for wp_debug_backtrace_summary(), the depth limit being the lever, so it runs on every firing, 2,601 render_block calls costing 2.3 ms. Right, trace_callers: caller_of() records wp_debug_backtrace_summary(self::class) onto the hook's own start entry as caller, not c, which means count throughout the schema; the rule's number is the count of deep chains, default 0, with a stored true reading as a count of 1, because the pair key makes one chain per caller a chain from every caller, and a strip of one CALLER's firings of one hook shows the first twenty carrying chains at trace_callers = 20 and the rest none, with a tick under the twentieth, the cap being per caller of a hook, not per hook and not per request; the window is CALLER_FRAMES, 20 frames, because a fixed 20 leaves 21 percent of a record unattributed and an 8-frame window stops one frame short of rest_preload_api_request. Footer: a field nothing renders does not exist, so LogEntriesTable renders the caller chain as called by …; both knobs are off by default, like log_queries and unlike log_http; and Log_Manager::message() merges arbitrary keys into the entry, [ 'n', 'k' ] + $data + [ 'ts' ], so neither needs a new wire field.](img/dec-provenance-knobs.png)

**`trace_hooks` is the cheap one and does the real work**: `origin_frame()` takes ONE frame, who called the hook, and puts it on the entry's `l`, which is the flame's aggregation label, so [`Flame_Tree`](../includes/class-flame-tree.php) and [`Flame_Fold`](../includes/class-flame-fold.php) split `the_content ×16` into one node per caller with MEASURED durations and no new tree code. Gyrobase uses the same idiom for `include: /Macros/Global.html`. It deliberately does NOT call `wp_debug_backtrace_summary()`, which walks and formats the whole stack to produce a string all but one frame of which is discarded: measured at **12.7us against 0.9us** for `debug_backtrace( DEBUG_BACKTRACE_IGNORE_ARGS, ORIGIN_DEPTH )`. The LIMIT is the lever, not `IGNORE_ARGS`: args are refcounted, not copied, and cost 0.8us even on a multi-megabyte `the_content`; depth is what costs. At 0.9us it runs on EVERY firing (2,601 `render_block` calls cost 2.3ms), which makes the split complete rather than truncated at a budget. **What it must NOT do is synthesise ANCESTOR nodes** for the uninstrumented frames: a `wp_trim_excerpt` parent valued at the `the_content` inside it would assert a duration nobody measured, which is [decision 12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact)'s whole point. Attribution is honest; invented ancestry is not.

**`trace_callers` is the expensive one**, default 0: `caller_of()` records `wp_debug_backtrace_summary( self::class )` onto that span's OWN start entry as `caller`, not `c`, which already means COUNT throughout this schema, ignoring this class so the top frame is the caller and not the instrumentation. **The cap is what makes it affordable, and it is per KEY, not per request** — a hook name, a query's statement shape or an outbound URL, whichever the flame aggregates that span on, PAIRED with `l`, the calling frame that span is already labelled by. A hook fires, a query shape runs and an endpoint is called for the same reason: code asked. Keying the budget per request instead would spend it on the bootstrap and trace none of the 477 taxonomy reads that came later. Keying it on the hook alone has the same failure one level down: `l` is what SPLITS the flame node, so the caller that fires first takes the whole allowance and every other node reads as an unexplained repeat — which is why the number had to be large enough to cover all of them at once. Paired, 1 reaches every caller, and that is the setting to reach for. The RULE names the number: `trace_callers` IS the count of DEEP chains, and a stored `true` is a count of 1, because the pair key makes one chain per caller a chain from every caller. What a diagnostic run wants is not what steady state wants: a fixed 20 leaves 21% of one real record's time unattributed. The window is `CALLER_FRAMES`, 20 frames, because an 8-frame window stops one frame short of `rest_preload_api_request`, the frame that explains that whole request, and `Log_Manager::MAX_DATA_SIZE` is the only other bound — which a query start entry meets differently from a hook's: it carries `l` and `caller` but no `m`, so `fit_data()` has no string to trim and the entry drops straight to the floor, keeping `n`, `k`, `ts` and a 1000-byte excerpt. The span still opens, because `Flame_Tree::PATTERN_START` reads `k`. The cap exists because the same question asked of `render_block` on that record would be 2,601 backtraces. Price the whole of it before raising either number: a traced rule pays roughly 12.7us per chain, times the number of KEYS it meets — hook names plus distinct statement shapes plus distinct URLs, none of which the operator declares — and the pair key multiplies that count by the distinct CALLERS of each, which is exactly why the number comes down as the key narrows: sixty shapes at twenty is about 15ms and five hundred is 127ms, where the same sixty shapes asked from three places each at 1 is about 2ms, and a traced query also pays `without_literals()` twice, once for the budget key at the open and once for the statement `m` at the close. A cap that bound tighter used to stop tracing the shape being hunted, which is why the answer was the per-key budget and a rule the operator turns off again rather than a smaller number; narrowing the key to the pair is what makes a smaller number safe, because 1 now buys one chain from EVERY caller instead of one from the first. The budget resets on every scope change, so a worker draining a hundred jobs traces each one rather than spending the request's allowance on the first. Sixteen firings of one hook are one budget PER CALLER — three callers, three chains at 1 — so there is no named default: `true` reads as 1, and an operator who wants more writes the number. There is nothing for a named default to seed, either: the editor fills its field from the stored value or 0, and `to_array()` writes an int. `Log_Manager::message()` merges arbitrary keys into the entry (`[ 'n', 'k' ] + $data + [ 'ts' ]`), so neither knob needs a new wire field. **A field nothing renders is a field that does not exist**, so `LogEntriesTable` renders `l` and then `caller`, as "called by …", muted ahead of the entry's value. Per-rule and off by default, like decision 22 and unlike 21: a backtrace is cheap once and not cheap always.

*Alternatives rejected:* capturing unconditionally for bound hooks (a rule naming sixty hooks pays sixty times per request for an answer nobody asked); tracing only firings AFTER the first, on the reading that a repeat is the signal (the first caller is half the answer: which of the sixteen is the odd one out is exactly what you are reading for); a separate `(called by)` entry (a new keyword that `logEntryUtils` and `Reqgrep_Core` would both have to learn, to carry a field the start entry already had room for). **This decision's revisit condition is MET.** It named a THIRD per-rule diagnostic knob as the trigger, on the reading that two booleans is a pair and three is a flags map. `Rule` carries five, `log_queries`, `log_http`, `log_plugin_loads`, `trace_hooks` and `trace_callers`, and they are still five separate constructor properties. A flags map would buy one property and cost every reader a lookup and every knob its type — `trace_callers` is an int, not a boolean — so the count alone is not the trigger it was taken for.

## Decision 24: A duration nobody measured is not a timing sample

[`Flame_Builder_Node::accumulate_all_stats()`](../includes/class-flame-builder-node.php) runs two independent gates, `$count_global` ([decision 15](#decision-15-the-urls-verb-owns-every-url-set-fact-overview-owns-the-site)) and `$record_timing`, and conflating them is the classic bug in that class. `$count_global` is "not a worker": it keeps worker traffic out of every site-wide aggregate. `$record_timing` is true only when `duration_ms` is positive AND `error_status` is neither `T` nor `A`. Both statuses mark a duration that measures elapsed time to an interruption rather than what the request cost: `Request_Builder_Node::evict_request()` stamps `T` and `now - start` on a trace the LRU evicted mid-request, and `Log_Manager` stamps `A` when a cooperative stop lands inside `finish()` or when `end_job_context()` is told the job never finished. Summing either skews `sum_ms`, `max_ms`, `min_ms` and every mean drawn from them.

![The two gates every completed request passes in accumulate_all_stats(). Gate 1, $count_global, is simply not a worker: it keeps worker traffic out of every site-wide aggregate while the per-URL row keeps worker timing on rows of its own. Gate 2, $record_timing, requires duration_ms above zero and an error_status that is neither T, which Request_Builder_Node::evict_request() stamps with now minus start on a trace the LRU evicted, nor A, which Log_Manager stamps when a cooperative stop lands inside finish() or end_job_context() hears the job never finished. A table shows what every request adds and what only a timed request adds: on the per-URL row, ROW_COUNT and its count_Nxx bucket, ROW_SUM_PEAK_MB, ROW_MAX_PEAK_MB, ROW_LAST_SEEN and ROW_WORKER always, and ROW_TIMED_COUNT, ROW_SUM_MS, ROW_MIN_MS and ROW_MAX_MS only when timed; on the per-URL flame aggregate, count always and sum_value with the children merge only when timed; on every dimensional slot, c always and s only when timed; in hourly, non-worker only, sum_peak_mb from every request and count and sum_ms only when timed; and the profiles, both leaderboards, the three category series and auto-tune, skipped whole. So count and timed_count diverge for a reason that has nothing to do with workers: mean_ms divides sum_ms by timed_count while avg_peak_mb divides by count, and overview's global_avg_peak_mb divides across a wider set than its divisor.](img/dec-timing-gate.png)

A request failing the timing gate still COUNTS: it increments `ROW_COUNT` and its `count_Nxx` bucket, `ROW_SUM_PEAK_MB`, `ROW_MAX_PEAK_MB`, `ROW_LAST_SEEN` and `ROW_WORKER` on the per-URL row, the `DIM_COUNT` of every dimensional slot with `DIM_SUM_MS` left at zero, and `count` on the per-URL flame aggregate. It contributes nothing to `ROW_TIMED_COUNT`, `ROW_SUM_MS`, `ROW_MIN_MS`, `ROW_MAX_MS`, the aggregate's `sum_value` and children merge, the dimensional `DIM_SUM_MS`, or `hourly`'s `count` and `sum_ms`; and `accumulate_profiles()` is skipped whole, so both leaderboards, the three category series and auto-tune never see it. **So `count` and `timed_count` diverge for a reason that has nothing to do with workers**, since the row records worker traffic separately in `ROW_WORKER`, which is why `Performance_CI_Node::mean_ms()` divides `sum_ms` by `timed_count` while `avg_peak_mb` divides by `count`. `hourly` does not keep those two populations apart: its `sum_peak_mb` accumulates from every non-worker request while its `count` takes only the timed ones, so `overview`'s `global_avg_peak_mb` divides across a wider set than its divisor. **Revisit if** an evicted or aborted request ever carries a duration someone measured, which would make it a sample like any other.

## Decision 25: Read tools and TUNE-scoped write tools share one MCP session, and every tool result is fenced

Every read tool returns recorded site traffic, and a visitor writes part of it. `dump_request` carries the `environment_v3` entry, whose `m` map is the curated `$_SERVER` block: `HTTP_USER_AGENT`, `HTTP_REFERER` and `HTTP_X_FORWARDED_FOR` are the visitor's own prose, capped at 256 bytes and stripped of control characters but otherwise verbatim. Serialized into a tool result with no delimiter, that prose reaches an agent's context indistinguishable from the server's own answer — and the same session may hold `rules_upsert` and `rules_delete`, so the agent it is talking to can edit the logging ruleset. What forced the decision is that pairing: recorded visitor text arriving unmarked beside a write tool.

One marking serves both exits, named once. A value recorded from site traffic leaves inside `<site-data>…</site-data>`, and the reader is told in standing text that whatever sits inside that tag is recorded data and never an instruction. `MCP_Controller::fence()` encodes every reply with `wp_json_encode( $reply, JSON_HEX_TAG | JSON_UNESCAPED_SLASHES )` and wraps the result, so a string reply encodes as a JSON string and the reader needs no second rule for it. `JSON_HEX_TAG` is what makes the fence unbreakable from inside: every `<` and `>` in the payload becomes `\u003C` or `\u003E`, so no visitor string can carry a literal `</site-data>` and close the tag early. The `initialize` reply's `instructions` field carries the standing text alongside the measurement caveat. An `isError` result is left alone, because that text is the site's own message rather than anything a visitor wrote. The browser's own exit, `src/overview/askBrief.js`, applies the same marking to the values a log record wrote — the subject URL and an entry's message — escaping `<` as `\u003C`, the spelling the MCP fence produces, collapsing control characters to one space and capping at 512 characters with a trailing `…`; both prompts it builds carry the same sentence. Rule ids, rule patterns, span names, hashes, rids and numbers stay bare, because the operator or the server wrote those. `Ask_Assembler::entry_shape()` ships the `environment_v3` entry with no body at all: its map is the visitor's headers and the peer, and the brief's `env` field already carries the allowlisted facts, so a second list over the map would only drift from the writer's.

Two alternatives were weighed and rejected. The first was a separate write-only session, so that no session holding a read tool could also edit the ruleset. That does not remove the injection, it only moves it: an agent holding both sessions reads the same recorded data out of one and writes through the other, and the operator now maintains two credentials for a boundary the agent crosses in a single turn. The second was dropping the write tools entirely. That would cost the surface its point — the ruleset is exactly what an agent investigating a slow URL needs to widen — for a defence the fence already provides more cheaply. The scope is subtractive and bounded by the minting user, so a `read` session offers no write tool at all and a `tune` session minted by someone who holds nothing does nothing; the operator chooses `tune` at mint time knowing the agent can then edit the logging ruleset and nothing beyond it, since the vault and the fleet are substrate `manage` and unreachable here. The fence plus the `initialize` instructions are the defence, and the blast radius stays recoverable: the ruleset is re-seeded from the config file and the schema through `Rule_Set::seed_from_config()`.

The cost is real. Every tool result is JSON, so an agent client that parsed a string reply as text has to strip the fence and decode; the hex-escaped angle brackets make a raw result harder for a human to read in a transcript; and the wrapper adds bytes to every reply. The marking is also advisory — it tells a reader what the bytes are, and a model that ignores standing instructions is not stopped by a tag. **Revisit if** MCP gains a transport-level way to label untrusted content, or a write tool appears whose blast radius is not recoverable from the config file, at which point the write half needs its own session after all.

## Decision 26: A merged transport node keeps the statements it ran

The fold replaces a request's entries with one node per path, and the statements go with them. A real `/wp-admin/post.php` record says `sql: WP_Query->get_posts` ran 667 times for 58.3s, and cannot say what any one of them was — the question a repeat that size raises. [Decision 22](#decision-22-query-spans-are-the-same-pair-as-decision-20-but-per-rule) argues the other way in as many words, that naming the TABLE "says `SELECT wp_posts` ran 156 times and never which code ran it, and which code ran it is the only version of the question worth asking." That holds for the SPAN'S NAME, and it still does: `l` is the caller, `Flame_Tree::node_name()` merges on it, and this decision does not touch it. What it revises is the unstated second half — that the statement is therefore worth nothing — which is true only while the entries survive to carry it. In a folded record they do not, and the caller alone cannot separate one query repeated 667 times from thirty different ones.

So a merged node whose span is one of the logger's own round trips — `Flame_Tree::is_transport_span()`, the `sql` and `http` states — carries `shapes`: the distinct statements or URLs it ran, each with a call count and summed milliseconds. **Only those two**, because their message is a bounded identifier by construction: `without_literals()` collapses `IN (?,?,?)` to `IN (?)` and every literal to `?`, and a redacted URL is one line. A hook's message is prose of any size and any cardinality, so it gets no table. **The identifier is the FIRST non-empty `m` of the pair**, because which half carries it is the producer's business and they disagree: `http_start` writes the URL and its complete the status code, `query_end` writes the statement and its start nothing. Reading the close alone builds a table of `200`s — and an `http` complete never stands in for a start a checkpoint lost, for the same reason.

Three bounds, and the third is the one that matters. A shape is cut to `MAX_SHAPE_BYTES` (512), measured against 308,395 real `sql` completes here — mean 146 bytes, median 122, p99 488 — so it truncates 0.6% of statements. A node keeps `MAX_SHAPES` (24) rows, one slot of which is reserved for the `…` bucket everything else folds into; one record in 184 had a node exceed it. A full table EVICTS its cheapest row rather than refusing the newcomer, because the statement worth naming is as likely to arrive twenty-fifth as first and first-seen-wins would bury it on exactly the record this exists for. **And the record itself is bounded, at `MAX_RECORD_SHAPE_BYTES` (32KB of new shapes), because the per-node caps bound a NODE and a record's node count is `O(distinct paths)` by design**: the heaviest real folded record here carries 117 transport nodes against 73KB of record, so per-node caps alone admit megabytes. The POOL sizes that number rather than the record: `Request_Builder_Node` holds 300 requests in flight against an entry budget worth ~18MB, so 32KB apiece keeps the worst case near half of it, and that heaviest record — whose own statements cost 33.7KB — is the one shape that spends its budget and buckets the tail. **The budget charges what the table GREW by**, never what a statement the bucket swallowed would have cost: charging the attempt let one high-cardinality caller spend 65,603 bytes to store 9,206 and strip every other node's table, measured at 7.1×. It charges a ROW's cost too, `SHAPE_ROW_BYTES` beside the key's own length, because a byte budget alone bounds bytes and not rows: at eight-byte shapes, which `without_literals()` readily produces, the rows cost twelve times what the budget thought it had allowed. A spent budget refuses a new row the table has ROOM for, and nothing else: a statement the node already keeps costs no bytes to count, and a full table's eviction trades one row for another and pays only the difference, which it may do while spent so long as the new key is no longer than the one it replaces — refusing every trade would bucket the worst statement on the one record shape that ever spends its budget, and admitting a growing one carried a record to 3.2× the budget, one filled table at a time. A folded envelope is also invisible to `Request_Builder_Node`'s pressure loop, which counts `entries` and skips a folded one, so nothing downstream would catch the growth.

The statement is recorded data, so it leaves through [decision 25](#decision-25-read-tools-and-tune-scoped-write-tools-share-one-mcp-session-and-every-tool-result-is-fenced)'s marking like any other: `askBrief.js` gives it a fenced line of its own rather than a slot in the `numbers:` list, which a reader splits on spaces and a statement carries plenty of.

`shape_ms` is a MEASURED sum, unlike the node's `value`, which [decision 12](#decision-12-a-stat-times-the-request-a-flame-value-is-a-rendering-artifact) calls a rendering artifact that every producer raises to cover its children. Nothing raises `shape_ms`, and nothing may: it is the time those statements took. The pair is positional per [decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants), under that decision's `LB_ENTRY_SUMS` exemption — a closed 2-tuple read by `Findings::worst_shape()`, `merge_shapes()` and one React function.

**An unfolded record gets the same table, derived rather than stored.** Its entries survive, so the log table shows every statement — but a brief ships sixty entries, so for any reader but the detail view the finding is the only place the answer can land. `Findings` folds the record's entries transiently through `Flame_Fold` and reads each node's table by its name path, which runs the one set of rules rather than a second, and adds nothing to the stored flame. That fold passes no record budget: the budget exists for a pool of in-flight envelopes, and a fold built, read and dropped holds nothing against it — keeping it would bucket a slow statement that first appears late and name a cheaper one.

*Alternatives rejected:* keeping ONE representative statement, the slowest instance's (costs no table, and answers "was it one query or thirty?" with a guess); a digest at the producer, in `App\Core::query_end` (the producer cannot know the record will fold, and a per-request digest would ride the firehose against `MAX_DATA_SIZE` on every request that never folds); the table on the per-URL aggregate (cardinality across thousands of requests is unbounded, and the aggregate's numbers are per-request means, which a summed pair is not — `merge_flame_children_incremental()` rebuilds each node from four keys, so it cannot leak there by accident). **Revisit if** a THIRD span kind earns a table, which would make "is it transport?" the wrong question and a producer-set marker on the entry the right one — `Log_Manager::message()` already merges arbitrary keys, and `Request_Builder_Node` already allowlists such fields beside `keep`. The sibling producers are the reason it would come up: pyrobase's `customquery_sql` and gyrobase's `query_sql`, `search_query` and `<tag> (sql)` spans all carry an already-shaped statement, and none of them is named `sql`.

## Decision 27: The platform's requests to itself are worker traffic, named by path

The cron loopback and the substrate's own endpoints — `/wp-json/newspack-nodes/v1/{command,log/stream,messages/stream,workers/spawn}` — are requests the platform makes to itself, and until 0.101.0 the shipped seed skipped every one, so the logger never logged the logger. A skip loses the record: a `command` poll that took nine seconds, or a spawn that fataled, left nothing to read. So the seed is the `/` log rule alone, and [`Log_Manager::PLATFORM_WORKERS`](../includes/class-log-manager.php) names each of those requests a worker by its path — `cron`, `command`, `stream`, `spawn` — as the `worker_type` entry `log_worker()` writes right after `process (start)`. The substrate's own processes name themselves through `NEWSPACK_NODES_WORKER_TYPE`, and that wins where it is set; the path answers where it is not, which for the spawn endpoint is always, since the substrate sets the var at REST dispatch, after the request was opened. A worker's record keeps every entry, sits on the worker shard's URL rows, and stays out of the global sums at [decision 24](#decision-24-a-duration-nobody-measured-is-not-a-timing-sample)'s `$count_global` gate.

**The five paths are a copy the substrate does not know it owns.** `Http_In_Node`, `SSE_Out_Node`, `Log_Stream_Out_Node` and `Spawn_Controller` declare those routes in newspack-nodes; this plugin spells them again as literals, root-relative and `wp-json`-prefixed, as the seed's skips did before it. The failure on drift is chosen with open eyes: a route the substrate moves, a subdirectory install or a site rewriting its REST base yields a request `platform_worker_type()` does not name, and it lands on the global rows as visitor traffic. That is a misclassification the overview would show, where the skip list's failure was a record that never existed. The map is not derived from `rest_url()` or `site_url()` because the seed never was, and because a copy that nothing checks costs one line per route where a derivation costs a `get_option()` per request.

*Alternatives rejected:* keeping the seed's skips (loses the record, and every stored ruleset already carries whatever skips its operator kept); the substrate stamping its own endpoints (its env var is set at dispatch, after `process (start)`, so the stamp would arrive too late for the entry that names the worker); a `Rule` property marking a rule's matches as worker traffic (a sixth knob, its serialization and its editor control, to say what five literal paths say). **Revisit when** the substrate publishes its route paths as a constant or filter this plugin can read, at which point the copy becomes a read, or when a platform request is seen in the overview's global totals, which is the symptom this decision accepts.

## Decision 28: The writer ranks each bucket and indexes each name, and the page reads those rather than the index

Folding the whole URL index answers every question about the URL set, and costs the whole index: sixteen shards across every flame-builder partition's store over the whole read plan, 18,432 keys and 54MB on a hub holding 689,800 distinct URLs in its window, decoded and merged by hash. That fold measures 29 to 38 seconds on such a hub, and the overview polls it once per tab; [decision 14](#decision-14-a-server-scope-the-key-cannot-carry-rides-inside-the-value-and-is-applied-as-a-projection) forbids memoizing the merged index because nothing bounds its row count. What the dashboard asks for is a page: the top hundred rows by one sort key, `URLS_PER_PAGE`, or the rows whose name carries a word. So the WRITER answers both questions while it already holds the data, and the reader reads its answers.

`Flame_Builder_Node` writes one ranked list per `Stats_Store::URL_SORTS` key and `URL_ORDERS` direction — fourteen site-wide a bucket, and fourteen more for each server a row's split names — as `urlrank`, `urlrank_h`, `urlrank_s` and `urlrank_sh` (schema in [decision 1](#decision-1-namespaced-memcache-schema)'s table). An entry is positional ([decision 18](#decision-18-a-stored-value-may-be-positional-and-then-its-indexes-are-named-constants)): the hash, the row's thirteen scalars, and on the `url` lists the path. `ROW_SRV` is never in one, because the split is the field that grows with the fleet and a server-scoped list has already projected it — through `Stats_Store::url_row_scoped()`, the writer's twin of the reader's `swap_url_server_sums()`, so the two cannot disagree about a scoped row. The union of the per-shard top-N is exactly the bucket's top-N, because every URL lives in one shard, so one ranking over the merged shards is enough.

**A bucket is ranked over its whole STORED content, not over the flush.** Each row intent collects what its write produced through the intent's `landed` closure, and `rank_flushed_buckets()` reads back — in ONE multi-get per chunk of buckets — only the reader-family shards this flush did not land. A chunk is as many ranking groups as one write chunk holds, `WRITE_BATCH_KEYS` over 32, so a ranking holds no more rows than the flush chunk that fed it. Ranking the flush's own rows instead would rank one worker's slice of five minutes and call it the bucket. The ranking runs per `flush_writes()` chunk rather than after the flush, so a replay spanning the window holds a chunk's buckets rather than the window's; worker-family shards never enter the collector, because no worker row ranks. A bucket's reader-family row and name writes form one ranking GROUP — at most 32 keys — and `flush_writes()` chunks by `WRITE_BATCH_KEYS` without splitting one, so a bucket is ranked once, from every shard that landed, rather than off whichever half of it the first chunk carried. `Stats_Store::ranked_writes()` is the one entry to ranking and answers with every scope's lists at once — the site, then each server a row's split names, the split expanded once per row — because a caller left to enumerate the scopes itself is a caller that can rank the site and forget the servers; `write_url_ranks()` chunks those writes the way the flush does.

**A bucket's lists are rewritten at most once a minute.** The page cache holds a ranked page for `Stats_Store::URL_PAGE_REFRESH_S` (60 seconds) and the dashboard polls against that, so ranking every five-second flush spends twelve rankings on one read. The reader's TTL and the writer's cadence are ONE constant, on the store both read, because they are one number. Under traffic a ranked row lags live traffic by up to twice it plus `Flame_Builder_Node::FLUSH_INTERVAL_SEC`, because a ranking waits for the flush it runs in. The flame builder has no timer and flushes only from `fill()`, so on a partition that goes quiet a deferred or closed-bucket ranking waits for the partition's next record or the worker's stop, whose `shutdown_sweep()` ranks every bucket owed and comes within the worker's `max_runtime`; a stale hour waits for the next flush with room under its bound, or the next worker's probe. Two constants that happened to be equal would drift the first time either moved, and nothing would fail. A bucket that has CLOSED since it was last ranked is ranked whatever the cadence says, because nothing will come back for it. A bucket the cadence defers drops its collected rows and is remembered as PENDING instead; `rank_owed()` runs at the end of every flush and ranks each one that has come due, in those same chunks, gap-filling all sixteen reader shards from the store, which is the whole content it ranks anyway; every due bucket ranks in that flush, and only the batch is bounded. Every ranking ends its owing whether its lists landed or were refused: a bucket is stamped and leaves the pending memo, and an hour leaves the stale set. `rank_due()` tests buckets alone; a stale hour has no cadence and ranks at the next flush with room under its bound. **Nothing retries a refused cache write** *(Chris, 2026-09-22)*: the refusal is logged through the rate-limited `print_less_often()`, counted as attempted, and left. A cache item over the size limit never fits, so a retry buys nothing; the lists are top-N bounded to fit, so a refused list is a wrong N, which the `URL rank write refused` line names; and a transient memcache failure heals at the ranking the next write into that key brings. The same rule covers the fold, whose refused row, name or list write is logged and not retried by the flush — an hour missing a key is re-derived at the next reprobe like an evicted one: every `REPROBE_EVERY_FLUSHES` (60) flushes `roll_up_hours()` empties its memo, and the probe re-folds any hour whose row shard, name shard or leaderboard hour is missing, whatever removed it, reading the fine buckets back from the mirror — and the token index, whose refused write is logged and leaves its URLs unfiled until the name refresh files them again. The shutdown sweep's flush ranks every bucket still owed whatever its stamp, because the pending memo lives in memory alone and dies with the worker. It ranks no more stale hours than any flush does: every stale hour is one the probe found folded with no marker, and the store still holds it that way, so the next worker's probe finds it again. The pending memo is what reaches a bucket nothing writes into again — the closed-bucket clause fires on a WRITE, and a bucket whose last writes landed inside the cadence gets none once it closes, so its final rows would otherwise never reach its lists. Both memos are pruned below the oldest bucket of the read plan's fine tail, and a flushed bucket below it is not offered to the ranker at all; `flush()` builds that plan once and hands it to the roll-up and the ranker; the stale set is pruned to the read plan's hours in `roll_up_hours()`, because no reader plans an hour the window has passed. One flush ranks at most `ROLLUP_HOURS_PER_FLUSH` stale hours, the same bound as the folds, since a stale ranking holds an hour's coarse rows as a fold does; a stale hour the probe finds spends none of the fold budget, because ranking it is not a fold. `set_stats_store()` empties every memo outright, since every bucket they name belongs to the old store's keyspace. On the HOUR tier a separate DONE marker, `urlrank_h:done:{hour}`, rides the ranking's own batch whatever its lists answer, and that one key is what `url_hours_derived()` probes: it says the ranking ran, not that every list stands. The reader asks no more of it than that, because `ranked_page()` serves an hour ranked only where the list for the scope it pages is present, and folds the page otherwise. Its value is empty, because the PRESENCE is the whole fact.

**The marker answers neither a refused list nor an evicted one** *(Chris, 2026-09-22)*. A refused list is never retried, and while a list and the marker share their tier's TTL, memcached evicts by SLAB CLASS, and a 60KB list and a one-key marker are not in the same class: the list goes first. So an hour can read as ranked with a list missing, and `ranked_page()` then folds for the rest of that hour's stay in the window, because nothing re-probes a marker that is still there. **Revisit when** a hub's ranked pages fold persistently while `url_hours_derived()` reports every hour ranked — that pairing IS this asymmetry, and the answer is a probe that reads a list rather than a second marker.

`roll_up_hours()` reads that probe and branches three ways. An hour folded AND ranked is memoized and skipped. An hour folded but not ranked — one folded by a release before the rank tier existed, one whose marker was evicted or itself refused, or one a late write landed in — joins the stale hours and is ranked from its STORED coarse rows and names by `rank_hours_from_store()`, never folded again: its fine buckets may be gone, and a second fold would overwrite the hour with nothing. An hour that is neither is folded and ranked in one pass while the flush's fold budget lasts, and past it waits for the next flush; the probe still memoizes every folded hour behind it. A write into a folded hour ([decision 19](#decision-19-a-request-is-filed-in-the-bucket-it-finished-in-and-a-write-into-a-folded-hour-reaches-its-fine-bucket-and-the-hour-key)) goes to its fine bucket and, while the hour key exists, into that key, and an hour-key write that lands forgets the hour's marker, so the probe finds it stale and a flush re-ranks it from the store within the per-flush bound. With the key missing, or a failed batch read reporting it missing, the key is forgotten, only the fine write lands, and the reprobe's re-fold picks it up. Same-key intents compose in `add_intent()`, as the flush BUILDS its intents: they are filed by cache key, and each merge receives what the one before it produced, so two fine buckets of one folded hour both reach the hour key rather than the second discarding the first. One key is therefore one intent for the whole flush, which is also why no key can straddle two chunks.

**A list ranks by the BUCKET's own value, and the two averages are means of bucket averages.** `url_rank_value()` ranks `avg_ms` on `sum_ms / timed_count` and `avg_peak_mb` on `sum_peak_mb / count` over that bucket's row, so a page hit rarely but slowly ranks on how slow it is; ranking by the window's totals would hide it behind every busy page *(Chris, 2026-09-22)*. `ranked_page()` then presents the mean of the per-bucket averages the URL ranked with, each at its own tier — a five-minute bucket inside the fine tail, a folded hour behind it — every stored bucket weighing the same, so an hour entry contributes one average covering an hour where a fine entry contributes one per five minutes, and nothing reweights them. That is a different number from the fold's request-weighted mean over the window, so the reply carries `ranked` and the page says so. Every other field folds through `fold_index_row()`, exactly as the fold merges it.

**The reader pages from the lists only when they can answer the whole question.** `ranked_serves()` requires no `search`, no `errors_only`, no `include_workers` and an `offset + limit` inside `URL_RANK_N`; anything else folds. Both tiers are known before the first read, so `ranked_page()` asks each store for every planned hour AND every fine bucket in ONE round trip, and reads a second time only for the `buckets` half of `Stats_Store::fine_fallback()` — where an hour's list is missing, only the LEADING hour falls back to its twelve buckets' fine lists, as the row fold does for `urls_h`. Its other half is the `holes`, and this is the one reader that refuses them: a planned hour behind the grace hour that ANY store holds no list for takes the whole page back to the fold, because those hours have no fine buckets left to read and serving a window an hour short as ranked is worse than folding: the minute after a deploy while the heal runs, or one evicted list key, means folds until the reprobe re-ranks the hour. The header is the fold's — `totals.urls` is the count of DISTINCT URLs in the window, which no list can answer and no per-bucket count sums to — and `url_header()` holds it under the scope, the window bucket, the retention and the store count for `BUCKET_SECONDS`, so the thirty-second fold runs once per five minutes while the lists answer the table every poll.

**The header's own miss folds the page the poll answers with.** `ranked_page()` asks for the header BEFORE it reads a list, and a miss folds this page — the caller's sort, order, offset and limit — and returns it whole rather than throwing away a `0, 0` fold and then reading the lists as well. So the poll that pays for the walk answers with what it walked, `ranked: false`, and the next poll inside the bucket reads the lists. Both entries are read THROUGH `Table_Node::backed_by()`, the substrate's own read-through, rather than a lookup-build-store wrapper of the reader's; a build the mirror read budget cut short states `ttl => 0`, which serves it without warming the cache. The page SHAPE rides in the key as an md5 of its field list, because a read-through cannot report a stored value missing a field this reader needs. The reply also carries `as_of`, the page's build time, cached with it, which the dashboard measures each row's `Last seen` age from.

**A search reads a token index, so it names its candidates instead of reading every name.** `urltoken:{token}` maps each hash whose path carries a token to the unix seconds that URL was last named, filed under every prefix of the token from `URL_TOKEN_PREFIX_MIN` (3) characters to `URL_TOKEN_PREFIX_MAX` (12), the path lowercased and split on every non-alphanumeric run. The writes ride the flush's own read-merge-write batch, for the names `persist_url_names()` wrote — a token's set must UNION with what earlier flushes filed, which a bare store cannot do — so a URL costs `sum( min( word, 12 ) - 2 )` keys over its words of three characters or more, six for `/wombat-7731`, once per URL per half retention window. A refused write is logged, and its URLs stay unfiled until the name refresh files them again.

**The stamp is what lets a set SHRINK, and the walk is decided before it runs.** `merge_token_set()` restamps this flush's hashes and saturates when the count passes `URL_SEARCH_MAX` (5,000); before it counts, it drops every entry a retention window has passed over — so a hash leaves a set when its URL stops being named rather than when the key dies, a dead hash is never named to a reader that would count it against the cap, and a common prefix that once passed the max does not stay saturated while anything keeps rewriting it. What the cap bounds is the WALK, not the shrinking: one pass over the stamps, stopping at the first expired one, says whether the prune has anything to do, and a flush that would pass the cap prunes without making that pass. A set of four re-read entry by entry on every flush of every token of every URL is the cost that buys off. The `TOKEN_SATURATED` sentinel is an entry like any other, under its own stamp, and a live one is returned UNCHANGED: `flush_writes()` skips a write whose merged value equals what it read, so the key keeps the TTL it had, expires after a retention window and rebuilds live-only. `url_token_sets()` hands a reader the KEYS; the stamps are the writer's alone.

**An identical write is not a write, in every namespace.** `flush_writes()` compares each composed value with the one it read and drops the write where they are equal, so the key keeps the TTL it had. [Decision 1](#decision-1-namespaced-memcache-schema) makes a key's TTL the retention mechanism, and this is what keeps that honest: a write refreshes a lifetime only where something was ADDED. For a bucketed namespace it never binds — a bucket has an intent only when the accumulator holds rows for it, and rows always add — so the one place it decides anything is `urltoken`, which is not bucketed, and where a saturated sentinel returned unchanged rests on exactly this: the key expires after a retention window and the token rebuilds live-only. A namespace wanting a touch to mean "still current" has to add something the merge can see.

`search_candidates()` intersects the term's tokens across every store, smallest set first, skipping any token the store could not answer, and returns null — the fold — for a term with no token, for one whose EVERY token the store refused, and for a set over the max. One unanswerable token among several narrows nothing and costs nothing: the others still name the candidates, and the fold matches the whole term against their names anyway, so a term carrying one two-character word no longer folds the site. WHICH tokens can be answered is the schema's: `url_token_sets()` returns `false` for a token below `URL_TOKEN_PREFIX_MIN`, which it refuses without a read, and for one whose set has saturated, so no reader tests for the sentinel. A token nobody holds is a real answer, an empty set, and folds nothing: it walks no shard and answers zero totals, where `totals: null` would claim the index predates splits.

The fold that follows is bounded to the shards the candidates fall in, with names from `urlmap` over that set rather than every shard's whole `urlnames` blob, and it applies the name check only to a candidate `urlmap` still names — the index already answered for that hash, so an expired or refused name drops nothing. `term_matches()` matches each token at a WORD boundary there, as the index files them; only a term that tokenizes to nothing is a substring match. Two readers share one spelling apiece: `Stats_Store::path_of()`, beside `join_url()`, is the one place a reader takes the path out of a name pair, and `Stats_Store::token_sets_of()` is the one tokenize-and-group, used by the writer and by the test helper alike.

**This changes what a search matches: a word or a word prefix, not any substring** *(Chris, 2026-09-22)*. `/wombat-7731` is found by `wom`, by `wombat` and by `7731`; `mbat` finds nothing, because the index files prefixes and not infixes and the fold behind it matches at the same word boundary. The search box's placeholder says so, and a term the index cannot serve degrades to the fold's cost rather than to a refusal. **The server scope rides in the KEY for the ranked lists** *(Chris, 2026-09-22)*: what decision 14 rejected it for was O(servers) × the per-shard cap in a namespace mirrored whole, and a list is `URL_RANK_N` entries per server in a tier the mirror skips. A stored `url` is absolute, so a hash belongs to one site and appears in one or two servers' lists — the per-server lists together hold about as many rows as the site-wide ones, not servers times as many — and the server axis already carries `MAX_SERVER_VALUES` (128) from the split's own fold. **`URL_RANK_N` is 200 on the fine tier and `URL_RANK_N_HOUR` 500 on the hour tier** *(Chris, 2026-09-22)*, one list being one memcache item and 500 positional rows under 60KB; a page deeper than 200 folds. **And a `count`-ranked page may be approximate** *(Chris, 2026-09-22)*: the union of per-bucket top-Ns is a superset of the window's top-N only for `min_ms`, `max_ms` and `last_updated`, which merge by extreme, while for a sum a URL just outside every bucket's list can still be top overall and one inside some lists ranks on those buckets alone. The error shrinks with N and with the hour tier, where one list ranks twelve buckets' folded rows, and `search` keeps the exact fold behind it.

*What it costs:* fourteen site-wide list writes a bucket a partition a flush, each a sort of at most 32,000 rows by one key, plus the per-server lists, which together hold about as many rows again; `sum( min( word, 12 ) - 2 )` token keys per URL named, six for `/wombat-7731` and nine for `/blog/2026/my-post-title`, once per URL per half-window; and a ranked page reading 37 keys per partition of at most 500 entries, about 3MB against the fold's 54. All of it in the worker, none of it in the request.

*Alternatives rejected:* window totals maintained incrementally by the writer — exact, but the window slides a bucket at a time, so the writer must subtract each bucket as it leaves, and the totals for 690,000 URLs are the merged index again, over the item limit per shard and a fold per flush to rank; a whole-index memo ([decision 14](#decision-14-a-server-scope-the-key-cannot-carry-rides-inside-the-value-and-is-applied-as-a-projection)); per-server stored rows (`urls_s`, the same decision), where decision 14's rejection stands: `urls` gained no mirror bound, and what makes the key form affordable HERE is that a list is `URL_RANK_N` entries and all four rank tiers are derived, so the mirror holds none of them; and a bare `store_multi()` for the token sets, which would overwrite each token's set with the flush that touched it last. **Revisit when** the hour tier's N misses pages a bucket-weighted average should show, which is the number to raise first; when the refused-write log names a rank list, since a list over the item limit is entries times row width and the answer is a smaller N; when a saturated token is the only token an operator can type, which sends every such search to the fold and is the signal `URL_SEARCH_MAX` is sized wrong for that URL space; or when the substrate can tell a failed batch read from an all-miss. `Cache_Backend::read_multi()` returns `[]` for both, so a flush that suffers one merges every key of that chunk onto `[]` — widest for a token set, which is the one value built by union rather than overwritten — and the fix belongs to the substrate, not to a guess here.

## Decision 29: Every reader dates from the tick, and a reply reads it once

Every stats reader dates from `Core::$now`, never from a wall read of its own. That tick is not still: `Core::right_now()` writes it, so every caller re-pins it, in a worker and in a request alike. Two examples from this plugin, not a list: the firehose logger re-pins it once per line `Log_Manager::message()` writes, and a partition write lock taken inside a flush re-pins it as it is acquired. Loading the substrate's `Core` class pins it first, through `Core::reset()`, so a verb has a tick before it runs. A reader wanting one instant reads it once and passes it down, and a test pins `Core::$now` directly. The flame builder reads it once per flush, in `flush()`, and hands it to the mirror stamp, the hour plan, the name memo, the due test, the ranking stamp and the prune floor, with no seam of its own; `save_state()` reads it once for `mirror_url_stats()`, `flush_stats_mirror()` and `checkpoint_mirror()`. `shutdown_sweep()` reads none: its flush reads the tick, and the stale hours it ranks after that flush need no instant.

**So a reply reads that clock ONCE, at its entry, and passes it down.** Any `right_now()` caller can advance the tick while a long reply runs, the firehose logger once per line, and a fold over a hub's index runs tens of seconds. Each `Performance_CI_Node` verb reads `self::now()` in its handler and hands the instant to every reader of the window beneath it — `read_window()`, `recent_buckets()`, `scan_floor()`, the page cache key, the header key, the `$load_index` seam and `as_of` — so one reply is one window: a page keyed under one bucket cannot be built from the next, and two panels of one overview cannot answer for different windows. Two readers are the exception and read the tick themselves: `Stats_Store::absence_holds()` and the flame builder's mirror read-back, because the substrate's `Table_Node` calls them through `backed_by()` (`newspack-nodes/includes/class-table-node.php`), whose closures are `\Closure(string): int` and `\Closure(array): ?array` with no instant in either, and the table holding them is built once and serves every reply after it. `read_window()`'s memo stays, keyed on the bucket and the retention, because it saves the `gmdate()` per key; it is not what holds a reply together.

*What it costs:* a `$now` parameter on twenty-four private `Performance_CI_Node` signatures and on the two public loaders, `load_row()` and `load_index_default()`, plus the `$load_index` seam's signature, which a test replacing the seam must match; and an `int $now` on `flush()`'s callees in the flame builder — `mirror_url_stats()`, `roll_up_hours()`, `persist_aggregate_stats()`, `persist_url_names()`, `rank_flushed_buckets()`, `rank_owed()`, `rank_buckets()`, `rank_bucket_chunk()` and `rank_due()` — which take the flush's one read.

*Alternatives rejected:* a fresh wall read per reader (`\time()` or `Core::right_now()`), which puts the flame builder's ranking and its prune on either side of a second and lets a reply's panels straddle a bucket — `right_now()` also WRITES the tick, so a reader calling it moves the clock its own reply is dated from; a stamp pinned in `dispatch()` for the readers to consult, because a static stamp is a second clock with a lifetime of its own, which every caller and every test must remember to set, where a parameter makes the instant explicit at each call; and changing `Log_Manager::message()` to stop re-pinning, which leaves request scope with a tick frozen at class load and starves the debounce that reads it. **Revisit if** the substrate's tick ever holds still between drains, with no `right_now()` caller outside the drain in either scope, at which point `Core::$now` is itself one window and the parameter can go; or if a reply ever needs two instants on purpose, which would be a second parameter named for what it measures, never a second read.
