# AGENTS.md — Newspack Event Logger Nodes

The application layer of the event logger, built on `newspack-nodes` (the runtime substrate). High-throughput request-lifecycle logging, flame-graph generation and hub/spoke aggregation all run as Nodes, and the dashboards stream live over the substrate's SSE endpoints, whose server side this plugin does not own.

This plugin owns `Log_Manager`, `Request_Builder_Node`, `Request_Flight_Node`, `Flame_Builder_Node`, `Auto_Tuner_Node`, `Job_Router_Node`, `Remote_Job_Rewrite_Node`, `Discovery_Collector_Node`, `Stats_Store`, the per-URL logging ruleset (`Rule` / `Rule_Set` / `Rule_Matcher`), the `App\*_CI_Node` service CIs (`performance`, `discovery`, `rules`), the React dashboards and the topology files. Node subclasses carry a `_Node` suffix; helpers like `Log_Manager` and `Stats_Store` don't.

Three things live in the substrate and have no alias here — call the substrate class directly:

- **Hub fan-in** is `\Newspack_Nodes\Remote_Source_Node`; this plugin declares no fan-in node of its own.
- **`Job_Worker_Node`**. This plugin keeps only the request-context glue, `Log_Manager::begin/end_job_context`, hooked onto `newspack_nodes/job_worker/{before,after}_job`.
- **`Job_Intake`**, the large-write ingress, is `\Newspack_Nodes\Job_Intake`; no `class_alias` answers to `Newspack_Event_Logger_Nodes\Job_Intake`. `job-router.tsl` and `job-feed.tsl` each `include job-intake` and add their own router leg; the substrate's stock `job-intake` topology is a standalone SUBSET for substrate-only installs, and the conflict gate refuses co-activating it with either.

Caching is the single shared `\Newspack_Nodes\Core::$memd` handle — a raw `\Memcached` built once by `\Newspack_Nodes\Bootstrap::init_memcached()` from `memcache_servers`. This plugin never builds one of its own, and there is no plugin-local cache class. Keyed stores go through the substrate's `Table_Node` (`store()` / `lookup()` / `lookup_multi()` / `forget()`) rather than the raw handle, because its keys are scoped per install: `Stats_Store` holds one Table per storage role over the `evlog:p{N}` namespace and reads and writes every stats key through them, and `Rule_Set` mirrors the hook list of any rule past `INLINE_HOOK_LIMIT` into a fourth. Exactly one call site reaches the raw handle — `Flame_Builder_Node::apply_auto_tune()` takes a cross-worker lock with `Memcached::add()`, which the Table does not offer.

## Plugin Load Order

WordPress loads plugins alphabetically, and `newspack-event-logger-nodes` sorts BEFORE `newspack-nodes` (`-event-` < `-nodes`), so `\Newspack_Nodes\Node` is NOT available at this plugin's file-load time.

So `newspack-event-logger-nodes.php` defers everything that touches a substrate class — the two WP-CLI commands, the `Config::RESET_ACTION` cache-reset listener, the job-context hooks, the `Topology_Registry` mount, the `App\` CommandInterpreter namespace, the `<eln:>` config-token resolver, the three named TSL formatters, the `newspack_nodes/settings_sync/value` resolver, the MCP route, `App\Core`, and in admin the settings page and the current-request overlay — to a closure on `plugins_loaded` priority 11. That bootstrap is version-gated, not merely presence-gated: it checks `class_exists( '\Newspack_Nodes\Bootstrap' )` AND `Bootstrap::version_at_least( '2.57.0', … )`. A substrate below the floor leaves an admin notice naming both versions and the plugin goes dormant; a missing substrate, or one predating `version_at_least()` itself, returns silently. `Requires Plugins: newspack-nodes` keeps the substrate active on WP 6.5+ but says nothing about its version, and WordPress does not order plugin updates, so this plugin really can land ahead of the substrate it needs.

2.57.0 is the `/auth` reply naming the signing key `secret`, which this plugin's bundled auth client and `MCP_Controller` read: below it a minted session carries no key to sign with. 2.56.0 before it is `Admin::overlay_pages()` and the `newspack_nodes/station_tab_bundles` filter the current-request tab registers on, and the verb names the dashboards send (`raw-logs dump_log`, `workers dump_cleanup`, `aggregator list_servers`, `topologies dump`): below it the station has no Request tab and every rail's fetch is refused. 2.53.0 before it was `Capabilities::can()` applying the operator's `allowed_users` list: this plugin deleted its own copy of that list and its own gate, so below the floor the capability still resolves and the list narrows nothing — a silent widening no gate can see. 2.51.0 before it was `Partition_Node::locate_by()` and `scan_index()` reading WITHOUT a write-side index formatter installed. This plugin's two read-only handles — `Flame_Builder_Node::mirror_partition()` and `Performance_CI_Node`'s index scan — used to arm one just to unlock the read, and 2.51.0 refuses `with_index()` on a partition that has not claimed sole writer, so they no longer can. Below the floor those reads return nothing and the stats mirror silently stops rehydrating. That is a BEHAVIOUR requirement, which `check-substrate-floor.sh` cannot see: it audits which substrate APIs exist, not what they do, so this one is raised by hand or not at all.

Raise the floor by hand whenever a new hard requirement appears — `bump-version.sh` repins `release.yml`, not this — and two gates cover the two ways it drifts. `scripts/lint-docs.sh` rule 6 holds every `version_at_least` mention in `README.md`, `AGENTS.md`, `docs/` and `.claude/skills/` to the 2.57.0 the loader enforces, line by line. `scripts/check-substrate-floor.sh` resolves each substrate API PHPStan sees this plugin call to its DECLARING class, binary-searches the substrate's tags for the first one carrying it, and takes the maximum — a floor set too LOW is the failure it exists for, because the handshake then passes and the plugin fatals later. Priority 11 is intentional; don't lower it. Tests bypass this and require the runtime explicitly in `tests/bootstrap.php`.

## Workflow discipline (mandatory)

Every code-writing turn — main Claude AND every subagent — MUST:

1. **Invoke `superpowers:test-driven-development` BEFORE writing any code.** No production code without a failing test first.
2. **Main Claude runs `/code-review` before every commit.** It spawns its own review agents, so subagents cannot run it and do NOT commit. Run it after every subagent finishes, then commit.
3. **Make regressions loud**, in two layers — green suites hid real bugs, and `?? default` reads decoupled config silently for weeks:
   - *Tests* must fail on the OLD code, seeded with values **distinct from every default and fallback**. A test seeded with the default still passes when the change is ignored, so it proves nothing.
   - *Runtime* config fails LOUD. Never `?? default` a key you depend on, i.e. never `$config['key'] ?? default` — a renamed key should throw at the boundary. Read through this plugin's fail-loud `Config::value()`, validated against the shared substrate registry.

Subagent prompts MUST carry this literal phrase; subagents have no memory of conventions, and omitting it is a workflow violation:

> "Invoke `superpowers:test-driven-development` via the Skill tool BEFORE writing any code — mandatory, no exceptions; the failing test must use values distinct from every default/fallback. Do NOT commit: implement, run your tests, and report; main Claude runs `/code-review` and commits."

Full rule: `~/.claude/rules/workflow-discipline.md`.

## Build / Test

Fresh clone, once. The substrate checkout must sit at `../newspack-nodes` — the build kit and shared JS resolve through it.

```bash
npm install                  # JS toolchain (esbuild, jest, eslint, lint-staged)
composer install             # PHP deps + the classmap autoloader
npm run build                # compile the dashboard bundles into build/
```

After adding or renaming a Node class, regenerate the classmap that `make_node` and the console palette read: `composer build:autoloaders` (= `composer install --optimize-autoloader`) or `composer dump-autoload -o`. Use `composer update` only when you mean to move dependency versions.

```bash
# Tests need newspack-nodes installed and activated, and must run as a NON-ROOT user —
# Log_Manager refuses to run as root, which fails the whole suite. Use the vendored
# binary (composer pins `^10.0`, resolved 10.5.64), not a bare `phpunit`: neither
# container puts one on PATH, and an 11.x one would crash the bootstrap with
# `DispatchingEmitter::exportsObjects`. Always pass `--enforce-time-limit` so a hung
# test (readline without a TTY, infinite drain loop) aborts at the per-test budget;
# tests that legitimately sleep through production code mark their class `#[Medium]`.
cd tests && ../vendor/bin/phpunit --enforce-time-limit

tests/run-coverage.sh        # coverage HTML/Clover
npm run lint:php             # phpcs, then the comment-length gate
npm run lint:js              # eslint, the comment-length gate, the contract lint
npm run lint:scss            # stylelint, then the appearance-ownership gate
npm run lint:types           # tsc over the JSDoc types
npm run test:js              # jest
npm run lint:shell           # shellcheck over pre-push and scripts/*.sh, all at once
npm run build

# PHP static analysis, and the JS dead-code audit beside it. `lint:deadcode` is an ALIAS
# of `lint:phpstan`, and the run is larger than either name says: `phpstan-deadcode.neon`
# includes `phpstan.neon.dist`, so one invocation is PHPStan level 10 over
# `newspack-event-logger-nodes.php`, `mu-plugins/` and `includes/` with the full
# `phpstan-strict-rules` set — minus five WordPress and node-runtime idioms (`empty()`,
# truthy conditionals in and out of loops, short ternary, dynamic property and method
# access) — and ShipMonk's dead-code detector on top. Point a manual run at
# `phpstan-deadcode.neon`. lint-staged runs it on every staged `*.php`; pre-push
# deliberately does not repeat it, because the feedback loop is tightest at commit.
#
# Run PHPStan on the HOST, never through `docker exec`: the containers mount `/services`
# read-only, so it cannot write its `tmpDir` (`.phpstan/cache/`) and dies before it
# analyses anything.
#
# Read the dead-code findings rather than obeying them. Tests are excluded as consumers,
# so an export only its test imports reads as unused — mark those `@testonly` in the
# docblock. Most findings are live by hook, by reflection, by `.tsl` topology or from JS;
# verify every call path first. knip's jest plugin is off, so a module reachable only from
# its own test reads as dead, the same rule phpstan-deadcode applies. knip cannot parse
# JSX in a `.js` file, which drops that file's `import()` expressions, so each
# `lazy( () => import( './X' ) )` target is `entry` in knip.json.
npm run lint:phpstan         # types, strict rules and dead code (= lint:deadcode)
npm run lint:deadcode:js     # knip
```

`scripts/pre-push` runs the JS suite with coverage and its per-file 90% gate on every push and scopes the rest to the file types the push touched: PHP takes `lint:php`, a container deploy, the PHPUnit coverage suite and a per-class 90% gate; JS and SCSS take their linters and a build. Three checks run on every push, docs-only included — `scripts/lint-docs.sh` holds the prose to the runtime, `scripts/check-substrate-floor.sh` holds the declared floor to the substrate APIs this plugin calls, and dndocker's `tools/check-firehose-parity.py` holds the PHP and Perl firehose producers to one wire contract. The last two skip cleanly when the checkout they need — the sibling substrate, the dndocker tree — is absent.

This plugin ships as a standard WordPress plugin; deployment is environment-specific and lives outside this repo.

### Git hooks

Hooks are the tracked files in `scripts/` (`pre-commit`, `commit-msg`, `pre-push`), reached via `core.hooksPath`, which `composer install` sets:

```bash
git config core.hooksPath scripts    # what composer's post-install-cmd runs
```

A clone that never ran `composer install` has no hooks at all. `pre-commit` first runs `scripts/sync-shared-scripts.sh`, refreshing this plugin's copy of the shared tooling from `../newspack-nodes/scripts/` when that sibling is checked out — **edit shared scripts there, not here.** The vendored set is the linters, the two coverage gates, `reorder-node-methods.{js,php}`, `fix-blank-lines.php`, the five `test-*.sh` twins that exercise them, `check-substrate-floor.sh` with its PHPStan collector, `lint-docs.sh`, `pre-commit`, `commit-msg` and everything under `scripts/lib/`. Only `build.mjs`, `pre-push` and `bump-version.sh`'s per-plugin knobs are this plugin's own.

`pre-commit` then runs `lint-staged`, which scopes each gate to the staged file's type: eslint, the contract lint, knip and tsc on `*.{js,jsx}`; phpcs, PHPStan and `fix-blank-lines.php` on `*.php`; stylelint and the appearance-ownership gate on `*.scss`; the comment-length gate on both languages; and shellcheck on a staged `*.sh` or `scripts/pre-push`. `reorder-node-methods.{js,php} --check` runs on every staged PHP and JS file, so a Node subclass whose methods drift out of newspaper order fails the commit rather than the review.

`fix-blank-lines.php` is a FORMATTER, not a linter, and the only shared script that rewrites what you staged: lint-staged runs it over every staged `*.php`, collapsing runs of blank lines to one — the holes `reorder-node-methods.php` leaves behind when it moves a method span under a byte-preserving histogram. It rewrites in place and still exits 0, so a commit is never rejected for something already fixed; `--check` rewrites nothing and exits 1.

## Versioning & Release

The version lives in three places: the `Version:` header and the `NEWSPACK_EVENT_LOGGER_NODES_VERSION` constant in `newspack-event-logger-nodes.php`, and `"version"` in `package.json`. Never edit them by hand — `scripts/bump-version.sh` rewrites all three in one pass, syncs `package-lock.json` through `npm version`, repins the substrate in `release.yml`, and refuses a version that's already current. It resolves the pin BEFORE it edits anything, so a missing one aborts with the tree untouched rather than half-bumped. Each has a distinct consumer: the header is what WordPress shows in the admin, the constant is what the runtime and the dashboards' cache-busting read, `package.json` is what npm tooling reads. Drift between any two has shipped as a real bug.

Releases are automated by GitHub Actions (`.github/workflows/release.yml`): pushing a `v<major>.<minor>.<patch>` tag builds the archive and publishes the Release with both artifacts. You only bump, changelog, commit and tag:

```bash
# 1. CHANGELOG.md: rename `## [Unreleased]` -> `## [<version>] - <date>`,
#    then add a fresh empty `## [Unreleased]` above it (Keep-a-Changelog).
# 2. Bump header + constant + package.json:
./scripts/bump-version.sh <version>
# 3. Commit changelog + bump together (`chore(release): <version>`).
# 4. Tag and push — the workflow does the rest:
git tag v<version>
git push origin main
git push origin v<version>
```

On the tag push the workflow validates the tag shape, runs `npm run release:archive` (= `build-release.sh`: build dashboards, rsync via `.distignore`, `composer install --no-dev`, zip, emit the profiler drop-in), extracts the matching `CHANGELOG.md` section as the notes, and publishes with **both** `release/newspack-event-logger-nodes.zip` and `release/00-newspack-profiler.php` attached. No manual `gh release create`.

`build-release.sh` is the single source of truth for archive contents and what the workflow invokes; run `npm run release:archive` locally to build the same artifacts. It rsyncs the plugin into staging minus everything `.distignore` names — `src/`, `tests/`, `docs/`, `scripts/`, `types/`, `mu-plugins/`, `vendor/`, `node_modules`, `.github`, `package*.json` — builds the `--no-dev --optimize-autoloader` vendor tree THERE so the dev `vendor/` is never disturbed, deletes `composer.json` and `composer.lock` from the staged copy, and zips it with the plugin directory at root. It then copies `00-newspack-profiler.php` into `release/` as a standalone asset, because that file ships as an `mu-plugins/` drop-in and the zip excludes the directory it lives in. `fail_on_unmatched_files` guards against a missing artifact.

**Substrate pin.** The two version numbers are independent; the BUILD is not. `release.yml` checks the substrate out at a pinned tag (`ref: v2.56.0`) and points `NEWSPACK_NODES_SRC` at its `src`, from which `src/build-kit/alias-map.cjs` derives every `@newspack-nodes/*` alias esbuild and jest share. Locally those aliases resolve to the working tree; in CI they resolve to the pin, and a stale pin still builds — it inlines older shared code — so **a green Release workflow proves nothing about which substrate got bundled**. `scripts/lib/bump-substrate-pin.sh` rewrites the pin to the substrate version in `../newspack-nodes` and refuses to bump when that version carries no local tag; never hand-edit it.

Release the substrate first, this plugin second, and verify the published asset third: `gh release download v<version> -R Automattic/newspack-event-logger-nodes -p '*.zip'`, unzip, and `diff -rq` its `build/` against the local one. Identical bytes mean the pin was right. v0.43.4 announced the canonical substrate UI layer and shipped dashboards built against the pre-normalization stylesheet instead, because the workflow still pinned the older substrate; the run was green, and v0.43.5 was the fix.

A release that needs a newer substrate at RUNTIME raises the loader's version floor instead — see Plugin Load Order — and says so in the CHANGELOG entry.

## Layout

| Path | What |
|------|------|
| `newspack-event-logger-nodes.php` | Entry; deferred loader gated on `class_exists('\Newspack_Nodes\Bootstrap')` AND `Bootstrap::version_at_least( '2.57.0', …)`. `Topology_Registry::register_plugin()` registers the top-level `Newspack_Event_Logger_Nodes\` prefix for node-class resolution plus the stock-topology dir; `register_namespace` registers only the `App\` service-CI sub-namespace; service CIs mount on `request_graph_ready`. It also registers the `<eln:>` TSL token namespace — three keys, `is_hub`, `stats_mirror_node` and `stats_mirror_lifetime`, the last DERIVED as twice `Config::stats_retention_seconds()` — and three named formatters, because TSL has no closures: `request-index`, `flame-index` and `stats-index`. The admin menu and its five dashboard enqueues register at file scope behind their own `class_exists` guard, and so do six substrate-only hooks, which need none because the action cannot fire without the substrate: `newspack_nodes/declare_config_keys` (which the substrate PULLS, so it names the action as a literal), `registered_log_producers` (this plugin's firehose dir template, which the log GC and the Workers dashboard read), the `before_reconcile` / `after_reconcile` pair giving the minute-cadence reconciliation its own `/jobs/newspack-nodes` request context, `stderr` (the `Diagnostics_Bridge` listener) and `request_graph_ready` |
| `includes/class-settings-schema.php` | The single declarative Field/Schema source, one `Field` per setting, from which Config overlay keys, the admin register/render loop and worker-restart classification all derive. Every one of the nine application keys is declared here WITH its default: three rendered checkboxes (`enable_logging`, `log_memory`, `flush_every_line`) and six overlay-only `ui: false` keys (`rules`, `hook_start_priority`, `custom_colors`, `stats_mirror_node`, `stats_mirror_read_budget_ms`, `recommended_log_events`). `allowed_users` is the substrate's key, not this plugin's: the admin surface gates on `\Newspack_Nodes\Capabilities::can( MANAGE )`, which applies that list itself. URL filters, hook lists and auto-tune thresholds are per-rule fields of the `rules` ruleset, which the React editor owns through the `rules` service CI — never the Settings API |
| `includes/class-{rule,rule-set,rule-matcher}.php` | The per-URL ruleset. `Rule` is an immutable value object whose id is the pattern's `url_hash`; `Rule_Set` handles durable load/save plus two-tier hook storage — inline in the autoloaded list up to `INLINE_HOOK_LIMIT`=100, else a per-rule non-autoloaded option mirrored into the substrate's `Table` (a memoized `Table_Node::table( TABLE_HOOKS, TABLE_TTL )`, whose `store()` / `lookup()` scope keys per install; the accessor is nullable, and a host with no cache backend simply has no warm mirror); `Rule_Matcher` ranks query-bearing patterns above exact patterns above prefixes, with length breaking ties only WITHIN a rank, case-insensitively, and no match meaning skip. `Log_Manager` resolves the governing rule per request through it |
| `newspack-event-logger-nodes-config.php` | Deployment OVERRIDES, not the definition: a commented ledger returning `[]`, each of the nine keys commented out beside the default `Settings_Schema` declares. Four layers, weakest first: the schema default, this file, the file named by `LOCAL_NEWSPACK_NODES_CONF`, and a stored `newspack_event_logger_nodes_<key>` option — PRESENCE decides the option layer, not truthiness, so a stored `''`, `[]` or `false` beats both files. A key here the schema does not declare is reported to stderr and ignored, never registered and never thrown — a deploy copies the operator's own copy over this path, and throwing at `plugins_loaded:-10001` would take wp-admin down with it. `ConfigSchemaTest` parses the commented entries back into an array and holds them to `Settings_Schema::get()->defaults()`, so a default changed in one file alone fails the suite. The active `.tsl` list is the substrate's `topologies` key, and remote-pull segment geometry its `newspack_nodes_*` config; neither lives here |
| `includes/class-config.php` | Application config loader; substrate keys live in `newspack-nodes` |
| `includes/class-log-manager.php` | Per-request firehose writer; redacts URL secrets; refuses root |

## Common Pitfalls

Mistakes that have actually happened.

- **`@wordpress/*` is pinned to the `wp-7.0` dist tag — never bump it to close an advisory.** Each runtime package is declared exactly, no caret, and `scripts/lint-wp-pin.mjs` fails the push when a declaration carries a range or the lock resolves it elsewhere. A caret let every lock climb to trunk while the declaration still read as the tag, and `npm ci` built against the climb. Transitive `@wordpress/*` packages still float within the ranges the family's own manifests declare; the build externalizes those too. Every declared runtime version IS its `wp-7.0` tag (`components 32.2.1`, `element 6.40.1`, `i18n 6.13.1`, `api-fetch 7.40.1`, `icons 11.7.1`). The build externalises four of the five to the `wp.*` globals, so npm's copy never ships — raising it delivers no new code, it moves the API you compile, lint and type-check against AHEAD of the one the browser is handed. A component changed or removed between majors then builds clean, passes eslint and jest, and breaks at runtime, with nothing mechanical to catch it. `@wordpress/icons` is the exception: WordPress registers no `wp-icons` handle, so the build kit's `WP_EXTERNALS` map omits it deliberately and the one icon `src/settings/settings/TagInputField.js` imports is bundled — a bump there does change what ships. Check `npm view @wordpress/<pkg> dist-tags --json` against `wp core version` before proposing any bump, and move the whole family together only when the WordPress target itself moves. A Dependabot advisory reachable only PAST the pin gets dismissed, not bumped: 2026-08-17, uuid GHSA-w5hq-g745-h8pq needed `components >= 33.1.0`, one major past `wp-7.0`, for a package absent from `build/` entirely — dismissed `not_used`. npm `overrides` cannot rescue that, because npm matches an override by package NAME anywhere in the tree: both `{uuid: …}` and the nested `{"@wordpress/components": {uuid: …}}` reach the copy the pinned component library legitimately depends on — `uuid@^9.0.1`, the one uuid in this lock — and swap it out from under it.
- **There is no global logging or auto-tune option; logging is per-URL-rule.** No config key named `log_urls`, `skip_urls`, `log_events`, `custom_events`, `significant_events`, `auto_disable_threshold` or `auto_protect_time_threshold` is declared or read: the last four name per-rule fields of `Rule`, and the first three have no counterpart at all. Each rule is a URL pattern (`/prefix` or exact `/x?`) with a `log`/`skip` action and, for `log` rules, its own hooks, custom events, significant events, two auto-tune thresholds and four diagnostic knobs — `log_http` (default on), `log_queries`, `trace_hooks` and `trace_callers` (all default off). Matching ranks query-bearing patterns (`/jobs/x?job-work`) above ALL exact patterns, which rank above ALL prefixes — length only breaks ties within a rank, so this is NOT longest-prefix-wins. Case-insensitive; **no match means skip, and empty means empty — there is no implicit log-all baseline.** Declare a `/` log rule to log everything, as the shipped seed does alongside five exact skips: the substrate's `command`, `log/stream`, `messages/stream` and `workers/spawn` routes, and `/wp-cron.php`. Rule id = the pattern's `Log_Manager::url_hash()`. Discovery only *stages* what spokes report, into the non-autoloaded `discovered_hooks` and `discovered_events` options the editor's pickers read; the editor is the only rule writer.
- **There is no operator hub toggle: no `enable_workers`, no `enable_aggregator`.** `tests/unit/RetiredConfigKeysTest.php` guards both names against reintroduction. Hub-mode derives from whether `aggregator` is in the substrate's `topologies` list. Settings fan-out is structurally ungated: without `hub-control` active and per-spoke `HTTP_Out` nodes wired, a recorded settings event is tailed and dropped.
- **Two bounds, and BOTH fold.** Both are `Request_Builder_Node` node arguments declared in its `node_schema()` and parsed by `parse_schema_args()`, not config keys — `make_node Request_Builder request-builder <bucket_size> <num_buckets> <entry_budget> <max_entries_per_request>`, and the shipped topology passes only the first two. `entry_budget` constrains the SUM of entries across everything in flight (what a staging site ran out of) and folds the largest envelope when crossed; `max_entries_per_request` constrains ONE envelope and folds that one, a faster trigger for a single runaway than waiting for the next pressure check. A cap that merely stops appending and sets a `truncated` flag nothing surfaces loses every entry past it — never build that. A folded record ships `flame` + `folded` plus its kept head and tail rejoined around an `entries (aggregated)` marker; `Flame_Builder_Node` and the detail view read the folded and the unfolded shape alike, because both sit on disk.
- **PIPE_BUF (4096 bytes) for firehose writes.** `Log_Manager::message()` builds the whole entry — `n`, `k`, the caller's data and `ts` — and enforces `MAX_DATA_SIZE = 3840` on THAT encoding, which is the headroom that keeps a lock-free append atomic. The three stamped keys are why the ENTRY is what gets fitted rather than `$data`: a payload sitting exactly at the cap on its own goes over budget the moment `n`, `k` and `ts` land, and the gap left under PIPE_BUF is then the Message envelope's alone. Over the cap, `fit_data()` trims a string `m` progressively — from the cap down 10% a step, re-encoding each time, because JSON escaping expands bytes — and drops `m` outright when trimming cannot fit it or when it is an array. The entry is marked `truncated => true`, and every other key survives, `l` and `caller` included, so the flame still merges the span under its `l` label and the request record keeps its caller summary. What opens a span is the category `k` alone — `Flame_Tree::PATTERN_START` and `Request_Builder_Node`'s `' (start)'` suffix test both read it — so **the category is NOT renamed**: a `" (truncated)"` suffix breaks both tests, the span never opens and its `(complete)` orphans. The floor case, where the other keys alone exceed the cap, keeps `n`, `k`, `ts` and `truncated` and carries a 1000-byte slice of the oversized encoding as `m` — strip those three and no reader can place the line. Nothing is chunked and nothing is logged to `error_log` — the entry says so itself. A firehose entry has no escape, because every request process appends that log with no lock: shape a large value at the producer or split it across entries. A partition with one writer lifts its cap to 32 MiB, by a held lock (`allow_large_writes()`, which is how `\Newspack_Nodes\Job_Intake::queue()` admits a large job) or by the `void_warranty` assertion the `requests` and `flames` partitions carry.
- **One shared `Core::$memd` handle — read it, don't build your own.** It is built once at boot by `Bootstrap::init_memcached()` from `memcache_servers` (default `127.0.0.1:11211`). Consumers read `Core::$memd` directly with null-safe `Core::$memd?->...`. Never hardcode server lists or open a second connection.
- **Tests set `Core::$memd` to an in-memory `\Memcached` double.** There is no `Cache_Interface` / `Memcached_Cache` to inject — the substrate ships the double at `tests/Helpers/InMemoryMemcached.php` and tests assign it in setUp. New cache call-sites read `Core::$memd`; nothing should type-hint a cache interface.
- **Salt rotation requires a worker restart.** `Cache_Backend::rotate_salt()` orphans keys, but a worker memoizes the install scope at boot.
- **Stats fail soft, SSE slots fail closed. Don't unify them.** Dashboards must show "no data" on memcache failure; SSE connections must reject with 429, because the slot pool IS the rate limit.
- **Application Node classes resolve by namespace prefix — no per-class registration.** The entry point calls `\Newspack_Nodes\Topology_Registry::register_plugin( 'Newspack_Event_Logger_Nodes\\', …/topologies )` and `\Newspack_Nodes\Command_Interpreter_Node::register_namespace( 'Newspack_Event_Logger_Nodes\\App\\' )` for the service CIs. `make_node Flame_Builder` resolves `\Newspack_Event_Logger_Nodes\Flame_Builder_Node`, and the palette scans the classmap. A new node needs only `class Foo_Node extends \Newspack_Nodes\Node` under that namespace plus `composer dump-autoload -o`.
- **Token-array command contract.** TM_COMMAND `arguments` and node-constructor `arguments` are a token array (`list<string>` argv), never a space-joined string. Every `App\*_CI_Node` verb handler takes `array $args` and parses via `Command_Args::parse( self::arg_strings( $args ) )` — the `rules` `save`/`upsert` verbs read the whole JSON blob as `self::arg_strings( $args )[0]`. `Request_Builder_Node` and `Discovery_Collector_Node` declare `arguments( ?array $args = null ): array`, while `Flame_Builder_Node` and `Job_Router_Node` get the same handling free via the substrate's `Schema_Reflection` trait's `parse_schema_args()`. (Substrate mirror: `../newspack-nodes/AGENTS.md`.) `Reqgrep_Command` and `Log_Manager`'s firehose `Topic` construction pass token arrays; the dashboard hooks build args with `formatCommandArgs(...)`. The token array is the COMMAND envelope's alone: a TM_INFO VALUE stays a flat `KEY VALUE` string, and a firehose line's VALUE is the entry array TM_STRUCT declares. A handler typed `string $args`, or code splitting a joined args string, is a stale port.
- **Type flags**: an array VALUE takes `TM_STRUCT`, a string VALUE `TM_BYTESTREAM`. Consumers reading an array VALUE gate on TM_STRUCT.
- **Don't add `class_exists()` guards for in-plugin classes.** `vendor/autoload.php` loads at file scope and its composer CLASSMAP resolves everything under `includes/` on demand, so such a check can only ever be true. What a missing class really means is a stale classmap — run `composer dump-autoload -o` after adding or renaming one.
- **`complete` is what a config or layout naming `combined` means.** It runs request-builder, flame-builder, job-router and job-worker in one worker; no plugin ships `combined.tsl` or `jobs.tsl`. A topology name resolving to no `.tsl` is dropped SILENTLY — `Bootstrap::get_topologies()` synthesizes each active entry from that file's frontmatter and skips the names it cannot resolve — so dndocker's `services/pyrobase/server/default/newspack-nodes-config.php`, which still names `combined`, boots a `job-worker` fleet and nothing else. Stored options outrank the file, so read `wp nodes status` before believing it. `restart` validates its target against those same live worker rows: the target is an ACTIVE topology name, never a hardcoded one.
- **`wp nodes cli {reader}` requires the worker to exist.** `attach_to_worker` looks for `{base}/locks/{reader}.lock.d/` and, failing that, asks `Spawn_Coordinator::wake_sleeping_worker()` — refusing on the absent lock alone would refuse every on-demand worker. Only when neither answers does it throw "no worker '<id>' (run `wp nodes status` to list active workers)", so a typo'd reader id fails fast rather than silently creating ghost IPC. Surface that error if you script it.
- **The substrate passes ALL message types through Partition/Topic**, TM_REQUEST, TM_ERROR and TM_EOF included, which is what makes attached-mode error responses, `request_node` cli verbs and the stdin-close drain work. Application data partitions emit only TM_BYTESTREAM and TM_STRUCT in practice, so the broader contract is a no-op on the write path — but a Partition serves as an ad-hoc message transport.
- **Piped `wp nodes cli` sessions drain cleanly.** The substrate does a TM_EOF round-trip on stdin close, so a scripted pipeline needs no trailing `sleep N`.
- **`App\Core` hook instrumentation has two non-obvious correctness mechanisms — don't strip them.** `wrap_callbacks()` skips any callback whose reflection reports a by-reference param (`callback_has_ref_param()`), because wrapping those breaks the WordPress by-reference contract. And a sacrificial `hook_spacer` at `PHP_INT_MAX - 2` (`SPACER_PRIORITY`) keeps `hook_complete` at `PHP_INT_MAX - 1` firing when a filter unhooks itself mid-run and shifts WP's pointer past it; `wrap_callbacks` treats everything at or above the spacer priority as ours and leaves it alone.
