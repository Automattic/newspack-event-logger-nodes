# AGENTS.md — Newspack Event Logger Nodes

The application layer of the event logger. It replaced the legacy `newspack-event-logger-plugins` monorepo with two plugins: this one and `newspack-nodes` (the runtime substrate). High-throughput request-lifecycle logging, real-time SSE streaming, flame-graph generation and hub/spoke aggregation, all expressed as Nodes.

This plugin owns `Log_Manager`, `Request_Builder_Node`, `Request_Flight_Node`, `Flame_Builder_Node`, `Auto_Tuner_Node`, `Job_Router_Node`, `Remote_Job_Rewrite_Node`, `Stats_Store`, the per-URL logging ruleset (`Rule` / `Rule_Set` / `Rule_Matcher`), the `App\*_CI_Node` service CIs (`performance`, `discovery`, `rules`), the React dashboards and the topology files. Node subclasses carry a `_Node` suffix; helpers like `Log_Manager` and `Stats_Store` don't.

Three things moved to the substrate and have no compatibility alias here — call the substrate class directly:

- **Hub fan-in** is `\Newspack_Nodes\Remote_Source_Node`. The old ELN `Stream_Merger_Node` / `Remote_Source_Node` were deleted in the pull-side cutover.
- **`Job_Worker_Node`**. This plugin keeps only the request-context glue, `Log_Manager::begin/end_job_context`, hooked onto `newspack_nodes/job_worker/{before,after}_job`.
- **`Job_Intake`**, the large-write ingress, now `\Newspack_Nodes\Job_Intake` — there is no compatibility `class_alias` for the old `Newspack_Event_Logger_Nodes\Job_Intake` FQN. `job-router.tsl` and `combined.tsl` keep their own jobintake→jobs legs unchanged; the substrate's stock `job-intake` topology is a standalone SUBSET for substrate-only installs, and the conflict gate refuses co-activating it with either.

Caching is the single shared `\Newspack_Nodes\Core::$memd` handle — a raw `\Memcached` built once by `\Newspack_Nodes\Bootstrap::init_memcached()` from `memcache_servers`. This plugin only reads it; there is no plugin-local cache class. Keyed stores go through the substrate's `Table_Node` (`store()` / `lookup()` / `forget()`) rather than the raw handle, because its keys are scoped per install — `Stats_Store` is the exception, and earns it with `getMulti` batching, value caps and salt rotation the Table has no equivalent for.

## Plugin Load Order

WordPress loads plugins alphabetically, and `newspack-event-logger-nodes` sorts BEFORE `newspack-nodes` (`-event-` < `-nodes`), so `\Newspack_Nodes\Node` is NOT available at this plugin's file-load time.

The workaround: `newspack-event-logger-nodes.php` defers its wiring (CommandInterpreter namespace, `Topology_Registry` mounts, `App\Core` init) to a closure on `plugins_loaded` priority 11. That bootstrap is version-gated, not merely presence-gated — it checks `class_exists( '\Newspack_Nodes\Bootstrap' )` AND `Bootstrap::version_at_least( '2.40.0', … )`, staying dormant with no notice on a missing or too-old substrate. `Requires Plugins: newspack-nodes` keeps the substrate active on WP 6.5+ but does not guarantee the floor, and WordPress does not order plugin updates — this plugin really can land ahead of the substrate it needs. 2.40.0 is `Config_System\Schema::defaults()`, which `Config` reads the schema's own defaults through; 2.38.0 was `Partition_Node::index_mtimes()`, which the `performance` CI reads its per-index freshness from; 2.37.0 was `Node::publish_sibling()` / `Node::sibling_name()` — `Request_Builder` publishes its `flight` sibling on every request and `Flame_Builder` addresses its `auto-tuner` by that name, so below it the request path itself fatals on an undefined method — plus the `Schema_Reflection` trait's `dump_setters()`, which `Request_Builder::dump_config()` appends. 2.35.0 was `Table_Node::backed_by()`, the read-through both `Stats_Store` and `Rule_Set` reach their durable tier through. 2.31.0 was `Capabilities::TUNE` — every verb here declares a capability role, and an older substrate throws "unknown capability role" on the `tune` ones — plus `Bootstrap::mount_request_graph()`, which the MCP controller builds its request graph with; below it every MCP call fatals on an undefined method. 2.25.0 was `\Newspack_Nodes\Line_Fitter`, which Request_Builder and Request_Flight fit their emits through. 2.21.0 was `Table_Node::store()` / `forget()`, which `Rule_Set` writes its pointer-tier hooks mirror through — below it every heavy rule's save fatals on an undefined method. 2.21.0 also made those methods NON-STATIC and moved `LRU_Cache` into `Newspack_Nodes`. Raise the floor by hand whenever a new hard requirement appears — `bump-version.sh` repins `release.yml`, not this — and `lint-docs.sh` rule 6 gates the prose against the loader. Priority 11 is intentional; don't lower it. Tests bypass this and require the runtime explicitly in `tests/bootstrap.php`.

## Versioning & Release

The version lives in three places: the `Version:` header and the `NEWSPACK_EVENT_LOGGER_NODES_VERSION` constant in `newspack-event-logger-nodes.php`, and `"version"` in `package.json`. Never edit them by hand — `scripts/bump-version.sh` rewrites all three atomically and refuses a version that's already current. Each has a distinct consumer: the header is what WordPress shows in the admin, the constant is what the runtime and the dashboards' cache-busting read, `package.json` is what npm tooling reads. Drift between any two is a real bug we have shipped.

Releases are automated by GitHub Actions (`.github/workflows/release.yml`): pushing a `v<major>.<minor>.<patch>` tag builds the archive and publishes the Release with both artifacts. You only bump, changelog, commit and tag:

```bash
# 1. CHANGELOG.md: rename `## [Unreleased]` -> `## [<version>] - <date>`,
#    then add a fresh empty `## [Unreleased]` above it (Keep-a-Changelog).
# 2. Bump header + constant + package.json:
./scripts/bump-version.sh <version>
# 3. Commit changelog + bump together (`chore(release): <version>`).
# 4. Tag and push — the workflow does the rest:
git tag v<version>
git push origin main
git push origin v<version>
```

On the tag push the workflow validates the tag shape, runs `npm run release:archive` (= `build-release.sh`: build dashboards, rsync via `.distignore`, `composer install --no-dev`, zip, emit the profiler drop-in), extracts the matching `CHANGELOG.md` section as the notes, and publishes with **both** `release/newspack-event-logger-nodes.zip` and `release/00-newspack-profiler.php` attached. No manual `gh release create`.

`build-release.sh` is the single source of truth for archive contents and what the workflow invokes; run `npm run release:archive` locally to build the same artifacts. It rsyncs the plugin minus development artifacts (`src/`, `tests/`, `node_modules/`, `.github`, `composer.{json,lock}`, `package*.json`) so the zip holds the plugin directory at root, and copies `00-newspack-profiler.php` into `release/` as a standalone asset — it ships as an `mu-plugins/` drop-in, separate from the zip. `fail_on_unmatched_files` guards against a missing one.

**Coupling**: this plugin's version is not tied to the substrate's; they release independently. If a release depends on a specific runtime version, say so in the CHANGELOG entry.

## Architecture Decisions

Intentional. Don't "fix" them.

1. **9-namespace memcache schema.** Stats live in memcache only, never on disk. Per-partition prefix `evlog[:salt]:p{N}:`, then namespace: `hourly`, `lb`, `lb_s`, `urls`, `url`, `dim`, `url_dim`, `categories`, `url_cat`. The `urls` index is additionally SHARDED — `urls:{shard}:{bucket}`, sixteen shards by the first hex digit of the url_hash. A shard is not a scope, which is what makes it the one component here that names no dimension of the data: it is physical partitioning, and it exists because one blob per bucket is what every cap in this schema was defending. **Eight of the nine are bucketed, and the bucket key is always the LAST component** — so every scope (server, URL, dimension) is a pure key prefix, one `lookup_multi` serves them all through `Stats_Store::lookup_buckets()`, retention is the key's own TTL rather than a hand-rolled cutoff pass, and whether the bucket a key names is still open is decided from the key alone (`Stats_Store::is_open_bucket()`). `url` is the exception: per-URL, not bucketed. Per-URL flame stats get TTL `max(3600, max_lifespan/24)`; everything else the full `max_lifespan` — a `Stats_Store` constructor property seeded from the substrate's `min_lifetime` key (default 43200) through `Config::stats_retention_seconds()`, which floors it at `Stats_Store::PREFIX_FLOOR` = 3600. `max_lifespan` is not itself a config key on either side. Caps prevent value-explosion against memcache's 1MB limit: `MAX_DIM_VALUES=20`, and the `server` axis takes `MAX_SERVER_VALUES=128` instead (`Stats_Store::dim_cap()`), through the same traffic-ranked `Other` fold. It was once exempt on the reading that a cap is a cardinality guard and this axis is the FLEET — one `{c,s,m}` per spoke, so a hundred cost about four kilobytes and there is nothing to guard. That is wrong: `server_name` is `$_SERVER['SERVER_NAME']`, which under Apache's default `UseCanonicalName Off` is the CLIENT'S Host header, so a domain-mapped multisite or any catch-all vhost taking Host-header spray makes the axis visitor input with no ceiling. The ceiling is 128 rather than `MAX_DIM_VALUES`' 20 precisely because 20 bound on a real fleet: it dropped every spoke past the twentieth into `Other`, per bucket by request count, which is how a 24-spoke fleet lost four sites from its own picker. So it sits far above any fleet in evidence and the tail FOLDS rather than dropping, keeping every total exact. **Decision 14 owns the reopen condition for this ceiling** — wherever the `server` axis is stored, one tripwire, stated there. `MAX_URL_DIM_VALUES=10`, `MAX_CAT_VALUES=50`, `MAX_DURATIONS_PER_BUCKET=100` (reservoir-samples the raw durations `Flame_Builder_Node` keeps per bucket for percentiles — Algorithm R once capped). Overflow rolls into a synthetic "Other" bucket; the `total` pseudo-category is preserved before capping.

2. **Sums, not means.** Leaderboard buckets hold raw `count`, `sum_req_time`, `samples`, `sum_time`, `sum_count`, so cross-bucket and cross-partition merges are exact addition and the display layer computes means at read time. Do NOT regress to running-mean storage — that introduced an EMA-clamp bug we explicitly fixed.

3. **Fail-soft stats, fail-closed SSE slots.** The memcache failure asymmetry is deliberate. Every `Stats_Store` method returns `null` / `[]` / `false` when memcache is unreachable and never throws, so dashboards show "no data" instead of erroring. SSE slots fail CLOSED at the caller — memcache down means new connections get HTTP 429, preserving the rate-limit invariant.

4. **Settings fan-out is a node graph; no consumer means a silent no-op.** Propagation is the substrate `Settings_Sync_Node` graph in the `hub-control` topology. An option change always records a settings event (`Settings_Event_Writer` → `settings.p0`), and `Auto_Tuner_Node` mutates the specific rule named in the message (`rule_id`) and persists the whole ruleset via `Rule_Set::save()` — no `remote_manager` job, no `suppress_sync`; each write records a settings event like any admin edit. Nothing fans the change out unless `hub-control` is active and per-spoke `HTTP_Out` nodes are wired; on a spoke or standalone site the event is tailed and dropped. That IS the structural gate. `enable_workers` (retired v0.5.0) and `enable_aggregator` are both gone — hub-mode derives from which topologies are active.

5. **Salt-rotation schema migration.** Flushing is the substrate's one button, `Cache_Backend::rotate_salt()`, which moves the install scope for every plugin at once; `Stats_Store` keeps no salt of its own. Schema bumps and emergency flushes share the mechanism. The scope is memoized per process, so restart long-running workers for immediate effect.

6. **`get_multi` batching is essential.** Reader paths multi-get across all retention buckets per partition in one round-trip; per-key `get` is a latency cliff on dashboards. Implemented in both the real and Fake memcached.

7. **Job_Intake for >4KB payloads, firehose for ≤4KB.** Small runtime jobs go through the firehose with `k:"job"` and `Job_Router_Node` extracts them. Large jobs go straight to `jobintake.log` via `Job_Intake::queue()`, which takes the auto-lock around large writes. The wrong path loses jobs: `Log_Manager` truncates data over `MAX_DATA_SIZE` (3840B) to a 1000-char excerpt with `" (truncated)"` on the category, so the handler never sees a parseable payload.

8. **Hub vs spoke topology.** Hub = the `aggregator` (+ `hub-control`) topologies active; there is no `enable_aggregator` toggle. Every node runs its own `Job_Worker_Node` dispatching `k='job'` against `newspack_nodes/job_handlers`. The hub additionally runs `aggregator`: per-spoke substrate `Remote_Source_Node`s pull spoke firehoses, and ELN's `Remote_Job_Rewrite_Node` — wired between the sources and the firehose `Topic` — rewrites incoming `k:"job"` to `k:"remote_job"`, which the hub's `Job_Worker_Node` dispatches against `newspack_nodes/remote_job_handlers`. The two filters are independent registrations, so a job type registers under either or both depending on where it should run.

9. **CRC32 + 31-bit-mask partition routing**, inherited from `Partition::hash_to_partition()`. Used by Topic, `Job_Intake`-keyed mode and `Log_Manager`'s URL routing. Same key → same partition across all producers.

10. **The durable mirror writes a bucket once, when it closes.** `flame-stats` is append-only and last-frame-wins per key, so mirroring the bucket still being accumulated into — once per 30s checkpoint, ten times over a 5-minute bucket — leaves nine dead copies retained for `stats_mirror_lifetime`. Measured before the change: **4,279,767 of 5,531,418 bytes (77.4%)** of a real `flame-stats.p0` were frames a later frame had already superseded. `flush_stats_mirror()` therefore holds a bucket's frames until `Stats_Store::is_open_bucket()` says it closed. *Alternatives rejected:* writing every checkpoint and shortening `stats_mirror_lifetime` instead (loses history rather than duplicates); keying frames by bucket+checkpoint and compacting later (a compactor to own, for the same bytes). **Revisit if** the partition ever stops being last-frame-wins on read.

11. **The open bucket is durable in the OFFSETLOG until it closes, and the carry is capped.** A held frame is in no durable log, so `save_state()` carries the held frames and `restore_state()` takes them back — a self-pruning ring of at most 60 keyframes, where the mirror retains for twice the stats window, so the open window costs bounded disk in the cheap place. Three invariants the code must keep: the worker's `rehydrate` seam consults held frames FIRST, or a mid-bucket eviction makes the read-modify-write restart the bucket from zero; a restored frame carries what is LEFT of its TTL, per substrate ADR-18 — an expired frame is a miss, not a resurrection; and the carry is capped at `MAX_CHECKPOINT_MIRROR_BYTES` because the per-server aggregates grow with the spoke count while `Partition_Node` DROPS an oversize record — and that record is the whole checkpoint, cursor included. **Dropping the biggest is the design, not a fault**: smallest-first keeps the most keys recoverable per byte, and a dropped frame is re-merged from memcache by the next write to its bucket — lost only if the process AND memcache both fail before the bucket closes. The budget is set from the observed held size — ~267KB–348KB per checkpoint on a production hub, against a topics cache peaking under 3.8MB across a day — and clears that peak by ~6x, so the log does NOT fire in routine operation and "it fired at all" is informative. It was not always so: at a budget of 262144 the held totals sat just over the cap, so a multi-spoke hub dropped one to thirteen frames on essentially every checkpoint and the tripwire was permanently tripped, which tells you nothing. The log carries the numbers too: how many frames dropped of how many held, the budget, the held TOTAL, and the largest dropped frame with its namespace and size — the namespace because a sharded `urls` key and an `lb_s` key are both opaque, and which one fired is the whole question this tripwire asks. `mirror_held_bytes` / `mirror_held_frames` on the GET_STATS payload carry the same total continuously, so the trend is readable before it trips. **Revisit when** the log fires AT ALL — any drop now means the held set has grown past ~6x the size it was measured at, which is the O(servers) signal arriving — or when the largest dropped frame is NOT a per-server leaderboard, which would mean something other than fleet size is driving it. Read the trend in BYTES, off `mirror_held_bytes`, not in frames: `urls` is sharded, so one open URL bucket holds SIXTEEN frames rather than one, each a sixteenth the size, and `mirror_held_frames` steps up accordingly with no fault behind it. Sharding also repaired the other half of this tripwire: an unsharded `urls` blob carrying a split and a duration reservoir per row was larger than the whole budget, so it was always the largest dropped frame and "the largest dropped frame is NOT a per-server leaderboard" was permanently satisfied. Sixteen smaller frames sort in among the leaderboards and the fleet-size signal reads true again. What bounds the budget from ABOVE is the offsetlog ring, 60 keyframes × the budget of disk (~120MB today) plus a write every 30s — that ring caps keyframe COUNT and never bytes, and nothing else bounds it, so raising the budget raises the disk cost in direct proportion and that is the true cost of the number. NOT `Partition_Node::MAX_LARGE_LINE_SIZE`, which is 16× away and does not bind. **The real lever is upstream**: `STATS_MIRROR_TOPN` rank-caps the three per-URL namespaces while the per-server ones fall to the keep-all branch, so the held set grows O(servers) without limit and any fixed budget eventually loses to fleet size. Bounding that axis is the structural fix and a deliberate trade, not a refactor — buffer-time eviction drops a frame from the durable mirror at bucket close, a strictly larger loss than dropping it from a checkpoint.

12. **A stat times the request; a flame value is a rendering artifact.** Two numbers describe one request and they are not interchangeable. `duration_ms` on the record is what the request took, measured once. A flame node's `value` is a LAYOUT WIDTH: `Flame_Tree::cover_children()`, `Flame_Fold::flatten()` and `Flame_Builder_Node::fill()` all RAISE it so a parent covers its positioned children, because the browser prunes on a single cutoff and takes a whole subtree with anything it drops, and `treemapDice` scales children by `parentWidth / parent.value`. Raising is correct for drawing and wrong for counting. **Every stat therefore reads `$request['duration_ms']`; nothing measured reads a flame `value`** — that covers all nine namespaces of decision 1 plus the per-URL aggregate's `sum_value`. *Measured before the change:* a 356,312ms request reached `avg_ms` as 724,662.87ms, because `fill()` had raised the root to cover a child that ran 355 seconds after the parent's own occurrence. *Alternatives rejected:* not raising at all (deletes exactly the frames a viewer opened the graph to see); computing stats before the raise (the ordering is invisible at the call site, and one reorder reintroduces it). **Revisit if** the browser stops pruning on a single value cutoff — the raise can go then, and the two numbers converge.

13. **A sequence-break marker is missing detail, not idle time.** `entries (lost)` and `entries (aggregated)` stand in for entries `Request_Builder_Node` removed — discarded on overflow, or merged by the fold. It mints them, so it owns the vocabulary as `Request_Builder_Node::SEQUENCE_BREAK_KEYS`; consumers reference that constant rather than keeping their own copy, and the JS holds the only deliberate duplicate because it is a separate deploy unit. **No consumer may reason across a marker.** `Findings::entry_gap()` skips a gap on either side of one, `Reqgrep_Command` breaks its sequence there, and `logEntryUtils` splices the merged spans back at it. Reading the interval as unexplained had one record's `entry_gap` proposing MORE hooks while its `truncation()` proposed fewer — both at once, on the same record. What a consumer MAY read across one is the record's own ending: whether anything closes the outermost pair. That decides FRAMING — which spans were severed and which ran to the end — and leaves the interval exactly as unmeasurable as it was, which is what this decision protects. `logEntryUtils`' `pruneSeveredSpans()` and `Reqgrep_Command::prune_severed_spans()` are the one rule, and the parity test in `logEntryUtils.test.js` pins the vocabulary they share. **Revisit if** a marker ever carries its own duration, which would make the interval measurable rather than merely missing.

14. **A server scope the key cannot carry rides inside the value, and is applied as a PROJECTION.** Decision 1's shape is that every scope is a key PREFIX — `lb_s` is `lb` with a server component, and one `lookup_multi` serves it. The URL index cannot follow that: a `urls_s` namespace applies the 500-row cap **per key**, so the index that is mirrored in FULL — `urls` is absent from `STATS_MIRROR_TOPN` — grows O(servers × 500) rows per bucket, on the same axis decision 11 already names as the one that outgrows any fixed checkpoint budget. So the split rides in the value instead: each row carries `srv`, its summed fields per reporting server, capped at `Stats_Store::MAX_SERVER_VALUES` by the same ranked `Other` fold `dim_cap()` now gives the `server` axis everywhere it is stored. The axis is NOT the fleet, which is what the earlier uncapped form rested on: `server_name` is `SERVER_NAME`, and under Apache's default `UseCanonicalName Off` that is the client's Host header, so a domain-mapped multisite or any catch-all vhost makes it visitor input with no ceiling. What a cap must not do is bind on a real fleet — a folded server's scoped read matches nothing, and the URL leaves the filtered table AND its totals silently, exactly as the dimension cap dropped it from the picker — so the ceiling sits far above any fleet in evidence (five times the largest hub, three times the widest per-URL split any test asserts) and the tail FOLDS rather than dropping, keeping every total exact. The cap is applied ONCE, after the `MAX_URLS_PER_SHARD` fold, because the fold is what mixes hosts: a stored `url` is absolute, so a real row carries one or two splits while the two overflow rows carry every server the tail was seen on. Bytes are then bounded on both factors of rows × servers rather than one, with the refused-write log left as the backstop it always was — a guard that REPORTS where the cap CORRUPTED: an oversized shard is one loud line and a bucket's rows lost until the next write. **Revisit when** that log fires at a row count well UNDER `MAX_URLS_PER_SHARD` — a shard over the item limit on few rows is bytes per row, which is rows × servers, and the answer is a byte-derived row cap, not a lower value count — or when a real fleet approaches `MAX_SERVER_VALUES`, which the picker announces by growing an `Other` entry and which means the ceiling, not the mechanism, is what needs raising. Refusal AT the cap is the row count doing its job and says nothing about the fleet, and the namespace cannot be the signal: the log lives in the URL-index write path and can name nothing but a `urls` shard. **Only fields that ADD are split** (`Stats_Store::URL_SRV_SUMS`): `min_ms`, `max_ms` and the percentiles are extremes over a sampled reservoir, so a server-scoped row keeps the URL's own across every server — deliberate, and on a fleet of disjoint sites invisible. Because every split field adds, selecting then summing and summing then selecting agree, so the scope is a projection over the MERGED row (`Performance_CI_Node::project_row`), not a filter before the merge: `load_index_default()` reads once, unscoped, and each verb cuts the scope it needs out of that one read. Scoping inside the loader instead made the memo a per-scope cache, and a filtered poll — `urls` scoped, `overview` not — paid the whole `lookup_multi`, unserialize and merge twice, against decision 6. WHICH fields swap is `Stats_Store::swap_url_server_sums()`, beside the table that defines them; the means and the recent-window share are the READER's — a mean is a display division per decision 2, and the window is reader geometry the schema has no name for — so `project_row()` finishes what the store starts. Neither half returns a row in one scope on its own, and both are named for what they do rather than for what the caller wants. The row also carries `sum_ms` and `sum_peak_mb` to display, so the projection divides once, in its own scope, and nothing has to un-average a figure another function divided. The split is capped at persist and not in the accumulator, so an open bucket's rows carry one entry per distinct reporting server SEEN IN THAT FLUSH WINDOW on the checkpoint, which decision 11 counts as uncounted `pending`. Spray does not widen that: an absolute `url` puts the sprayed host in the row KEY, so the accumulator answers it with rows — bounded by `URL_ACCUMULATOR_SIZE` — each carrying one server, not with a wide split. Unlike the three per-server AGGREGATES it sits beside, the split is **not** hub-gated: the filter is offered wherever the `server` dimension has values, and a scoped read of a row without a split returns nothing, so gating it would empty the URL table on every spoke rather than save one. *Alternatives rejected:* a `urls_s` namespace (above); resolving the scope from `url_dim` at read time (O(urls) gets per poll). The `urls_s` rejection is NOT an argument against the sharding that shipped, though both add a key component: a shard count is a constant this schema chooses, while a server count is an input this schema does not control — visitor-driven at worst, and the one decision 11 watches. A per-key axis has nowhere to put a fold, so capping it is not even available. Sixteen shards of 500 rows is a ceiling; O(servers) × 500 is not. **Not taken, deliberately:** `url_dim`'s `server` axis looks like a duplicate and is not one in either direction — it is a per-BUCKET time series of `{c,s,m}`, which is what the URL-detail breakdown chart draws, while `srv` is one window-merged scalar carrying eight fields including the status classes. Neither can produce the other. (Both now take `MAX_SERVER_VALUES` on the `server` axis; any remaining cap asymmetry between the two namespaces is unobservable: `url_detail` throws `URL not found` for any hash absent from the index, so a URL that never survives `MAX_URLS_PER_SHARD` cannot reach its own `url_dim` rows.) **Revisit if** `urls` ever gains a top-N mirror bound, which would cap a per-server namespace too and make the key-prefix form affordable again; if the row ever carries its split PER BUCKET, which is the one shape that would retire `url_dim`'s server axis; or if one URL is routinely served by more than `MAX_SERVER_VALUES` servers, at which point `cap_bucket` rolls the surplus into a synthetic `Other`, a scoped read of a demoted server matches nothing, and the URL leaves the filtered table AND its totals silently. That is unreachable today and worth knowing why: a stored `url` is ABSOLUTE (`https://host/path`), so a URL hash belongs to one site and carries one or two splits, not a hundred. The same fact is why `find_recent_requests_for_url()` is not scoped — the request index carries no server, and it does not need one.

15. **The `urls` verb owns every URL-set fact; `overview` owns the site.** One verb applies the filters, so one verb answers for what they left: how many URLs, how many requests, the averages, the rate, the slowest ten, and — as its default page, sorted by count DESC — the busiest. The header and the table beneath it therefore cannot disagree, and a filter matching nothing reads as an empty set rather than as zero traffic. `overview` keeps only what the URL index cannot answer: `total_requests` and the two averages come from the global `hourly` namespace, which has no server dimension, and scoping some of a payload and not the rest is how it comes to contradict itself. It no longer touches the index at all, which is also what holds a filtered poll to one fan-out. The two totals differ by construction in one way worth knowing: `hourly` drops worker requests, while the URL index keeps them on their own rows. The per-shard cap no longer costs the index anything — `MAX_URLS_PER_SHARD` folds its tail into a synthetic `Other` row (`Stats_Store::OTHER_KEY`) carrying only the fields that ADD, splits included, so a total summed from this index is exact site-wide, and per server for every server `MAX_SERVER_VALUES` keeps — its own tail folds into an `Other` server no real fleet reaches. That row is marked `aggregate` and the table renders it un-clickable: its key is not a url_hash and `url_detail` cannot answer for it. `url_detail` takes the same `server`, because the modal opens from a row that filter scoped and a site-wide average under a scoped count is the same defect one click in. Every rate divides by the WINDOW — `RECENT_BUCKETS` × `Stats_Store::BUCKET_SECONDS`, dropping the bucket still filling — never by the buckets that happened to carry traffic; the client used to do the latter, so a URL seen in two of twelve read six times its rate beside a header that did not. The reply echoes the `filters` it applied, and the Ask brief carries them on EVERY surface, so a narrower number never reads as the site's. Two surfaces the scope deliberately does NOT reach, both because the storage cannot answer them: `url_detail`'s `breakdown_time_series`, `category_time_series` and `aggregate_flame` are per-URL only — a per-URL-per-server series would be new storage on the axis decision 11 watches — and `find_recent_requests_for_url()` has no server in the request index. Both are harmless while a stored `url` is absolute, which makes one URL one site. The table EXCLUDES worker traffic by default, and so the header does. `$count_global` keeps workers out of every site-wide aggregate — one long-running job would otherwise dominate the averages — while the per-URL row deliberately keeps their timing, so a header summed from the index inherited them: on a staging hub that made "Avg Response" read 227ms of cron against 3ms of reader traffic. The row RECORDS whether its traffic was a worker (never derived from `?worker_type` in the URL text, which is the substring guess that emptied a table once), the `urls` verb's `include_workers` opts IN because its default excludes — the mirror of `errors_only`, which opts in to narrow — and the capped tail folds into TWO overflow rows (`Stats_Store::other_key()`), because one cannot answer a filter about a mixed set. One scope rule across the surface, so it is not re-litigated per widget: a FETCH sends the live selection — `urls`, `url_detail` and `ask` all ask for what is selected now — while a LABEL reads the scope the server echoed back, because it names numbers already on screen. Mixing them put a brief for one server beside a panel showing another's. **Revisit if** the header ever needs a number the URL index cannot produce (the answer is a new field on the `urls` reply, not a second source read beside it), or if a host is ever reported by two servers, at which point those three charts and that examples list start describing a wider set than the count above them.

16. **The breakdown panel is always mounted, and says which kind of nothing it has.** `BreakdownControls` is the chart and the dropdowns that drive it — one panel, because the Metric and Breakdown values it reads are exactly the ones its own selects set. Both callers mount it unconditionally: those dropdowns are the only way out of a dimension with no rows, a read still in flight or a refused reply, so any gate that can unmount them can trap an operator. The Overview card's gate is what proved it — it once fell back to `overview.aggregate_time_series` when the selected dimension had no values, which drew a flat series legended "Total" under a dropdown reading "User Agent", and the modal's version once gated on `breakdownData` while `useCommandOnce` treats a refusal as an answer, so an error unmounted the only control that could have recovered from it. There is no "None" breakdown, so the totals are never the requested view and the chart holds no undifferentiated source at all. What replaces the gate is `breakdownState( breakdownData )`, one resolver the chart and the panel both read: `pending` when no series is in hand, `empty` when one arrived carrying no values, `series` otherwise. Only `series` draws. The two callers reach `pending` by two different mechanisms, and the wire guarantees neither on its own. The Overview card reads `overview.breakdowns[ dimension ]`, a map the server keys by every dimension it was ASKED for, so an absent KEY is a dropdown switch the reply has not caught up with. The URL modal's `url_breakdown` reply carries one dimension and no key to look it up by, so its `pending` is the explicit `setBreakdownData( null )` the switch runs, and what keeps a stale answer out of it is the ADDRESS: `subjectOf` makes the subject the (URL, dimension) PAIR, so a superseded dimension's reply matches no outstanding ask, fills nothing, and retires nothing. The distinction is the whole point — "No User Agent data" during a fetch is a lie that flickers, and the totals under either is an answer to a question nobody asked. *Alternatives rejected:* a `mountWhen` prop (a gate, passed in, and every value of it can strand the operator); two panel components (one panel, two callers, and the second copy exists to hang one boolean on); emptiness alone as the discriminator (collapses `pending` into `empty`, which is the flicker). **Revisit if** the server ever OMITS a requested dimension that turned out to have no rows, which would make the two states indistinguishable on the wire and move the fix server-side — and watch `CHART_BREAKDOWN_OPTIONS` against `Performance_CI_Node::DIMENSIONS`, two hand-matched lists in two files. `pending` is terminal, so a dimension the server drops hangs the panel rather than degrading it; `overview` therefore REFUSES a dimension it does not know instead of answering about the rest, which turns that drift into a message under the dropdowns.

## Common Pitfalls

Mistakes that have actually happened.

- **`@wordpress/*` is pinned to the `wp-7.0` dist tag — never bump it to close an advisory.** Every declared runtime version IS its `wp-7.0` tag (`components 32.2.1`, `element 6.40.1`, `i18n 6.13.1`, `api-fetch 7.40.1`, `icons 11.7.1`). The build externalises them to the `wp.*` globals, so npm's copy never ships — raising it delivers no new code, it moves the API you compile, lint and type-check against AHEAD of the one the browser is handed. A component changed or removed between majors then builds clean, passes eslint and jest, and breaks at runtime, with nothing mechanical to catch it. Check `npm view @wordpress/<pkg> dist-tags --json` against `wp core version` before proposing any bump, and move the whole family together only when the WordPress target itself moves. A Dependabot advisory reachable only PAST the pin gets dismissed, not bumped: 2026-08-17, uuid GHSA-w5hq-g745-h8pq needed `components >= 33.1.0`, one major past `wp-7.0`, for a package absent from `build/` entirely — dismissed `not_used`. npm `overrides` cannot rescue that, because npm matches an override by package NAME anywhere in the tree: both `{uuid: …}` and the nested `{"@wordpress/components": {uuid: …}}` downgraded the fourteen `@wordpress/*` packages that legitimately require `uuid@^14`.
- **The seven global logging/auto-tune options are gone; logging is per-URL-rule (v0.26.0).** `log_urls`, `skip_urls`, `log_events`, `custom_events`, `significant_events`, `auto_disable_threshold` and `auto_protect_time_threshold` are no longer read. Each rule is a URL pattern (`/prefix` or exact `/x?`) with a `log`/`skip` action and, for `log` rules, its own hooks, custom events, significant events and auto-tune thresholds. Matching ranks query-bearing patterns (`/jobs/x?job-work`) above ALL exact patterns, which rank above ALL prefixes — length only breaks ties within a rank, so this is NOT longest-prefix-wins. Case-insensitive; **no match means skip, and empty means empty — there is no implicit log-all baseline.** Declare a `/` log rule to log everything, as the shipped config does alongside baseline skips for the substrate's worker IPC/SSE/spawn endpoints and `/wp-cron.php`. Rule id = the pattern's `Log_Manager::url_hash()`. Discovery only *stages* spoke-reported hooks into a non-autoloaded `discovered_hooks` option for the editor's hook picker; the editor is the only rule writer.
- **`enable_workers` AND `enable_aggregator` were retired.** There is no operator hub toggle — `tests/unit/RetiredConfigKeysTest.php` guards both keys. Hub-mode derives from whether `aggregator` is in the substrate's `topologies` list. Settings fan-out is structurally ungated: without `hub-control` active and per-spoke `HTTP_Out` nodes wired, a recorded settings event is tailed and dropped.
- **Two bounds, and BOTH fold.** `entry_budget` constrains the SUM of entries across everything in flight (what a staging site ran out of) and folds the largest envelope when crossed; `max_entries_per_request` constrains ONE envelope and folds that one, a faster trigger for a single runaway than waiting for the next pressure check. The per-request cap used to just stop appending and set a `truncated` flag nothing surfaced, which lost every entry past it — don't reintroduce that. A folded record ships `flame` + `folded` plus its kept head and tail rejoined around an `entries (aggregated)` marker; `Flame_Builder_Node` and the detail view read both shapes, and every record already on disk carries the old one.
- **PIPE_BUF (4096 bytes) for firehose writes.** `Log_Manager::message()` enforces `MAX_DATA_SIZE = 3840` on the JSON-encoded data: oversize payloads get an `error_log` notice, `" (truncated)"` on the category, and the data replaced with a 1000-char excerpt (`['m' => substr(...) . '...']`). The payload is lost, not chunked. Anything that might exceed — job payloads with serialized option blobs, image-handler args, large serialized arrays — MUST use `Job_Intake::queue()` (locked, `MAX_JOB_SIZE` 32MB).
- **Hub vs spoke routing.** Nodes only ever write `k:"job"`. Every node's `Job_Worker_Node` dispatches its own entries against `newspack_nodes/job_handlers`. On the hub, `aggregator`'s per-spoke `Remote_Source_Node`s pull spoke firehoses and `Remote_Job_Rewrite_Node` rewrites the incoming lines to `k:"remote_job"` for `newspack_nodes/remote_job_handlers`. The two filters are independent — register a job type under whichever side should handle it.
- **One shared `Core::$memd` handle — read it, don't build your own.** It is built once at boot by `Bootstrap::init_memcached()` from `memcache_servers` (default `127.0.0.1:11211`). Consumers read `Core::$memd` directly with null-safe `Core::$memd?->...`. Never hardcode server lists or open a second connection.
- **Tests set `Core::$memd` to an in-memory `\Memcached` double.** There is no `Cache_Interface` / `Memcached_Cache` to inject — the substrate ships the double at `tests/Helpers/InMemoryMemcached.php` and tests assign it in setUp. New cache call-sites read `Core::$memd`; nothing should type-hint a cache interface.
- **Salt rotation requires a worker restart.** `Cache_Backend::rotate_salt()` orphans keys, but a worker memoizes the install scope at boot.
- **Stats fail soft, SSE slots fail closed. Don't unify them.** Dashboards must show "no data" on memcache failure; SSE connections must reject with 429, because the slot pool IS the rate limit.
- **Application Node classes resolve by namespace prefix — no per-class registration.** The entry point calls `\Newspack_Nodes\Topology_Registry::register_plugin( 'Newspack_Event_Logger_Nodes\\', …/topologies )` and `\Newspack_Nodes\Command_Interpreter_Node::register_namespace( 'Newspack_Event_Logger_Nodes\\App\\' )` for the service CIs. `make_node Flame_Builder` resolves `\Newspack_Event_Logger_Nodes\Flame_Builder_Node`, and the palette scans the classmap. A new node needs only `class Foo_Node extends \Newspack_Nodes\Node` under that namespace plus `composer dump-autoload -o`.
- **Token-array command contract.** The substrate migrated the `{name, arguments}` envelope to a token array (`list<string>` argv), so TM_COMMAND `arguments` and node-constructor `arguments` are no longer space-joined strings. Here: every `App\*_CI_Node` verb handler takes `array $args` and parses via `Command_Args::parse( self::arg_strings( $args ) )` — the `rules` `save`/`upsert` verbs read the whole JSON blob as `self::arg_strings( $args )[0]`. `Request_Builder_Node` and `Discovery_Collector_Node` declare `arguments( ?array $args = null ): array`, while `Flame_Builder_Node` and `Job_Router_Node` get the same handling free via the substrate's `Schema_Reflection` trait's `parse_schema_args()`. (Substrate mirror: `../newspack-nodes/AGENTS.md`.) `Reqgrep_Command` and `Log_Manager`'s firehose `Topic` construction pass token arrays; the dashboard hooks build args with `formatCommandArgs(...)`. TM_INFO and firehose-log VALUEs stay flat strings — only the command envelope changed. A handler still typed `string $args`, or code splitting a joined args string, is a stale port.
- **Type flags**: array VALUE → `TM_STRUCT`; string VALUE → `TM_BYTESTREAM`. Consumers reading an array VALUE gate on TM_STRUCT.
- **Don't restore `class_exists()` guards for in-plugin classes.** The deferred-loader require_once chain loads every class in this plugin before anything constructs them, so those checks are dead branches. Removing them was deliberate.
- **`wp nodes cli {reader}` requires the worker to exist.** `attach_to_worker` checks for `{base}/locks/{reader}.lock.d/`, so a typo'd reader id fails fast with "no worker '<id>' (run `wp nodes status` to list active workers)" rather than silently creating ghost IPC. Surface that error if you script it.
- **The substrate passes ALL message types through Partition/Topic.** TM_REQUEST/TM_ERROR/TM_EOF used to be silently dropped, which broke attached-mode error responses, `request_node` cli verbs and the stdin-close drain. Application data partitions only emit TM_BYTESTREAM / TM_STRUCT in practice, so the broader contract is a no-op on the write path — but Partitions now work as ad-hoc message transports.
- **Piped `wp nodes cli` sessions drain cleanly.** The substrate does a TM_EOF round-trip on stdin close, so scripted pipelines no longer need a trailing `sleep N`.
- **`App\Core` hook instrumentation has two non-obvious correctness mechanisms — don't strip them.** `wrap_callbacks()` skips any callback whose reflection reports a by-reference param (`callback_has_ref_param()`), because wrapping those breaks the WordPress by-reference contract. And a sacrificial `hook_spacer` at `PHP_INT_MAX - 2` (`SPACER_PRIORITY`) keeps a self-removing complete-hook at `PHP_INT_MAX - 1` firing (v0.13.1); `wrap_callbacks` treats everything at or above the spacer priority as ours and leaves it alone.

The former local `src/admin-field-reset/` module and its `sync-shared.sh` copy gave way to the `@newspack-nodes/shared` build aliases resolved in `scripts/build.mjs`
